# 01 · 技能的本质与边界

> **这篇要回答**：Skill 到底是什么？它和普通提示词、MCP、Subagent 的分工在哪？什么活儿**不该**做成 skill？

---

## 1. 一句话定义

Skill 是**一个按需注入的操作手册 + 工具包**。

它由两部分组成：

1. **一段永远在上下文里的元数据**（`name` + `description`）——这是"开关"，决定它什么时候被激活
2. **一包平时不占上下文、触发时才展开的资源**（`SKILL.md` 正文 + `references/` + `scripts/` + `assets/`）

关键在于第 2 点：**平时不占**。这是 skill 和"写一大段系统提示词"的根本区别。

---

## 2. 三层加载机制

```
┌─────────────────────────────────────────────────────────┐
│ 第 1 层  元数据（name + description）                    │  ← 永远在上下文
│         每个技能约 50 token，22 个技能 ≈ 1.2k token      │
├─────────────────────────────────────────────────────────┤
│ 第 2 层  SKILL.md 正文                                   │  ← 触发时才载入
│         建议 < 500 行 / < 5k 词                          │
├─────────────────────────────────────────────────────────┤
│ 第 3 层  references/ · scripts/ · assets/                │  ← 按需读取或直接执行
│         脚本可以不读进上下文，直接跑                      │
└─────────────────────────────────────────────────────────┘
```

### 用你本机的真实数据看这笔账

仓库里通过 `skills-lock.json` 装了 **22 个 LangChain 官方技能**。实测（token 用 CJK 1 字≈1 token、其它 4 字符≈1 token 的启发式估算）：

| 指标 | 实测值 |
| --- | --- |
| 技能数量 | 22 个 |
| **常驻成本**（全部 description 合计） | **≈ 1,239 token**（平均 56/个） |
| **正文总量**（触发后才会进上下文） | **≈ 56,465 token**（平均 2,566/个） |
| 单个最大正文 | 8,730 token |
| 带 `references/`、`scripts/` 等附属资源的 | 4 / 22 |

**这组数字就是 skill 的全部经济学：**

装 22 个技能只花掉 1.2k token 的常驻成本，但那 5.6 万 token 的正文**一个字都没进上下文**。
等你真的触发 `langgraph-persistence` 时，才载入它那 4,553 token 的正文。

如果把这 22 份正文直接塞进系统提示词，你每次对话都要为 5.6 万 token 付费——而且大部分内容跟当前任务毫无关系。

> 复现命令：`cd Demos/examples && uv run --project .. python -m skill_lab day1`

## 3. 那 1.2k token 是怎么变成 5.6 万的？

不是靠"更聪明的检索"，而是靠**一个纯文本约定**：

模型的运行时会把所有已安装技能的 `name` + `description` 拼成一段清单交给模型（就是你看到的 `<available_skills>` 块）。
模型自己读这段清单，判断当前任务该用哪个，然后请求把对应的 `SKILL.md` 读进来。

```xml
<available_skills>
  <skill>
    <name>langchain-rag</name>
    <description>Build RAG applications...</description>
  </skill>
  ...
</available_skills>
```

**没有任何向量检索、没有相似度计算。** 就是把描述摆出来，让模型自己选。

这决定了两件事：

1. **`description` 是唯一的开关**——写得含糊，技能就永远不触发；正文写得再好也没用。
2. **description 必须自包含**——它是模型在"还没读正文"的情况下唯一的决策依据。

第 2 天会专门讲怎么写这个 description。

## 4. 边界：Skill 到底该管什么？

这是最容易搞混的地方。把四样东西摆在一起：

| 机制 | 解决什么 | 什么时候加载 | 典型例子 |
| --- | --- | --- | --- |
| **提示词 / 系统提示词** | 这一轮对话的临时要求 | 每轮 | "这次回答用中文" |
| **AGENTS.md / 项目约定** | 这个仓库的长期规矩 | 一直在上下文里 | 本仓库的目录结构、提交规范 |
| **Skill** | 某个**领域**的完整操作流程 | 匹配到就加载 | "怎么做一次 LangGraph 人审流程" |
| **MCP Server** | **运行时能力**（读写外部系统） | 常驻，需要工具调用 | 数据库查询、飞书日程 |
| **Subagent** | 一个**隔离上下文的执行者** | 派发时 | 让一个 agent 独立跑长任务 |

一句话区分：

- **Skill 管"怎么做"**（知识、流程、判断标准）
- **MCP 管"能碰到什么"**（外部系统的读写能力）
- **Subagent 管"谁去干"**（上下文隔离与并行）

### 判断表：该不该做成 Skill？

| 场景 | 做成 skill？ | 更好的选择 |
| --- | --- | --- |
| 每次对话都要遵守的仓库规范 | ❌ | 写进 `AGENTS.md` |
| 一年只用一次的操作 | ❌ | 写进文档，让模型自己读 |
| 需要读写外部系统（数据库、API） | ❌ | MCP Server |
| 一个复杂、可复用的多步流程 | ✅ | Skill |
| 某领域的判断标准和取舍依据 | ✅ | Skill（放 `references/`） |
| 一段每次都要重复写的长提示词 | ✅ | Skill（省 token） |
| 需要独立上下文的长任务 | ⚠️ | Skill + Subagent 组合 |

## 5. Skill 放在哪、什么时候生效

以你本机的 MiniMax Code（MCode）为例，技能有三个位置：

| 类型 | 路径 | 可见范围 |
| --- | --- | --- |
| 内置 | `~/.minimax/.builtin-skills/<name>/SKILL.md` | 所有 agent，**受保护不可改** |
| 用户级（全局） | `~/.minimax/skills/<name>/SKILL.md` | 所有 agent |
| agent 私有 | `~/.minimax/agents/<agent>/skills/<name>/SKILL.md` | 仅该 agent |

另外 `~/.claude/skills/` 是 Claude 风格技能的目录，本机也装了一批（`skill-creator`、`docx`、`pptx` 等）。

**生效时机：下一个会话。** 改完 SKILL.md 不需要重启运行时，新开会话即可看到。

## 6. 一个最小 skill 长什么样

本仓库 `Demos/examples/skills/demo-assistant/SKILL.md` 的全部内容：

```markdown
---
name: demo-assistant
description: 演示技能加载。当用户要求按规范回答、分点总结、或明确提到使用技能时加载本技能。
---

使用本技能时：

1. 先用一句话说明你已加载 `demo-assistant`。
2. 用简洁条目回答，避免冗长铺垫。
3. 如果结论依赖外部事实，先调用 `web_search` 再作答。
4. 如果需要查看或修改本机文件，再调用 `run_command`。
```

就这么多。一个 skill 的**最小可运行形态**只有两样东西：一个 `SKILL.md` 文件，
加上 frontmatter 里的 `name` 和 `description`。其余全是可选的复杂度。

值得注意的是，这个 skill 的正文里**没有任何"何时使用"的内容**——触发信息全部在 description 里。
第 2 天会解释为什么这很重要。

---

## 8. 本章要点

- Skill = 常驻元数据 + 按需展开的资源包，核心是**分层加载**
- 常驻成本只有几十 token，正文动辄几千 token——这是 skill 存在的经济学基础
- 触发是**纯文本决策**（读 description 选技能），没有向量检索
- Skill 管"怎么做"，MCP 管"能碰到什么"，Subagent 管"谁去干"，`AGENTS.md` 管"这个仓库的规矩"
- 最小 skill 就是一个 SKILL.md；一切复杂度都要有理由
