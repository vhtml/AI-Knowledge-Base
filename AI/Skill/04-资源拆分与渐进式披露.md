# 04 · 资源拆分与渐进式披露

> **这篇要回答**：一个技能该长什么样才不臃肿？正文、references、scripts、assets 各自装什么？

---

## 1. 四类资源的分工

```
skill-name/
├── SKILL.md              必需。正文：流程、决策点、边界
├── references/           可选。按需加载的文档
│   ├── schema.md
│   └── api_docs.md
├── scripts/              可选。可执行的代码
│   └── validate.py
└── assets/               可选。用于产出物的文件
    └── template.md
```

| 目录 | 装什么 | 什么时候进上下文 | 判据 |
| --- | --- | --- | --- |
| `SKILL.md` | 流程骨架、判断依据 | 触发时全量 | 模型**做决策**需要的信息 |
| `references/` | 详细文档、schema、API 说明 | 模型判断需要时主动读 | 模型**查细节**时用的信息 |
| `scripts/` | 确定性代码 | **不读也能执行** | 重复写、容易错、要求一致的操作 |
| `assets/` | 模板、字体、图标 | 不进上下文 | 最终产出**要用到的文件** |

**最容易搞混的是 scripts 和 references。**

| | `references/` | `scripts/` |
| --- | --- | --- |
| 形态 | Markdown 文档 | 可执行代码 |
| 进上下文？ | 会，被读进来 | **不会**，直接跑 |
| 适合 | "有哪些字段""API 怎么签" | "把 40 个文件重命名" |
| 正确性来源 | 模型理解 | 机器执行 |

## 2. 三种拆分模式

### 模式一：高层导航 + references（最常用）

SKILL.md 只留主干和导航，具体细节分流：

```markdown
# PDF 处理

## 快速开始

用 pdfplumber 提取文本：

```python
import pdfplumber
with pdfplumber.open("doc.pdf") as pdf:
    for page in pdf.pages:
        print(page.extract_text())
```

## 进阶功能

- **表单填写**：见 [FORMS.md](references/forms.md)
- **API 参考**：见 [REFERENCE.md](references/reference.md)
- **示例**：见 [EXAMPLES.md](references/examples.md)
```

模型需要哪个就读哪个，**其余的完全不占上下文**。

### 模式二：按领域拆

一个技能横跨多个领域时，按领域切：

```
bigquery-skill/
├── SKILL.md              概览 + 导航
└── references/
    ├── finance.md        收入、开票指标
    ├── sales.md          商机、管道
    ├── product.md        API 用法、功能
    └── marketing.md      归因、活动
```

用户问销售指标，只读 `sales.md`。

### 模式三：按变体拆

一个技能支持多个框架时，按框架切：

```
cloud-deploy/
├── SKILL.md              通用流程 + 选型指引
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

用户选了 GCP，只读 `gcp.md`。

## 3. 四条硬规则

### 规则一：references 只允许一层深

所有 reference 必须从 SKILL.md **直接**可达，不要嵌套：

```
✓ SKILL.md → references/aws.md → references/aws-iam.md   ← 违规
✓ SKILL.md → references/aws.md
```

嵌套的代价：模型要"先读 A 才知道该读 B"，多一轮往返，而且经常读不到。

### 规则二：超过 100 行的 reference 要加目录

模型预览长文件时，先看到目录才知道里面有什么：

```markdown
# AWS 部署参考

## 目录
- [凭证配置](#凭证配置)
- [S3 静态托管](#s3-静态托管)
- [Lambda 部署](#lambda-部署)
- [常见错误码](#常见错误码)

## 凭证配置
...
```

### 规则三：同一信息只住一处

信息**要么**在 SKILL.md，**要么**在 references，**不能两边都有**。

重复的后果是：改了一处忘了另一处，模型看到矛盾版本时行为不可预测。
详细资料优先放 references，SKILL.md 只留真正核心的操作步骤。

### 规则四：不要在 skill 里写 README

`skill-creator` 明确列了禁止清单：

> The skill should only contain the information needed for an AI agent to do the job at hand.
> Do NOT create extraneous documentation or auxiliary files, including:
> README.md、INSTALLATION_GUIDE.md、QUICK_REFERENCE.md、CHANGELOG.md 等

**理由**：这些文件是写给**人**看的（怎么安装、怎么贡献、版本历史）。
skill 是给**模型**读的，模型不需要知道"这个技能怎么安装"——它已经在运行了。

## 4. 官方 22 个技能的实际资源分布

用 `skills-lock.json` 装的 LangChain 官方技能里，**只有 4 个带附属资源**：

| 技能 | 附属资源 |
| --- | --- |
| `eval-engineering` | `references/` `scripts/` `agents/` `examples/` 等共 20 个文件 |
| `swarm` | `scripts/` 8 个文件 |
| `langgraph-fundamentals` | `references/` 2 个文件 |
| `langgraph-decision-models` | `references/` 1 个文件 |

其余 18 个是**单文件 SKILL.md**，最长的一份正文 8,588 token。

**这是两种不同的合理风格：**

- **单文件型**：技能领域窄、内容线性可读，一次性读完不亏。`langgraph-persistence` 4,553 token 就是典型——它是"一条完整的持久化知识"，拆开反而割裂。
- **多文件型**：技能覆盖多主题，读者只需要其中一块。

**选哪种的判据：正文超过 500 行了吗？超了就拆。**
不是因为"多文件更专业"，而是因为超长正文会让模型在触发后被一次性灌入大量可能无关的内容。

## 5. 拆分的成本

拆分不是免费的。每次引用多一层，模型要多一次文件读取往返。

**拆分的真实收益：**

| 场景 | 不拆 | 拆了 |
| --- | --- | --- |
| 触发后要读全部内容 | 读 4,553 token | 只读需要的 800 token |
| 内容会各自独立更新 | 改一处要重读整个正文 | 改一个文件 |
| 不同任务读不同部分 | 永远带全部 | 按需加载 |

**什么时候别拆：**

- 正文不到 200 行 —— 拆了收益小于往返成本
- 内容之间强耦合、必须一起读 —— 拆开模型可能只读一半
- reference 少于 2 个 —— 一层深的优势体现不出来

## 6. 目录模板

用官方脚手架生成的标准结构：

```
my-skill/
├── SKILL.md
├── references/
│   └── <主题>.md
├── scripts/
│   └── <动作>.py
└── assets/
    └── <模板>
```

`init_skill.py` 会**自动生成示例文件**（一个示例 SKILL.md、几个示例资源文件）。
**用不上的必须删掉**——留着就等于每次打包都塞进没人读的垃圾。

```bash
python ~/.claude/skills/skill-creator/scripts/init_skill.py my-skill --path ./skills
```

## 8. 本章要点

- SKILL.md 管**决策**，references 管**查细节**，scripts 管**执行**，assets 管**产出**
- references **只能一层深**；超 100 行加目录
- 同一信息只住一处
- **不要在 skill 里写 README / CHANGELOG / 安装指南**——那是给人看的
- 正文超 500 行就拆；不到 200 行别拆
- 脚手架生成的示例文件用不上就删
