# 06 · 评测与迭代闭环

> **这篇要回答**：怎么判断一个技能写得好不好？改了一版，怎么知道是变好了还是变差了？

---

## 1. 技能有两类评测，缺一不可

| 类型 | 测什么 | 不测会怎样 |
| --- | --- | --- |
| **触发评测** | 该触发时触发了吗？不该触发时闭嘴了吗？ | 技能永远不被用，或者到处乱用 |
| **效果评测** | 触发后做对了吗？ | 触发了但做错，等于没做 |

**新手最常只做第二个。** 但实际上，大部分"技能不好用"的抱怨，根源在第一个：
描述写得不好，模型压根没加载它，于是用户觉得"这技能没用"。

---

## 2. 触发评测：正例 + 负例

### 正例（该触发）

写用户**真会说的话**，不是你技能文档里的术语：

```json
{"query": "帮我把这个 PDF 旋转 90 度", "should_trigger": true}
{"query": "把这份 docx 里的批注提取出来", "should_trigger": true}
{"query": "pdf 表格里的数字怎么提取成 csv", "should_trigger": true}
```

### 负例（不该触发）

**最关键的是"近邻负例"**——字面接近、语义不同：

```json
{"query": "帮我写个爬虫", "should_trigger": false}
{"query": "用 python 读 pdf 的库有哪些", "should_trigger": false}
{"query": "写一个生成 PDF 的程序", "should_trigger": false}
```

近邻负例才有区分度。全是"今天天气怎么样"这种负例，测不出任何东西。

### 评测怎么做

用一个**关键词命中率**做代理指标（离线、免费、可复现）：

```
命中 = description 里出现了 query 的关键词（或其同义词）
```

更实用的做法是**人工标注 + 规则打分**：
把 query 和 description 一起交给一个判官（人或模型），问"这个技能该不该被触发"，
打出 `should_trigger` 的命中情况。

> 本仓库 `Demos/examples/rag-demo/backend/rag.py` 里的 `GOLD` 集就是同一个思路：
> 手工维护一组期望答案，用程序算命中率，把结果写进 `data/eval_log.json`。
> **技能也需要一个自己的 GOLD 集。**

---

## 3. 效果评测：产物对不对

技能通常产出一份东西（一份笔记、一段代码、一个包）。评测方式取决于产物类型：

| 产物类型 | 评测方式 |
| --- | --- |
| 文档 / 笔记 | 结构检查、术语检查、必填段落是否齐（用脚本判定） |
| 代码 / 包 | 能不能跑通、退出码、单元测试 |
| 数据处理 | 结果和黄金值的差异 |
| 打包产物 | 能不能被校验、被安装、被加载 |

**关键设计：让效果评测可脚本化。**
如果评测要靠人肉通读，这个闭环就跑不起来。

第 7 天的毕业作品就是这么设计的：它的 `scripts/validate_skill.py` 同时充当
"效果评测器"——校验通过就说明产物合规。

---

## 4. 迭代闭环：改什么、怎么改

`skill-creator` 的第 6 步：

> 1. Use the skill on real tasks
> 2. Notice struggles or inefficiencies
> 3. Identify how SKILL.md or bundled resources should be updated
> 4. Implement changes and test again

**关键在于第 1 步要用真实任务。** 一个从没在真实任务里跑过的技能，
你不知道它哪里断了。

### 迭代时的编辑原则：**证据驱动的最小补丁**

不要因为一次失败就大改。分三步：

1. **定位**：失败发生在哪一层？
   - 没触发 → 改 `description`（第 2 层）
   - 触发了但走错路 → 改正文流程/决策点（第 3 层）
   - 走到一半卡住 → 补 `references` 或加脚本（第 4/5 层）
2. **最小改动**：只改导致失败的那一处
3. **回归**：重跑评测集，确认没把之前对的弄坏

这个原则在本机的 `skill-refiner` 技能里有更完整的版本：
> 只在有**具体证据**支撑时做最小补丁——有确凿问题（指令错误、步骤过时、边界情况缺失）才改。
> 不要为了风格统一而顺手重构。

## 5. 评测集怎么维护

### 放在技能里

```
my-skill/
├── SKILL.md
└── evals/
    ├── trigger_cases.json    触发正例 + 负例
    └── expected/             期望产物样例
```

### 和脚本放在一起

```
scripts/
└── run_eval.py               一条命令跑完
```

**评测要能一条命令跑完**，否则不会有人跑。

### 记日志

每次评测的结果写进一个日志文件（像 `rag.py` 写 `eval_log.json` 那样），
这样你能看到"这次改动让准确率从 0.7 变成 0.9"或者"从 0.9 掉到 0.6"。

没有日志，迭代就退化成感觉。

---

## 6. 评测集该有多大

别一上来写 100 条。

| 阶段 | 规模 | 重点 |
| --- | --- | --- |
| 第一版 | 5 正 + 5 负 | 先把 description 写对，够用 |
| 能用了 | 10 正 + 10 负（含 3 近邻负例） | 覆盖主要说法 |
| 发布前 | 20 正 + 20 负 | 加边界场景、跨语言、模糊表达 |

**规模不是目的，覆盖率才是。** 10 条覆盖 5 类说法的评测集，
比 50 条千篇一律的更有用。

## 7. 一个典型的评测输出长什么样

```
触发评测 (kb-note-writer)
  正例 8/10 命中  ████████░░  80%
  负例 9/10 排除  █████████░  90%
  近邻负例 2/3 排除 ██████░░░░  67%
  ─────────────────────────────────
  总分 19/23 = 83%

未命中的正例：
  ✗ "把这事儿记下来"        —— description 缺"记一笔"这个说法
  ✗ "沉淀一篇 RAG 的经验"    —— 缺"RAG"这个领域词

误触发的负例：
  ✗ "帮我写个 RAG 的 demo"   —— 边界不够严
```

**这份输出直接告诉你下一版 description 该改什么。** 这就是评测的价值。

## 8. 本章练习

```bash
cd Demos/examples && uv run --project .. python -m skill_lab day6
```

练习做三件事：

1. **写评测集**：给 `kb-note-writer` 写 10 正 + 10 负，其中 3 条近邻负例
2. **跑评测**：实现一个离线打分器（关键词覆盖 + 近邻惩罚规则），输出上面那种报告
3. **迭代**：根据报告改 description，至少改三轮，记录每轮得分，
   验证**改动是收敛的**（最后一轮比第一轮高，且没有反复震荡）

---

## 9. 本章要点

- 触发评测和效果评测**都要有**，大部分问题出在触发
- 负例里**近邻负例**最有价值
- 评测集要**能一条命令跑完**，结果要**写日志**
- 迭代是**证据驱动的最小补丁**：先定位到层，再改一处，再回归
- 先 5+5 条跑通，再扩到 10+10，最后 20+20
- 评测报告要能直接**指出下一版改什么**
