# 02 · 触发设计：description 是唯一的开关

> **这篇要回答**：为什么 description 决定了技能会不会被用？怎么写才能既该触发时触发、不该触发时闭嘴？

---

## 1. 最反直觉的一条

**正文里写"何时使用本技能"是无效的。**

很多人第一次写 skill 会这样：

```markdown
---
name: pdf-editor
description: PDF 编辑工具
---

## 何时使用本技能

当用户要求旋转 PDF、提取 PDF 文本或填写 PDF 表单时，使用本技能。
```

这段"何时使用"写在正文里，等于**永远不会被读到**——因为模型要先决定"要不要加载这个技能"，
而那个决定只能靠 `description` 做出。正文要等触发之后才进上下文，那时"何时用"已经没意义了。

正确的做法是把触发信息**全部搬进 description**：

```markdown
---
name: pdf-editor
description: PDF 旋转、文本提取、表单填写与批注处理。用户提到"改 PDF""转 PDF""填 PDF 表单""pdf 文本提取"时使用本技能。
---
```

**规则：凡是"什么时候该用"的信息，一律写进 description；正文只写"怎么用"。**

---

## 2. 触发是怎么发生的

```
用户的请求 ──► 模型读 <available_skills> 清单
                    │
                    ├─ description 里有"匹配"的内容？──否──► 用通用能力直接干
                    │
                    └─是─► 模型调用 skill(name) ──► SKILL.md 正文进上下文 ──► 按正文执行
```

没有向量检索，没有相似度阈值。**就是一次文本匹配 + 一次模型判断。**

这意味着两件事：

1. **description 的关键词必须出现在用户的表达里**（或语义上高度接近）
2. **description 写得再漂亮，关键词对不上就是死技能**

## 3. 官方 22 个技能的 description 到底怎么写的

把本机 `skills-lock.json` 装的 LangChain 官方技能全部拉出来看，能看到 4 种成熟范式。

### 范式 A：`INVOKE THIS SKILL when ...`（最主流）

```
langgraph-fundamentals:
  INVOKE THIS SKILL when writing ANY LangGraph code. Covers StateGraph,
  state schemas, nodes, edges, Command, Send, invoke, streaming, and error handling.

langchain-rag:
  INVOKE THIS SKILL when building ANY retrieval-augmented generation (RAG)
  system. Covers document loaders, RecursiveCharacterTextSplitter,
  embeddings (OpenAI), and vector stores (Chroma, FAISS, Pinecone).
```

**结构：`INVOKE THIS SKILL when <触发场景>. Covers <覆盖点清单>.`**

两个组成部分各司其职：

- `when <场景>` —— **触发条件**，决定会不会被选中
- `Covers <清单>` —— **关键词兜底**，命中其中任何一个词也能触发

注意 `ANY` 这个词：它把触发范围从"写 LangGraph 图"扩大到"写任何 LangGraph 代码"，
是一个刻意的**放宽**。

### 范式 B：`INVOKE FIRST for ...`（路由型技能）

```
ecosystem-primer:
  INVOKE FIRST for any LangChain / LangGraph / Deep Agents agent building
  project before consulting other skills or writing any agent code.
  Required starting point for up to date info on framework selection ...
```

这个技能不解决具体问题，它解决**"该先加载哪个技能"**。
用 `INVOKE FIRST` + `before consulting other skills` 明确表达了**优先级**。

> 这是做"总入口"技能的标准写法。如果你有一组相关技能，需要一个总控技能把路引过来，就用这个。

### 范式 C：`Use when the user wants to ...`（第二人称）

```
langchain-python-quickstart:
  Scaffold a minimal local LangChain agent in Python by following the official
  quickstart. Use when the user wants to quickly build or try a LangChain agent locally.
```

注意 `the user wants` —— 把触发主体写成用户，读起来是在**描述用户的意图**而不是描述技能。

### 范式 D：能力陈述式（不写 when）

```
swarm:
  Dispatches many independent items in parallel: create a table, fan out to
  subagents, aggregate results. One row = one unit of work.
```

只说"我是干什么的"，不说"什么时候用"。适用于**技能名本身就很独特**、靠名字就能匹配的情况。
风险是触发不稳定，不推荐新手用。

## 4. 统计一下：官方怎么分配笔墨

| 维度 | 22 个官方技能的情况 |
| --- | --- |
| 用 `INVOKE THIS SKILL when` 开头 | 12 个（55%） |
| 用 `Use when the user ...` 开头 | 6 个（27%） |
| 能力陈述式（不写 when） | 3 个（14%） |
| `INVOKE FIRST`（路由型） | 1 个（5%） |
| 带 `Covers <清单>` 子句 | 12 个 |
| 显式写"不要在什么情况下用" | **0 个** |
| 平均长度 | 56 token |
| 最长 | 129 token（`managed-deep-agents`） |

**注意最后两行里那个 0。** 官方这批技能几乎不写负向边界——这是个可以改进的地方，第 6 节会讲怎么补。

## 5. description 的四段式模板

综合上面的观察，一个可靠的 description 由四段组成：

```markdown
---
description: >
  <① 做什么：一句话说清这个技能产出的结果>。
  <② 触发场景：用户会在什么情况下需要它>。
  <③ 关键词：覆盖用户可能使用的具体术语、说法、中英表达>。
  <④ 边界：明确不该用它的相邻场景>。
---
```

拿一个真实例子来填：

```markdown
---
name: kb-note-writer
description: >
  把技术经验写成符合本仓库规范的知识笔记（中文、Python 风格约定、目录分类）。
  当用户要求"写笔记""沉淀到知识库""整理成文档""记一笔"或提到
  AI/Business/Finance 知识分类时使用。
  不用于生成代码实现、撰写 PRD 或做代码审查——那些请走对应的专门流程。
---
```

四段的分工：

| 段 | 作用 | 写错的后果 |
| --- | --- | --- |
| ① 做什么 | 让模型理解产物形态 | 模型不知道该产出什么 |
| ② 触发场景 | 提供匹配语境 | 不触发 |
| ③ 关键词 | 兜底多种说法 | 换个说法就不触发 |
| ④ 边界 | 防止误触发 | 什么都用这个技能 |

## 6. 三条实战原则

### 原则一：关键词要覆盖用户的多种说法

用户不会用你的术语。用户说"把这个整理一下"，不会说"请沉淀知识笔记"。
你的 description 里得同时有**术语词**和**口语词**：

```
✗ 只写术语：rag、embedding、chunking
✓ 术语+口语：rag、检索增强、向量检索、"查资料问一嘴"
```

### 原则二：写正例，也要写反例（官方没做，但值得做）

`description` 的第 ④ 段（边界）是防误触发最有效的手段。
本仓库就有天然的例子——`kb-note-writer` 和"写代码"必须分开：

```
不用于生成代码实现、撰写 PRD 或做代码审查。
```

**判断误触发成本的两种情况：**

- 技能**纯输出文本**（写笔记、起标题）→ 误触发代价低，不用写边界
- 技能**会动文件、跑命令、花钱**→ 误触发代价高，**必须**写边界

### 原则三：描述的是"用户会说的话"，不是"你的实现"

```markdown
✗ description: 一个封装了 Chroma 向量库和交叉编码器重排序器的 RAG 检索模块
✓ description: 用户要"查资料""问一嘴文档里的内容""做知识库问答"时使用
```

前者是给开发者看的，后者是给匹配器看的。

## 7. 校验规则（官方脚本里的硬约束）

`quick_validate.py` 对 frontmatter 的检查是硬门禁，写错了打包会直接失败：

| 字段 | 规则 | 来自 |
| --- | --- | --- |
| `name` | 必须存在；字符串；`^[a-z0-9-]+$`；≤ 64 字符；不能以 `-` 开头/结尾；不能有连续 `--` | 正则校验 |
| `description` | 必须存在；字符串；**≤ 1024 字符**；**不能含 `<` 或 `>`** | 正则校验 |
| frontmatter | 必须是 YAML 字典；只允许 `name` `description` `license` `allowed-tools` `metadata` | 键白名单 |

> 注意 `description` 里**不能有尖括号**——因为 `<` `>` 在 XML 风格的上下文里会被当成标签。
> 写 `支持 <b>富文本</b>` 会被校验拦下。

另外 `skill-creator` 的 SKILL.md 里写着"只写 name 和 description"，但校验器实际允许
`license` `allowed-tools` `metadata` 三个附加键。**以校验器为准**，多写不会失败，
但 `allowed-tools` 在 MiniMax Code 里不生效，写了也没用。

## 9. 本章要点

- 触发 = 读 description 做文本匹配，**没有向量检索**
- "何时使用"写在正文里是**无效的**，必须写进 description
- 官方范式：`INVOKE THIS SKILL when <场景>. Covers <清单>.`
- 四段式：做什么 / 触发场景 / 关键词 / 边界
- 误触发代价高的技能（动文件、跑命令、花钱）**必须**写边界
- description 里不能出现 `<` `>`，长度 ≤ 1024
