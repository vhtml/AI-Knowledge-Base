# 05 · 脚本化：把确定性的活儿交给代码

> **这篇要回答**：什么时候该写脚本？脚本要写成什么样才算合格？

---

## 1. 为什么要写脚本

模型写代码有两个固有弱点：

1. **不稳定**——同样的输入，两次生成的代码可能不同，尤其是长代码
2. **烧 token**——每次重写同一段逻辑，都要重新生成、重新推理

脚本正好治这两条：

| | 模型直接写 | 脚本 |
| --- | --- | --- |
| 正确性 | 每次可能不同 | 一次写对，重复执行 |
| token 成本 | 每次生成 N 行代码 | 只生成 1 行调用 |
| 可测试 | 难 | 直接跑 |
| 可复用 | 每次重来 | 改一次，永久生效 |

`skill-creator` 的原话：

> Bundled Resources (optional): Scripts — Executable code (Python/Bash/etc.) for tasks that require deterministic reliability or are repeatedly rewritten.
> Benefits: Token efficient, deterministic, may be executed without loading into context.

注意最后半句：**脚本可以不读进上下文，直接执行。**
这是比 references 更强的一层——references 读了要占 token，脚本跑了不占。

---

## 2. 什么时候该写脚本

### 该写

- 同一段逻辑你**已经写过两次以上**（记忆的可靠信号）
- 操作**容易出错**（格式、命名、边界条件）
- 需要**确定性结果**（校验、转换、计数）
- 操作**步骤多**（模型容易漏掉中间步）
- 需要**大范围重复**（40 个文件重命名）

### 不该写

- 一次性的、模型随手就能写对的逻辑
- 需要模型**判断**的决策（脚本做不了判断）
- 逻辑依赖当前对话上下文（脚本是无状态的）

## 3. 合格脚本的五条规范

### 规范一：`--help` 必须能用

模型可能只看一眼参数名就跑。`--help` 是它的说明书：

```python
#!/usr/bin/env python3
"""校验 SKILL.md 是否符合发布要求。

用法：
    python validate_skill.py <skill目录>
    python validate_skill.py <skill目录> --json

退出码：
    0 校验通过
    1 校验失败
"""
```

### 规范二：退出码可靠

```python
if __name__ == "__main__":
    sys.exit(0 if ok else 1)
```

**退出码是给模型看的**——模型能通过它判断"成功还是失败"，不需要解析输出文字。
这是脚本与模型之间最可靠的接口。

### 规范三：stdout 干净，诊断信息走 stderr

```python
print(json.dumps(result, ensure_ascii=False))   # stdout：结果
print(f"警告：{msg}", file=sys.stderr)            # stderr：诊断
```

模型常做 `script.py > out.json` 这类重定向，stdout 混进别的字就会解析失败。

### 规范四：幂等

跑两次的结果应该一样（除非参数不同）。
幂等的脚本可以放心地被模型反复调用、被放进工作流、被重试。

### 规范五：**必须真的跑过**

这是 `skill-creator` 的硬要求：

> Added scripts must be tested by actually running them to ensure there are no bugs and that the output matches what is expected.

**没跑过的脚本不能进 skill。** 一个报错的脚本比没有脚本更糟——
模型会照着 skill 的指示去调用它，然后卡在那儿。

## 4. 脚本在 skill 里怎么被引用

SKILL.md 里要明确给出**调用方式**，不能只说"有个脚本可以用"：

```markdown
## 校验

改完 SKILL.md 后，运行校验：

```bash
python scripts/validate_skill.py <本技能目录>
```

退出码 0 表示通过，1 表示有问题。
```

对比这种写法：

```markdown
✗ 附带了一个校验脚本，请使用。
```

第二种模型不知道路径、不知道怎么传参、不知道成功长什么样。

### 参数化优于硬编码

```python
# ✗ 硬编码：换个技能目录就得改文件
SKILL_DIR = Path("./my-skill")

# ✓ 参数化：脚本通用
def validate(skill_dir: Path) -> tuple[bool, str]: ...
```

一个通用脚本可以服务一族技能，这是脚本复用的全部意义。

## 5. 本仓库的现成范例

`Demos/examples/rag-demo/backend/rag.py` 里有一个可参考的模式：

- 内部维护一个 `GOLD` 黄金集（问题和期望命中点）
- 提供 `python -m backend.rag eval` 子命令跑评估
- 结果写入 `data/eval_log.json`

这是"技能自带评测"的雏形。**如果你的技能有可验证的正确性，就把黄金集和评估命令一起打包进去**，
让下一个使用者（和下一个会话里的你自己）能立刻验证它还灵不灵。第 6 天会展开讲。

## 6. 常见反模式

| 反模式 | 症状 | 修法 |
| --- | --- | --- |
| 没跑过的脚本 | 模型调用后报错、卡死 | 提交前必须实跑 |
| 输出不解析 | stdout 里混了日志 | 日志走 stderr |
| 硬编码路径 | 换个环境就失效 | 全部参数化 |
| 脚本承担决策 | 遇到变体就崩 | 判断留给模型，脚本只做机械动作 |
| 脚本太长（>300 行） | 比模型直接写还难维护 | 拆成多个小脚本 |
| 没有退出码 | 模型无法判断成败 | 0 / 1 语义固定 |

## 7. 本章练习

```bash
cd Demos/examples && uv run --project .. python -m skill_lab day5
```

练习做三件事：

1. **写脚本**：实现 `validate_skill.py`——检查 frontmatter 合法性、正文行数、
   references 深度、有没有多余文件，输出 JSON、退出码 0/1
2. **跑起来**：用它检查本仓库的 `demo-assistant` 和官方 `skill-creator`，
   看输出是否符合预期
3. **改到过**：故意制造 3 个问题（超长正文、非法 frontmatter、多余 README），
   确认脚本**能检出**，然后修好

## 8. 本章要点

- 脚本治的是**不稳定**和**重复烧 token** 两件事
- 该写：重复两次以上、易错、要求确定、步骤多
- 五条规范：`--help`、退出码、stdout 干净、幂等、**必须实跑**
- SKILL.md 里要写清**调用方式**，不能只提一句"有个脚本"
- 脚本参数化，才能服务一族技能
- 有可验证正确性的技能，**把黄金集一起打包**
