# 03 · 正文与自由度分级

> **这篇要回答**：SKILL.md 正文该写多细？什么时候给模型"框架"，什么时候给"死命令"？

---

## 1. 自由度的三档

写 skill 正文时，每一条指令本质上都在给模型设定**自由度**。选错档位，技能要么僵到没用，要么散到失控。

| 档位 | 形态 | 什么时候用 | 典型例子 |
| --- | --- | --- | --- |
| **高自由度** | 文字描述、原则、启发式 | 有多种正确做法，取决于上下文 | "优先复用仓库已有的模块，而不是重新造" |
| **中自由度** | 伪代码、带参数的脚本 | 有推荐做法，但允许变体 | "用 `scripts/rotate_pdf.py <路径> <角度>` 旋转" |
| **低自由度** | 固定脚本、几乎无参数 | 操作脆弱易错，一致性关键 | "必须用 `make_link.py` 生成链接，不要手写 Markdown" |

### 判断口诀

> **问自己：换个做法会不会明显变差？**
>
> - 会明显变差 → 低自由度，写死命令
> - 会稍差但可接受 → 中自由度，给带参数的脚本
> - 换个做法也没问题 → 高自由度，给原则

### 真实例子

**高自由度**（`skill-creator` 的"设置自由度"章节）：
> 高自由度：多种方法都有效时用；中自由度：存在首选模式、允许少量变体时用；低自由度：操作脆弱且易错、一致性关键时用。

**低自由度**（本仓库 `AGENTS.md` 的密钥约定）：
> 密钥只写进 `Demos/.env`（已在 `.gitignore` 中），提交的是 `.env.example`

这类"绝对不要做错"的事，就应该写成**没有选择空间**的指令，而不是"建议把密钥放在 .env"。

## 2. 正文的骨架

一个成熟的 SKILL.md 正文基本是这四块：

```markdown
# <技能名>

<一段话说明这个技能解决什么问题——不是复述技能名>

## 流程 / 工作步骤

<按顺序的步骤，或带决策分支的流程>

## 关键决策点

<遇到岔路口时怎么选，带判断依据>

## 边界与失败处理

<什么情况下不该继续、失败了怎么办、什么时候该问用户>

## 产出格式

<如果产出有固定形态，定义模板；否则省略>
```

**不是每块都要有。** 判据很简单：**这块内容会不会导致模型做出不同的动作？**
不会的删掉。

### 决策点怎么写

不要写成一个线性长流程，除非流程真的没有岔路。有岔路就写成决策树：

```markdown
1. 先确定改动类型：

   **新建文件？** → 走「新建流程」
   **修改已有文件？** → 走「修改流程」

2. 新建流程：
   - 用 `init_skill.py` 生成骨架
   - ...

3. 修改流程：
   - 先读现有 SKILL.md，确认当前 description
   - ...
```

这是 `skill-creator` 官方 `references/workflows.md` 里的**条件式流程**范式。

### 失败处理要写

模型遇到意外时，缺省行为是"自己想办法"。如果你不接受这个结果，就得显式写：

```markdown
## 失败处理

- 模型接口超时：不要重试超过 2 次，改用规则模式继续，并在回复末尾注明"已降级"
- 检索无结果：不要编造，直接回答"知识库中没有相关内容"
```

第二条例子尤其重要——**"不要编造"必须写出来**，因为模型不会默认遵守它。

## 3. 什么该从正文里删掉

`skill-creator` 的第一原则是：

> **默认假设 Claude 已经很聪明。只添加 Claude 不知道的上下文。**
> 对每条信息发问："Claude 真的需要这个解释吗？这段话值得它的 token 成本吗？"

翻译成可执行的删减清单：

| 该删 | 例子 | 为什么 |
| --- | --- | --- |
| 模型本来就会的 | "用 Markdown 格式回答""代码要可读""注意语法错误" | 浪费 token，且稀释重点 |
| 通用软件工程常识 | "先写测试再写实现""注意处理异常" | 与技能无关 |
| 重复的自我说明 | "本技能用于处理 PDF 相关任务" | description 已经说了 |
| 客套话 | "希望这些说明对你有帮助！" | 纯噪声 |

### 一个真实案例：`skill-creator` 正文的构成

它的正文 4,348 token，逐段看：

| 内容 | 是否必要 | 说明 |
| --- | --- | --- |
| "Skills are modular, self-contained packages..." | ❌ 可删 | 定义性开场，模型已知 |
| "Think of them as onboarding guides..." | ⚠️ 半必要 | 比喻没信息量，但"给另一个 Claude 实例写"的视角有用 |
| "The context window is a public good..." | ✅ 必要 | 这是**非显然的方法论**，模型不会自带 |
| 自由度三档的定义 | ✅ 必要 | 具体分类法，模型不会自带 |
| `init_skill.py` 的调用方式 | ✅ 必要 | 具体事实 |
| "Do NOT create README.md, INSTALLATION_GUIDE.md..." | ✅ 必要 | 反直觉的禁令，模型默认会写这些 |

**判据总结：模型会不会自己想到？** 会 → 删；不会 → 留。

## 4. 写法规范

### 用命令式，不用解释式

```markdown
✗ 开发者应该考虑是否需要把这段逻辑写成一个脚本
✓ 把重复出现两次以上的逻辑写成脚本
```

### 写"为什么"，不写"做了什么"

```markdown
✗ 调用 `web_search` 工具
✓ 结论依赖外部事实时先调用 `web_search`，因为模型知识有截止日期
```

第二种写法让模型在**边界情况**下也知道该不该这么做。

### 用具体名词，不用泛指

```markdown
✗ 使用适当的 API
✓ 调用 `web_search`（参数 `query`），不要用 `web_fetch` 直接抓网页——后者拿不到搜索结果排序
```

## 5. 常见反模式

| 反模式 | 症状 | 修法 |
| --- | --- | --- |
| 提示词搬家 | 正文就是一大段 system prompt | 按第 2 节重排成流程 + 决策点 |
| 全是高自由度 | 模型每次做法都不一样，输出不稳定 | 把关键步骤降级成低自由度脚本 |
| 全是低自由度 | 机械执行，遇到变体就崩 | 留出"允许的变体"说明 |
| 隐含假设 | 正文说"用配置文件"但没说哪个文件 | 写全路径 |
| 自我重复 | 正文复述 description | 删掉 |
| 无失败处理 | 模型自己发挥 | 显式写"不要编造""降级策略" |

## 7. 本章要点

- 自由度三档：**高**（原则）、**中**（带参脚本）、**低**（固定命令）
- 正文四块骨架：流程 / 决策点 / 边界与失败处理 / 产出格式
- 删减判据：**模型会不会自己想到？会就删**
- "何时用"留给 description，"怎么用"留给正文
- **"不要编造"这类禁令必须显式写出来**
