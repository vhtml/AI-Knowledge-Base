# 06 · 记忆系统：短期、长期与检索

> **这篇要回答**：上下文（context）和记忆（memory）到底差在哪？短期记忆和长期记忆怎么分？什么时候该去检索记忆？以及一个更要紧的问题——为什么"记错了"比"记不住"严重得多？

---

## 1. 上下文是"这一轮"，记忆是"跨轮"

新手最容易把这两个词混着用，结果写出一堆"记忆系统"，其实只是把聊天记录存进了数据库。

**上下文**是本轮真正发给模型的那一串东西：系统提示 + 历史消息 + 工具结果 + 检索片段 + 本轮输入。它是**每轮重新装配一次**的产物，装配完就用完。

**记忆**是活在模型外面的信息：存在存储里，跨会话存在，需要被**检索**才能进上下文。模型本身没有记忆，它只"看到这一轮"。

| 维度 | 上下文 Context | 记忆 Memory |
| --- | --- | --- |
| 生命周期 | 一轮 | 跨轮、跨会话 |
| 谁决定内容 | 上下文策略（预算、压缩、召回） | 记忆策略（写、取、忘） |
| 每轮都在吗 | 是，每轮重新装配 | 否，只在被召回时进来 |
| 存哪 | 模型输入里，不落盘 | 模型外面的存储（列表 / 文件 / 库） |
| 满了怎么办 | 压缩、截断（第 5 章） | TTL 过期、容量淘汰、冲突覆盖 |

一句话：**上下文是"这一轮给模型看什么"，记忆是"跨轮要留下什么"。**

两个常见误解要当场拆掉：

- **"把聊天记录存起来就是记忆"**——那是短期记忆，没有检索、没有取舍、没有遗忘机制；
- **"记忆就是向量库"**——向量库只是"怎么取"那一问的答案，不是"存什么"那一问的答案。

---

## 2. 记忆四问：存什么 / 存哪 / 怎么取 / 怎么忘

设计记忆系统时，四个问题必须一起回答。**四个都想不清楚，记忆系统必然失控**——不是长胖，就是变脏。

| 问题 | 要回答什么 | 答不清楚的后果 |
| --- | --- | --- |
| **存什么** | 哪些信息值得跨会话保留：偏好、事实、文档、任务历史？ | 全存 → 污染 + 成本；只存聊天记录 → 等于没做 |
| **存哪** | 短期工作区、长期档案、还是外部知识库？谁和谁隔离？ | 全塞进上下文 → 预算爆；全塞一张表 → 无法淘汰 |
| **怎么取** | 什么查询会召回它？召回几条？按什么排序？ | 该记的没取到 = 没存；取太多 = 噪声，还白花预算 |
| **怎么忘** | 什么条件下它失效？TTL？容量？用户能删吗？冲突了谁说了算？ | 只写不删 → 档案自相矛盾，越用越差 |

四问不是并列的，是一条链：**存哪决定了怎么取，怎么取决定了怎么忘**。召回的粒度必须和存储的粒度对得上——存的是"一条完整事实"，取出来的也必须是"一条完整事实"，不能是半句话。

---

## 3. 短期记忆就是消息列表，长期记忆是跨会话的档案

**短期记忆（working memory）**就是当前会话的消息列表。它进上下文的方式非常朴素：把消息按顺序拼到本轮输入前面。

```python
# 短期记忆的全部实现
history = [
    human("我叫小王，常用订单号 A-1001。"),
    ai("收到，小王。需要我查哪一单？"),
]
result = agent.run("我的订单怎么了？", history=history)   # ← history 就是入口
```

它的边界也朴素：**进程一死就没了**，容量由上下文预算决定（第 5 章那一整套配额和压缩策略作用在它身上）。凡是"这一轮任务里需要，但下一轮不一定需要"的信息，都该留在短期记忆里，不要急着提升为长期记忆。

**长期记忆**是跨会话存在的档案，存**关于这个用户或这段经历**的东西：用户偏好、稳定的事实、引用的文档、上次任务的结论。它不自动进上下文——**每次用都得重新召回**。

| | 短期记忆 | 长期记忆 |
| --- | --- | --- |
| 范围 | 本会话 | 跨会话、跨任务 |
| 形态 | 消息列表 | 有结构的条目（内容 / 类型 / 重要度 / 来源） |
| 进上下文 | 全量、按序 | 按需召回，通常只放 top-N 条 |
| 谁写的 | 对话双方 | 写入策略（显式或隐式） |
| 何时失效 | 会话结束 | TTL / 淘汰 / 覆盖 / 用户删除 |

---

## 4. 写入：显式提取 vs 隐式推断，风险不对称

记忆从哪来？只有两条路，风险却完全不对称。

| 写法 | 触发 | 置信度 | 风险 | 落地策略 |
| --- | --- | --- | --- | --- |
| **显式提取** | 用户明说"记住：以后用中文回答" | 高 | 低 | 直接落库 |
| **隐式写入** | 从对话里推断："我平时在 Mac 上随手记一下" → 推断"用户用 macOS" | 低 | 高——推断可能错、可能临时、甚至只是玩笑 | 默认待确认，用户点头才生效 |

隐式写入危险在于**推断这一步没有任何人负责**。用户随口一句话，Agent 自己把它升格成"长期事实"，从此影响所有后续会话——包括用户根本没参与推断的那些。

所以一条硬纪律：**隐式写入默认不生效**，先存成"待确认"，用户认可再转正。仓库里的真实实现 `Demos/examples/study_planner/backend/memory.py` 走的是另一条路——**只允许通过"晋升"写长期记忆**：进长期档案这一行，就是"值得记住"的判断。

---

## 5. 检索：四种策略，四种取舍

"怎么取"这一问的核心：**不是把整个记忆库塞给模型，而是挑出这一轮真正相关的那几条。** 没召回的记忆，一条都不许出现在发给模型的消息里。

四种策略，各自的适用面：

| 策略 | 适合什么 | 优点 | 代价 |
| --- | --- | --- | --- |
| **关键词检索** | 专有名词、订单号、错误码、明确的事实 | 精确、便宜、可解释 | 接不住同义表述 |
| **语义检索** | 同义改写、口语化表达、模糊描述 | 能接住"换个说法问"的场景 | 要 embedding、贵、容易召回噪声 |
| **时间检索** | "上次""刚才""最近说过什么" | 便宜、直觉上对 | 旧但重要的事实会沉底 |
| **按重要性检索** | "我的偏好是什么""我的长期约定" | 直接命中长期核心 | 新写的垃圾也能刷上去 |

实现上有个关键分层：**候选**和**排序**是两件事。关键词/语义决定"谁有资格进召回"，时间/重要度决定"谁排前面"。默认用混合打分（相关性 + 新鲜度 + 重要度），但**召回条数必须有上限**——每条召回的记忆都在花第 5 章的预算。

配套实验给了四种策略在同一批记忆上的对照：关键词命中"用户常驻上海"，时间检索命中最新写入的"用户偏好用中文回答"；而关键词检索对"以后回复我时请用汉语"这种同义改写**一条都召不回**，语义检索才接得住。

## 6. 遗忘：TTL、容量淘汰、用户可删、冲突覆盖

只写不删的记忆系统，最终一定自相矛盾："每天能学 2 小时"和"现在改成 3 小时"同时躺在档案里，模型每次都得自己猜信哪个——这不是记忆，是噪音。

| 机制 | 触发时机 | 适合治什么 | 注意 |
| --- | --- | --- | --- |
| **TTL 过期** | 时间到 | 临时事实（"今天在赶一个 deadline"） | 过期条目在**召回层**就要跳过，不能只在清理时处理 |
| **容量淘汰** | 条数超上限 | 整体膨胀 | 要定淘汰顺序：常见是 (重要度, 写入时间)，淘汰"又轻又旧"的 |
| **用户可删** | 用户主动要求 | 用户自己的数据主权 | 这是唯一真正的"遗忘"权利，别只提供"更正"不给"删除" |
| **冲突覆盖** | 同主题新说法写入 | 自我矛盾 | 旧的**标记为被取代**而不是物理删除——"曾经这么以为"要能追溯 |

注意"标记而不是删除"：被取代的条目不参与召回，但仍留在存储里。事后复盘记忆污染，唯一能查的就是"它是什么时候、依据什么被写进去的"。

---

## 7. 记忆污染：长期记忆最大的风险

**记忆污染**指错误信息一旦写进长期记忆，就持续影响之后所有会话。

它比"记不住"严重得多，因为**恢复成本不对称**：记不住，用户再说一遍，成本是一次交互；记错了，用户根本不知道系统在替他做错误决定，等发现时已经影响了 N 个会话，**越信任 Agent，错误传播得越快**。

还有一个放大器：记忆通常以**高优先级**（system 角色）注入上下文，模型几乎不会怀疑它——第 4 章讲过的指令优先级机制，在这里变成了反噬。

配套实验把后果跑成了断言：写入一条错误的"用户主力使用的电脑系统是 macOS"之后，**第一个新会话按 macOS 回答，下一个新会话仍然按 macOS 回答**——错误会自己复制自己。修复路径是同槽位覆盖：用户更正为 Windows 后，新会话的回答变回 Windows，旧条目留在存储里可追溯。

所以防线要落在**写入那一刻**，而不是指望召回时能分辨对错：隐式写入默认待确认；同槽位只保留最新说法；每条记忆留出处（哪次会话、什么来源、什么时候写的）；用户随时能查、能改、能删。

> ⚠️ **坑**：以为"模型记得"就等于"用户能信它"。
> 记忆一旦写进去就成了系统的**事实来源**，模型不会再质疑它。
> 没有出处的记忆条目，等于让用户替系统的猜测背书——用户根本不知道你在替他猜什么。

## 8. 记忆 vs RAG，以及"记忆是给模型的输入"

**记忆和 RAG 都在做检索，但检索的是两种东西。**

| | 记忆 Memory | RAG |
| --- | --- | --- |
| 检索对象 | 关于**这个用户 / 这段经历**的事实 | 外部**知识库**里的文档片段 |
| 语料来源 | 对话与交互过程 | 离线索引的文档 |
| 怎么进去 | 运行时写入（显式或隐式） | 离线建索引，运行时只读 |
| 更新频率 | 每轮都可能变 | 相对静态 |
| 错了的后果 | 持续影响之后所有会话 | 通常只影响当前这一次回答 |

两套系统常常同时存在：问"我的订单号是多少"走记忆，问"连接池打满怎么排查"走 RAG。

接下来是最容易做歪的地方：**记忆是给模型的输入，要按"模型能不能用得上"组织，而不是按"数据表结构"组织。**

数据表按"字段齐全、互不重复"组织；模型输入按"**单条自足、彼此不打架、越少越好**"组织。同一条事实存三种说法，模型看到的是三份矛盾证据，而不是一条被确认的事实。

具体到一条记忆该怎么写：

- **自足**：说清谁、什么、什么时候。"他喜欢快一点"是废料，"用户偏好交付速度优先于价格"才有用；
- **单一**：一条只放一件事，放两件就等于给模型一个可以错一半的组合；
- **成组呈现**：召回后拼成带块头的形式，明说"这是关于这个用户的已知事实"，而不是扔一堆裸文本；
- **没召回的不进上下文**：召回不是"全都给"，是"这轮需要的给"。

## 9. 反模式对照表，以及和别的章节怎么接

| 反模式 | 问题 | 改法 |
| --- | --- | --- |
| 把聊天记录存下来就叫记忆 | 没有检索、没有遗忘，等于把噪音永久化 | 先回答记忆四问，再动手写代码 |
| 每轮把所有记忆塞进上下文 | 预算爆、噪声淹没有效信息 | 只放召回的 top-N |
| Agent 自己推断完就写长期记忆 | 推断无人负责 → 记忆污染 | 隐式写入默认待确认 |
| 记忆注入用 system 角色且不加来源 | 高优先级 + 无出处 = 错误被放大且无法追溯 | 带块头、带出处、提供更正与删除入口 |
| 只提供"更正"，不提供"删除" | 用户失去了对自己数据的控制权 | 三个都要：查、改、删 |
| 冲突时物理删除旧条目 | 事后查不到"它当初为什么这么写" | 标记 superseded，保留可追溯 |
| 把向量库当记忆系统 | 只解决了"怎么取"，没解决"存什么/怎么忘" | 四问齐了再选检索手段 |

**和别的章节怎么接：**

- **第 2 章（ReAct 循环）**——记忆检索也可以是循环里的一步：把 `查记忆` 做成工具，让模型自己决定什么时候取；
- **第 5 章（上下文工程）**——召回的记忆照样占预算、照样会被压缩，记忆块要进配额表；
- **第 8 章（反思与自纠错）**——反思结论是长期记忆的重要来源，也是最容易被污染的来源；
- **第 11 章（可观测性）**——写入与召回必须留痕：写了什么、召回了哪几条；
- **第 12 章（评测体系）**——记忆系统需要黄金集：固定查询集 + 期望召回的记忆条目；
- **第 13 章（安全）**——从文档里抽取的记忆可能夹带提示注入，这是"记忆投毒"，比聊天记录注入更难发现；
- **第 17 章（框架地图）**——框架里的 store / checkpointer 对应的是本章的"存哪"那一问；
- **`AI/LangGraph/07-持久化：检查点与时间旅行.md`**——那篇的 checkpointer 是"同一线程内的状态快照"，和本章的"跨会话用户事实"不是一回事：前者为回放续跑，后者为个性化。别把两者混成"记忆"。

配套实验：`Demos/examples/agent_lab/lessons/ch06_memory.py`，全部离线运行，把上面每条判断都变成可执行的断言——短期记忆进上下文、长期记忆跨会话、召回集合精确、TTL 过期不再召回、污染持续存在且可被更正、容量淘汰生效、未召回的记忆不进上下文。

---

## 一句话结论

> **记忆 = 跨轮的持久层，上下文 = 每轮重新装配的输入；**
> 四问（存什么 / 存哪 / 怎么取 / 怎么忘）答不清楚，系统必然失控；
> 写错一次的代价远大于记不住——**先设写入闸门，再谈召回**。
