# 12 · 评测体系：黄金集、轨迹评测与回归

> **这篇要回答**：改了 prompt 之后，怎么知道是变好了还是变差了？Agent 的"对"到底怎么定义？

---

## 1. "对"不是一个布尔值，而是三个维度同时成立

改一句提示词很容易，难的是回答"这算变好了吗"。之所以难，是因为**"对"本身不是一个布尔值**。
一次运行至少要同时满足三件事：

| 维度 | 问的问题 | 怎么判 | 不合格的后果 |
| --- | --- | --- | --- |
| **结果** | 任务完成了吗 | 最终回答是否命中期望 | 用户拿到错答案 |
| **轨迹** | 过程对吗 | 有没有调不该调的工具、有没有绕路 | 多花钱、可能产生副作用 |
| **成本** | 代价多少 | token / 步数 / 延迟是否超预算 | 规模化之后账单爆掉 |

**任一维度不合格，整条用例就算失败。** 这条纪律比任何单个指标都重要——
评测体系松一个口子，剩下的就全漏了。

三种典型组合，各自指向完全不同的修法：

- **结果对 + 轨迹错**：答案没错，但顺手调了不该调的工具。多一次写操作、多一次审批打扰。
- **结果错 + 轨迹对**：路径完全正确，说明锅在工具或数据，**不在提示词**。这时候改 prompt 是白改。
- **结果对 + 轨迹对 + 超成本**：每次都对，但一次要三万 token。上线跑量之前必须解决。

只有把三个维度拆开看，你才知道该改哪里。

---

## 2. 结果怎么判：五种方式，可靠性和成本各不相同

| 判定方式 | 可靠性 | 成本 | 什么时候用 |
| --- | --- | --- | --- |
| **精确匹配** | 最高 | 最低 | 有唯一正确答案：数字、ID、枚举值 |
| **断言**（可执行检查） | 高 | 低 | 有结构化要求：必须含 X、必须引用 Y、必须出现两次 |
| **包含关键字** | 中 | 低 | 开放式回答，答案是其中一个片段 |
| **LLM-as-judge** | 中偏低 | 中 | 开放质量判断：完整性、语气、有没有跑题 |
| **人工** | 最高，但慢 | 最高 | 上线前抽检；以及**定义**"对"到底指什么 |

原则：**从下往上选**。能用确定性判定就别用 judge，能用 judge 就别用人。

理由很直接：判定方式越靠上，你越需要为"判定本身对不对"再写一套评测。
用关键字判就只需要相信关键字对不对——这件事你通常有把握；
用 judge 判就还要回答"这个 judge 准不准"，那是另一个无底洞。

---

## 3. 只看结果不够：轨迹必须单独评

上一节的表格里，结果维度只有"最终回答"这一个观测点。但 Agent 的产物不只有答案，
还有**一串过程**。第 11 章说过：轨迹 ≠ 答案。现在要补一句：**轨迹 ≠ 答案，而且轨迹要单独打分**。

理由有两个方向：

1. **结果对了，过程可能有害。** 模型多调了一次写工具，多花了钱、可能改了外部状态。
   答案还是对的，但这次运行是**不该发生的**。
2. **结果错了，过程可能完全正确。** 路径选对了、参数也对，是工具挂了或数据错了。
   这种失败改提示词没用，该修工具——不分开评，你连该改哪儿都不知道。

**轨迹评测抓的是"调用行为"，不只是"是否真的执行"。**
就算审批关卡把那次写操作拦下了，调用依然发生了：它消耗了轮次、token、可能触发了通知。
本仓库的实现里，`EvalCase.forbidden_tools` 就是这条规则：

```python
@dataclass
class EvalCase:
    case_id: str
    question: str
    script: list[ModelReply]
    expect_answer: str          # 期望答案（结果维度）
    forbidden_tools: tuple[str, ...] = ()   # 绝对不该调用的工具（轨迹维度）
    max_tokens: int = 4000      # 成本维度
```

期望轨迹不只有"禁止清单"这一种形式，还有"必须清单"（否则模型可能在瞎猜）
和"调用次数上限"。但无论哪种，**先记下来，才谈得上评**。

---

## 4. 黄金集不是拍脑袋写的，是从失败里长出来的

黄金集的质量，决定了后面所有分数的可信度。三条硬规矩：

**第一，它从真实失败案例里长出来。** 来源只有几种：线上事故、用户投诉、人工抽检发现的坏输出。
拍脑袋写的用例测的是"你想让它做什么"，真实失败测的是"它真的会做错什么"——
后者才是你要防的东西。

**第二，每条用例要记录期望轨迹，不只是期望答案。** 只记答案的用例，
在"结果错、轨迹对"和"结果对、轨迹错"这两种失败面前都是瞎的。

**第三，覆盖度优先于数量。** 起步阶段，20–50 条覆盖面合理的用例，比 5 条精心编的用例有用得多。
先列场景维度——只读 / 写 / 危险 / 该拒绝 / 该降级 / 幻觉工具名 / 超长输入 / 多轮记忆召回——
每个维度至少一条。分布上要**故意加重失败场景**：线上 90% 是简单问答，
你的黄金集不该 90% 都是简单问答。

还有一条容易被忽略：**黄金集里要留"已知失败"的用例**。
一条全是绿灯的黄金集没有灵敏度——门禁无从发现退化。实验里那条 `x01` 就是这个角色：
线上提示词多了一句"回答前先把要点存一份笔记"，于是只读问答也开始写笔记，
**答案完全正确**，只有轨迹维度能抓住它。

## 5. 回归门禁：同一份黄金集跑两遍，掉了就阻断

评测体系的闭环长这样：

```
改动 → 跑同一份黄金集 → 比分 → 掉了就阻断 → 更新基线（带原因）
```

**同一份**是关键。换了用例集再比，比的是两套不同的题，没有意义。

基线怎么定？**当前生产版本在黄金集上的分数**——它可以低于 100%。
把基线定成 100% 的做法有个致命后果：一旦有真实缺陷被发现，你的第一反应是"改基线"，
于是门禁就再也没有约束力了。

所以基线的更新要有纪律：

- **必须写原因**——不许无声无息地把基线挪一挪；
- **分数下降必须显式声明**——"把基线调低"是绕开门禁的后门，得留痕；
- 门禁本身要能给出**明确的失败信号**：CI 里就是非零退出码，
  而不是打一行红字让人自己决定要不要在意。

门禁跑在哪、用什么模型？**CI 里跑确定性路径**——用脚本化的假模型把轨迹录下来，
不联网、结果可复现、断言可以写死。真实模型的分数会飘，用它卡门禁，你会天天在追噪声。

## 6. LLM-as-judge 的四个坑

judge 很好用：它是唯一能判"这个回答好不好"的办法。但它有四个必须知道的坑。

**坑一：同源偏袒。** 评委和被评对象如果是同一个模型（或同一家供应商），
评委会倾向于给"看起来像自己写的"答案打高分——自己家的孩子自己看着顺眼。
解法不是加提示词，而是**换评委**：换模型、换厂商，
或者干脆把外部断言的结果喂给评委当输入。

**坑二：判定标准必须可执行。** "回答得好不好"不是标准，评委只能猜。
"必须回答了问题、必须包含关键信息 X、不得跑题"才是标准。
再配一个**固定输出格式**（比如只输出「得分：0」或「得分：1」），
否则每次都要写正则去捞，评测本身就成了一团不可靠的东西。

**坑三：judge 的一致性要自己测。** 同一份答案问两遍，判定应当一致；
再拿一批已知答案的样本跑一遍，看**假阳性率**——把不合格的说成合格。
假阳性比准确率更要命：漏判只是浪费一次人工复核，
误判会让整条门禁形同虚设。

**坑四：judge 不是判据，是启发式。** 最终判定必须由外部断言兜底。
judge 负责"在两个都还行的答案里挑一个更好的"，不负责"放不放行"。

## 7. 防过拟合：分数涨了，不等于变好了

这是评测体系里最阴险的一类事故，因为**它长得像成功**。

典型经过：你反复在黄金集上调提示词 → 某天你把黄金集的期望答案贴进了系统提示，
"这样模型答得更稳" → 分数从 60% 跳到 95% → 你宣布改进了。

但模型真正学会的是：**不检索，直接背**。凡是被你贴过的题，它都能背；
线上那些没被贴过的问题呢？它开始瞎猜。

**症状特征**：黄金集分数跳升，**留出集分数不动甚至下跌**。
所以评测必须分两份：

- **黄金集**：参与调优，用来驱动改进；
- **留出集**：不参与任何调优，只在最后验收。

配套的**扩充机制**才是黄金集唯一的合法来源：

> 线上每出现一次真实失败 → 往黄金集补一条用例 → **记录来源**（哪个工单、哪次会话、什么时间）。

记录来源不是形式主义。半年后你会问"这条用例为什么存在"，
答案只能是"3 月 12 日线上有个用户被误删了笔记"。记不住来源的用例，
迟早会被当成冗余删掉，然后那个 bug 就回来了。

## 8. 指标定义要钉死，评测要放在对的位置

### 8.1 指标怎么算，不许含糊

- **任务成功率 = 通过用例数 ÷ 用例总数。**
  分母里**包含**失败用例。把失败的从分母里剔掉是常见的粉饰手法：
  跑挂了 3 条但只报"跑了 1 条且成功"，通过率就从 0% 变成 100%。
- **步骤效率 = 实际模型轮次 ÷ 理想轮次。**
  大于 1 说明它绕了路——而绕路在结果评测里是查不出来的；
  小于 1 通常意味着它没真做。
- **平均 token / 任务**：成本维度的汇总指标，同样要写清是均值还是中位数。

### 8.2 评测放在哪跑

| 位置 | 跑什么 | 用什么模型 | 频率 |
| --- | --- | --- | --- |
| **CI** | 确定性路径 | 脚本化假模型 | 每次提交，卡门禁 |
| **发版前** | 真实模型抽样评测 | 真模型 | 每次发版 |
| **线上** | 抽样打分 + 失败样本回收 | 真模型 | 持续 |

CI 里的确定性路径负责**卡住回归**：可复现、断言能写死、不花钱。
线上的抽样评测负责**发现新问题**：真模型分数会飘，只看趋势不看绝对值，
但每一笔失败都要能**一键回收**成黄金集用例。

## 一句话结论

> **"对" = 结果对 ∧ 轨迹对 ∧ 成本没超；黄金集从真实失败里长出来，改一次跑一次，分数掉了就阻断。**
> 分数只是信号，不是结论——它会骗人，尤其是当你自己就是那个评委的时候。
