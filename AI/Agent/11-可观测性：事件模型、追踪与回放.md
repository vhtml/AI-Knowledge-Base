# 11 · 可观测性：事件模型、追踪与回放

> **这篇要回答**：Agent 出问题的时候你怎么查？到底要记下什么，才能在三天后回放出"它当时为什么这么做"？

---

## 1. 为什么 Agent 的日志特别难查

普通后端的故障链是线性的：请求进来 → 某行代码出错 → 报错。栈信息直接指向原因。

Agent 不是。**同样的输入，模型这次走 A 路径、下次走 B 路径。**
一次运行可能经过 5 轮、调用 3 个工具、产生 12 条消息。当它给出错误答案时，
你要回答的是："第几轮开始跑偏的？当时模型看到了什么？它为什么选了这个工具？"

**而这些信息，模型的回答里没有。** 它只会给你一个看起来很合理的最终答案。

所以 Agent 的可观测性不是"锦上添花的日志"，是**唯一的事故调查工具**。

---

## 2. 事件 vs 日志

| | 日志（log） | 事件（event） |
| --- | --- | --- |
| 形态 | 文本行 | 结构化记录（字段固定） |
| 读者 | 人 | 人 + 机器 |
| 例子 | `"调用工具 查询订单 耗时 120ms"` | `{"type":"tool_call","name":"查询订单","args":{...},"ms":120}` |
| 能不能回放 | 不能 | **能** |
| 能不能聚合 | 要靠正则硬抠 | 直接 group by |

**判断标准**：这条记录如果要用 `grep` 才能回答"过去一小时 `write_note` 失败了多少次"，
它就该是事件。

---

## 3. 一次运行要记什么

### 3.1 最小集合

| 字段 | 为什么必须有 |
| --- | --- |
| `run_id` | 把一次运行的全部事件串起来 |
| `parent_id` | 串起父子关系（第 4 节） |
| `type` | 事件类型：`model` / `tool_call` / `tool_result` / `error` / `approval` |
| `timestamp` | 算耗时、算顺序 |
| `elapsed_ms` | 哪一步慢 |
| `payload` | 这一步的具体内容 |

### 3.2 至少要记的内容

**① 模型这一轮看到了什么。**
不是"我发了什么 prompt"，而是**模型实际收到的完整 messages**。
这两者经常不一样——中间件改过、模板拼过、上下文压缩过。

> **这一条是最容易漏、也是最有价值的。**
> 排查"模型为什么胡言乱语"时，第一件事就是看它实际收到了什么。
> 没有这条，你只能猜。

**② 工具的入参和出参。**
入参看出模型理解得对不对，出参看工具是不是返回了奇怪的东西。

**③ token 与成本。**
分轮次记，才能看出"哪一轮开始爆 token"。

**④ 错误。**
按类型记（参数错 / 业务错 / 限流 / 未知），不要只记字符串——
第 10 章说过，这几类的处理方式完全不同。

**⑤ 停止原因。**
`completed` / `max_iterations` / `rejected` / `error`。
`max_iterations` 意味着**它在烧钱之前被切断了**，这个信号不能丢。

### 3.3 不要记什么

- **明文密钥**——脱敏必须在**写入时**做，不是读取时做。trace 通常会进日志系统，
  事后补救来不及。
- **大段原始内容**——完整网页、整个文件。记摘要 + 长度 + 内容哈希。
- **模型的"自我解释"**——见第 6 节。

---

## 4. 父子关系：一次运行是一棵树

Agent 的轨迹**不是一条线，是一棵树**：

```
run (根)
├── model: 第 1 轮
│   └── tool_call: 检索
│       └── tool_result
├── model: 第 2 轮
│   └── tool_call: 读取
│       └── tool_result
└── model: 第 3 轮 → 最终回答
```

父 span 是"一次运行"或"一次模型调用"，子 span 是工具调用。
父子关系让你能回答：

- 这次运行一共花了多少 token？（根 span）
- 哪个工具最慢？（子 span 聚合）
- 这次运行调用了多少次模型？（根 span 的计数）

**并行工具调用**会让子 span 变成兄弟节点，这时候要靠 `parent_id` 而不是顺序来对齐。

---

## 5. 回放：让同一次运行再发生一次

回放有两种，含义不同：

| 类型 | 复用什么 | 用途 |
| --- | --- | --- |
| **重放模型输出** | 复用工��调用的**响应**，重新跑一遍流程 | 验证我的新代码逻辑对不对，**不花模型钱** |
| **重放完整请求** | 用**原样参数**重新发请求 | 验证"是不是模型那边的问题" |

**排查时的标准动作**是第一种：把 trace 里的模型响应喂回去，看新代码跑出来的轨迹对不对。
这样每次调试迭代都是零成本的。

要能重放，trace 就必须记下：

1. 模型实际收到的 messages（不是"应该收到的"）；
2. 模型返回的完整响应；
3. 工具的入参出参；
4. 随机性的来源（temperature、seed）。

> **第 4 条常被忽略**：如果你的流程里有随机性，重放就对不上。
> 要么在 trace 里记下随机种子，要么把随机源收敛到一处并记录它的取值。

## 6. "让模型解释一下"是不可信的

Agent 给出错误结果时，很自然会想："问它一句为什么"。**不要相信这个答案。**

原因很简单：模型**没有**"我当时为什么这么选"的内部记录。它是在**事后**编一个听起来合理的解释。
这个解释会非常自信、非常有道理，而且**大概率是错的**。

更糟的是它会把你带偏——你会花一小时追查一个模型编出来的原因。

> **纪律**：判断"它为什么这么做"，只看 trace，不听它自述。
> trace 记的是**发生过什么**，模型自述是**事后编的故事**。

---

## 7. 该盯哪些指标

单条 trace 只够查一次故障。要发现趋势，得看聚合指标：

| 指标 | 怎么用 |
| --- | --- |
| **任务成功率** | 主指标，按任务类型分开看 |
| **工具调用分布** | 某个工具**从没被调用过** = 它的描述写坏了，模型从不选它 |
| **工具失败率（按错误类型）** | 参数错高 = 模型没学会用；业务错高 = 后端有问题 |
| **轮次分布** | P90 轮次突然上升 = 某类任务开始绕圈 |
| **token 分布（按轮次）** | 输入 token 斜率变陡 = 上下文没裁剪 |
| **停止原因分布** | `max_iterations` 占比上升 = 有任务在烧钱 |
| **成本 / 任务** | 商业指标，不达标就要做分级路由 |

**"从没被调用过的工具"是最被低估的信号**：
它不报错、不告警，但意味着你精心写的那段描述是无效的。

## 8. 脱敏：必须在写入时做

```python
SENSITIVE_KEYS = {"api_key", "password", "token", "secret", "authorization"}

def redact(payload: dict) -> dict:
    """把敏感字段换成占位符——递归处理嵌套字典。"""
    clean = {}
    for key, value in payload.items():
        if key.lower() in SENSITIVE_KEYS:
            clean[key] = "***REDACTED***"
        elif isinstance(value, dict):
            clean[key] = redact(value)
        else:
            clean[key] = value
    return clean
```

三个要点：

1. **按字段名匹配，不按值猜**——按值猜会误伤正常数据。
2. **要递归**——敏感字段常常藏在嵌套结构里（`{"request": {"headers": {"api_key": ...}}}`）。
3. **在写入时做**——trace 一旦落进日志系统，事后补救就来不及了。

---

## 9. 最小可用方案

如果你的团队只想要 80% 的价值，先做这四件事：

1. **每次运行一个 `run_id`**，所有事件挂在这个 id 下；
2. **记模型实际收到的 messages**（可截断，但要知道截了多少）；
3. **记工具的入参出参 + 错误类型**；
4. **写入时脱敏**。

这四条做完，你的排查能力会从"看最终答案猜"变成"翻出那一轮看它到底看见了什么"。

---

## 一句话结论

> **Agent 的 trace 不是日志，是唯一的事故调查工具。**
> 最该记的是"模型实际收到了什么"——那一条能省掉你 80% 的猜测时间；
> 最该不信的是"模型自己解释为什么"——那是事后编的故事。
