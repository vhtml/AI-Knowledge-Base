# 15 · 成本与延迟工程

> **这篇要回答**：一次任务烧多少钱、跑多久？怎么在**不掉质量**的前提下把两者压下来？

---

## 1. 先建立两个数

任何成本讨论都要从两个具体数字开始：

- **单次任务成本**（美元）——一次完整运行，包括所有轮次、所有工具调用；
- **单次任务延迟**（秒）——从请求进来��最终答案出去。

**说不出这两个数字，就没法谈优化。** "有点贵""有点慢"不是可操作的描述。

本章的实验里这两个数都是算出来的，不是估的。

---

## 2. 成本构成：钱烧在哪

一次 Agent 运行的成本：

```
总成本 = Σ(每轮 输入 token × 输入单价 + 输出 token × 输出单价)
       + 工具调用本身的开销（多数工具不花钱，但会花延迟）
```

四个观察：

### 2.1 输入 token 通常是输出的十倍以上

一次带 10 轮历史的对话，输入上万 token，输出只有几十。

> **所以成本优化的第一杠杆不是"让模型少说话"，是"别把没用的东西塞进上下文"。**

### 2.2 轮次是乘数

5 轮的任务比 2 轮的贵 2.5 倍——**不是线性**，因为每一轮都重发全部历史。

```
第 1 轮：输入 1000
第 2 轮：输入 1500
第 3 轮：输入 2000
...
第 n 轮：输入 1000n
总输入 ≈ 1000 × n(n+1)/2   ← 平方增长
```

**这是"上下文没裁剪"最致命的地方**：轮次涨一点，总成本涨很多。

### 2.3 工具 schema 每轮都要重发

10 个工具的 schema 大约 1000–2000 token，**每轮都付一遍**。
一个 8 轮的任务，光工具 schema 就付了 16000 token。

所以"减少工具数量"省的不只是选择准确率，还有实打实的钱（第 13 章）。

### 2.4 缓存命中能大幅降低输入单价

前缀不变时，命中的部分按折扣价计费。

---

## 3. 延迟构成：时间花在哪

```
总延迟 = Σ(每轮 模型延迟) + Σ(工具延迟) + 网络开销
```

关键区分：

| 指标 | 含义 | 谁关心 |
| --- | --- | --- |
| **TTFT**（首字延迟） | 从请求到用户看到第一个字 | **对话类产品**——用户等的是"开始了没" |
| **总延迟** | 到最终答案 | **后台任务类**——用户等的是"做完了没" |
| **吞吐** | 每秒生成多少 token | 批量场景 |

**流式只改善 TTFT，不改善总延迟。** 拿"我用了流式所以更快"来回答延迟问题，
在对话场景成立，在批量场景不成立。

---

## 4. 成本控制：五个杠杆

按性价比排序：

### ① 裁剪上下文（收益最大）

- 历史裁剪、工具结果截断、摘要压缩
- 对应第 5 章
- **收益**：输入 token 直接降；轮次多了是平方级降

### ② 模型分级路由（收益第二大）

**不是所有任务都需要最贵的模型。**

| 任务类型 | 需要的档位 | 例子 |
| --- | --- | --- |
| 分类、路由、抽取 | 便宜档 | 意图识别、实体抽取 |
| 常规问答、工具调用 | 标准档 | 大多数 Agent 任务 |
| 复杂推理、长程规划 | 前沿档 / 推理档 | 多步数学、架构决策 |

分级路由的收益要**用评测证明**：便宜档在它负责的那类任务上，
成功率不能低于标准档。

### ③ 提高缓存命中率

- 系统提示、工具 schema、检索文档这些**前缀要稳定**
- 把易变内容（时间戳、随机 ID）放到**末尾**
- 命中部分按折扣价计费

### ④ 减少轮次

- 合并工具调用（一轮里并行调用多个工具）
- 减少"模型→工具→模型"的往返
- 直接给出答案而不是"再确认一下"

### ⑤ 控制工具数量

工具 schema 每轮重发，工具越少越便宜。

---

## 5. 延迟优化：三个手段

### ① 流式输出

把 TTFT 从"整段生成完"降到"第一个字出来"。对话场景必做。

### ② 并行工具调用

一轮里多个工具并行执行，延迟从"求和"变成"取最大"。

**代价**：部分失败的处理变复杂（第 10 章）；而且并行会**增加** token 成本
（每个并行分支都要自己的上下文）。

### ③ 缓存与推测

- 检索结果缓存、相同前缀命中
- "推测执行"：不等模型决定就先跑最可能的那条路径——**危险**，
  因为推测错了要回滚，第 10 章的幂等性就是为它准备的

---

## 6. 单位经济学：分级路由的临界点

分级路由不是免费的：它要一个"路由决策"（谁来决定用哪个档位）。
如果路由本身要调一次模型，那要多付一次调用的钱。

设：
- 标准档单价 `c_s`，便宜档单价 `c_c`，`c_c < c_s`
- 路由成本 `c_r`（用规则实现时接近 0，用模型实现时是一次调用）
- 便宜档能正确处理的比例 `p`

**期望成本** = `p × c_c + (1-p) × c_s + c_r`

判据：**期望成本 < 全部走标准档的成本**，也就是：

```
p × c_c + (1-p) × c_s + c_r  <  c_s
⟺  p × (c_s - c_c)  >  c_r
```

翻译成人话：**便宜档的命中率必须高到足以摊平路由成本。**

- 路由用规则实现（`c_r ≈ 0`）→ 只要 `p > 0` 就划算；
- 路由用模型实现 → `p` 必须超过一个可观的阈值。

> 这就是为什么**规则路由优先**：能用关键词、格式、任务类型判断的，
> 不要用模型判断。

---

## 7. 成本护栏

优化是事后的，护栏是事前的。四个：

| 护栏 | 作用 | 超了怎么办 |
| --- | --- | --- |
| **单任务 token 上限** | 防止一个任务烧掉一天预算 | 停止并报告 |
| **单任务轮次上限** | 防止死循环（第 2 章） | 停止，返回最好的一版 |
| **单任务成本上限** | 直接以金额封顶 | 停止并报告 |
| **会话级预算** | 防止一个用户无限消耗 | 降级到便宜档或要求充值 |

护栏必须**在运行时检查**，不能靠事后统计。

---

## 8. 质量不能掉

任何成本优化都必须回答：**质量掉了吗？**

判据：**用同一份黄金集跑一遍（第 12 章）**。

```
优化前：成功率 92%，平均成本 $0.08
优化后：成功率 91%，平均成本 $0.03   ← 掉 1 个点，换 62% 的钱
```

这样的交换值不值得？取决于你的场景：
- 高频低价值任务 → 值；
- 低频高价值任务 → 不值。

> **一条纪律**：**先有评测，再优化。**
> 没有评测集的优化是在赌，而赌的是"质量没掉"这个你最不该赌的东西。

---

## 9. 上生产前算一遍

- [ ] 单次任务成本（最坏情况，不是平均）是多少
- [ ] 单次任务延迟（TTFT 和总延迟）是多少
- [ ] 成本构成拆开了吗：输入/输出/轮次/工具 schema 各占多少
- [ ] 上下文裁剪策略上线了吗（第 5 章）
- [ ] 模型分级路由有评测支撑吗（第 12 章）
- [ ] 缓存前缀稳定吗
- [ ] 四个护栏都实现了吗
- [ ] 成本优化有黄金集验证质量没掉吗

---

## 一句话结论

> **输入 token 通常是输出的十倍，轮次是平方级放大器——所以先砍上下文，再砍轮次，最后才砍模型。**
> 任何优化都必须用同一份黄金集证明质量没掉；没有评测的优化，是在赌你最不该赌的东西。
