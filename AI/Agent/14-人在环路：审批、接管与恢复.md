# 14 · 人在环路：审批、接管与恢复

> **这篇要回答**：哪些操作必须让人点头？人不在的时候怎么办？审批怎么做才不把人烦死？以及——当人不想点头而想自己动手时，控制权怎么交出去、交完之后怎么再拿回来？

---

## 1. 审批触发点：按动作风险触发，不按工具名

第 13 章的结论直接延伸过来：**工具名可以被绕过**。`delete_note` 被禁了，模型可能去调 `remove_note`。
所以审批触发点不能挂在工具名单上，要挂在**动作语义**上。

判断只有一个问题：**这次调用会不会改变外部世界？能不能撤销？**

| 等级 | 判据 | 例子 | 处理 |
| --- | --- | --- | --- |
| `READ_ONLY` | 不改变任何东西 | 查订单、搜文档、读文件 | 直接执行，不打断人 |
| `WRITE` | 改变世界，可逆或半可逆 | 建笔记、改配置、发内部消息 | 要审批 |
| `DANGEROUS` | 改变世界，不可逆或对外 | 删除、支付、对外发送、改权限 | 要审批 + 更严的确认 |

阈值本身也是策略：阈值设在 `WRITE`，写操作全部要批；设在 `DANGEROUS`，只有危险操作要批。
**默认阈值应该偏严**——审批的收益是不出事，代价只是多点一次。

> **一条纪律**：审批必须落在**执行层**，不能只写在系统提示里。
> 提示词是建议（第 13 章），执行层才是防线——模型绕不过执行层。

关卡落在哪里，长这样：

```python
# 执行层关卡：模型绕不过这几行
if gate.needs_approval(tool):              # 按风险判定，不按工具名
    request = gate.request(tool, args)
    outcome = gate.await_decision(request)  # 批准 / 改参数 / 拒绝 / 接管
    if outcome.status != "approved":
        return outcome.message              # 回填给模型，让它换条路
    args = outcome.arguments                # 用人改过的参数执行
return tool.invoke(args)
```

注意 `args = outcome.arguments` 那一行——它就是"改参数后放行"的落点，
也是最容易漏掉的一行。

## 2. 审批粒度：一次一个，还是一次一批

粒度是一个**双向**的错：

- 太细：每个动作点一次，人很快就不看了；
- 太粗：一批里混着不该做的动作，一起放行就等于漏审。

| | 一次一个（per-call） | 一次一批（batched） |
| --- | --- | --- |
| 5 个同质操作 | 5 次点头 | 1 次点头 |
| 人每次要判断的上下文 | 一个动作 | 完整一批 |
| 主要风险 | 审批疲劳 | 一批里混进危险动作会跟着放行 |
| 适用场景 | 动作异质、高危 | 动作同质、批量 |

**规则很简单**：同质（同一工具、同一风险等级、要么都做要么都不做）就合批；异质就拆开。
拆批的判断依据是"这批动作能不能被区别对待"——能，就不该合批。

合批还有个被低估的好处：**一次请求承载更多信息，人看得更仔细**。
五个动作摊开成五张卡片，人是在做五次无信息的点击；合并成一张"写 5 篇笔记（标题列表）"，
人至少还知道自己在批什么。

---

## 3. 坑：审批疲劳是审批机制最常见的失效方式

审批机制的失效，往往不是被攻击，而是**被人训练出来的**。

每件事都要点，人就会形成"闭眼点同意"的习惯。疲劳有三个征兆：

1. 审批次数远多于任务里真正高风险的步骤数；
2. 人的响应时间随审批次数增加而**下降**——他在赶时间，不是在判断；
3. 审批界面上开始出现"全部同意"按钮。

第三条是致命的：**它把审批从"逐个判断"降级成了"一次性放行"**，只是换了个界面。

三条对策：

- **减少审批次数**——合批同质动作、把阈值放宽到真正高危的那些；
- **让审批有信息**——审批卡片必须显示参数和影响面（删哪几条、改哪个文件），不看就没法判断；
- **区分"事前审批"和"事后审计"**——低危操作走事后审计（留台账、可回溯），不要占用人的注意力。

> **一条纪律**：如果你的系统每天要人点 50 次，那不是审批，是许愿。
> 审批疲劳不是 UX 问题，是**安全机制失效**——因为人已经不再真的在检查了。

## 4. 超时策略：人不在的时候，默认应该是拒绝

人总会不在。审批请求发出去之后没人响应，你必须提前决定"那接下来怎么办"。

| 策略 | 行为 | 风险 | 什么时候用 |
| --- | --- | --- | --- |
| **自动放行** `allow` | 超时后直接执行 | **高**：人没看过的操作照样发生，审批退化成橡皮章 | 几乎不该用；只在低危且有完整事后审计时 |
| **自动拒绝** `reject` | 超时后拒绝，并回填给模型 | 低：动作没发生，模型可以换条路 | **默认** |
| **挂起等待** `hold` | 停在检查点，等人晚点来批 | 中：动作没发生，但流程卡住 | 异步审批，且有人一定会回来 |

**默认必须是拒绝。** 三条理由：

1. 自动放行等于承认"人没看也无所谓"——那这个关卡本来就不该存在；
2. 自动拒绝能给出明确的回填（"未获批准"），模型可以换条路，流程不会死；
3. 挂起等待的前提是**有人真的会回来**。如果没人会回来，挂起就是挂死——比拒绝更糟，因为它既没执行也没给模型交代。

三档策略的实际差别，可以看成一组对照：

```
reject：不执行 → 回填"未获批准" → 模型换条路 → 流程继续
allow ：执行了 → 人事后才知道 → 审批只是走个形式
hold  ：不执行 → 落检查点 → 人回来后从暂停点恢复
```

## 5. 审批不止点头：批准 / 改参数 / 拒绝 / 接管是四件事

把审批简化成"是 / 否"会丢掉最常用的第三种答案：**人看完之后觉得该改**。

| 决策 | 语义 | 工具执行吗 | 给模型什么 |
| --- | --- | --- | --- |
| **批准** | 按原参数做 | 是 | 正常结果 |
| **改参数** | 用我改过的参数做 | 是（用**新**参数） | 正常结果（改了什么进台账） |
| **拒绝** | 别做 | 否 | "未获批准 + 请换条路" |
| **接管** | 我自己做 | 否（人做） | 控制权交出去 |

**改参数**是最容易做错的一种：人把"删 100 条"改成"删这 3 条"，运行时如果还用原参数执行，
人的修改就只是个摆设。所以实际执行必须用**改后的参数**，而且：

- 改后的参数要进 trace（第 11 章）；
- 原始参数也要留一份——两相对照才知道人改了什么。

拒绝和接管更不能用同一个分支处理：拒绝是"这件事别做"，接管是"这件事**我**来做"。
两者的后果完全不同，混在一起会让状态说不清。

---

## 6. 接管：把控制权干净地交出去

接管是 HITL 里最常被误解的一半。**审批是"点头/摇头"，接管是"我来"。**

审批是纯交互：人看到请求，回一个决定，Agent 继续跑。接管不是——
接管要求 **Agent 的状态可以被外部修改**：模型能被人替掉，工具能被人直接在界面上调，
任务描述能被人改写。这对运行时有一个硬性要求：**状态必须是显式的、可序列化、可被覆盖的**，
而不是藏在某个函数的局部变量里。

接管要交得干净，交接包至少包含四样：

| 交接包内容 | 少了会怎样 |
| --- | --- |
| 当前状态：做到哪一步了 | 人得从头摸索 |
| 已完成的动作清单 | 人可能重复做 |
| 待办清单 | 人不知道该接什么 |
| 上下文快照（读了什么、搜到啥） | 人得自己去查一遍 |

接管之后 Agent 必须**停止自动执行**——不能一边交接一边继续跑。
交接是"我退出控制台"，不是"我把遥控器递给你，同时我自己还在按按钮"。

## 7. 恢复：从暂停点继续，不是从头重跑

挂起之后，人批了，Agent 怎么接着跑？

恢复有三个前提，缺一个就一定会出重复副作用：

1. **检查点存够东西**：消息历史、卡住的那次调用、它的参数、当时的决策位置；
2. **恢复时不重做已完成的动作**——这靠的是"从第几轮继续"，不是"从第 0 轮重跑"；
3. **恢复时状态必须是对的**：谁批的、批了什么、参数有没有被改，都要在恢复后的上下文里。

第 3 条就是第 11 章的用武之地：轨迹能回答"恢复之前到底做过什么"。
没有轨迹，恢复就是盲跑——你不知道该重做哪一段、不该重做哪一段。

手写运行时里，"接着跑"其实只需要多记一个数字：

```python
# 挂起时：记住"下一轮从哪儿继续"，而不是"从头再来"
checkpoint = {
    "messages": messages,          # 已经产出的上下文
    "iteration": index + 1,        # 下一轮从哪儿开始 ← 关键就这一行
    "pending": pending_request,    # 卡住的那次调用和它的参数
}
# 恢复时：messages = checkpoint["messages"]，从 checkpoint["iteration"] 继续
```

`iteration` 记成 `index` 而不是 `index + 1`，那一轮就会再跑一遍——
副作用重放、消息重复、模型看到重复的上下文。

> **框架层的坑**（对照 [`AI/LangGraph/08-人在环路：中断、审批与恢复.md`](../LangGraph/08-人在环路：中断、审批与恢复.md)）：
> LangGraph 的 `interrupt()` 在恢复时是**从头重跑整个节点**，中断之前的代码会再执行一遍。
> 所以副作用必须放在中断**之后**，而且要幂等。
> 手写运行时可以做得更好——直接记住"下一次从第几轮继续"——但代价是你得自己写检查点。

幂等和检查点，两个都要。检查点解决"别重做"，幂等解决"万一重做了也不出事"。

## 8. 拒绝之后要能换条路，批过之后要留得下证据

### 8.1 拒绝的回填要让模型能换条路

拒绝的文案是有技术含量的，它决定了模型下一步是"换个办法"还是"原地撞墙"。

一条合格的拒绝回填要写清三件事：

1. **发生了什么**——"写笔记 未获批准"；
2. **为什么**——"这周的数据还没核对完"；
3. **接下来可以怎么办**——"请改用其他方式完成"。

第 3 条最容易漏。漏了它，模型的下一步多半是**换个参数再提一次同一个请求**：
内容里加个后缀、标题改一个字——参数变了，但它还是同一件事，人还是得再拒一次。

所以运行时还要有一道防线：**记住被拒过的操作指纹**（工具名 + 参数）。
模型再提同一个操作时直接拦下，回一句"这个操作已经拒过了，别再试"，然后收手。

> **一条纪律**：拒绝是一扇**门**，不是一段**死路**。
> 门是让人换路的；死路是让人反复回到同一个已知的拒绝上。
> 运行时必须能区分"新的尝试"和"同一个操作的重试"。

### 8.2 审批台账要可审计

审批台账要回答三个问题：**谁批的、批了什么、什么时候**。三样缺一不可。

| 字段 | 为什么必须有 |
| --- | --- |
| `request_id` | 串起一条请求从发起到落地的完整生命周期 |
| `approver` | 谁点的——多人和人机混合审批时必需 |
| `tool_name` | 批了哪个动作 |
| `arguments` | 实际执行的参数（人改过就是改后的） |
| `original_arguments` | 模型原本请求的参数——两相对照才知道人改了什么 |
| `outcome` | `approved` / `rejected` / `timeout` / `taken_over` |
| `at` | 什么时候——排查"这事怎么批出去的"全靠它 |

台账不是日志。日志可以丢，台账不行——它是事后追责和复盘的唯一凭据。

### 8.3 上线前的检查单

- [ ] 审批触发点挂在**动作风险**上，不在工具名上
- [ ] 审批落在**执行层**，模型绕不过
- [ ] 只读操作**不**触发审批（否则第一轮就会把人烦死）
- [ ] 同质操作**合批**审批，异质操作拆开
- [ ] 超时策略显式配置，且**默认是拒绝**
- [ ] 拒绝回填里写了"接下来可以怎么办"
- [ ] 运行时能识别"同一个操作的重试"，不会无限重问
- [ ] 改参数后放行时，执行用的是**改后的**参数
- [ ] 接管之后 Agent **停止**自动执行
- [ ] 恢复时**不重做**已完成的动作；副作用本身是幂等的
- [ ] 审批台账记全了：谁、批了什么、什么时候、参数改没改

## 一句话结论

> **审批触发看动作风险，超时默认拒绝，同质操作合批；接管要交得干净，恢复要接着跑而不是重跑。**
> 审批最常见的失效不是被攻击，是把人点烦了——先设计"人不点头会发生什么"，再设计按钮。
