# 01 · 什么是 Agent：定义、边界与最小内核

> **这篇要回答**：什么是 Agent？它和"调用一次大模型"、"写个 if-else"、"用框架搭个工作流"到底差在哪？一个东西要满足哪些条件才配叫 Agent？我什么时候**不该**用 Agent？

---

## 1. 一句话定义

> **Agent = 一个能自主决定"下一步做什么"的循环。**

拆开看，这句话里有四个缺一不可的部件：

| 部件 | 是什么 | 少了会怎样 |
| --- | --- | --- |
| **模型** | 提供决策能力的引擎 | 没有它就没有"决定"这件事 |
| **工具** | 感知世界与改变世界的接口 | 只能说话，不能做事，退化成聊天机器人 |
| **循环** | 让模型能基于新信息再决定一次 | 只能一轮，没有"行动—观察—再行动" |
| **自主性** | 下一步由模型选，不是人写死的 | 退化成普通工作流（Workflow） |

**第四点是区分 Agent 和 Workflow 的关键**，也是最容易被宣传话术糊弄过去的一点。

---

## 2. 一张图看清四层

```
┌──────────────────────────────────────────────────────┐
│  决策层   模型输出：调哪个工具 / 调什么参数 / 直接回答  │
├──────────────────────────────────────────────────────┤
│  循环层   while 没结束: 决策 → 执行 → 把结果喂回去      │
├──────────────────────────────────────────────────────┤
│  工具层   读文件、查数据库、调 API、跑命令              │
├──────────────────────────────────────────────────────┤
│  状态层   消息历史 + 工具结果 + 长期记忆               │
└──────────────────────────────────────────────────────┘
```

读法：**上层可以换，下层不能少。**

- 换掉决策层 → 换成推理模型、小模型、本地模型，Agent 照旧成立；
- 换掉循环层 → 换成 LangGraph 的状态图、Deep Agents 的 harness，Agent 照旧成立；
- 抽掉工具层 → 那不是 Agent，是聊天机器人；
- 抽掉状态层 → 单轮函数，连"循环"都谈不上。

---

## 3. Agent 和"看起来很像"的东西差在哪

### 3.1 和一次性模型调用的差别

```python
# 不是 Agent：一次调用，一次输出，没有反馈
answer = llm.invoke("帮我查一下 A 项目的营收")

# 是 Agent：模型看到结果后还能再决定一次
while not done:
    action = model.decide(context)      # 选工具
    result = tools.execute(action)      # 执行
    context.append(result)              # 喂回去
    done = model.is_done(context)       # 再决定
```

关键差别不是"代码行数多"，而是**中间结果会影响后续决策**。

### 3.2 和固定工作流的差别

工作流里，下一步走哪条路由是**人写死的业务规则**：

```python
if 意图 == "查询":
    return 查询分支(payload)
elif 意图 == "退款":
    return 退款分支(payload)
```

Agent 里，下一步走哪条路由是**模型根据上下文选的**。

这不是"更高级"，是**代价不同**：

| | 工作流 | Agent |
| --- | --- | --- |
| 可预测性 | 高，路径确定 | 低，路径由模型决定 |
| 可调试性 | 容易，就是一段代码 | 难，要回放轨迹才能知道它为什么这么走 |
| 成本 | 可预测 | 不一定——可能绕 5 圈才收敛 |
| 适合 | 步骤已知且稳定 | 步骤事先不知道，或路径依赖语义判断 |

> **一条纪律**：能用工作流解决的，不要上 Agent。
> Agent 的不确定性是要**付费**的——付费买的是"处理事先不知道的步骤"的能力。
> 如果你事先就知道步骤，那这笔钱白花。

### 3.3 和"框架搭出来的东西"的差别

`create_agent(tools=[...])` 出来的确实是一个 Agent。区别只在于：

- 框架替你写了循环层；
- 你仍然要负责**工具层的设计**和**状态层的策略**。

所以"用了框架"和"会做 Agent"是两件事。会用 `create_agent` 是 10 分钟的事；
知道**什么时候不该用**、**工具该怎么切**、**上下文怎么省**是几个月的功夫。

这正是这套教程要覆盖的部分。

## 4. Agent 的能力梯度

不是所有"Agent"都一样强。按自主程度从低到高：

| 级别 | 形态 | 谁决定下一步 | 典型场景 |
| --- | --- | --- | --- |
| L0 | 单次调用 | 人 | 翻译、分类、改写 |
| L1 | 固定流水线 | 人（预先写死） | 固定格式的数据处理 |
| L2 | 单 Agent + 工具 | 模型 | 客服问答 + 查询工具 |
| L3 | 多 Agent 协作 | 模型 + 编排器 | 需要不同视角交叉验证的任务 |
| L4 | 有状态的长任务 Agent | 模型 + 持久化状态 | 跑几十分钟的代码改造、深度研究 |

**大多数生产需求落在 L2**。L3 以上的复杂度要非常小心——多 Agent 系统的调试成本是指数级的，
每加一个 Agent，轨迹组合数就翻一倍。

> **常见的过度设计**：一个 L2 需求被做成了 L4。
> 上 L3 之前先问一句：能不能用"一个 Agent + 更多工具"解决？

---

## 5. 什么该用 Agent，什么不该

决策按顺序判断，命中即停：

| 你的处境 | 该用什么 | 为什么 |
| --- | --- | --- |
| 步骤完全已知，格式固定 | 普通函数 / 流水线 | 上 Agent 只会增加不确定性和成本 |
| 一次调用就能答完 | 直接调模型 | 套 Agent 是纯浪费 |
| 步骤已知但**偶尔**有变体 | 工作流 + 少量模型调用 | 大部分路径不用模型参与 |
| 需要"看情况选工具" | Agent（L2） | 这就是 Agent 的主场 |
| 任务很长、要跨几十分钟 | 有状态 Agent（L4）+ 持久化 | 需要断点续跑 |
| 需要多方独立验证 | 多 Agent（L3） | 单一视角容易自洽地错 |

### 三个必须警惕的信号

**信号一：为了"显得智能"而引入 Agent。**
如果你的流程可以画成一张没有分支的流程图，那它不该是 Agent。

**信号二：Agent 的失败不可观测。**
如果你无法回答"它上次为什么调了这个工具"，就不要上生产。
轨迹看不见的系统，出问题只能靠猜。

**信号三：任务本身要求确定性，但你在用 Agent 做。**
"这个字段必须严格等于数据库里的值"——这种事不要交给模型判断。
模型的自由度要花在**需要语义判断**的地方。

## 6. 最小内核：整套教程要造的东西

从第 2 章开始，我们会从零手写一个 Agent 运行时。它的全部结构就是：

```python
def run(user_input):
    messages = [system_prompt, user_input]

    for _ in range(MAX_ITERATIONS):
        reply = model.complete(messages, tools=TOOLS)
        messages.append(reply)

        if not reply.tool_calls:          # 模型说完了
            return reply.content

        for call in reply.tool_calls:     # 模型要工具
            result = run_tool(call)       # 执行（错误也回填给模型）
            messages.append(tool_result(result, call.id))

    return "达到最大轮次，没能给出答案"
```

**这 12 行就是 Agent 的全部。** 后面的 15 章做的所有事，都是在回答同一类问题：

> 这 12 行里的每一环，在真实生产里会怎么崩？我怎么防它崩？

- 模型说要调一个不存在的工具 → 第 3 章（工具设计）
- 模型传错参数 → 第 3 章
- 工具返回一百万字 → 第 5 章（上下文工程）
- 模型聊了 20 轮还没完 → 第 5、10 章
- 工具是只读的还是会改数据 → 第 13 章（安全）
- 改数据之前要不要人点头 → 第 14 章（人在环路）
- 一次任务烧多少钱 → 第 15 章（成本）
- 出问题怎么查 → 第 11 章（可观测）、第 12 章（评测）

## 7. 术语澄清

这几个词在中文语境里常被混用，动手前先对齐：

| 术语 | 本教程的定义 | 常见误解 |
| --- | --- | --- |
| **Agent** | 自主决定下一步的循环 | 以为"接了工具的 LLM"就是 Agent |
| **Tool（工具）** | 模型可调用的外部能力 | 以为工具必须是 HTTP 接口 |
| **Harness（脚手架）** | 替 Agent 预置能力的运行时 | 以为框架 = Agent |
| **Workflow（工作流）** | 步骤由人写死的编排 | 以为"用了图"就是工作流 |
| **上下文（Context）** | 本轮喂给模型的全部信息 | 以为只是"对话历史" |
| **记忆（Memory）** | 跨轮次持久化并可检索的信息 | 以为等于"保存聊天记录" |
| **Trajectory（轨迹）** | 一次运行的完整步骤序列 | 以为等于"最终答案" |

第 6 章会专门讲"上下文 ≠ 对话历史"，第 11 章讲"轨迹 ≠ 答案"。

---

## 8. 动手前检查一下

开始写代码前，先用这四条问自己：

1. **这个任务的步骤我真的不知道吗？** 知道就别用 Agent。
2. **Agent 出错时，我能看出来它错在哪一步吗？** 不能就先补可观测性。
3. **它的工具会改变外部世界吗？** 会就要考虑审批和权限。
4. **单次任务的成本上限是多少？** 说不出数字就别上生产。

四条都能答上来，才值得动手。

---

## 一句话结论

> **Agent 的全部结构只有 12 行；生产的难度全在这 12 行的每一环会怎么崩。**
> 先确认"这件事真的需要自主决策"，再动手——不该用 Agent 的地方用了 Agent，
> 后面 15 章的所有工作都会变成你自找的麻烦。
