# 17 · 框架地图：从手写运行时到 LangGraph 与 Deep Agents

> **这篇要回答**：前面 16 章手写的每一环，LangGraph / LangChain / Deep Agents 分别替我做了什么？我又为此付出了什么？什么时候**不该**上框架？

---

## 1. 先说结论

> **框架不是"更高级的写法"，是"别人替你做决定"。**
> 你手写运行时时做的每一个决定（消息怎么存、循环怎么停、错误怎么回填、状态怎么归约），
> 框架都替你做了默认选择。这些默认值往往是对的——但**它们是对谁的场景对的**，
> 取决于框架作者见得多不多，而不是取决于你的场景。

所以本章不讲"框架好不好"，只讲三件事：

1. **映射表**：我手写的每一环对应框架的哪个概念；
2. **账本**：框架替你省了什么，你又多了什么；
3. **判据**：什么规模的任务值得上框架。

---

## 2. 完整映射表

左边是 `Demos/examples/agent_lab/` 里手写的东西，右边是框架里的对应物。

| 我手写的 | 在框架里是 | 谁替你做了决定 |
| --- | --- | --- |
| `Message` 列表 | `MessagesState` 的 `messages` 通道 | 消息的追加与更新语义（`add_messages` 归约器） |
| `Agent.run` 的 while 循环 | `StateGraph` 的 `model` / `tools` 两个节点 + 条件边 | 循环结构本身、终止条件 |
| `AgentConfig.max_iterations` | `recursion_limit` | 默认值与超限行为 |
| `Agent._run_tool` | `ToolNode` | 工具分发、错误默认行为 |
| 三类失败的错误措辞 | `handle_tool_errors`（True / False / 自定义函数） | 错误的默认翻译方式 |
| `AgentResult.steps` | `stream_mode="updates"` 的事件流 | 事件形状与投影方式 |
| 上下文预算与压缩 | 中间件（如摘要中间件） | 压缩时机与触发阈值 |
| 工具 schema 生成 | `@tool` / `StructuredTool` | schema 从哪来、参数说明放哪 |
| `ApprovalGate`（第 14 章） | `interrupt()` + `Command(resume=...)` | 中断点、检查点恢复 |
| `MemoryStore`（第 6 章） | `Store` / 外部数据库 | 持久化与检索 |
| `TraceRecorder`（第 11 章） | LangSmith tracing | 采样、脱敏、字段定义 |
| 黄金集与回归（第 12 章） | LangSmith dataset + evaluator | 评测集与打分方式 |
| **没有做** | `Checkpointer` | 断点续跑、状态快照、时间旅行 |
| **没有做** | 子图 / handoff | 多 Agent 编排 |
| **没有做** | `Studio` / 本地服务器 | 可视化调试与部署形态 |

**这张表最重要的信息是最后三行。** 我手写了 16 章，但框架额外给我的三样东西
——持久化、中断恢复、可视化调试——**恰好是我手写运行时里最费劲的部分**。

> 第 7 章说"持久化是一等公民"时，指的就是 `Checkpointer` 那一行。
> 手写它不难，难的是想清楚"检查点应该落在哪个边界上"。

## 3. 账本：框架替你省了什么

### 3.1 省掉的三件大事

**① 持久化与恢复。**
手写 `Checkpointer` 要处理：状态快照存在哪、并发写怎么办、
进程重启后怎么找到对应的线程、清理策略是什么。
框架已经替你把这些做完了——而且做过很多次。

**② 中断与人在环路。**
第 14 章的审批流，手写要处理"在哪暂停、暂停状态存哪、恢复时怎么知道要恢复什么"。
框架的 `interrupt()` + `Command(resume=...)` 是一等公民，配合检查点就能断点续跑。

**③ 多 Agent 编排的拓扑。**
第 9 章的五种拓扑，手写要自己管状态传递、上下文隔离、结果聚合。
框架有现成的子图、handoff、supervisor 模式。

### 3.2 但你也要多付三样

**① 状态 schema 的设计负担。**
框架的状态是一张 `TypedDict`，每个键都要决定归约器语义：

```python
class State(TypedDict):
    messages: Annotated[list, add_messages]   # 追加
    result: str                                # 覆盖
    steps: Annotated[list, operator.add]       # 累加
```

手写运行时里，状态就是一个 dict，`state["result"] = x` 就完事了。
上了框架，你必须想清楚**每个键是覆盖还是累加**——这个决定在框架里是显式的、必须做的。

**② 控制流从"顺序代码"变成"图"。**
```python
# 手写
while True:
    reply = model(...)
    if not reply.tool_calls: break

# 框架
builder.add_conditional_edges("model", route, {"tools": "tools", END: END})
builder.add_edge("tools", "model")
```

图更可视化、更容易加分支，但**调试时你面对的是一张图，不是一段代码**。
从"顺着读"变成"顺着跳"。

**③ 依赖与版本。**
框架发版很勤（LangGraph 一年三十多个稳定版）。你从此要管依赖、读 changelog、
在升级时验证行为没变。手写运行时只有标准库加 `openai`，这个问题不存在。

## 4. 什么时候**不该**上框架

| 你的处境 | 建议 |
| --- | --- |
| 刚学 Agent，还没搞清楚循环是怎么回事 | **别上**。手写一遍，你才知道框架在做什么 |
| 任务只有一次模型调用 + 一次工具调用 | **别上**。直接写 Python |
| 流程固定，不需要中断、不需要断点续跑 | **别上**。图的状态设计成本大于收益 |
| 需要审批 + 断点续跑 + 长任务 | **上**。这正是框架的主场 |
| 需要多 Agent 编排 | **上**。拓扑管理比自己写省太多事 |
| 需要可视化调试、团队协作 | **上**。Studio 的价值无法手写替代 |
| 要交付给外部团队 | **上**。统一写法比个人风格重要 |

### 一条判据

> **你能不能用一句话说清"框架替我干了哪件事"？**
>
> 说得出"我要断点续跑，它有检查点" → 上。
> 说不出、只觉得"大家都用" → 先手写一章。

## 5. 三层生态怎么选

沿用 `AI/LangGraph/01-生态全景与选型.md` 的三层划分（框架 / 运行时 / harness），
但从**"我手写了什么"**的角度重新看一遍：

| 层 | 谁 | 对应我手写的哪部分 | 什么时候上 |
| --- | --- | --- | --- |
| **框架** LangChain | `create_agent` + 中间件 | 我手写的循环，但**不给你看** | 单一职责、工具集固定、想快速起步 |
| **运行时** LangGraph | `StateGraph` + 检查点 | 我的循环 + **持久化 + 中断 + 流式** | 需要控制流、要审批、要续跑 |
| **harness** Deep Agents | 规划、文件系统、子智能体 | 我的循环 + **规划 + 委派** | 长程任务、任务长到需要管理文件 |
| **横切** LangSmith | 追踪、评测、部署 | 我的 `TraceRecorder` + 黄金集 | 任何一层都建议开 |

**关键认知**：`create_agent` 出来的确实是一张编译后的 `StateGraph`。
所以"我该学 LangChain 还是 LangGraph"是伪命题——**它们是同一张图的不同封装深度**。

## 6. 迁移路径：上框架时哪些东西能带走

如果你决定把第 2–16 章手写的运行时换成框架，下面这些**可以原样带走**：

| 手写的东西 | 迁移后放哪 |
| --- | --- |
| 工具函数与 schema | **完全不变**，还是 `@tool` 装饰的函数 |
| 系统提示 | 不变，还是那条 system message |
| 错误分类与措辞 | 不变，包装成 `handle_tool_errors` 的自定义函数 |
| 风险分级与审批 | 不变，但挂到 `interrupt()` 上 |
| 黄金集与打分逻辑 | 不变，接到 LangSmith dataset 上 |
| 上下文预算表 | 不变，但压缩动作交给中间件 |
| 记忆的写入/检索/遗忘 | 不变，后端换成 `Store` |

**必须重测的**（这些是框架换掉的行为）：

1. **工具调用的消息形状**——框架有没有改动 assistant/tool 消息的字段？
2. **错误回填的措辞**——框架默认的翻译方式是不是你想要的那种？
3. **循环终止条件**——`recursion_limit` 和你的 `max_iterations` 语义一致吗？
4. **流式事件形状**——你消费事件的代码要重写。
5. **中断恢复**——恢复时状态是不是你预期的那个状态？

> **一条纪律**：迁移时**评测集不许动**。
> 评测集是判断迁移有没有搞坏东西的唯一依据；
> 迁移中改评测集，等于把尺子换成新的然后宣布自己进步了。

## 7. 上框架前要补的三个概念

按这个顺序补，每一项都是上框架后立刻会用到的：

1. **状态与归约器**——对应 `AI/LangGraph/03-状态定义与归约器.md`。
   想清楚每个状态键是覆盖还是累加。
2. **持久化与检查点**——对应 `AI/LangGraph/07-持久化与时间旅行.md`。
   决定检查点落在哪个边界上（每个节点？每个 super-step？）。
3. **中断与恢复**——对应 `AI/LangGraph/08-人在环路：中断、审批与恢复.md`。
   决定审批挂在哪个节点上。

这三章正好是你手写运行时里**没有做**的三件事（映射表最后三行）。
先补上，再上框架，顺序就顺了。

## 8. 迁移清单

准备上框架时，逐条过：

- [ ] 工具函数与 schema **零改动**就能用
- [ ] 系统提示**零改动**
- [ ] 错误分类逻辑包装成自定义 handler，行为不变
- [ ] 审批点映射到 `interrupt()`，暂停/恢复路径手工验证过
- [ ] 黄金集**一个字都没改**，在新框架上跑一遍
- [ ] 新框架得分 ≥ 旧运行时得分
- [ ] 流式事件的消费代码重写并验证
- [ ] `recursion_limit` 与原来的 `max_iterations` 语义对齐
- [ ] 依赖版本已 pin 死，升级流程写下来了
- [ ] **能用一句话说清"框架替我干了哪件事"**

最后一条是重点。如果还是"大家都用"，那说明你还没想清楚要什么。

---

## 一句话结论

> **框架替你做决定，框架也替你承担你没想清楚的后果。**
> 手写 16 章换来的是"我知道每一环为什么这样"；
> 有了这个，框架对你来说就是**可替换的实现**，而不是黑箱。
> 而上框架最大的收益，恰恰是你手写时最费劲的那三件事：
> 持久化、中断恢复、可视化调试。
