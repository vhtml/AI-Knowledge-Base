# 附录 C · 常见故障排查

按**症状**组织，而不是按原因——出故障的时候你手里只有症状。
每一节的结构是：症状 → 最可能的原因（按概率排序）→ 怎么确认 → 怎么修。

---

## 一、模型不调工具 / 调用了错的工具

### 症状
模型直接回答了，没有发起任何工具调用；或者调了一个完全不相关的工具。

### 可能原因（按概率）

1. **工具描述没写清楚**——模型看到的只有 `name` / `description` / schema。
   如果 description 是"订单相关工具"这种废话，它没有理由选它。
2. **工具太多**——20 个工具时选择准确率明显下降。
3. **系统提示把流程写死了**，或者反过来，**系统提示没说该用工具**。
4. **`tool_choice` 的默认值不是 `auto`**——某些封装默认是 `none`。
5. **任务本来就不需要工具**，模型直接回答是对的。

### 怎么确认
- 把工具 schema 打出来，**以模型视角读一遍**："我凭什么选它？"
- 看 trace 里模型收到的 messages，确认工具确实传过去了。
- 临时把工具数量砍到 2 个，看准确率是否上升。

### 怎么修
见第 3 章。核心是：**description 写"什么时候用我"，参数说明落到字段级**。

## 二、模型传错参数

### 症状
工具抛参数错误，或者传了个语义上不对的值（查 2024 年的数据却传了 2023）。

### 可能原因

1. **参数说明缺失**——字段级 description 没写，模型只能靠字段名猜。
2. **参数名不表意**——`v`、`dt`、`t2` 这类命名。
3. **取值域没写**——`status: "active"` 是枚举还是布尔？没说清。
4. **时间参数用绝对时间**——模型不知道"今天"是哪天。

### 怎么确认
把 schema 的 `properties` 打出来逐个字段读——有没有一个字段让你猜？

### 怎么修
- 枚举参数写清全部合法值。
- 时间参数**由代码注入当前时间**，不要让模型算。
- 语义模糊的参数拆开或改��。

## 三、Agent 反复绕圈 / 不收敛

### 症状
同一轮里反复调同一个工具，或者在两个工具之间来回横跳，直到撞上限。

### 可能原因

1. **工具报错被原样回填**——模型看见同样的错误，做同样的事。
2. **错误信息里没有"换条路"的暗示**。
3. **目标不可达**，但模型不知道——它没有权限、工具不存在、能力不足。
4. **没有轮次上限**（那就不是"绕圈"，是"烧钱"）。
5. **上下文太长**，模型已经看不到自己之前做过什么。

### 怎么确认
看 trace 的工具调用序列：**重复的 `(工具名, 参数)` 模式**就是信号。

### 怎么修
- 错误措辞分三类改写（见第 10 章）：工具不存在 / 参数非法 / 业务故障。
- 加重复调用检测（见第 2 章）。
- 轮次上限 + 超限时返回**最有价值的那次输出**，而不是空字符串。
- 上下文压缩（见第 5 章）。

## 四、模型回答了但内容不对（自信地错）

### 症状
格式完全正确，内容却是编的。数字、引用、API 名称全是错的。

### 可能原因

1. **模型在编**——这是最常见的原因，不是 bug。
2. **上下文里没有它需要的信息**，但它被要求回答。
3. **提示词暗示了它应该知道**（"根据我们的数据…"）。
4. **工具返回值它没真的读**（被压缩掉了、被截断在看不见的位置）。

### 怎么确认
- 看模型这次**实际收到**的 messages（trace 里是有的），逐字找答案来源。
- 答案来源不在上下文里 → 它就是编的。

### 怎么修
- 让它**引用来源**；无法引用时明说"我不知道"。
- 查全问题就在第 8 章（反思）与第 12 章（评测）。

## 五、JSON 解析失败

### 症状
`json.loads` 抛异常，或者解析出来是字符串而不是对象。

### 可能原因

1. **模型包了 markdown 围栏**——`` ```json ... ``` ``。
2. **模型加了前后废话**——"好的，结果如下：{...}"。
3. **模型输出被截断**（`finish_reason == "length"`）——JSON 是半截的。
4. **schema 太复杂**，模型没能力一次生成对。

### 怎么确认
**先看 `finish_reason`**。是 `length` 的话，问题不是 JSON，是输出上限。

### 怎么修
见 `AI/LLM/03-结构化输出.md`：
- 用 `response_format` 而不是靠提示词请求；
- 解析端容错（抠围栏、抠花括号）；
- 校验失败**重试**，把校验错误回给模型。

## 六、工具返回内容太长，挤爆上下文

### 症状
对话进行到一半突然变慢/变贵，或者模型开始"忘记"前面的内容。

### 可能原因
工具返回了整页 HTML、整个日志文件、一次查询的几千行结果。

### 怎么确认
看 trace 里每条 tool 消息的字符数。

### 怎么修
- 截断 + **显式标记**（模型要知道被截断了）。
- 工具侧做**分页/摘要**，只返回模型真正需要的字段。
- 检索类工具只返回 top-k，别全给。

---

## 七、成本突然翻倍

### 症状
账单突然是原来的 3–5 倍。

### 可能原因（按概率）

1. **轮次变多**——某次改动让 Agent 多绕了几圈。
2. **历史没裁剪**——每轮都带上全部历史，输入 token 线性增长。
3. **工具返回值变大**——每次都返回几万字符。
4. **换了更贵的模型**。
5. **重试风暴**——429 之后退避策略写错，疯狂重试。

### 怎么确认
看 trace 的 `usage` 分布：**按轮次画出输入 token 曲线**。是斜线 → 历史没裁剪；
是台阶 → 某轮工具返回变大了。

### 怎么修
见第 15 章。核心是：**先砍输入，再砍输出**——输入通常是输出的十倍以上。

## 八、多轮对话记不住前面说过的事

### 症状
第 3 轮开始，模型忘了第 1 轮的用户偏好。

### 可能原因

1. **历史被截断掉了**（裁剪策略太激进）。
2. **压缩把关键约束压没了**。
3. **关键信息在上下文中段**，权重下降。
4. **每次请求没有带上系统提示**（拼接历史时漏了）。

### 怎么确认
打印**模型实际收到的** messages，看关键信息在不在。

### 怎么修
- 关键事实**前置到系统提示**，或每轮复述。
- 压缩时保留"关键约束"白名单。
- 长期信息放进**记忆**而不是上下文（第 6 章）。

## 九、审批没拦住危险操作

### 症状
Agent 改了不该改的东西。

### 可能原因

1. **审批靠提示词约束**——"请勿未经批准删除文件"。模型不保证遵守。
2. **审批按工具名触发**，而危险操作换了个工具名就绕过了。
3. **审批逻辑在模型层而不是执行层**——模型可以直接调底层 API。

### 怎么确认
问自己：**如果模型完全不受控，这个操作还能发生吗？**
能 → 审批是假的。

### 怎么修
审批必须放在**工具执行层**，按**动作语义**分级（第 13、14 章）。

---

## 十、提示注入

### 症状
Agent 忽然开始执行和用户请求无关的操作——发邮件、删文件、访问某个网址。

### 可能原因
工具返回的内容里藏了指令（网页、文档、邮件正文里的"忽略之前的指令……"），
模型把它当成了指令。

### 怎么确认
找到那条可疑的工具返回值，看它的内容里有没有祈使句。

### 怎么修
纵深防御（第 13 章）：
- 工具结果**标记为不可信数据**（结构上与指令分离）；
- 高危操作**在执行层**要审批；
- 最小权限 + 沙箱；
- 出站数据过滤。

---

## 十一、多 Agent 系统结果不稳定

### 症状
同样输入，有时对有时错；换个跑法结果就变。

### 可能原因

1. **投票没有多数**（三个 Agent 各说各的）。
2. **并行 Agent 看到的信息不一致**，导致结论不可比。
3. **聚合器本身是模型**——它也会挑一个看起来最顺眼的，而不是最对的。
4. **上下文串了**——一个 Agent 的输出污染了另一个。

### 怎么确认
看每个子 Agent 的**输入**是否一致，以及聚合的判据是什么。

### 怎么修
- 统一输入，明确聚合判据（不要"让主管选一个"）。
- 给聚合器**结构化的候选**和**可执行的判据**，而不是自由文本。
- 先问一句：**这个任务真的需要多 Agent 吗？**（第 9 章）

## 十二、排查总流程

遇到任何故障，按这个顺序走，不要跳步：

```
1. 拿到 trace —— 没有 trace 就先补（第 11 章）
      ↓
2. 看 finish_reason —— 是 length 吗？→ 先查输入长度
      ↓
3. 看模型实际收到的 messages —— 信息在里面吗？
      ↓
4. 看工具调用序列 —— 有重复模式吗？→ 循环问题
      ↓
5. 看错误回填的内容 —— 模型看得懂吗？→ 错误措辞问题
      ↓
6. 对着黄金集跑一遍 —— 是普遍问题还是个例？
      ↓
7. 定位到具体哪一环 → 回到对应章节
```

**七步里最容易被跳过的是第 1 步和第 3 步。**
没有 trace 你只能猜；不看模型实际收到的内容，你会一直在怀疑模型，
而问题往往在你发给它的东西上。
