# 09 · 多智能体编排模式

> **这篇要回答**：多 Agent 有哪几种拓扑？什么时候值得把一件事拆给多个 Agent？拆错了会怎样？

---

## 1. 多 Agent 解决的是分工问题，不是"变聪明"问题

第 1 章说过一句重话：**能用工作流解决的，不要上 Agent**。这一章要把它往前推一步：

> 能用**一个** Agent 解决的，不要上**多个** Agent。

多 Agent 唯一的真实收益是**分工**：不同的工具集、不同的上下文、不同的评价标准，
硬塞进一个 Agent 就会互相干扰——工具列表太长会选错（第三章），
上下文太杂会看漏重点（第五章），评价标准混在一起会两头都不达标（第七章）。

反过来，多 Agent 的代价是硬的：

- **每个 Agent 都是一次独立的模型调用**——不是"共享一次推理"，是 N 次；
- **每个 Agent 都有一份自己的上下文**——它看不见别人的对话历史；
- **多出来的每一次调用都要有人来路由、来搬运、来收口**。

所以正确的顺序永远是：**先证明"这个任务单 Agent 干不了"，再挑拓扑**。
默认答案是"不拆"。

---

## 2. 五种拓扑各管一段什么活

| 拓扑 | 谁决定下一步 | 信息怎么流 | 适合什么 | 主要代价 |
| --- | --- | --- | --- | --- |
| **Router** | 分类器（判一次） | 一进一出，分完就撒手 | 任务类型可以枚举：查订单 / 办退款 | 分类器选错，后面全错 |
| **Sequential** | 人写死的顺序 | A 的产出直接进 B 的输入 | 步骤有明确先后依赖：抽取 → 成稿 | 延迟叠加；产出要显式搬运 |
| **Parallel + 聚合** | 编排器 | 分叉出去，再合并成一个 | 同一件事要多个独立视角：投票、取优、合并 | token 成倍；聚合规则要另外设计 |
| **Supervisor** | 主管 Agent | 主管派活 → 收结果 → 收口 | 步骤数事先不知道，但需要一个全局视角 | 主管多轮调用；上下文最重 |
| **Handoff** | Agent 之间互相移交 | 控制权转移 | 对话式转接：客服 → 技术支持 | 容易转圈；责任边界模糊 |

五种拓扑的差别，归根结底只有两件事：**控制权在谁手里**，以及**信息怎么从上一个角色到下一个角色**。

Router 和 Supervisor 最容易混。区别就一处：**Router 判完一次就不管了**，
选中谁就把任务丢给谁；Supervisor 派完活还要**再被叫醒一次收口**——
只有主管看得到所有专家的产出，也只有主管能写出最终答复。多出的那次调用，就是全局视角的价格。

## 3. 什么时候值得拆：三条判据必须同时成立

判断该不该拆，用三条判据。它们不是"或"，是"与"——**少一条就别拆**。

| 判据 | 问什么 | 怎么判断 |
| --- | --- | --- |
| **工具集不同** | 两个角色要动的资源是不是同一批？ | 列出各自的工具清单，比对 |
| **需要的上下文不同** | 它们要读的数据域是不是分开的？ | 看工具读写的是不是互不相干的域 |
| **评价标准不同** | 怎么算"做得好"？ | 写出各自的验收标准，比对 |

这条判据可以直接写成代码（实验里叫 `should_split`）：

```python
def should_split(tools_a, tools_b, criteria_a, criteria_b) -> bool:
    different_tools = set(tools_a) != set(tools_b)
    different_context = domain_of(tools_a) != domain_of(tools_b)
    different_criteria = set(criteria_a) != set(criteria_b)
    # 三条同时成立才值得拆——少一条，收益抵不上协调成本
    return different_tools and different_context and different_criteria
```

"上下文不同"这一条最容易被糊弄过去。很多时候两个角色的工具**看起来不同**，
但读写的是同一个数据域——查订单 vs 查物流都在订单域里。这种情况下拆开毫无意义：
两个 Agent 还是要读同一份数据，标准也多半一样，
只是把一次调用变成两次，还多了一个协调者。

> **一条纪律**：拆分的默认值是"不拆"。
> 多 Agent 的收益是真的，但协调成本涨得比大多数人预期的快。

## 4. 拆错了会怎样：协调成本与轨迹爆炸

拆错的代价不是"慢一点"，是**问题变得不可定位**。三件事同时发生：

**一、成本翻倍。** 每个 Agent 都是一次独立的模型调用加一份独立的上下文。
拆成 3 个，账单就是 3 倍，而且这 3 次调用**互相看不见**——
第 8 章的反思循环里，一次自我批评可能只花一次调用；
换成 3 个 Agent 各批评一次，花三次，收益却未必有三倍。

**二、轨迹从线变成树。** 单 Agent 的轨迹是一条线：第 1 步错在第 3 步被看到。
多 Agent 的轨迹是一棵树：主管可能派错人，被派的人可能带着错误的前提往下做，
收口时又可能把两个错误结论合并成一个看起来很自信的答案。
**"哪一步走错了"这个问题，在树上的难度是在线上的好几倍。**

**三、失败可能来自编排，而不是任何一个 Agent。** 这是多 Agent 最阴险的失败面：
每个 Agent 单独看都"做对了"，错的是**谁被派去做了什么**，
或者**A 的产出有没有真的送到 B 那里**。
单 Agent 系统里没有这类失败——它的每一步都是同一个模型在同一个上下文里做的。

拆错了的三个典型症状：**总产出不如单 Agent**、**同一个错误在多处重复出现**、
**没人能说清为什么这次走了这条分支**。三个症状里出现任何一个，都该退回单 Agent 重来。

---

## 5. 共享状态还是隔离上下文

拆开之后，下一个必答题是：**Agent 之间怎么传信息**。只有两种做法，各有各的账。

| | 共享状态 | 隔离上下文 |
| --- | --- | --- |
| 怎么传 | 都往同一个状态对象里写 | 每个 Agent 独立，最后由聚合器搬运 |
| 好处 | 不用显式搬运，谁都能看到最新结果 | 干净：谁也看不见别人的中间过程 |
| 坏处 | **互相污染**：下游会看见上游的中间过程 | **搬运有成本**：要明确决定搬哪些字段 |
| 适合 | 产出是并列的、要互相参考 | 角色边界硬、上下文敏感（法务、风控） |

关键认知：**共享状态不是"免费的共享"**。它省掉了搬运，但代价是
上游 Agent 写在状态里的**中间过程**会一并进入下游的上下文——
那些过程是给上游自己看的，不是给下游准备的。
实验里量出来，共享模式下一个 Agent 会"看见"另外两个的中间过程；
隔离模式虽然一个也不看见，但聚合器搬 3 份结果本身也要花钱。

所以：**搬运本身就是成本**。隔离不是"更正确"，只是把成本从"隐式污染"
换成了"显式搬运"——而显式的成本至少是可数的（第 15 章会把它算进账里）。

## 6. 成本与延迟：并行买到什么，付出什么

这是本章最反直觉的一段。**在多 Agent 里，延迟和成本是两个反方向的指标。**

| | 墙钟延迟 | 账单（token） |
| --- | --- | --- |
| **N 个 Agent 串行** | N 倍：一份做完再做下一份 | 较低：后一个只接上一个的产出 |
| **N 个 Agent 并行** | 接近 1 倍：同时做 | 较高：每个都从零读一遍同样的材料 |

并行把 N 份工作压进同一段时间，代价是**重复劳动**：
每个并行 Agent 都要自己读一遍那份大材料，串行时后面几个只需要读上一环的摘要。
实验里同样的材料，串行 1091 tokens / 0.16 秒，并行 3105 tokens / 0.055 秒——
**延迟降了 2.9 倍，token 涨了 2.8 倍**。

所以选拓扑时问的不是"哪个快"，而是：

- 这份材料**能不能压成摘要**？能压就用串行，不能压（比如每个角色都要看到全文）才用并行；
- 用户等的是**墙钟**还是**账单**？C 端交互选并行，后台批处理选串行；
- **允许多少分歧**？并行 + 投票的价值恰恰在于"允许不一致"——
  2/3 多数要保留反对票并标记成有分歧，没有多数时该升级仲裁或弃权，而不是硬凑一个答案。

## 7. 坑：多 Agent 的调试地狱

多 Agent 有四个反复出现的坑，每一个都有对应的工程手段。

**坑一：分类器静默失败。** Router 选错了专家，但因为"错误专家也能返回点什么"，
整条链路看起来是跑通了的。手段：把路由决策**记成结构化事件**（它是一次工具调用，
不是一段自然语言），并在评测集里单独统计路由准确率（第 12 章）。

**坑二：共享状态悄悄污染。** 上游 Agent 的中间过程进了下游的上下文，
下游的结论因此变了，而你根本不知道它变了。手段：把**结果**和**过程**分成两个字段，
只让下游看结果；实在要共享过程，就在共享时按角色过滤。

**坑三：多 Agent 的失败无法归因。** 出错了，你不知道是编排错了还是某个 Agent 错了。
手段：给每个 Agent 独立的 trace，并记下**父子关系**——
"谁把谁叫起来的"这条边一旦丢了，第 11 章的回放就无从谈起。

**坑四：为了"看起来高级"而拆。** 两个角色工具一样、域一样、标准一样，
拆完之后每个都变慢了、变贵了、还变难查了。手段：用第 3 节那三条判据，
并且把判定写成代码，让它能进 CI——"该不该拆"必须是**可回归**的决定，
不能靠每次讨论时重新吵一遍。

## 8. 和第 7、8 章的边界，以及后续章节

多 Agent 是**并行 / 分工**问题，第 7 章的规划和第 8 章的反思是**串行改进**问题。
它们的判据完全不同：

| | 第 7 章 规划 | 第 8 章 反思 | 本章 多 Agent |
| --- | --- | --- | --- |
| 解决什么 | 先做什么后做什么 | 发现错了怎么纠 | 谁来做、做几份、怎么合 |
| 结构 | 串行，一棵决策树 | 串行，一条改进闭环 | 并行或分叉，一棵调用树 |
| 成本 | 一次额外规划调用 | 每次反思一次调用 | 每个 Agent 一次调用 |

同一条流水线里三者可以叠：主管 Agent 内部用规划拆步骤（第 7 章），
产出用反思自检（第 8 章），整体是 Router 分派给主管（第 9 章）。
但**不要用多 Agent 去解决"顺序不对"的问题**——那是规划的活；
也**不要用规划去解决"需要不同视角"的问题**——那才是拆 Agent 的理由。

框架层面的对应实现见 [`AI/LangGraph/10-子图与多智能体编排.md`](../LangGraph/10-子图与多智能体编排.md)：
本章的五种拓扑在那里分别对应子图、handoff、router 等 LangGraph 能力。
再往后，第 11 章讲怎么把多 Agent 的**树状轨迹**记成可回放的 trace，
第 12 章讲怎么用黄金集评估路由准确率和最终结论，
第 15 章讲怎么给上面那张"延迟 vs 成本"的表算出真实账单。

---

## 一句话结论

> **多 Agent 是分工，不是变聪明：三条判据同时成立才拆，拆了就为协调成本买单——
> 并行买到延迟，付出的是重复读同一份材料的账单。**
