# 16 · 生产化：部署形态与上线检查单

> **这篇要回答**：demo 跑通之后，离上线还差什么？Agent 该部署成什么形态？灰度和回滚怎么做？上线前那张检查单，怎么从"记得看一眼"变成"不过就不许发"？

---

## 1. 前面 15 章补的是 Agent 内部，这一章补的是它外面那一层

前 15 章讲的全是"Agent 内部会不会崩"：循环会不会不收敛（第 2 章）、工具会不会被调错（第 3 章）、上下文会不会爆（第 5 章）、记忆会不会污染（第 6 章）、失败该怎么重试（第 10 章）、轨迹看不看得见（第 11 章）、质量有没有回归（第 12 章）、提示注入挡不挡得住（第 13 章）、人拦不拦得住（第 14 章）、一次任务烧多少钱（第 15 章）。

这些全对，但它们有个共同的隐含前提：**有一个进程正稳稳当当地跑着这个 Agent**。

生产事故里相当一部分不是 Agent 变笨了，而是这个前提塌了：

| 塌掉的方式 | 现象 |
| --- | --- |
| 进程重启 | 队列里的任务凭空消失，用户看到"提交成功但什么都没发生" |
| 并发打满 | 新请求排成长队，或者被上游 429 拖死 |
| 重复提交 | 同一个任务跑了两遍，写操作类的工具执行了两次 |
| 版本回滚 | 新版本有 bug，可回滚时数据库结构已经回不去了 |
| 检查单靠记性 | 上线前那晚漏了一条，第二天在生产上炸 |

这一章补的就是这层：**部署形态、状态持久化、并发与限流、幂等、灰度与回滚、配置与密钥、模型版本 pin、多租户隔离、上线门禁、运维指标**。

## 2. 部署形态怎么选：只看三个判据

判据只有三个，按顺序问：

1. **任务要跑多久？** 秒级、分钟级、还是小时级？
2. **中途需不需要反馈？** 用户要不要看到"正在查第 3 步"？
3. **用户能不能等？** 等 30 秒和等 10 分钟是两种产品。

| | 同步 API | 后台任务 + 队列 | 长驻流式（SSE / WebSocket） |
| --- | --- | --- | --- |
| 交互 | 请求—响应，一次往返 | 提交拿 task_id，之后轮询或订阅 | 保持连接，服务端持续推事件 |
| 适合时长 | 秒级（通常 <30s） | 分钟到小时级 | 秒级到分钟级 |
| 中途反馈 | 没有 | 只能给状态（运行中 / 第几步） | 有，可以逐 token、逐工具调用推送 |
| 超时压力 | 大：网关、客户端、代理三层都可能掐 | 小：HTTP 早就返回了 | 中：要处理断线重连 |
| 进程重启 | 无所谓，客户端会重试 | **致命**：任务全丢 | 要处理断线后的恢复 |
| 典型场景 | 分类、改写、查一次库 | 报表生成、批量处理、深度研究 | 对话式助手、需要"正在思考"的任务 |

**选择规则**：任务时长一旦超过用户愿意等的时长，就不能是同步 API——不是"优化同步 API"，而是换形态。

这里有个常见误解值得点名：

> **同步 API 的超时是上限，不是计划。** "超时了就把它调成 10 分钟"是错的——网关超时、客户端超时、负载均衡器空闲超时是三个独立的数字，改一个不改另外两个，结果是客户端断开、服务端还在烧钱。形态选错，后面全是补丁。

## 3. 状态必须活过进程重启：先有状态机，再谈存储

任务状态机（实验里那张表就是这个）：

| 状态 | 含义 | 允许的去向 |
| --- | --- | --- |
| `pending` | 已入队，没被领走 | `running`、`cancelled` |
| `running` | 正在执行 | `waiting_approval`、`succeeded`、`failed`、`cancelled` |
| `waiting_approval` | 卡在人工审批（第 14 章） | `running`、`cancelled` |
| `succeeded` | 成功结束 | 无（终态） |
| `failed` | 失败结束 | 无（终态） |
| `cancelled` | 被取消 | 无（终态） |

三条纪律：

- **终态没有出边。** `succeeded → running` 必须是硬错误，否则一次误操作就能让一个已经扣过款的任务重跑一遍。
- **非法转移要抛错，不要"容错地忽略"。** 非法转移要么是代码 bug，要么是并发写坏了状态，两种都得当场暴露。
- **`pending → succeeded` 不合法。** 中间必须真的跑过，否则"任务成功"这个状态就失去了意义。

状态存哪，按规模选：

| 方案 | 撑得住的规模 | 进程重启 | 适合 |
| --- | --- | --- | --- |
| 内存 | 单机、单副本 | 丢 | 本地开发 |
| 文件（JSON / SQLite） | 单机、几千任务 | 保留 | 单机部署、教程实验 |
| Postgres / Redis | 多副本、百万任务 | 保留 | 生产 |

**多副本部署的前提是状态在共享存储里。** 两个副本各持一份内存队列，用户提交到 A、轮询到 B，B 根本不知道有这个任务。这是"水平扩容"最常见的翻车点。

> `waiting_approval` 是第 14 章那套审批流的落点：审批天然有状态，
> 中断后必须能从暂停点接着跑，不能只是一个 HTTP 请求。

## 4. 并发与限流：两层闸门，排队还是拒绝

你有**两个**独立的闸门，性质完全不同：

- **上游模型给的额度**（429、并发上限）：不是你的错，也不是任务失败，该做的是退避后重排（第 10 章）；
- **你自己设的并发上限**：保护自己的内存、数据库连接和下游。

超限时选"排队"还是"拒绝"，要看**被拒的东西是什么**：

| 场景 | 该怎么做 | 为什么 |
| --- | --- | --- |
| 执行侧并发满了 | **排队**（任务留在 `pending` 里等） | 任务已经存在了，丢掉等于用户的活儿白干 |
| 提交侧队列深度满了 | **拒绝**（返回 429） | 再排下去内存会爆，拖垮的是整个服务 |
| 上游模型限流 | **退避重排** | 那是别人的额度，退让就行 |

关键区别：**执行侧不能丢任务，提交侧不能无限接单。** 两者被写成同一个"限流中间件"时，线上要么丢任务，要么 OOM。

还有第三件容易忘的事：**超限的响应必须明确**。是排队（给个预计等待）、是拒绝（给 429 和重试建议）、还是降级（换个更便宜的模型跑）——三选一，但必须让调用方知道。"默默卡住"是最糟的，调用方既不知道该重试也不知道该放弃。

## 5. 幂等：重复提交不会变成两个任务

用户点了两次提交、网络抖动重试、上游超时后客户端重投——这三种情况在生产上天天发生。

做法是**幂等键**：客户端生成一个唯一的请求 id，服务端拿它去重。

```python
def submit(self, payload, *, tenant_id, idempotency_key):
    existing = self.store.find_by_key(tenant_id, idempotency_key)
    if existing is not None:          # 重复提交：返回同一个任务
        return SubmitResult("duplicate", existing)
    ...                               # 新任务：入队
```

三条细节：

- **幂等键的作用域是租户**：同一个键在不同租户下是两个不同的任务。
- **幂等命中不是错误**，返回 200 和原任务，不要返回 4xx——客户端的重试逻辑会被吓退。
- **幂等键要在"产生副作用"之前落盘**。先干活再记键，中间崩了就白干一次。

> 幂等和第 10 章的重试是两回事：重试解决"这次失败了怎么办"，
> 幂等解决"这次会不会被做两遍"。两个都要有——重试没有幂等会重复扣款，
> 幂等没有重试会让一次偶发失败变成用户的失败。

## 6. 灰度与回滚：切流量容易，切回去难

**灰度**按三种维度切：

| 维度 | 怎么切 | 适合 |
| --- | --- | --- |
| 按比例 | 1% → 10% → 50% → 100% | 新版本整体能力有提升 |
| 按用户 | 白名单、指定账号 | 内部试用、重点客户先行 |
| 按场景 | 某类请求走新版本 | 新版本只对某类任务有改进 |

**按用户必须是粘的**：同一个用户两次请求落到不同版本，会话就被劈开了——上下文、记忆、任务状态全都对不上。所以分桶要用稳定的哈希（用户 id 的哈希），不能用进程内随机的 `hash()`。

**回滚**要能在**一分钟内**切回去，而且切回去的是**完全一致的旧版本**——同样的模型版本、同样的提示词、同样的工具集。

> **坑**：数据库迁移不可逆时，回滚代码救不了你。
> 假如新版本把 `orders.status` 从枚举改成了自由文本，回滚代码之后，
> 新版写入的那些自由文本旧代码根本解析不了——你会同时失去"新功能"和"旧功能"。
>
> 这类迁移只能"向前修"（写兼容代码 + 数据修复脚本），不能靠回滚。
> 所以规矩是：**回滚路径上的每一步迁移，都必须让旧代码仍然能读懂数据**。
> 做不到的迁移（删列、改类型、拆表），就不能和代码回滚绑在同一个发布里。

所以"一键回滚"这句话，严格说是**"一键回滚代码，且数据库仍在旧版的可读范围内"**。
发版前必须演练：回滚之后，旧版本面对新版本写过的数据还能不能正常工作。

## 7. 配置、密钥与模型版本 pin

三条纪律：

- **配置全部走环境变量**，代码里不出现任何环境相关的值。不同环境（dev / staging / prod）用不同配置，同一份代码。
- **密钥不进代码库**，进环境变量或密钥管理服务。而且**密钥缺失要显式暴露**：没有兜底默认值，"忘了配"和"配错了"会静悄悄连上不该连的端点。
- **模型版本 pin 死**。写成常量或者打进构建产物，升级走独立流程：新版本 + 评测 + 灰度。

为什么模型版本不能靠环境变量切？那会让同一份代码产生两种行为——线上出问题时无法复现，也答不出"上周三那次到底用的哪个模型"。

> 这是 LangGraph 生态里流过血的教训：模型端点悄悄升级，行为跟着变，
> 而没人知道变化发生在哪一刻。pin 死版本 + 显式升级，是唯一可控的做法。

密钥这件事最好交给机器：CI 里加一条静态扫描，命中就阻断合并。本章的实验里就带了一个极简版本，并且它被**反向验证过**——扫描器本身确实能抓到人为放进去的密钥，不会是条永远返回空的摆设。

## 8. 多租户隔离：隔离要落在查询层

多租户系统的隔离有三层，缺一层就是数据泄露：

| 层 | 隔离什么 | 怎么保证 |
| --- | --- | --- |
| 数据 | 任务、消息、轨迹 | 查询条件里带租户 id，不是拿到数据再过滤 |
| 记忆 | 跨会话的长期记忆 | 记忆条目带租户 id，检索时一起过滤 |
| 工具 | 能调用哪些工具、能碰哪些系统 | 按租户授权工具集（第 13 章的最小权限） |

关键在**查询层**。如果代码是"先按 id 查出任务，再判断租户对不对"——那已经晚了；正确写法是查询条件里就带上租户 id，让数据库保证你查不出来。

越权访问要报错，不是返回 None：返回 None 和返回"别人的数据但权限不足"在客户端看来一样，你会以为自己是权限问题，而不是代码 bug。

## 9. 上线检查单要变成闸门；上线之后要盯什么

`AI/Agent/附录-B-工程检查单.md` 是一份十节、几十条的清单。它的问题是：**清单靠人过，就一定会漏**。

把它变成闸门需要三件事：

1. 每一条改写成**可判定的布尔条件**——不是"要考虑并发问题"，而是"压测时 100 并发下 P99 延迟低于 800ms"。判不了的说明标准还没定义，不能算通过。
2. 每一节都要**有覆盖**。漏掉一整节（比如"终审三问"）也要阻断，不能只检查现有条目是否满足。
3. 门禁要有**退出码**：通过 0，阻断 1。这样它才能进 CI，而不是靠上线前那晚的记性。

本章实验里就实现了这一版：32 条覆盖十节，全部满足 → 通过；故意缺 1–2 项 → 阻断并指出是哪几条；整节漏掉 → 报"未覆盖小节"。

上线之后盯这几个指标（第 11、15 章的产出）：

| 指标 | 告警条件 | 说明 |
| --- | --- | --- |
| 任务成功率 | 跌破基线 | 最直接的变坏信号 |
| 单次成本 | 超出预算上限 | 轮次失控的信号 |
| 平均轮次 | 持续上涨 | 模型开始绕圈 |
| 停止原因分布 | `max_iterations` 占比上升 | 更早暴露 |
| 上游 429 比例 | 明显上升 | 该降并发或换额度 |

**值班和复盘**：上线后前两周有人盯轨迹（第 11 章）。事故复盘要产出的不是"下次注意"，而是**一次改动**——改提示、改工具、加护栏、改指标。复盘不改代码等于没复盘。

## 一句话结论

> **形态按任务时长和反馈需求选，状态必须活过进程重启，超限的请求要明确表态，**
> **而上线检查单要变成有退出码的闸门——靠记性的上线准备，等于没准备。**
