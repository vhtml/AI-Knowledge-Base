# 03 · 工具设计：schema、错误面与粒度

> **这篇要回答**：模型调错工具、传错参数，责任在谁？工具该怎么切分粒度？描述怎么写才能让模型选对？

---

## 1. 模型看不见你的函数，它只看得到三样东西

一段工具代码到了模型面前，只剩三样东西：`name`、`description`、`parameters`（JSON Schema）。函数体、类型注解、异常处理、写在函数上面的注释——模型一个都看不到。

| 模型看到的 | 模型看不到的 |
| --- | --- |
| 工具名 `search_orders` | 函数名、类名、模块路径、调用它的代码 |
| 一句话说明 | 实现细节、副作用、什么时候不该调 |
| 参数名 / 类型 / 是否必填 / 字段说明 | 默认值背后的业务约定、前置条件、错误怎么重试 |

**所以：模型调错工具、传错参数，责任不在模型，在你的 schema。** 模型没有第二个信息源，它只能按 schema 字面执行。schema 写歪了，模型"错"得完全合理——它没错，它只是忠实执行了一份有问题的说明书。

第 2 章的运行时把失败分成三类（工具不存在 / 参数不合法 / 工具内部出错）分别回填。但真正决定模型**能不能自我纠正**的，是这些失败被翻译成了什么样的文字。

---

## 2. 参数说明必须落到字段级 description

这是本章最容易被跳过、代价又最大的一件事。

人读参数说明的方式和模型不一样：人会把"订单号，形如 A-1001"自然地对应到 `order_id`；模型只会逐字段匹配。说明如果只停在函数级，模型就得靠猜。

| 实现 | 函数级 description | 字段级 description |
| --- | --- | --- |
| 本仓库 `labkit.tool()` | 整个 docstring（含 `Args:` 段落） | ✅ 从 `Args:` 段落解析出来 |
| LangChain `@tool` 默认 | 整个 docstring（含 `Args:` 段落） | ❌ 没有 |
| LangChain `@tool(parse_docstring=True)` | 只有摘要（`Args:` 被剥掉） | ✅ 有（Google 风格 docstring） |

前两行是本仓库 `_parse_arg_descriptions` / `_json_schema_for` 的实际行为，后两行是实测 `langchain-core` 的行为。**框架只是帮你把说明搬进 schema，源头上的说明永远是你写的**——这也是第 3 章实验不 import 任何框架的原因之一。

写法上没什么讲究，Google 风格即可：

```python
@tool
def 查订单(order_id: str) -> str:
    """按订单号查询订单状态。

    Args:
        order_id: 订单号，形如 A-1001
    """
```

生成出来是这样（`description` 挂在字段上，不是挂在一整坨文本上）：

```json
{"properties": {"order_id": {"type": "string",
  "description": "订单号，形如 A-1001"}}, "required": ["order_id"]}
```

对照实验：把 `Args:` 段落删掉，字段就退化成 `{"type": "string"}`——函数级说明还在，模型能读到"订单号"这三个字，但它挂不到字段上，只能在多个参数之间猜哪个是哪个。本仓库这两种写法的 schema 体积是 35 vs 23 tokens，省下的这点 token 要用错答率来还。

## 3. 坑：schema 说谎，模型必然犯错

schema 生成器靠类型注解推参数类型。**而本仓库的代码规范要求模块顶部写
`from __future__ import annotations`——PEP 563 会把注解从类型对象压成字符串**。
于是任何"按类型对象查表"的生成器都会失手：

```python
def 查库存(item_id: str, quantity: int) -> str: ...
# 原始注解是字符串 "int"，不是类型 int
# 按类型对象查表 → schema 里 quantity 是 {"type": "string"}，不是 integer
```

于是模型照着 schema 传了字符串 `"3"`，工具按注解要求整数，直接抛 `TypeError`。
**模型没有犯错，是 schema 先撒了谎。**

修法有两条：

1. 生成器用 `typing.get_type_hints(func)` 把注解解析回类型对象——
   `labkit.tool()` 现在就是这么做的，所以它不会踩这个坑；
2. 退一步用 `inspect.signature(func, eval_str=True)`，或显式写 `__annotations__`。

本章的实验把两条路都留了对照组：`typed_tool()` 手工还原注解（可照抄的修复模板），
探针则演示 naive 生成器为什么会被 PEP 563 绊倒。

LangChain 的默认 `@tool` 不踩这个坑（它用 Pydantic 生成 schema，Pydantic 会自己解析字符串注解），但它默认也不把 `Args:` 搬进字段。`@tool(parse_docstring=True)` 可以补上这一点，代价是 docstring 必须写成严格的 Google 风格。

> **一条纪律**：schema 是模型看到的唯一真相。发布前把 schema 完整打印出来读一遍——
> 每个字段的类型、说明、必填项都要和工具的实现对得上。

## 4. 错误面的三种设计，第三种最糟

工具失败了，错误要**以模型能读懂的形式回到模型面前**。三种设计，代价差得很远：

| 设计 | 做法 | 模型能看到什么 | 适用 |
| --- | --- | --- | --- |
| **A 抛异常** | 工具抛异常，运行时翻译成文字 | "参数错误：参数 quantity 需要整数，实际收到 str" | 调用方式错了：缺参、类型错 |
| **B 返回结构化错误** | 工具正常返回 `{"ok": false, "error": {...}}` | JSON 里的 `param` / `expected` / `received` | 业务上的否定结果：库存不足、余额不够 |
| **C 直接吞掉** | 工具 `try/except` 后返回"查询完成" | 什么都没有 | **没有场景** |

设计 C 是最常见的错误，也是最贵的。工具返回"查询完成"，模型只能顺着编下去——它会回答"库存现有 30 件"，而这个数字工具从来没给过。**静默失败比显式失败危险得多**：显式失败会让 Agent 卡住（吵闹但可见），静默失败会让 Agent 自信地给出错答案（安静但致命）。

A 和 B 的分工也值得记牢：**调用没成功**属于异常，**调用成功了但结果是"不行"**属于返回值。把业务否定结果做成异常，模型会以为是自己调错了；把调用错误做成返回值，模型会以为业务上就是这么回事。

---

## 5. 参数校验的三种失败，模型的纠正能力依次下降

| 失败类型 | 典型报错 | 模型能改对吗 | 为什么 |
| --- | --- | --- | --- |
| 缺参数 | `missing 1 required positional argument: 'order_id'` | 容易 | 只有一个明显缺口，补上即可 |
| 类型错 | `参数 quantity 需要整数，实际收到 str` | 取决于文案 | 改对类型就行，但要**知道是哪个参数** |
| 取值域非法 | `取值必须是 1 以上的整数，实际收到 -3` | 难 | 要理解"合法范围"，可能得重新想意图 |

关键不在"哪类更难"，而在**错误文案里有没有可执行的线索**。本仓库实验里做了两个除参数名外完全相同的工具：

- 报错文案点名 `quantity` → 模型改成整数 → 正常收尾；
- 报错文案只写"参数不合法" → 模型无从判断该改哪个参数 → 只能原样重试 → 跑满轮次上限，`stop_reason=max_iterations`，**Agent 卡死**。

两个工具的 schema 一模一样，输入一模一样，结果一个 `completed` 一个 `max_iterations`。差别只在错误文案里有没有参数名。

> **所以写错误文案有一条硬规矩**：点名参数、说清期望、给出合法取值。
> `f"参数 {name} 需要 {expected}，实际收到 {received}"` 是及格线，
> "参数不合法"不是。

## 6. 工具粒度：一个工具 = 一个用户意图

粒度没有"越多越好"，三档各有各的病：

| 粒度 | 形态 | 症状 | 怎么救 |
| --- | --- | --- | --- |
| **太粗** | 一个工具管所有事，靠 `type` 参数分支 | 模型不知道该填哪个值；填错就静默跑偏 | 拆工具，或把"取值 → 意图"的映射写进字段说明 |
| **太细** | 几十个功能相近的工具 | 选择困难，同义工具互相干扰 | 合并相近的，删掉没人用的 |
| **适中** | 一个工具 = 一个用户意图 | — | — |

本仓库实验用同一个请求（"A-2001 的退款什么时候到账？"）跑了三条路径：

- **细粒度**（`查订单` / `查物流` / `查退款`）：模型先选了 `查物流`，工具自己回"本工具只处理 S- 开头的运单号，不支持订单号或退款单号"，模型换到 `查退款` → 答对了。
- **粗粒度 + 字段说明写清映射**（`业务类型: T1=订单，T2=物流，T3=退款`）：一次就对。
- **粗粒度 + 字段说明没写映射**（同样三个代码，就是不写哪个是什么）：模型只能猜，猜了 `T1` → **技术上成功、语义上跑偏**，回答成"订单已发货"。

第三条是最值得警惕的：它不报错，Agent 也不卡，评测里"成功率"还是 100%——但答案是错的。粗粒度工具把"意图"塞进了一个没有语义的值里，模型选错时没人拦它。

> **判断标准**：用户会用一句话说清一件事，就该有一个工具对应这件事。
> 反过来，如果一个工具需要靠一个 `type` 参数来区分三件不相干的事，它就该被拆开。

## 7. 工具命名：动词开头，不要造同义词

模型选工具时，名字是最先被读到的信号。命名反模式有三个：

| 反模式 | 例子 | 后果 |
| --- | --- | --- |
| 同义工具名 | `查订单` 和 `查询订单` 并存 | 模型二选一全凭运气；schema 里的说明一字不差，纯浪费上下文 |
| 前缀相近 | `查订单` 和 `查订单详情` | 名字只差几个字，模型分不清用户问的是哪个 |
| 不表意的名词 | `order_tool`、`util` | 模型只能靠描述猜，等于没有名字 |

好的命名是**动词 + 对象**（`search_orders`、`cancel_subscription`），因为模型是在"发起一个动作"，不是"引用一个类"。同一件事只留一个名字；想覆盖多种说法，靠 description 说明别名，别靠再造一个工具。

这三个坑都是**上线前就能查出来的**：名字两两之间是不是前缀关系、说明是不是一字不差重复——写个几十行的脚本扫一遍，比上线后看错答率便宜得多。

---

## 8. 工具数量：schema 变长，选择变难

工具不是免费的。每多一个工具，模型每次调用都要多读一段 schema：

| 工具数 | tools payload 体积 |
| --- | --- |
| 1 | ≈ 126 tokens |
| 4 | ≈ 503 tokens |
| 8 | ≈ 1006 tokens |
| 16 | ≈ 2015 tokens |
| 32 | ≈ 4035 tokens |

体积是线性增长的，而且**每次模型调用都要整段重付一遍**——一个 10 轮的工具调用，工具描述就付了 10 次。

更贵的不是 token，是**选错概率**。工具数量翻倍，模型要在两倍的候选里挑，schema 越长，"候选里长得都差不多"的那几个越容易互相干扰。第 12 章会用黄金集把这件事量化：固定任务集，比对不同工具数量下的选择准确率。

实践上：把工具数控制在**十来个**以内；超了就按场景分组（不同场景挂不同的工具集），而不是把所有工具一次性塞进上下文。

## 9. 上线前跑一遍这份清单

| 检查项 | 怎么查 | 不过关的后果 |
| --- | --- | --- |
| 每个参数都有字段级说明 | 打印 schema，看 `properties.*.description` | 模型在多个参数之间瞎猜 |
| 说明写的是格式和范围，不是实现 | 读一遍 description | "订单号，形如 A-1001"这种才有用 |
| 枚举值写清了每个值什么意思 | 检查字段说明里有没有逐值说明 | 静默的错答（本仓库实测） |
| 类型和实现一致 | 对照 schema 与函数注解 | 模型按 schema 传，工具报类型错 |
| 错误文案点名参数 | 故意传错参数看回什么 | 模型无从纠正，Agent 卡死 |
| 没有同义工具名 / 前缀冲突 | 名字两两比一遍 | 选择困难，schema 浪费 |
| 工具数量在十来个以内 | 数一下 | 上下文变贵，选错概率上升 |

## 和其它章节的关系

- **第 2 章（Agent 循环）**：本章讲的三类失败，正是那章运行时 `_run_tool` 里分开处理的三条路；本章补上"回填的文案长什么样"。
- **第 4 章（系统提示与角色设计）**：描述是工具的"说明书"，系统提示是 Agent 的"岗位说明"，两者都在替模型补上下文。
- **第 5 章（上下文工程）**：本章的 schema 体积就是上下文预算的一部分，工具太多是最常见的浪费。
- **第 8 章（反思与自纠错）**：本章讲的是"错误可见"，那章讲的是"模型自己发现错误"——前者是前提。
- **第 10 章（可靠性）**：重试、幂等、降级都要按错误类型分流，本章的错误面分类是那章的输入。
- **第 12 章（评测）**：工具选择的准确率要靠黄金集量化，本章的粒度与数量结论都该在那一章被测一遍。
- **第 17 章（框架地图）**：LangChain 的 `@tool`、`args_schema`、LangGraph 的 `ToolNode`，本质上都在做本章这三件事——搬说明、翻译错误、切粒度。

---

## 一句话结论

> **模型看不见你的代码，只看得见 schema 和错误文案：
> schema 说谎它就传错参数，错误文案含糊它就卡死，工具粒度不对它就静默地答错。**
> 工具设计做得对，Agent 的失败率才降得下来；做不对，后面所有章节都在给一份错的说明书打补丁。
