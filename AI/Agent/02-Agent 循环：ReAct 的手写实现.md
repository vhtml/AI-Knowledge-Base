# 02 · Agent 循环：ReAct 的手写实现

> **这篇要回答**：ReAct 循环到底由哪几个环节组成？为什么工具结果**必须**回填给模型？循环为什么会不收敛、有哪几道防线？以及——自己手写一遍和直接用参考运行时，差别到底在哪？

---

## 1. ReAct 循环只有三个环节，但代码里是四个动作

ReAct 这个名字来自 Reason + Act：**先想，再做，再看**，做完再看一眼，然后接着想。
听起来像鸡汤，但落到代码上，它就是三段信息在消息历史里反复出现：

| ReAct 段 | 是什么 | 落到消息协议上是什么 |
| --- | --- | --- |
| **Thought** | 模型的推理与判断 | `assistant` 消息的 `content` |
| **Action** | 决定调哪个工具、传什么参数 | `assistant` 消息的 `tool_calls` |
| **Observation** | 工具执行的结果 | `role="tool"` 的消息 |

一轮循环在代码里是四个动作：**问模型 → 看它要不要工具 → 执行并回填 → 再问**。

关键在于：**Thought 不是一个独立的消息**。它就住在 `assistant` 消息的 `content` 里，
和 `tool_calls` 并排。这解释了为什么一段对话里出现两次 `assistant` 是正常的——
第一次是"我要调工具"，第二次是"根据结果我这么答"。

---

## 2. 循环的骨架短得惊人，长的是护栏

手写一版 ReAct 循环，核心就是这十几行：

```python
def react_loop(model, tools, user_input, max_iterations=8):
    messages = [human(user_input)]
    for _ in range(max_iterations):
        reply = model.complete(messages, tools=tools)
        messages.append(reply.to_message())            # Action
        if not reply.tool_calls:
            return reply.content                        # 收工
        for call in reply.tool_calls:                   # 一轮可能有多个
            result = run_tool(call)
            messages.append(tool_result(result, tool_call_id=call.id))  # Observation
    return "达到最大轮次，没能给出答案"
```

这段代码里没有推理、没有规划、没有反思、没有记忆。它只做一件事：
**把"模型想要工具"和"工具跑完了"这两件事拼成一条消息历史。**

真正的工程量全在护栏上：

| 护栏 | 挡住什么 | 本章对应位置 |
| --- | --- | --- |
| 轮次上限 | 模型一直要工具，烧钱 | 第 6 节 |
| 重复调用检测 | 模型原地打转 | 第 7 节 |
| 错误改写 | 模型把同一个错重复犯 | 第 7 节 |
| 外部停止信号 | 人工中止、长任务超时 | 第 6 节 |
| 回填完整性检查 | 结果对不上号 | 第 4 节 |

> **一个判断**：如果你的"Agent"只有上面那十几行，没有右边这张表里的任何一行，
> 那它离生产还差着**一整个章节的差距**，而不是几个参数的距离。

## 3. 为什么工具结果必须回填给模型

因为**模型只能看见你喂给它的东西**。

工具在你这边执行，执行完的结果如果不回填进消息历史，模型下一轮收到的历史里
就只剩一句"我要查订单 A-1001"，没有任何关于结果的线索。它能做的只有两件事：
重复同一个调用，或者开始编。

这就是 ReAct 里 Observation 的全部意义——**它是模型和环境之间唯一的信道**。
没有回填，模型就退化成第 1 章说的"一次性模型调用"：它永远学不到任何东西，
因为它永远看不到自己行为的反馈。

具体到代码，Observation 的回填位置只有一个：

```python
messages.append(tool_result(result, tool_call_id=call.id))
```

这一行做了三件事：

1. 把结果文本放进消息历史；
2. 标记这条消息的 `role` 是 `tool`，让模型知道"这不是我说的话，是工具说的"；
3. 记下 `tool_call_id`，把结果和那次调用意图绑在一起。

第 3 点常被忽略，但它是下一节的主角。

---

## 4. `tool_call_id` 不能省——模型靠它把结果和调用意图对上

`tool_call_id` 是模型给出的一个调用编号。回填时带上它，模型才能知道
**"这段观察，是我上一次那次调用的结果"**。

省掉它会怎样？分两种情况：

| 情况 | 模型看到什么 | 后果 |
| --- | --- | --- |
| 缺 `tool_call_id` | 一段没有来源的文字 | 不知道是谁的结果，无法据此修正参数 |
| `tool_call_id` 写错 | 一段指向别的调用的文字 | 把 A 的结果当成 B 的，参数越改越乱 |
| 只有一条工具结果 | 勉强能对上 | 侥幸正确，但只要有一轮多个调用就全乱 |

注意第三行：**单工具调用的场景下，省掉 id 可能"看起来没出事"**。
这就是它危险的地方——bug 会潜伏到第一个并行调用的任务上才爆。

> **坑**：`role="tool"` 的消息在 OpenAI 兼容协议里**必须**带 `tool_call_id`，
> 缺了是直接的协议错误（400），不是"模型可能理解错"。
> 更坑的是很多手写实现用 `messages.append({"role": "tool", "content": result})`
> 这种不带 id 的写法，**在单工具场景的测试里完全看不出来**。
>
> 防线：回填之后立刻做一次完整性检查——每条 `tool` 消息的 `tool_call_id`
> 必须能在历史里找到对应的 `tool_calls`。这条检查只有几行，但它把
> "潜伏到上线才爆"变成"当场就报错"。

---

## 5. 并行工具调用：一轮多个 `tool_calls` 怎么回填

模型一轮里可以返回**多个** `tool_calls`——比如"订单状态和天气我想一起看"。
这时候历史里会发生：

```
assistant(tool_calls=[call_a, call_b])      ← 一条消息，两个调用
tool('已发货',   tool_call_id='call_a')      ← 两条结果消息
tool('晴 26℃',  tool_call_id='call_b')
```

规则很简单，但必须守住：

- **一个 tool_call 对应一条 tool 消息**，不能合并成一条；
- **每条 tool 消息带各自的 `tool_call_id`**，不能共用一个；
- 两条结果都要出现在**下一次提问之前**——模型是一次性看到全部结果的。

违反第二条的后果比第 4 节更具体：模型会把"查天气"的结果当成"查订单"的结果，
然后用一句天气去改订单的参数。模型不会报错，它只会**自信地答错**。

> **注意**：`tool_calls` 是"并行意图"，但执行通常还是顺序执行的。
> 真正的并行执行意味着要处理"部分失败"——有的工具成功了有的挂了，
> 得决定是全盘回滚还是回填成功的那几条。那是第 10 章的题目。

## 6. 循环什么时候停？三个终止条件，一个都不能省

| 终止条件 | 判据 | `stop_reason` | 少了会怎样 |
| --- | --- | --- | --- |
| **模型不再调工具** | 回复里 `tool_calls` 为空 | `completed` | — |
| **达到轮次上限** | 迭代次数用尽 | `max_iterations` | 无限烧钱 |
| **外部停止信号** | 人为中止 / 超时 / 配额用尽 | `stopped` | 长任务停不下来 |

第一个条件是"正常收工"。第二个是**兜底**，不是可选的——
没有它，一个陷入循环的 Agent 会一直跑到你主动杀掉进程。
第三个最容易被忘，但它才是**人还能控制 Agent 的唯一入口**：
第 14 章的"人在环路"、第 16 章的任务取消，走的都是这条通道。

有个细节值得单独说：**停止信号要在"问模型之前"检查**。
如果信号在工具执行完之后才被触发，而检查放在模型调用之后，
那模型会白白多问一次、多花一次钱。所以顺序是：

```
每轮开头：检查停止信号 → 检查轮次上限 → 问模型 → 执行并回填
```

## 7. 循环为什么不收敛？三个原因、三道防线

"不收敛"不是玄学，是三个具体原因：

| 原因 | 症状 | 防线 |
| --- | --- | --- |
| **工具报错被原样回填** | 模型收到"超时了"，换个参数再撞一次 | 回填时改写措辞：说清是什么错、并且提示换条路 |
| **目标不可达但模型不知道** | 同一个调用反复出现 | 检测同名同参的重复调用，第二次就收手 |
| **没有轮次上限** | 上面两个问题都变成无限循环 | `max_iterations` 兜底 |

第一条最反直觉，值得展开。假设工具挂了，你把异常原样塞回去：

```
tool('TimeoutError: connection timed out', tool_call_id='call_1')
```

模型读到的是"这次失败了"，于是它**换个参数再试一次**——因为在它的理解里，
失败可能是参数不对。于是同一个业务故障被重试 8 次，每次都超时。

正确的回填要多说一句人话：

```
tool('工具执行失败：TimeoutError: connection timed out。
      这个错误通常不是参数问题，请调整参数或换用其他工具，不要重复同样的调用。',
     tool_call_id='call_1')
```

差别只在一句话，但这句话把模型的策略从"重试"改成了"换路"。
**错误回填的措辞，是运行时能施加给模型的最强引导**——比 system prompt 更强，
因为它出现在最需要做决定的那一刻。

第二条防线是重复调用检测：给每次调用算一个指纹（工具名 + 排序后的参数），
同名同参第二次出现就停。误伤的情况是"确实需要再查一次同一个东西"，
那就调整阈值，或者只对连续重复计数。

第三条防线是轮次上限，它必须**永远开着**。
前两条是启发式，这条才是硬边界。

## 8. 手写循环和参考运行时，差在哪、怎么验

`Demos/examples/agent_lab/runtime.py` 里有一个更完备的参考实现。
自己手写一版很有必要，因为**只有自己写过一遍，才知道参考实现替我做了什么**。

| 维度 | 手写版（第 2 章） | `runtime.Agent`（参考） |
| --- | --- | --- |
| 主循环 | 同样四步 | 同样四步 |
| 工具错误 | 一律转成可读文本 | 分三类：工具不存在 / 参数错 / 业务故障，措辞不同 |
| 工具输出过长 | 不处理 | 截断到 `max_tool_output_chars` |
| 重复调用 | 检测并停止 | 不检测 |
| 外部停止信号 | 支持 | 不支持 |
| 轨迹记录 | 无 | 有 `steps` |
| 用量统计 | 无 | 有 `usage` |

所以本章的对照实验只验一件真正要紧的事：**同一段脚本下，
手写循环和参考运行时产生的工具调用序列、最终回答、结束原因都一致**。

一致，说明你理解了主循环；不一致，说明你抄错了。
护栏上的差异（第 3、4 节的那些）恰恰是**你手写时必须自己补上的部分**——
那才是第 3 章到第 15 章要展开的内容。

## 9. 这一章之后往哪走

本章是整套教程的地基，后面每一章都在往这十几行上加东西或者换掉其中一环。
本章实验在 `Demos/examples/agent_lab/lessons/ch02_react_loop.py`，
跑法：`cd Demos/examples && uv run --project .. python -m agent_lab ch02`。

- **第 3 章（工具设计）**——循环会崩的第一个地方是工具本身：模型调不存在的工具、
  传错参数。这一章讲怎么让工具的 schema 和报错信息都指向"模型能自我修复"。
- **第 5 章（上下文工程）**——每轮回填都会让消息历史变长。
  本章实验里每轮上下文的长度序列是 `[5, 18, 31, 44]`，轮次越多越贵。
- **第 10 章（可靠性）**——工具超时要重试，重试要幂等，部分失败怎么处理。
- **第 14 章（人在环路）**——外部停止信号的完整版本：审批、中断、恢复。
- **第 17 章（框架地图）**——把这段手写循环映射回 LangGraph 的状态图，
  对照阅读 `AI/LangGraph/04-控制流：分支、循环、Send 与 Command.md`
  和 `AI/LangGraph/06-工具调用与工具节点.md`。

想直接看框架版怎么表达同样的循环，可以先翻 `AI/LangGraph/06-工具调用与工具节点.md`
——它讲的"工具调用是两次模型往返"，就是本章第 3 节那条"Observation 是唯一信道"的另一种说法。

---

## 一句话结论

> **ReAct 循环 = 问模型 → 执行并回填 → 不调工具就收工；结果必须带 `tool_call_id`。**
> 停止靠模型收工 / 轮次上限 / 外部信号三件事；不收敛靠重复检测和轮次上限兜底。
