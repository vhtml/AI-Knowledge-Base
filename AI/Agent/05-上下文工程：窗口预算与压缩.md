# 05 · 上下文工程：窗口预算与压缩

> **这篇要回答**：上下文窗口的预算该怎么分配？历史塞不下时怎么办？什么该压缩、什么绝对不能压？

---

## 1. 上下文不是聊天记录，是六份预算的拼装

第 4 章写了系统提示，第 6 章谈长期记忆，中间这层还悬着：
**模型这一轮到底看到了什么、看到了多少**。

先把"上下文"拆开。很多人以为上下文 = 对话历史，其实喂给模型的这一轮请求里塞了六样东西：

| 部分 | 是什么 | 谁在长 |
| --- | --- | --- |
| **系统提示** | 角色、边界、约束、格式要求 | 很慢，几乎不变 |
| **工具 schema** | 每个工具的 name / description / parameters | 加一个工具就涨一截 |
| **历史消息** | 用户与助手的往返对话 | 随轮次线性增长 |
| **工具结果** | 工具回填的原始输出 | **增长最快，而且最不可控** |
| **检索内容** | RAG / 按需检索注入的文档片段 | 取决于检索策略 |
| **输出预留** | 留给模型写答案的空间 | 固定，但必须留 |

**这六样加起来，才是"上下文窗口"被消耗掉的地方。**

工具 schema 常常被忽略——五个啰嗦的工具比两页对话还贵；
检索内容也常被忽略——RAG 一股脑塞 20 个片段，比不检索还糟；
输出预留最常被砍成 0，然后模型写一半被截断。

> **第一条纪律**：先算清楚六部分各占多少，再谈怎么省。
> 不测量就优化，等于凭感觉砍东西。

## 2. 预算是分配问题，不是容量问题

有个特别容易搞错的直觉：

> ~~"上下文窗口是 128k，我的历史有 200k，塞不下"~~

这把问题讲成了**容量问题**——仿佛要么塞进去，要么塞不进去。
但窗口是**固定**的，历史是**可塑**的，真实问题是**分配问题**：

> 六部分共享 128k，谁多占、谁少占、超了先砍谁？

这个转变很关键："塞不下"是死路，"分配"有无数种解法——
截短工具结果、把老消息折成摘要、把检索片段从 20 个降到 3 个……
每一种都是**把额度从一处挪到另一处**。

**一张必须闭合的预算表**：

预算表不是建议，是**契约**：配额之和必须等于总窗口。

| 部分 | 配额 (token) | 依据 | 溢出会怎样 |
| --- | --- | --- | --- |
| 系统提示 | 2,000 | 一份人设 + 硬约束 + 格式说明 | —— |
| 工具 schema | 6,000 | 6 个工具，每个 ≤ 1,000 | 工具描述被模型忽略 |
| 历史消息 | 40,000 | 约 30 轮对话 | 记不住自己说过什么 |
| 工具结果 | 30,000 | 约 8 次工具调用 | 挤掉历史，模型失忆 |
| 检索内容 | 12,000 | 约 5 个文档片段 | 检索噪声淹掉信号 |
| 输出预留 | 4,000 | 一次较长的结构化回答 | 答案被拦腰截断 |
| 余量 | 34,000 | tokenizer 误差、突发输出、重试 | 直接溢出报错 |
| **合计** | **128,000** | **== 上下文窗口** | |

对应的代码骨架（实验里的 `Budget` 就是它）：

```python
@dataclass(frozen=True)
class Budget:
    total_tokens: int = 128_000
    system_tokens: int = 2_000
    tool_schema_tokens: int = 6_000
    history_tokens: int = 40_000
    tool_result_tokens: int = 30_000
    retrieval_tokens: int = 12_000
    output_tokens: int = 4_000
    reserve_tokens: int = 34_000

    @property
    def allocated_tokens(self) -> int:
        return (self.system_tokens + self.tool_schema_tokens
                + self.history_tokens + self.tool_result_tokens
                + self.retrieval_tokens + self.output_tokens
                + self.reserve_tokens)
```

**为什么必须闭合**：预算表不闭合，就意味着某一部分在偷偷吃别人的份额。
超限时你就会去砍错的东西——通常是砍历史，而真正的元凶是那个
一次返回三万字日志的工具。

余量那行看着浪费，其实是**必需**的：`approx_tokens` 这类粗估和真实
tokenizer 一定有偏差，模型偶尔也会超长。没有余量的预算表，生产上第一次就崩。

## 3. 塞不下时：六种压缩手段

压缩不是"把上下文变短"，而是六个各有代价的动作。

| 手段 | 做什么 | 损失什么 | 什么时候用 |
| --- | --- | --- | --- |
| **截断** truncate | 只留前 N 字符，后面标一句"已截断" | 后半段内容 | 工具结果、日志、堆栈 |
| **摘要** summarize | 老消息折叠成一条摘要消息 | 细节、原始措辞、语气 | 对话跑长之后 |
| **引用外部存储** | 正文只留一个指针（文件路径、对象存储 ID） | 需要再读一次 | 产物很长：写文件、生成代码 |
| **选择性保留** | 只留与当前子任务相关的消息 | 其它分支的上下文 | 多任务、多子目标并行时 |
| **分层** | 近期留原文 + 远期留摘要 | 中间那段的细节 | **默认策略**，多数场景够用 |
| **按需检索** | 不预置，需要时用检索工具取回 | 一次额外工具调用的延迟 | 知识型内容、代码库 |

六种手段的正交性在于：**它们压掉的东西不一样**——
截断砍深度，摘要砍过程，外部引用砍本体，选择性保留砍分支，
分层砍中间，按需检索砍预置。
选错的症状是"上下文变短了，但 Agent 变笨了"——你砍掉的恰好是它需要的。

多数项目只需要"分层 + 截断"两招；把六种都实现一遍是过度工程。

## 4. 工具结果截断：模型必须知道「这不是全文」

工具结果是唯一一块**你事先不知道会有多大**的内容。
它必须有一条独立的闸门，且闸门要设在**结果进上下文的那一刻**——
等它进了历史再补救，那一大坨已经占过预算了。

截断本身简单，难的是**标记**：

```python
def truncate_tool_output(content: str, max_chars: int) -> tuple[str, bool]:
    if len(content) <= max_chars:
        return content, False
    kept = content[:max_chars]
    return kept + "\n" + TRUNCATION_SUFFIX.format(n=len(content)), True
```

那行 `TRUNCATION_SUFFIX` 是"…（已截断，原始长度 7505 字符）"。
**没有它，模型会把残缺的结果当成完整事实。**

这不是理论担忧：模型看到一段从中间断掉的 JSON 或半张表格，
不会怀疑自己的输入，只会在错误前提上继续推理。
**残缺输入比明确报错更危险**——模型不怀疑输入，只怀疑结论。

两个配套约定：

- **截断上限从预算表推导**，别写魔法数字：教学实验里是
  `limit = budget.tool_result_tokens - 24`（24 留给标记本身）。
- **保留头部**。日志、堆栈、CSV，信息的密度通常在开头。

> 第 2 章的运行时里已经有一份等价实现：`AgentConfig.max_tool_output_chars`。
> 同一个语义全系统只应有一处定义，否则两处口径会慢慢漂移。

## 5. 什么绝对不能压

压缩是有损的，必须先划出**保护名单**。三类内容一旦被压掉，
Agent 会以一种很难排查的方式坏掉：

| 不能压 | 为什么 | 压了会怎样 |
| --- | --- | --- |
| **工具的错误消息** | 它是模型自我纠正的唯一依据 | 模型不知道自己错在哪，重复同一个错误 |
| **当前任务的关键约束** | "只读""不得修改数据"这类硬边界 | Agent 越权操作，闯下大祸 |
| **模型刚做出的决策依据** | 它记着为什么走这条路、传了什么参数 | 忘记自己在干什么，来回横跳 |

第三条最容易被忽略。"模型刚做出的决策依据"就是那条带 `tool_calls`
的助手消息——里面写着它选了哪个工具、传了什么参数。
把它摘要掉，等于抽掉 Agent 的短期记忆：模型会重新规划，
很可能规划出另一个方向。

实现上就是给它一个"受保护"的判定，压缩时单独捞出来：
```python
def is_protected(message: Message) -> bool:
    if message.role == "system":      # 当前任务的关键约束
        return True
    if message.role == "tool":        # 工具的错误消息
        return _looks_like_error(message.content)
    return False
```

注意错误判定只看**开头 40 个字符**：结果正文里出现"错误"两个字很常见
（比如某个字段叫 `error_code`），一律当成失败会误伤。

**摘要也不能只存结论。**

受保护的消息保住了，但**摘要本身可能把约束吃掉**：
"只读操作"若只存在于一条旧消息里，而那条消息被摘要成了
"用户要求排查延迟"，约束就没了。

对策：硬约束别放在历史里，**放在系统提示里**——它在所有策略下都受保护。

## 6. 上下文腐化：中段信息最先被忘掉

即使不压缩，长对话也会坏在一个地方：**中段的信息权重会下降**。

这叫 *lost in the middle*：同样一条关键事实，放在上下文开头或结尾
模型能准确引用；放在中间，它大概率会被忽略。位置越靠中间，权重越低。

实验把这事变成了可测的：构造 30 条带唯一编号的消息，
按不同策略裁剪，画一张"存活地图"：

```
30 条消息，按位置保留两端（头 6 / 尾 10）：
  ✓✓✓✓✓✓✗✗✗✗✗✗✗✗✗✗✗✗✗✗✓✓✓✓✓✓✓✓✓✓
只保最近 10 条：
  ✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✓✓✓✓✓✓✓✓✓✓
```

第一张图中间那片空洞，就是上下文腐化的位置。
第二张图更狠——只保最近，等于把开头也放弃。

对策两条：

1. **前置**：关键事实放进系统提示或历史最前面——它在最安全的位置。
2. **复述**：模型每轮开头把当前约束和结论重述一遍，
   用新的 token 换回已经衰减的权重。

这也是为什么 Agent 系统的系统提示不该只写"你是一个 helpful assistant"——
它的真正价值是**常驻的事实与约束**，而不是人设。

## 7. 压缩是有损的：短任务不该压，砍的要是过程不是状态

压缩会引入新的一类故障：摘要写错了、被截断的结论指错了方向、
模型在残缺上下文上推理出错误结论。

所以第一件事是判断**要不要压**：

> **对话本来就在预算内 → 一个字都别动。**

短任务（几十轮以内）做压缩是纯粹的净损失：
多一次摘要调用的成本和延迟，换来一个有损的结果。

判断标准很简单——历史 token 估计没过历史配额就别压。
此时压缩策略必须是**恒等变换**：压两次和压一次结果一样。

另一条纪律：**压缩必须可观测**。
Agent 突然变笨，你得能回答"是上下文被压掉了，还是模型本身不行"。
所以压缩策略要记录：压了几条、保住了什么、丢弃了什么——
否则压缩就成了**掩盖真问题的黑箱**。

### 那该放什么，不该放什么

同样的 token，信息量差别很大。

| 该放 | 不该放 | 为什么 |
| --- | --- | --- |
| 事实与状态（订单状态、已确认的结论） | 寒暄（"你好""收到""好的"） | 不携带任何状态，纯占配额 |
| 工具返回的**结论部分** | 工具返回的完整原文 | 原文进外部存储，结论进上下文 |
| 当前任务的约束与边界 | 与当前子任务无关的其它分支 | 无关上下文会稀释注意力 |
| 错误消息（哪怕是原文） | 重复出现过的相同内容 | 重复是纯浪费，去重即可 |
| 文件路径、对象存储 ID | 大段产物正文 | 正文按需读取（引用外部存储） |

一句话概括：**上下文里放"状态"，不放"过程"**。

过程该去哪儿？去轨迹（第 11 章）、去外部存储、去检查点
（`AI/LangGraph/07-持久化：检查点与时间旅行.md`）。
上下文只该承担一件事：让模型知道现在的状况。

## 8. 三个坑

**坑一：余量看起来浪费。**
余量占窗口的 20%–25%，第一反应是"太奢侈了，砍掉"。
但 token 估算和真实 tokenizer 一定有偏差，模型也会偶发超长输出。
没有余量的预算表，一定在某次生产环境的长输出上炸掉。

**坑二：摘要本身是模型的输出，会漂移。**
用 LLM 写摘要，摘要就是又一次生成——它可能漏掉约束，
甚至把"不能修改数据"写成"修改了数据"。
所以**硬约束不能只存在于摘要里**：要么前置进系统提示，要么每轮开头复述。
摘要适合承载"过程结论"，不适合承载"硬规则"。

**坑三：压缩把 bug 藏起来了。**
模型答错了，你去调提示词、调模型、调参数——而真正的失败点
可能早就在被丢掉的那条消息里。对策：**压缩要留痕**，且能回放到压缩前的上下文。

## 9. 与其它章节的关系

- **第 4 章（系统提示与角色设计）**：本章说明了系统提示为什么值得占预算——
  它常驻、受保护、位置最安全。
- **第 6 章（记忆系统）**：本章的"近期原文 + 远期摘要"就是**短期记忆**；
  第 6 章补的是跨会话的**长期记忆**，也就是第 3 节的"按需检索"。
- **第 10 章（可靠性）**：重试要重放**压缩后**的那份上下文，
  否则两次重试的输入不一样，故障无法复现。
- **第 11 章（可观测性）**：压缩必须留痕，且要能回放到压缩前的完整上下文。
  压缩后的上下文可以持久化——这正是
  `AI/LangGraph/07-持久化：检查点与时间旅行.md` 讲的事情：
  压缩过的状态怎么存下来、怎么回滚、怎么重放。
- **第 13 章（安全）**：检索内容和工具结果都是**不可信输入**，
  它们既会吃预算，也可能改写你的约束。

---

## 一句话结论

> **上下文预算是分配问题：先给六部分定配额，再决定超了砍谁——
> 但错误、约束和刚做出的决策依据，永远不参与压缩。**
