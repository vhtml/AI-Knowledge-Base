# 07 · 任务分解：规划模式与自适应分解

> **这篇要回答**：要不要先规划？计划是一次写死还是边做边改？什么时候分解反而是坏事？

---

## 1. 分解的前提：先算清这件事到底需要几步

第 2 章的 ReAct 循环已经能处理多步任务：模型看着上下文决定下一步，失败就换个工具再试。
那为什么还要"规划"？

因为 ReAct 的每一步都是**临场决定**——它只看得见眼前，没有全局。
遇到"先 A、再 B、最后 C"这种有依赖的任务，它可能做完 A 就忘了 C，也可能把 B 做两遍。
规划补的就是这块：先给出一条全局路径，再去走。

但规划不是免费的，它要付三笔钱：

1. **一次额外的模型调用**——规划就是问模型"你打算怎么做"，这次调用同样花钱、同样有延迟；
2. **每一步的上下文变长**——执行时要把计划一起喂给模型，步骤越多，每一步的 prompt 越大；
3. **刚性**——照计划走，代价是计划错了也得先走一段才会发现。

所以判断标准很直接，先估"要几步"：

| 任务形态 | 该怎么走 | 理由 |
| --- | --- | --- |
| 一步就答完 | 不分解，直接调模型 | 规划纯属浪费（第 1 章） |
| 步骤完全已知、顺序固定 | 不分解，写成工作流 | 确定性优先，规划买不到新信息 |
| 步骤可预知，但有明确的失败点 | 计划 → 执行 → 失败就重规划 | 失败点已知，换一次路就能救回来 |
| 路径完全未知（探索型任务） | 自适应分解 | 没有计划可写，写了也是猜 |

> **一条纪律**：估出来是 1 步，就别规划。估出来是 3 步以上、而且步骤之间有依赖，才值得规划。

## 2. 三种策略的差别不在第一步，而在失败之后

三种分解策略的第一步长得几乎一样：都是"问模型要一份计划"。
真正的分水岭是**第一步失败之后怎么办**。

| | 一次性规划<br>(plan once, execute all) | 计划-执行-重规划<br>(plan → execute → replan) | 自适应分解<br>(adaptive) |
| --- | --- | --- | --- |
| 谁决定下一步 | 计划一次性写死 | 失败时换一份新计划 | 每一步现场决定 |
| 失败怎么办 | 直接停，把错误抛出去 | 重规划一次，继续跑 | 只重规划剩下的部分 |
| 计划调几次 | 1 次 | 1 + 失败次数 | 1 + 需要重规划次数 |
| 适合 | 步骤可预知的任务 | 有明确失败点的任务 | 路径完全未知的探索型任务 |
| 代价 | 计划错了整条路都偏 | 重规划本身要钱 | 决策成本高，且容易发散 |

三句话记住它们的性格：

- **一次性规划** = 把赌注全押在第一版计划上。快、便宜、可预测，赌输了整条路都偏。
- **计划-执行-重规划** = 承认计划会错，但错一次就重写一次。适合失败点明确的任务——换条路就能继续。
- **自适应分解** = 不赌第一步，剩下每一步都现场决定。适合根本不知道会长成什么样的任务。

注意最后两列的差别：**自适应分解贵在"每一步都要重新想"，重规划贵在"计划要重写"**。
前者花在决策上，后者花在规划上。

## 3. 计划要过三道检查：可执行、无歧义、粒度合适

计划不是一段说明文字，是一份**能被机器检查的结构**。三条标准，缺一条就会在执行时炸。

**第一条：可执行——每一步都要有对应的工具。**
模型写了一个注册表里没有的工具名（"发送邮件"），执行到那一步才发现。
检查点：工具名是否在工具注册表里。

**第二条：无歧义——每一步都要有完成判据（`done_when`）。**
没有判据的步骤，你永远不知道它做完了没有，下游步骤只能靠猜。
判据要可验证："拿到订单状态文本"可以，"处理妥当"不行。

**第三条：粒度合适——一步只做一件事。**
"做完整个项目"这种空步骤，执行完也验证不了，等于没拆。

计划的存储格式就长这样，每条标准对应其中一两个字段：

```json
{
  "steps": [
    {
      "id": "s1",
      "goal": "查询订单 A-1001 的状态",
      "tool": "查询订单",
      "args": {"order_id": "A-1001"},
      "done_when": "拿到订单状态文本",
      "depends_on": []
    }
  ]
}
```

对应的检查函数可以短到这样：

```python
def validate_plan(plan, known_tools):
    problems = []
    for i, step in enumerate(plan.steps, start=1):
        if step.tool not in known_tools:
            problems.append(f"第 {i} 步引用了不存在的工具「{step.tool}」")
        if not step.done_when.strip():
            problems.append(f"第 {i} 步缺少完成判据")
        if len(step.goal) > MAX_GOAL_CHARS:
            problems.append(f"第 {i} 步粒度过粗")
    return problems
```

> **关键设计**：校验发生在**执行之前**。没有这道闸，模型的幻觉工具名会一路跑到执行阶段
> 才变成用户可见的错误；有了它，错误停在一行日志里。

## 4. 分解太细和太粗，账单都不小

分解不是"越细越好"。两头都有代价，而且方向相反。

| | 分解太粗 | 分解太细 |
| --- | --- | --- |
| 典型样子 | "调研竞品并出报告" | "打开文件"、"读第一行"、"数一下字数" |
| 问题 | 中间状态没法检查，失败时定位不到 | 每步都要重新调一次模型，成本爆炸 |
| 上下文代价 | 每步要带一大坨背景 | 每步要带计划，还要带上一段的产出 |
| 修复方式 | 拆细 | 合并 |

**太细为什么贵**：每一步都是一次独立的模型调用，而每一次调用都要重新读一遍上下文。
更要命的是，步骤越多，每一步的 prompt 里那份计划就越长——成本不是线性增长，而是**越分解越贵**。
实验里同一个任务，1 步的计划用 2 次模型调用、约 90 token 的 prompt；8 步的计划用 9 次调用、约 1700 token。

**太粗为什么危险**：粒度太粗的步骤没法验证。计划写着"整理竞品资料"，做完之后你无法判断它到底干没干，
只能让它继续往下走，等第 8 步炸了才发现第 3 步就已经偏了。

一条好用的经验规则：**一步 = 一次工具调用 + 一句可验证的判据**。
超过这个粒度就想合并，低于这个粒度就想拆分。

## 5. 重规划时，旧计划该全换掉还是只换剩下的

重规划不是"把计划删了重写"，而是要回答一个具体问题：**已经做完的那些步骤怎么办？**

| 口径 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| **全量替换** | 新计划从头写，旧计划整个作废 | 模型能看到全局，容易发现整体性问题 | 模型看不到现场，可能把已经做对的事改错 |
| **只改剩余部分** | 已完成的步骤变成"历史"，新计划只写剩下的 | 不浪费已完成的工作，不会引入回归 | 模型看不到全局，可能重复劳动或推翻前提 |

实践上的默认选择是**只改剩余部分**，但必须补两件事：

1. **把已完成步骤的结论喂给规划器**——它看不到现场，只能靠你告诉它；
2. **步骤 id 要沿用**——id 是计划的"血缘"。执行器靠 id 判断"这一步我已经做过了"。
   新计划里换了个 id，它就会把已经做完的活儿再做一遍。

另外要给重规划设**次数上限**。不设上限的 Agent 会在失败—重规划—再失败之间来回烧钱，
这是第 10 章要专门讲的失败分类问题。

## 6. 规划失败的三种表现

计划失败不只有一种形态，检测手段也不一样。

| 表现 | 症状 | 怎么检出 | 检出时机 |
| --- | --- | --- | --- |
| **引用了不存在的工具** | 计划里有注册表没有的工具名 | 拿工具名对注册表 | 执行前，一秒拦下 |
| **步骤之间的依赖断裂** | 第 2 步依赖第 1 步的产出，而第 1 步被跳过或失败 | 检查依赖的步骤是否已完成且有产出 | 执行到那一步之前 |
| **漏掉了关键步骤** | 计划里压根没有这一步 | **没法静态检出** | 只能靠完成判据 + 外部验证 |

第三种最难缠：计划语法完全合法、工具全都有、依赖也自洽，就是少了一件事。
静态检查抓不到它，只能靠两个手段兜住：

- 每一步的**完成判据**写得足够具体，缺的那一步会让下游判据对不上；
- 关键步骤用**外部事实**验证（测试跑没跑过、数据查没查到），而不是靠模型自述"我完成了"。

> 这也是第 8 章"反思"的用武之地：规划解决"下一步做什么"，
> 外部验证解决"上一步到底做没做成"。

## 7. 规划不是反思：方向相反的两件事

这是最常被混掉的一对概念。它们的方向是相反的：

| | 规划（planning） | 反思（reflection） |
| --- | --- | --- |
| 时间方向 | 前瞻，看下一步 | 回看，看上一步 |
| 核心问题 | "接下来做什么？" | "刚才那步做得对不对？" |
| 产物 | 一份步骤列表 | 一段判断：继续、改还是停 |
| 触发时机 | 执行之前 / 失败之后 | 执行之后、且有产出之后 |
| 输入 | 任务 + 已知信息 | 上一步的产出 + 验证结果 |

两者**可以组合**，而且组合起来才是完整的闭环：

```
规划 → 执行 → 反思 →（没问题就继续 / 有问题就改这一步 / 方向错了就重规划）
```

但别混淆：一个系统里同时叫"重规划"和"反思"，出问题时你就分不清
是计划错了还是执行错了。**先用外部事实判断是哪一类，再决定重做哪一层**——
这正好也是第 10 章"该重试还是该放弃"的判据。

## 8. 坑：三个真实翻车点

**坑一：把计划写成 checklist，然后闭眼执行。**
计划写完就不再看上下文，每一步只认计划里的那句"目标"。
计划漏了一步、或者第 2 步的工具返回了意外结果，它都不会反应。
**做法**：执行时每一步都把剩余计划和最新产出一起喂给模型，允许它偏离计划并说明理由。

**坑二：重规划时把已完成的工作也重写一遍。**
最常见的形式是"生成一份全新的计划"，于是已完成且正确的步骤被改了，
甚至被换了顺序、换了参数——白花钱，还可能引入回归。
**做法**：默认只重规划剩余部分 + 稳定步骤 id + 把已完成结论作为上下文喂回去。

**坑三：把步数上限当成护栏。**
步数上限是**刹车**，不是**护栏**。10 步的计划跑到第 3 步才发现方向错了，
这时候刹车才踩，已经花掉三步的钱和延迟了。
**做法**：上限之外还要有"质量检查点"——每 N 步校验一次计划还成不成立，
尤其是有外部世界副作用的任务（第 13、14 章）。

## 9. 和其它章节的关系

| 章节 | 关系 |
| --- | --- |
| 第 2 章（ReAct 循环） | 规划是给循环加的"上层结构"；循环负责"怎么走一步"，规划负责"该走哪几步" |
| 第 3 章（工具设计） | 计划的"可执行"直接依赖工具 schema 写得清不清楚 |
| 第 5 章（上下文工程） | 分解越细，每步的 prompt 越大——规划和上下文预算是同一件事的两面 |
| 第 6 章（记忆系统） | 计划要引用历史结论时，记忆是它的输入 |
| 第 8 章（反思与自纠错） | 规划说"下一步做什么"，反思说"上一步做得对不对"；两者串成闭环 |
| 第 10 章（可靠性） | 重试是同一步再试一次，重规划是换一步——两者别混 |
| 第 15 章（成本与延迟） | 规划调用是真金白银，"先规划还是直接干"是成本问题 |
| 第 17 章（框架地图） | 手写的这套计划器，怎么映射回 LangGraph 的节点图与 Deep Agents 的 harness |

框架层的对照见 `AI/LangGraph/14-Deep Agents：harness 视角.md`：
那篇从 harness 的角度看"规划"这件事被框架接管成了什么样——本质上，
我们在这里手写的"计划器 + 执行器"，在 harness 里就是一个带中间件的循环。

## 一句话结论

> **先规划还是边做边改，取决于失败点能不能预知；计划必须能被机器校验，否则只是把错误往后拖。**
> 分解是为了让每一步可验证、可归因——分解得越细越贵，越粗越没法验证，
> 而"写完就闭眼执行"的计划，比不写计划更危险。
