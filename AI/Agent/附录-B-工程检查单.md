# 附录 B · 工程检查单

这份检查单按**上线顺序**排列，每一项都是**可判定**的——不是"要考虑并发问题"，
而是"压测时 100 并发下 P99 延迟低于 X"。做不到判定的项，标了 `⚠️ 需要先定义标准`。

用法：上线前逐条过；每一条要么有答案，要么有负责人和截止日期。

---

## 一、该不该用（立项前）

- [ ] 任务的步骤**事先不可知**——如果可��，用工作流
- [ ] 失败是可接受的——Agent 会失败，业务能承受
- [ ] 有明确的完成判据——否则你无法验收，也无法评测
- [ ] 有人类兜底路径——Agent 答不上来时谁来接
- [ ] 单次任务的成本上限**已经算过**（见附录 B 第七节）

---

## 二、工具与提示（第 3、4 章）

- [ ] 每个工具的 `description` 写的是**给模型看的使用说明**，不是函数文档
- [ ] 每个参数都有**字段级** description，格式、取值域、单位都写清
- [ ] 一个工具 = 一个用户意图，没有"万能工具"
- [ ] 工具数量 ≤ 15；超过则分组或分阶段暴露
- [ ] 工具报错时，**回填给模型的内容经过改写**——业务故障不能原样回填
- [ ] 系统提示写了三段：角色与目标 / 边界与约束 / **失败时的行为**
- [ ] 系统提示里没有硬编码流程步骤（那会把 Agent 退化成 Workflow）
- [ ] 系统提示与工具描述没有重复同一句话
- [ ] 系统提示的长度 × 预估轮次 × 单价，已计入成本模型

---

## 三、上下文与记忆（第 5、6 章）

- [ ] 有显式的**上下文预算表**，各部分配额之和 + 输出预留 ≤ 窗口
- [ ] 输出预留 ≥ 单次任务最大预期输出
- [ ] 工具结果有截断，且截断**带显式标记**（模型要知道这不是全文）
- [ ] 工具**错误消息**永不参与压缩
- [ ] 压缩策略有测试：压缩后关键约束仍然存在
- [ ] 长对话里关键事实被**前置或复述**，不留在中段
- [ ] 记忆有四条路径：写入 / 检索 / 遗忘 / **用户更正**
- [ ] 用户能删除和更正自己的记忆（"忘掉我说过的 X"）
- [ ] 记忆检索有上限，不会一次召回上百条
- [ ] 未召回的记忆**不会**出现在发给模型的上下文里

---

## 四、可靠性与安全（第 10、13 章）

- [ ] 错误分了四类：认证 / 限流 / 服务端 / 请求本身，各自处理方式不同
- [ ] 429 用指数退避 + 抖动，**不是**固定间隔
- [ ] 有超时：单次模型调用、单轮、整个任务，三层都有
- [ ] 所有**写操作**工具都幂等（带幂等键），或被明确标记为不可重试
- [ ] 并行工具的部分失败有处理策略（不是静默丢弃）
- [ ] 有熔断：连续失败达阈值后停止打后端
- [ ] 有降级路径：主工具失败时走哪条路，用户看到什么
- [ ] 工具结果被当作**不可信数据**，不是指令
- [ ] 工具按风险分级：只读 / 写 / 高危
- [ ] 高危工具在沙箱里执行，文件系统与网络都有白名单
- [ ] Agent 只拿到完成当前任务所需的工具（最小权限）
- [ ] 出站数据有脱敏（密钥、身份证、卡号不出现在发给模型的内容里）
- [ ] 有提示注入的测试用例，纳入回归集

---

## 五、人在环路（第 14 章）

- [ ] 审批按**动作风险**触发，不是按工具名触发
- [ ] 高危操作的审批**无法被模型绕过**（不是靠提示词约束）
- [ ] 审批超时有明确策略（拒绝 / 挂起 / 降级），默认是拒绝
- [ ] 批量场景有批量审批，避免逐条骚扰
- [ ] 人可以修改参数后放行，且执行用的是**修改后**的参数
- [ ] 中断后能从暂停点恢复，不必从头重跑

---

## 六、可观测性与评测（第 11、12 章）

- [ ] 每次运行有 trace：输入、每轮消息、工具调用入参出参、耗时、token、错误
- [ ] trace 里**没有**明文密钥与个人信息
- [ ] trace 可回放：重放能复现同样的轨迹
- [ ] 有黄金集，样本 ≥ 30，覆盖真实场景分布
- [ ] 评测同时看**结果**和**轨迹**（是否调了不该调的工具）
- [ ] 回归门禁在 CI 里：分数低于阈值就阻断合并
- [ ] 黄金集有扩充机制，且记录了每次扩充的原因（防过拟合）
- [ ] 关键指标有看板：任务成功率 / 工具调用分布 / 失败率 / 平均轮次 / 单次成本

---

## 七、成本与延迟（第 15 章）

- [ ] 单次任务的成本上限写成了数字（不是"应该不贵"）
- [ ] 成本模型包含：输入 token、输出 token、缓存命中率、轮次、工具调用
- [ ] 有模型分级路由（简单问题走小模型），并有效果不降级的证据
- [ ] 提示前缀稳定，能命中缓存
- [ ] 长会话有上下文裁剪，且裁剪后质量不下降（有评测数据）
- [ ] 流式首字延迟达标
- [ ] 并行工具调用的延迟收益被量化

---

## 八、上线与运维（第 16 章）

- [ ] 选定了部署形态（同步 / 后台任务 / 长驻流式），并说明理由
- [ ] 会话与任务状态**持久化**，进程重启不丢
- [ ] 有并发上限和限流，超限的请求有明确响应
- [ ] 配置与密钥走环境变量，代码里没有硬编码
- [ ] 模型版本**已 pin 死**，升级有单独的流程
- [ ] 有灰度开关，能按比例把流量切到新版本
- [ ] 能一键回滚
- [ ] 有告警：任务成功率下跌、成本异常、轮次异常增长
- [ ] 上线后前两周有人盯轨迹

---

## 九、框架迁移（第 17 章）

- [ ] 知道自己的运行时每一环对应框架的哪个概念
- [ ] 知道框架替我做了什么：持久化 / 中断恢复 / 流式 / 多 Agent 编排 / 可视化
- [ ] 知道框架的代价：状态 schema、归约器、边设计都要自己扛
- [ ] 迁移时**评测集不变**——这是判断迁移有没有搞坏东西的唯一依据
- [ ] 迁移清单包含：工具调用协议、消息协议、流式事件形状、错误语义

---

## 十、终审三问

上线前，最后问自己三句话：

1. **"它坏掉的时候，我能在 5 分钟内定位到是哪一步、为什么吗？"**
   不能 → 回第 11 章补可观测性。

2. **"它烧掉的钱有硬上限吗？"**
   没有 → 回第 15 章补成本护栏。

3. **"它做错事的时候，有人能拦住它吗？"**
   没有 → 回第 13、14 章补权限和审批。

三问答不上来，就不该上线。
