# 07 · 上下文窗口、定价与缓存

> **这篇要回答**：一次调用到底花多少钱？缓存怎么命中？上下文塞不下的时候，你怎么在请求发出去之前就知道？

---

## 1. 上下文窗口是输入和输出共享的额度

厂商写的 "128K context" 不是说"能塞 128K 进去"，而是**输入和输出加起来不超过 128K**。

这个区别直接决定你该怎么规划：

- **总窗口**（context window）：输入 token + 输出 token 的总额度；
- **有效输入窗口**（effective input window）= 总窗口 − 你打算给输出预留的额度。

```python
@dataclass(frozen=True)
class ContextBudget:
    context_window: int          # 总窗口：输入和输出共享
    reserved_output_tokens: int  # 给输出预留的位置

    @property
    def effective_input_window(self) -> int:
        return self.context_window - self.reserved_output_tokens
```

> **为什么输出必须提前预留**：输出不是"剩下的空间"，是**要占的位**。
> 按 128K 塞满输入，模型只剩几个 token 写答案——症状是
> `finish_reason == "length"`（第 1 章），但根因在输入侧。

**结论：规划上下文按有效输入窗口算，不是按总窗口算。**

---

## 2. 一次调用怎么算钱，输入为什么是大头

账单只有两项：

```
一次调用的成本 = 输入 token / 1e6 × 输入单价 + 输出 token / 1e6 × 输出单价
```

价格按模型档位走（单位：美元 / 每 100 万 token）：

| 档位 | 输入单价 | 输出单价 | 输出/输入 | 典型用途 |
| --- | --- | --- | --- | --- |
| `cheap-small` | 0.15 | 0.60 | 4× | 分类、路由、短抽取 |
| `cheap` | 0.25 | 1.25 | 5× | 改写、摘要、简单问答 |
| `standard` | 2.50 | 10.00 | 4× | 大多数生产任务的默认档 |
| `reasoning` | 3.00 | 15.00 | 5× | 需要长思考的任务（第 5 章） |
| `frontier` | 15.00 | 75.00 | 5× | 最难的推理与代码 |

（数值随厂商调价会变，以官网当日价格为准。）

两个观察：

**输出单价是输入单价的 4–5 倍。** 生成一个 token 要一个一个算，
而"读懂"一整段输入可以并行摊薄。这个差额就是模型的**思考税**。

**但输入输出比通常很悬殊。** 带历史的对话里，每一轮都要重发全部历史：

| 8 轮对话累计 | token 数 | 成本（standard 档） | 占比 |
| --- | --- | --- | --- |
| 输入 | 19200 | 0.0480 美元 | **93.8%** |
| 输出 | 320 | 0.0032 美元 | 6.2% |

输出单价高 4 倍，可输出 token 少 60 倍，两头一算，**输入照样是大头**。

> **所以成本优化的第一杠杆不是"让模型少说话"，是"别把没用的东西塞进上下文"。**
> 第 1 章说过这句，这里给了它数字依据。

## 3. 成本和上下文长度线性，但价格有阶梯

两件事要分开看：

**成本曲线是线性的。** 同一档位内，token 翻倍 → 成本翻倍。没什么魔法，
也没有"长上下文其实更便宜"的弯弯绕。

**单价是有阶梯的。** 厂商按输入长度分档，整个请求按它落进的那一档计价：

| 档 | 输入长度上限 | 输入单价 | 输出单价 |
| --- | --- | --- | --- |
| 1 | 128K | 2.50 | 10.00 |
| 2 | 200K | 5.00 | 15.00 |
| 3 | 更长 | 10.00 | 30.00 |

于是 120K → 140K 这 20K 的跨越，不是贵 17%，而是**贵一倍以上**：

| 输入 | 成本 | 备注 |
| --- | --- | --- |
| 120K | 0.3050 美元 | 第 1 档 |
| 140K | 0.7075 美元 | 第 2 档 |
| 140K（若按第 1 档线性外推） | 0.3558 美元 | 实际多花了近一倍 |

> **踩线是要付钱的。** 上下文预算别贴着档位阈值设计，
> 否则"多塞了 1K"可能意味着账单翻倍。

## 4. 前缀缓存：命中靠的是前缀一模一样

前缀缓存（prompt caching）的规则一句话就能说完：**请求开头的这部分内容和上次完全一样，就按折扣价算。**

"前缀"指每次都一样的那些内容：

- 系统提示（system prompt）
- 工具声明（tools schema）
- 检索到的文档、few-shot 示例

**易变内容必须往后放。** 时间戳、随机 ID、用户这轮的问题——任何在前缀里
插一个变化字符的东西，都会让整段前缀缓存失效。

命中与否可以理解成算一个 key：把前缀内容拼起来哈希，一致就是同一条缓存。

```python
def prefix_key(system_prompt: str, tools: list[dict], documents: str) -> str:
    payload = json.dumps(
        {"system": system_prompt, "tools": tools, "documents": documents},
        ensure_ascii=False, sort_keys=True,
    )
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

同档位下，缓存对账单的影响长这样（前缀 4000 token + 尾巴 2000 token，standard 档）：

| 场景 | 缓存状态 | 前缀部分单价 | 整次输入成本 |
| --- | --- | --- | --- |
| 首次调用（写入） | `miss` | 全价 × 1.25 | 0.0175 美元 |
| 前缀相同再发一次 | `hit` | 全价 × **0.10** | **0.0060 美元** |
| 前缀改了一个字 | `miss` | 全价 × 1.25 | 0.0175 美元 |
| TTL 过期后再发 | `expired` | 全价 × 1.25 | 0.0175 美元 |
| 前缀太短（512 token） | `too_short` | 全价 × 1.00 | 按全价 |

三个必须记住的点：

1. **命中省的是输入单价，输出那部分一分钱不省。** 缓存不缓存你的输出。
2. **前缀变了立刻回落**，而且回落到"写入价"——比不缓存还贵（见下一节）。
3. **有最短长度门槛。** 前缀太短，厂商根本不给缓存，你开了也是白开。

---

## 5. 坑：缓存写入费会让短会话更贵

这是本章最贵的坑：**写入缓存本身要钱，而且比全价还贵**（典型是全价 × 1.25）。

命中时前缀按折扣价（约全价 × 0.10）计费，**折扣省下的钱要靠"多次命中"摊销写入费**。

于是短会话就是纯亏：

| 场景 | 不缓存 | 开缓存 | 结果 |
| --- | --- | --- | --- |
| 只调一次模型 | 0.0180 | 0.0205 | **更贵**（写入费没摊销） |
| 两次调用但中间 TTL 过期 | 0.0360 | 0.0410 | **更贵**（写了两回） |
| 8 轮对话前缀稳定 | 0.1440 | 0.0835 | 便宜得多 |

> **缓存不是免费开关，是一个需要"复用次数"来摊销的投资。**
> 短会话、单次调用、前缀经常变的场景，开缓存只会更贵。
> 判断标准很简单：**这个前缀会被重复用几次？** 一次，就别开。

TTL 也要算进去：缓存过期就不再命中，**下一次又要重新写一遍**。
会话间隔超过 TTL，等于从头再来。

## 6. 可以等的任务，去拿批处理折扣

批处理（batch）接口允许你把请求攒起来一起提交，换取更低的单价——
典型是**在线价格的一半**：

| 方式 | 同量 token 的成本 | 延迟 |
| --- | --- | --- |
| 在线调用 | 0.0580 美元 | 立刻返回 |
| 批处理 | 0.0290 美元 | 明显更久 |

折扣是对输入输出**一视同仁**的，不偏袒某一侧，所以账还算得清。

> **折扣拿延迟换。** 用户正等着看的请求不要走批处理；
> 离线抽取、批量分类、评测集回填这些"反正不着急"的活才是批处理的主场。

## 7. 上下文塞不下时，协议层能给你什么信号

本章只讲**协议层能判断什么**（怎么裁、怎么摘要、怎么外置，是 Agent 侧的上下文工程，
见 `AI/Agent/05-上下文工程：窗口预算与压缩.md`）。

好消息是：不需要等模型报错，请求发出前就能判定。

| 状态 | 判定条件 | 该做什么 |
| --- | --- | --- |
| `fits` | 输入 + 期望输出 ≤ 有效输入窗口 | 放心发 |
| `tight` | 装得进总窗口，但挤占了预留 | 降低期望输出，或先裁上下文 |
| `output_truncated` | 输入 + 期望输出 > 总窗口 | 一定会被截断，必须先裁 |
| `input_overflow` | 输入本身 > 总窗口 | 请求根本发不出去 |

关键在 `tight` 这一档：**它装得进总窗口，但已经超了有效输入窗口**——
也就是"预留不足"的真实代价。这种请求发出去不会报错，
只会安安静静地给你一个被截断的答案（`finish_reason == "length"`）。

> **别等 `length` 才发现。** 协议层提前算一次有效窗口，
> 比事后从截断结果里反推便宜得多。

至于真的塞不下，四条路：**裁剪**（丢旧历史）、**摘要**（压成一段话）、
**外置**（细节存外面，只往上下文里放指针）、**换长上下文模型**（贵，但省工程量）。
选哪条是运行时策略，本章不展开。

## 8. 账单用 usage，不要用估算

**结算一律以响应里的 `usage` 为准。** 原因有两条：

1. **不同厂商的 tokenizer 不同。** 同一段中文，厂商 A 数 24 个 token，
   厂商 B 数 50 个——差一倍多。跨厂商搬运的 token 数不能直接用。
2. **自己的估算只是启发式。** 按"英文 4 字符 1 token、中文 1 字 1 token"
   估出来的数字，偏差轻松到 10% 以上。用它结算，账单和实际对不上。

| 结算依据 | 输入 token | 成本 | 问题 |
| --- | --- | --- | --- |
| `estimate_tokens` 估算 | 33 | 0.000202 | 和真实账单对不上 |
| 响应里的 `usage` | 24 | 0.000180 | **这才是账** |

> **估算只用来事前估大小**（"这个上下文会不会超""大概要多少钱"），
> **结算永远用 usage**。两者不要混用。

## 9. 账单前面有两道闸：预算与限流

成本失控通常不是"某一次调用太贵"，而是**闸门没设**。账单前面有两道闸：

| 闸 | 谁设的 | 管什么 | 超了怎么办 |
| --- | --- | --- | --- |
| **预算** | **你自己** | 总金额 / 单任务金额 | 停止、降级、要求充值 |
| **限流** | **供应商** | 每分钟请求数、每分钟 token 数 | 退避重试、排队 |

两者的分工经常被搞混：

- **预算是你对自己设的红线**——它管的是"这个月不能花超"；
- **限流是供应商设的闸**——它管的是"你现在请求太密了"，和贵不贵无关。

> 一个 0.001 美元的请求也可能被限流拦住；
> 一个 10 美元的请求也可能顺利通过限流、然后被你的预算拦下。
> **两道闸都得留，缺一道就等于没设防。**

限流被拒（429）时的处理在第 1 章讲过：**退避重试**，不要立刻重打。

---

## 一句话结论

> **窗口是输入和输出共享的额度，账单大头在输入那一侧。**
> 成本随上下文线性增长但单价会跳档；缓存只认完全相同的前缀，
> 写入费会让短会话净亏；结算以 `usage` 为准，预算和限流是账单前的两道闸。
