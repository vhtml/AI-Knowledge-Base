# 附录 B · 常见故障排查（协议层）

按**症状**组织。每一节：症状 → 最可能的原因（按概率）→ 怎么确认 → 怎么修。

Agent 运行时层的排查见 [`AI/Agent/附录-C-常见故障排查.md`](../Agent/附录-C-常见故障排查.md)。

---

## 一、请求直接报错

### 症状
HTTP 400 / 422，请求被拒。

### 可能原因

1. **messages 结构错了**——`system` 不在第一位；`tool` 消息缺 `tool_call_id`；
   `assistant` 带 `tool_calls` 但 `content` 不是 `null`。
2. **工具 schema 不合法**——`parameters` 缺 `type: "object"`；字段类型不是合法 JSON Schema 类型。
3. **`response_format` 与 `tools` 冲突**——某些端点不允许同时用。
4. **图片/音频格式不支持**，或超出大小上限。
5. **参数名写错**——SDK 的字段名和文档不一致。

### 怎么确认
**先把请求体完整打印出来**，逐字段对文档。这一步能解决八成的 400。

### 怎么修
本地先校验（第 6 章的 `validate_request` 那套思路）：把能静态检查的都挡在发出去之前。

## 二、模型不调工具 / 调错工具

### 症状
直接回答了，或者调了一个不相关的工具。

### 可能原因

1. **工具描述含糊**——模型只能看到 name / description / parameters。
2. **工具太多**——选择准确率随工具数下降。
3. **`tool_choice` 是 `none`**——有些封装默认不是 `auto`。
4. **系统提示里写了"不要用工具"**这类反向指令。
5. **任务本来就不需要工具**。

### 怎么确认
打印 `tools` 的序列化结果，**以模型视角读一遍**："我凭什么选它？"

### 怎么修
见 `AI/LLM/02-工具调用协议.md` 与 `AI/Agent/03-工具设计：schema、错误面与粒度.md`。

---

## 三、工具调用参数是空的或解析失败

### 症状
`arguments` 是 `"{}"`，或者 `json.loads` 抛异常。

### 可能原因

1. **模型确实没填参数**——schema 里参数是可选的，模型就不填。
2. **参数名和 schema 对不上**——模型用的是自然语言名。
3. **`arguments` 不是合法 JSON**——模型在里面写了注释或尾逗号。
4. **流式下参数是分片的**——没拼接就解析（第 4 章）。

### 怎么确认
打印**原始的 `arguments` 字符串**，不要先 parse 再打印。

### 怎么修
- 必填参数用 `required` 声明；
- 解析失败时保留原文并标记，别静默变成空 dict；
- 流式场景先拼接再解析。

---

## 四、多轮对话后模型"忘了"

### 症状
第 3 轮开始，忘了第 1 轮说过的偏好。

### 可能原因

1. **历史被裁剪掉了**——裁剪策略太激进。
2. **压缩把关键约束压没了**。
3. **关键信息在上下文中段**——权重下降。
4. **拼接历史时漏了 system 消息**。
5. **超了上下文窗口**——被静默截断。**看 `finish_reason` 是不是 `length`**。

### 怎么确认
打印**模型实际收到的** messages 数组。看第 1 条是不是 system，看关键信息在不在。

### 怎么修
见 `AI/Agent/05-上下文工程：窗口预算与压缩.md`。

---

## 五、JSON 解析失败

### 症状
`json.loads` 抛异常，或解析出来是字符串。

### 可能原因

1. **包了 markdown 围栏**。
2. **加了前言废话**。
3. **输出被截断**——`finish_reason == "length"`，JSON 是半截的。
4. **模型用单引号**（JSON 不接受，但模型常犯）。

### 怎么确认
**先看 `finish_reason`**。是 `length` 的话，问题不是 JSON，是输出上限。

### 怎么修
见 `AI/LLM/03-结构化输出.md`：用 `response_format` 而不是靠提示词；
解析端容错；校验失败重试。

## 六、流式输出乱码 / 丢字

### 症状
拼出来的句子缺字、重复，或者顺序乱了。

### 可能原因

1. **用了 `=` 而不是 `+=`**——每个分片覆盖前一个。
2. **把 delta 当成了全量**。
3. **多路并发时把不同请求的分片混在一起**——流式一定要按请求隔离。
4. **服务端推送了非文本分片**（usage 分片、心跳），直接拼进正文。

### 怎么确认
打印前三个分片的 `delta`，看是不是增量。

### 怎么修
见 `AI/LLM/04-流式输出.md`。

---

## 七、成本比预期高

### 症状
账单是预期的几倍。

### 可能原因

1. **输入 token 远大于输出**——带历史的对话是重灾区。
2. **上下文没裁剪**——每轮都带全量历史，轮次一多就是平方增长。
3. **图片 token**——一张大图可能比一整页文字还贵。
4. **推理 token 计入输出**——思考很贵。
5. **缓存没命中**——前缀里有时间戳、随机 ID。
6. **重试风暴**——退避策略写错。

### 怎么确认
按维度拆开看：**输入/输出/图片/思考/缓存未命中**各占多少。

### 怎么修
见 `AI/LLM/07-上下文窗口、定价与缓存.md` 与 `AI/Agent/15-成本与延迟工程.md`。

## 八、换个模型就出 bug

### 症状
同一份代码、同一个提示词，换个模型后结构化输出坏了 / 工具调用格式变了 /
长历史被截断了。

### 可能原因
**这就是"换模型的破坏性变化"**，共六类：

| 变化 | 表现 |
| --- | --- |
| 工具调用格式 | `arguments` 是字符串还是对象 |
| JSON 严格性 | 加废话、不守 schema |
| 上下文长度 | 同样的历史，新模型接受、旧模型截断 |
| 流式事件形状 | 分片粒度、`finish_reason` 出现的时机 |
| 思考字段 | 有的端点不返回 `reasoning` |
| 安全策略 | 同一输入一边通一边被拦 |

### 怎么确认
**跑同一份评测集**——这是唯一的判断依据。

### 怎么修
见 `AI/LLM/08-模型选型与迁移纪律.md`。核心纪律：**版本 pin 死、评测集不动**。

## 九、响应时快时慢

### 症状
同样的请求，有时 0.5 秒，有时 5 秒。

### 可能原因

1. **缓存命中与否**——命中与否价格差好几倍。
2. **负载**——供应商侧的排队。
3. **输入长度**——长上下文的 prefill 明显更慢。
4. **推理模型**——思考时间不可控。
5. **重试**——第一次失败后重试，延迟叠加。

### 怎么确认
看 `usage` 里有没有 `cached_tokens`；把延迟和输入长度画在一张图上——
如果相关，是 prefill；不相关，是供应商侧的负载。

## 十、排查总流程

```
1. 打印完整请求体           ← 跳过这步等于闭眼排查
      ↓
2. 打印完整响应体
      ↓
3. 看 finish_reason         ← length = 被截断；tool_calls = 要调工具
      ↓
4. 看 usage                 ← 输入输出比、缓存命中
      ↓
5. 看模型实际收到的 messages  ← 上下文里有它需要的信息吗
      ↓
6. 换模型重跑一次           ← 是模型的问题还是我的请求的问题
      ↓
7. 同一份评测集跑一遍        ← 是个例还是普遍问题
```

**第 1 步和第 5 步最常被跳过。**
前者让你少猜一半；后者让你从"怀疑模型"转到"检查我发的东西"——
而问题通常就在你发的东西上。
