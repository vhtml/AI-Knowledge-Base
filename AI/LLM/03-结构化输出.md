# 03 · 结构化输出

> **这篇要回答**：怎么让模型稳定输出 JSON？为什么"提示词里请求 JSON"不够？解析失败之后怎么办？

---

## 1. 结构化输出是三段管道，不是一次调用

"让模型输出 JSON"听起来是一句话的事，工程上却是**三段**。少了任何一段，线上都会以奇怪的方式坏掉。

| 层 | 职责 | 失败时的样子 |
| --- | --- | --- |
| **解析层** | 从混杂文本里把 JSON 抠出来 | `json.loads` 抛 `JSONDecodeError` |
| **校验层** | 对着 JSON Schema 检查字段、类型、取值 | 字段名对不上、类型不对、枚举越界 |
| **修复层** | 把错误回给模型让它改，并限制重试次数 | 反复出错，直到预算耗尽 |

三段的顺序不能换：**解析成功 ≠ 符合 schema**。`{"order": "A-1001"}` 是完全合法的 JSON，但它不是你约定的字段名。这类错误不抛异常，只会在下游变成 `KeyError`，或者悄悄变成一个空值——排查难度差一个数量级。

> **坑**：最常见的写法是 `try: data = json.loads(text) except: data = {}`。
> 空的 `dict` 会被下游当成"用户什么都没填"，真正的错误被吞掉，
> 报错离根因十万八千里。**解析失败必须抛异常**，而且异常信息里要带原始输出。

---

## 2. 三条拿到 JSON 的路，可靠性差了一个量级

同一个"要 JSON"的需求，协议上有三种实现方式，成本和可靠性完全不同：

| 方式 | 请求体 | 语法保证 | 字段保证 | 什么时候用 |
| --- | --- | --- | --- | --- |
| **提示词请求** | 只有 `messages` | 无，靠模型听话 | 无 | 端点不支持 `response_format` 时的兜底 |
| **`response_format: json_object`** | `{"type": "json_object"}` | **有**（解码器保证是 JSON） | 无 | 字段少、形状固定、你自己会再校验 |
| **`response_format: json_schema`** | `{"type": "json_schema", ...}` | **有** | **有**（字段名、类型、枚举、封闭集合） | 正式业务抽取，**默认选它** |

约束最强的那种（json_schema）请求体长这样，线上就是这么发出去的：

```json
{"type": "json_schema",
 "json_schema": {
   "name": "order",
   "strict": true,
   "schema": {
     "type": "object",
     "properties": {
       "order_id": {"type": "string"},
       "status": {"type": "string", "enum": ["待付款", "在途", "已发货"]}
     },
     "required": ["order_id", "status"],
     "additionalProperties": false
   }}}
```

注意 `json_object` 形态里**没有 schema**。这不是偷懒，而是它的语义：只保证"吐出来的东西是个 JSON 对象"，字段叫什么、是什么类型，全都不管。而 `json_schema` 形态把 schema 直接写进请求体，服务端在解码时按它约束生成。

---

## 3. 约束解码和提示词请求差在哪：语法合法 ≠ 模型听话

这是本章最核心的一个对比，也是新手最容易混为一谈的地方。

- **提示词请求**：你在 `system` 里写"只输出 JSON"。这是一句**祈使句**，
  模型可能在绝大多数时候照做，但它没有机制保证——它是一个概率行为，
  换模型、换版本、改一句提示词，行为都可能变。
- **约束解码（constrained decoding）**：你在 `response_format` 里声明格式，
  **解码器在每个 token 上按 schema 剪枝**，语法非法的候选根本不会被采样出来。
  这是一个**机制保证**，不随模型心情变化。

所以两者的差距不是"提示词写得好一点"这种程度差，而是：

> 提示词请求：**希望**模型听话。
> `response_format`：**保证**输出是合法的。

再具体一点：`json_object` 保证"是 JSON 对象"，`json_schema` 保证"是符合这份
schema 的 JSON 对象"。**约束得越细，模型能犯的错就越少**——
错得少，就意味着解析层和校验层要干的活少，重试的概率低，成本也就低。

代价是 `strict: true` 通常要求所有字段都列进 `required`（没有"可选字段"），
并且 `additionalProperties` 要设为 `false`。这不是缺陷，是**用灵活性换确定性**：
封闭的字段集意味着模型没法自己发明字段名。

---

## 4. json_object 只保证"是个 JSON 对象"，字段名和类型还得自己管

这一条值得单独拎出来，因为很多人以为 `json_object` 等于"结构化输出"。

用 `json_object` 时，模型完全可以返回 `{"order": "A-1001"}`——语法合法，
JSON 对象没错，但你的代码读 `data["order_id"]` 就直接 `KeyError`。
`json_object` 拦不住这种事。

用 `json_schema` 时，字段名、类型、枚举、取值范围、是否允许额外字段，
全部写进了请求体。模型**不可能**返回 `{"order": ...}`——
那个 key 根本不在 schema 里，解码器不会生成它。

**决策很简单**：

- 只是要"一段能被 `json.loads` 吃掉的内容" → `json_object` 够用；
- 要落到数据库、要进下游接口、要能被业务代码按字段读 → **必须 `json_schema`**；
- 端点不支持 `json_schema` → 退回 `json_object` **并且自己写校验层**，
  别假装它有约束。

---

## 5. 提示词请求为什么一定会翻车

只要还在用提示词请求（或者端点只支持 `json_object`，模型仍可能"多说一句"），
就要预期这三种形态：

| 形态 | 模型输出长什么样 | 为什么会发生 |
| --- | --- | --- |
| **markdown 围栏** | ` ```json\n{...}\n``` ` | 模型把"输出 JSON"理解成"展示一段 JSON 代码" |
| **前言废话** | `好的，结果如下：\n{...}` | 助手人格让它先寒暄一句 |
| **半截 JSON** | `{"order_id": "A-1` | 撞到 `max_tokens` 上限，输出被截断 |

第三种最阴险，因为它**不抛异常也不会被察觉**——如果你只做 `json.loads`，
它会抛 `JSONDecodeError`；但如果你写了容错逻辑（比如"取第一个 `{` 到最后一个 `}`"），
半截 JSON 就会被悄悄吃掉或者切错。

> **诊断规则**：`finish_reason == "length"` 时，先怀疑输出上限，再怀疑 schema 太复杂。
> 这个字段（第 1 章说过）是最容易被丢掉、也最该保留的——
> 它是"输出被截断"的**唯一**明确信号。

另外，截断的 JSON 可以从**结构字符有没有闭合**上看出来：括号没配平、
字符串没闭合，都是"说到一半被掐断"的特征。逐字符扫比数括号个数可靠，
因为 JSON 字符串内部可能出现括号（`{"note": "a)b"}`）。

---

## 6. 解析层要容错，但抠不出来必须报清楚

解析层的职责是**从模型的自然语言外壳里把 JSON 剥出来**。至少要能处理三种形态：
裸 JSON、markdown 围栏、带前言的文本。

```python
def parse_model_json(text: str, finish_reason: str = "stop") -> dict:
    try:
        return extract_json(text)          # 围栏、前言、裸 JSON 都能抠
    except ValueError as exc:
        truncated = looks_truncated(text)  # 结构字符没闭合 = 说到一半被掐断
        hint = "疑似被截断" if truncated else "找不到 JSON"
        raise StructuredOutputError(
            f"{hint}（finish_reason={finish_reason}）；原始输出：{text[:200]!r}"
        ) from exc
```

三条设计要点：

1. **容错是必要的**：模型输出是概率产物，围栏和前言不是 bug。
2. **报错要能定位**：异常里必须有**原始输出片段**和 `finish_reason`，
   否则排查时你根本不知道模型说了什么。
3. **失败要抛异常**：不抛异常而是返回 `None`/空 `dict`，
   等于把"模型没听话"这个事实伪装成"没有数据"。

---

## 7. 校验层要能指出"哪个字段错了"

校验层的价值不在于"对或错"，在于**错的时候能说出哪儿错了**。
一句"格式不对"会让你重跑一遍；一句"`$.items[0].qty`: 期望 integer，实际 str"
让你直接改代码。

| 错误类型 | 报错长什么样 | 根因 | 怎么修 |
| --- | --- | --- | --- |
| **缺必填字段** | `$.order_id: 缺少必填字段` | 模型漏抽了 | 回灌错误让模型补 |
| **类型不对** | `$.amount: 期望 number，实际 str` | 模型把数字写成了字符串 | 回灌错误；schema 里写清描述 |
| **额外字段** | `$.coupon: 不允许的额外字段` | 模型自己加料 | `additionalProperties: false` + 封闭 schema |
| **枚举非法** | `$.status: 值 '已签收' 不在允许的取值 [...] 里` | 词表和业务对不上 | 扩充 `enum`，或改成分类任务 |
| **数值越界** | `$.amount: 999999 大于最大值 100000` | 领域约束没写 | 补 `minimum` / `maximum` |
| **数组元素类型错** | `$.items[0].qty: 期望 integer，实际 str` | 数组元素 schema 没约束全 | 把 `items` 的 schema 写完整 |

路径要能精确到**数组下标**（`$.items[0].qty` 而不是 `$.qty`）——
嵌套结构里，"哪个字段"这句话本身就是排查效率的一半。

校验通过和不通过，**返回的东西必须不一样**：通过返回 `data`，
不通过返回**错误列表**，绝不返回"一份看起来像数据的东西"。
本章的实验里，这条差异是被断言直接卡住的。

---

## 8. 修复重试：把错误回给模型，比自己猜靠谱

校验失败之后有两条路：自己补默认值，或者把错误回给模型让它改。
**默认选后者**。你补的默认值是猜测，模型改的是它自己的理解，
后者才可能真的对上。

```python
def repair_instruction(errors: list[str]) -> str:
    """只说"哪里错了"，不说"你应该怎么改"。"""
    lines = "\n".join(f"- {e}" for e in errors)
    return (
        "上一次输出没有通过校验，请只输出修正后的 JSON，不要加任何解释。\n"
        f"需要修正的问题：\n{lines}"
    )
```

关键在于**只回灌事实，不回灌猜测**。你说"金额改成 128.5"，模型会照抄；
你说"`$.amount` 不是 number"，模型得自己判断该怎么改。
前者把模型的推理能力关掉了，后者才是把它用上。

回灌的内容通常包括三样：模型上一次的原话（让它能对照着改）、
校验错误列表、以及"只输出 JSON，不要解释"的硬要求。

**但重试必须有上限。** 每一次重试都是一次完整的模型调用，
输入 token 还要把上一轮的输出和错误一起带上——所以重试一次的成本
通常是单次的 2.5 倍左右（本章实验里有实测数字）。
没有上限的重试循环等于一张无限额的发票：**3 次还不对，就该停下来报错**，
而不是继续烧钱，或者更糟——把一个错的结果当对的用下去。

## 9. schema 不是越详细越好，复杂了就拆成两次调用

`json_schema` 能约束得很细，但**模型一次生成对的概率会随复杂度下降**。
嵌套三层以上、字段一多，模型就要在一次生成里同时记住结构、填对值、
保持类型一致——出错的概率明显上升，而每次出错都要付一次重试的钱。

所以判断标准是：**一次生成对不了，就拆成多次调用**。

| 复杂度 | 表现 | 做法 |
| --- | --- | --- |
| 字段少、层级浅（≤2 层） | 一次基本就对 | 一次调用，`json_schema` + 校验兜底 |
| 层级深（3 层以上） | 错字段名、漏嵌套 | 拆成"先抽骨架、再抽细节"两次调用 |
| 字段特别多（十几个以上） | 频繁漏字段 | 按语义分组，分几次抽 |

拆调用不是把一个大 schema 切成两半，而是**按语义分层**：第一遍抽订单号和
商品名（扁平，一次就对），第二遍再针对每个商品抽规格和价格。
每次调用的 schema 都在预算内，成功率自然上去。

**同样的分步思想也回答了"什么时候用工具而不是结构化输出"**：

| | 结构化输出 | 工具调用 |
| --- | --- | --- |
| 模型的处境 | **填空**：字段已经定死，照着填 | **选择**：从你给的几个动作里挑一个 |
| 典型场景 | 从文本里抽订单、分类、填槽位 | 查订单、查天气、发消息、调用 API |
| 成本 | 一次调用 | 通常两轮（模型 → 你执行 → 回填） |
| 扩展性 | 加字段要改 schema | 加工具即可，模型自己选 |

一句话：**需要模型"做选择"就用工具，需要模型"填空"就用结构化输出**。
想要"模型自己决定调哪个工具"，给工具；想让模型把已知形状的数据填进来，
给 schema。两者经常一起用：先让模型选工具，工具返回后再用结构化输出抽取。

---

## 一句话结论

> **"提示词里请求 JSON"是许愿，`response_format` 才是合同。**
> 合同保证语法，schema 保证字段，解析层负责容错，
> 校验层负责说清"哪个字段错了"，修复层负责把错误回给模型——
> 而重试必须封顶，因为每一次重试都是真金白银。
