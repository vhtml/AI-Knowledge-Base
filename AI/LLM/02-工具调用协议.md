# 02 · 工具调用协议

> **这篇要回答**：模型调工具的完整协议长什么样？`tool_choice` 有哪些模式、并行调用怎么表达、调用结果怎么回填？

---

## 1. 工具调用是三段协议，不是一次调用

最容易踩的认知误区是：**"模型帮我执行了函数"**。

模型没有执行任何东西。它做的是：读你给的工具说明书，交回一份**调用意图**，
然后停下。真正执行函数的是你的代码。

```
第 1 次请求  →  你：tools 声明（模型看到说明书）
第 1 次响应  →  模型：tool_calls（调用意图，带 id）
第 2 次请求  →  你：role="tool" 消息（你执行完工具，把结果回填）
第 2 次响应  →  模型：最终回答
```

| 段 | 在哪一侧 | 关键字段 | 谁写的 |
| --- | --- | --- | --- |
| 声明 | 请求 | `tools` | 你 |
| 调用意图 | 响应 | `tool_calls` | 模型 |
| 结果回填 | 请求 | `role="tool"` + `tool_call_id` | 你 |

三段缺一段，模型都拿不到最终答案：

- **只声明不回填**：模型给出调用意图后就停了，你以为它在思考，其实它在等你。
- **只回填不回声明**：模型压根不知道有这个工具。
- **回填了但 id 对不上**：模型收到了结果，却不知道这是哪个工具的结果。

还有一个容易被忽略的推论：**一轮工具调用 = 两次模型请求**。
工具执行本身不花钱（是你的代码在跑），但模型被叫了两遍，
两次的输入 token 都要算钱。

---

## 2. 请求侧：tools 声明是模型唯一的说明书

模型看不见你的函数体。它能看到的只有 `name`、`description`、`parameters`
这三样东西——**它们就是工具的全部说明书**。

```json
{
  "model": "some-model",
  "messages": [{"role": "user", "content": "订单 A-1001 到哪了"}],
  "tools": [{
    "type": "function",
    "function": {
      "name": "查订单",
      "description": "按订单号查询订单状态与物流轨迹",
      "parameters": {
        "type": "object",
        "properties": {"order_id": {"type": "string", "description": "订单号，形如 A-1001"}},
        "required": ["order_id"]
      }
    }
  }],
  "tool_choice": "auto"
}
```

三个字段各自的作用：

| 字段 | 模型拿它干什么 | 写砸了的症状 |
| --- | --- | --- |
| `name` | 决定调哪个函数 | 名字含糊 → 选错工具 |
| `description` | 决定**什么时候**该用它 | 描述含糊 → 该调的不调，不该调的乱调 |
| `parameters` | 决定**怎么填参数** | 字段说明缺失 → 参数填错 |

`parameters` 是一份 **JSON Schema**，`required` 写清楚哪些字段必须有。
这里有个硬约束：模型填出来的参数只能来自 `properties` 里声明的字段，
你后面想读一个没声明的字段，读到的只会是空值。

**工具名不要带空格、不要用中文标点**——它是后续流程里的标识符，
不是给人看的展示名。

---

## 3. 响应侧：tool_calls 是调用意图，不是执行结果

模型决定调工具时，响应长这样：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [{
    "id": "call_abc123",
    "type": "function",
    "function": {"name": "查订单", "arguments": "{\"order_id\": \"A-1001\"}"}
  }]
}
```

四个字段，四个作用：

| 字段 | 含义 | 写错/用错的后果 |
| --- | --- | --- |
| `id` | 本次调用的唯一标识 | 回填时对不上 → 结果错配 |
| `type` | 固定是 `"function"` | 一般不变，扩展类型时才有区别 |
| `function.name` | 要调哪个工具 | 未声明 → 幻觉工具 |
| `function.arguments` | **JSON 字符串**，不是 dict | 直接当 dict 用会 `TypeError` |

两个必须记住的细节：

1. **`arguments` 是字符串**。`{"order_id": "A-1001"}` 外面还包了一层引号，
   因为它自己是一个 JSON 值。你要先 `json.loads` 才能拿到 dict。
   很多 SDK 帮你做了这一步，但线上协议是字符串——自己解析时别忘了。
2. **`content` 是 `null`**，不是空字符串。它表示"这一轮我说话的部分为空，
   全部内容在 `tool_calls` 里"。

另外，`finish_reason` 这次的值是 **`"tool_calls"`**。
它的含义不是"结束了"，而是"**我还要调工具，所以先停在这里**"。
看到它就要去执行工具，而不是把这一轮当成最终答案。
（反过来不能只信它：有些网关会把它写成 `stop`，
判据应当是 `tool_calls` 是否非空。）

---

## 4. tool_choice 的四种模式：把"要不要调"变成可控的

`tool_choice` 决定模型"能不能调、要不要调、必须调哪个"。四种模式：

| 模式 | 请求里怎么写 | 模型的行为 | 什么时候用 |
| --- | --- | --- | --- |
| `auto` | `"auto"`（默认值） | 自己决定调不调 | 工具多、意图不明确 |
| `none` | `"none"` | **禁止**调用，只能文本回答 | 只要一段摘要、避免误触副作用 |
| `required` | `"required"` | **必须**调用某个工具 | 必须从数据里抽取结果 |
| 指定函数 | `{"type": "function", "function": {"name": "查订单"}}` | **强制**调这一个 | 确定性路由、兜底 |

几点补充：

- 不写 `tool_choice` 就等价于 `auto`。很多 SDK 在传了 `tools` 时会自动补上 `"auto"`。
- `none` 不是"不传 tools"。真正禁止调用要显式写 `none`；
  不传 `tools` 的效果是模型压根不知道有工具，两回事。
- `required` 只保证"**发生了调用**"，**不保证参数对**。
  想要参数也稳，得靠 schema 和事后校验。
- 指定函数模式是"经典函数调用"的形态，很多只实现了这一种的老接口就靠它。
  它也是做**确定性路由**最省事的办法：不跟模型商量，直接告诉它调哪个。

### 什么时候该用 `required`

典型场景是"从一段结构化数据里抽取结果"。
这时候与其在提示词里写"请返回一个 JSON"，不如直接上 `tool_choice="required"`：

- "请返回一个 JSON" 是在**赌模型听话**——它可能包一层 Markdown 代码围栏，
  可能先说一句"好的，结果是"，可能干脆给出一段散文。
- `tool_choice="required"` 是**协议层的硬约束**——模型必然交回一次调用，
  参数由 schema 规定，形状是确定的。

这就是"约束解码"和"提示词请求"的可靠性差距。
两者不是一回事：前者改的是**生成的合法空间**，后者改的是**模型的倾向**。
需要稳定抽取时，把力气花在约束上，不要花在措辞上。

## 5. 并行调用：一条消息多个 tool_calls，结果一条条对齐

一条 assistant 消息里可以有**多个** `tool_calls`——模型一口气要调好几个工具，
比如"查订单"和"查天气"互不依赖。

对应地，**每个 `tool_calls` 都要各自回填成一条 tool 消息**：

```
assistant  tool_calls=[call_a, call_b]
tool       tool_call_id=call_a   content=订单已发货
tool       tool_call_id=call_b   content=杭州晴 26℃
```

规则三条：

1. **条数对得上**：两个 `tool_calls` 就要两条 tool 消息。少一条，模型会一直等。
2. **id 逐条对上**：每条 tool 消息的 `tool_call_id` 要等于对应那次调用的 `id`。
3. **配对靠 id，不靠顺序**：执行器返回结果的顺序不固定。
   按"第 N 个结果配第 N 个调用"回填，一定会在并行时错位——
   订单的结果会挂到天气工具名下，而模型无从察觉。

还有一个前提：**并行的工具之间不能有依赖**。
"先查用户，再按查到的 user_id 查订单"必须串行成两轮，
因为第二轮的参数依赖第一轮的结果。

## 6. arguments 解析失败：必须留痕，不能静默变成空 dict

`arguments` 是字符串，所以有解析这一步。而解析**会失败**——
模型可能吐出尾随逗号、可能吐了 JSON 片段、可能吐了带前后缀的散文。

```python
def parse_arguments(raw: str) -> ParsedArguments:
    try:
        value = json.loads(raw)
    except json.JSONDecodeError as exc:
        return ParsedArguments(ok=False, data={}, raw=raw, error=exc.msg)
    if not isinstance(value, dict):
        return ParsedArguments(ok=False, data={}, raw=raw, error="顶层不是对象")
    return ParsedArguments(ok=True, data=value, raw=raw)
```

**失败时为什么不能静默变成空 dict？** 因为空 dict 和"用户没填参数"
长得一模一样。工具会拿着空参数跑完全程，报出一个
"缺少必填字段 order_id"的错，而真正的故障——模型吐了非法 JSON——
被彻底吞掉了。你会查 schema、查提示词、查参数名，永远查不到那一行。

所以失败时的正确姿势是**留痕**：

- 保留**原文**（`raw`），模型到底吐了什么，要能打印出来；
- 标记**失败**（`ok=False` + `error`），让调用方走"重试或报错"的分支；
- 绝不用空 dict 冒充成功。

顺带两个边界：

- **空字符串是合法的空对象**。无参工具经常返回 `""`，那是"没有参数"，
  不是"解析失败"。
- **顶层不是对象也是失败**。`"A-1001"` 能被 `json.loads` 解析，
  但它不是参数对象。

## 7. 工具数量与 strict schema：schema 每轮重发，强约束靠 strict

### 7.1 工具数量是有代价的

`tools` 声明**每一轮都要重发**。一个工具的 schema 写一百字，
二十个工具就是两千字，每一轮对话都在为它付输入 token。
实测感很直接：8 个工具的声明常常比整段对话还长。

更糟的是**选择准确率会随着工具变多而下降**——功能相近的工具会互相干扰，
"查订单"和"查物流"同时在场时，模型选错的概率明显上升。

所以工具不是越多越好。**按需声明**（这一轮用不到就不发）是更划算的做法，
代价是你得自己管"当前该开哪些工具"这件事。

### 7.2 strict schema 是协议层的硬约束

普通 schema 只是**给模型的建议**：它说"这里应该有个 order_id"，
但模型可以少填、可以多填、可以填错，你要等事后校验才知道。

`strict` 模式改的是**生成的合法空间**——模型在解码阶段就不可能吐出非法结果。
代价是两条硬约束：

| | 普通 schema | strict schema |
| --- | --- | --- |
| 参数不合法 | 事后校验才发现 | 生成时就合法 |
| 可选字段 | 直接从 `required` 里省掉 | 得写成 `nullable` |
| 额外字段 | 可能出现 | 必须显式禁止 |
| 字段缺失 | 允许 | 不允许 |

要用 strict，两件事必须做到：`additionalProperties: false`，
以及**所有字段都进 `required`**——真正可选的字段用 `nullable` 表达，
而不是从 `required` 里删掉。

选型上：**参数固定、必填项多、错误代价高**的抽取任务用 strict；
探索性的、字段还会变的场景用普通 schema，因为 strict 的改动成本更高。

## 8. 协议层的四个坑

按踩中频率排序：

1. **tool 消息缺 `tool_call_id`**。模型收到一条"某工具的结果"，
   却不知道是哪个工具的。现象是它反复追问、或者把结果安到错的工具上。
2. **多结果对应错位**。并行调用时按顺序回填。现象是结果看着"有内容"，
   但内容属于别的工具——最隐蔽的一类，因为不报错。
3. **模型返回了没声明的工具**。模型偶尔会"发明"一个函数名。
   必须在执行前校验工具名，并把**当前可用工具清单**一起写进错误信息，
   否则排查的人只能回头翻代码才知道该改成啥。
4. **arguments 里的 JSON 非法**。见第 6 节：保留原文 + 标记，别静默吞掉。

这四个坑有一个共同点：**都在"模型说完了"之后才暴露**，
都在你的代码执行到一半时才炸。它们的代价不是一次报错，
而是一次你查不到根因的排查。

---

## 一句话结论

> **模型不执行你的函数，它只交回一份带 id 的调用意图。**
> 声明在请求侧、对齐靠 `tool_call_id`、失败要留痕——
> 这三段都做对了，工具才真的能用。
