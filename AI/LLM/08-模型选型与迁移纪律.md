# 08 · 模型选型与迁移纪律

> **这篇要回答**：怎么给一个任务选模型？换模型要重测哪些东西？什么规矩能防止"升个版本就出事故"？

---

## 1. 选型不是"挑最强的"，是"挑够用的"

模型选型最常见的三个误区：

- **默认用最强的档**——"贵的模型总不会错"。结果是一张账单在替你做无用功：
  80% 的请求是分类和抽取，却全部按最贵档计费。
- **只看价格**——"便宜的够用了"。结果是在最难的那类任务上悄悄掉质量，
  而掉质量的地方往往正是最贵的那部分请求。
- **抄排行榜**——"公开榜第一就是最好的"。结果是把别人的任务分布当成了自己的。

正确的姿势是**先给任务定难度，再给任务配档位**。模型档位是资源，
不是信仰：同一份代码里同时跑着三四个档位，是正常状态，不是浪费。

本章的实验把这件事变成可执行的：给定任务画像，选出的档位是确定的；
分流后的总成本、成功率都是算出来的，不是估的。

---

## 2. 三维矩阵：能力、延迟、成本缺一不可

只看一个维度就会选错。三个维度各自回答一个不同的问题：

- **能力**——这个档位能不能稳定完成这类任务；
- **延迟**——首字延迟（TTFT）能不能扛住交互场景；
- **成本**——按这个档位的量级，账单长什么样。

| 档位 | 能力分 | 输入/输出单价（$/1M token） | 折算单价 | TTFT | 适合的任务 |
| --- | --- | --- | --- | --- | --- |
| `cheap-small` | 2 | 0.15 / 0.60 | 0.24 | ~250ms | 分类、路由、短抽取 |
| `cheap` | 3 | 0.25 / 1.25 | 0.45 | ~400ms | 抽取、改写、摘要 |
| `standard` | 4 | 2.50 / 10.00 | 4.00 | ~800ms | 常规问答、工具调用 |
| `frontier` | 5 | 15.00 / 75.00 | 27.00 | ~1500ms | 多步推理、复杂代码 |
| `reasoning` | 5 | 3.00 / 15.00 | 5.40 | ~2500ms | 长程规划、需要思考预算 |

（价格随厂商调价变动，以官网当日价格为准；折算单价按输入:输出 = 4:1 折算，
第 7 章给过这个比例的推导。）

三个必须注意的地方：

1. **能力分和价格不是线性对应的。** `reasoning` 和 `frontier` 能力同级，
   价格差 5 倍——差别在"要不要思考预算"这件事上，不在通用能力上。
2. **贵的档位不一定更快。** `reasoning` 的 TTFT 是所有档里最高的，
   因为它要先想再答。交互式场景用推理档，用户先看到的是等待。
3. **`frontier` 是 `cheap` 的 60 倍。** 给只需要 3 分能力的抽取任务用 `frontier`，
   就是为同样的效果付 60 倍的钱。

> **选型的默认答案是 `standard`，不是最强的。**
> 需要更强时要有具体理由（评测集上的质量差距），而不是"以防万一"。

## 3. 任务难度决定档位：能用便宜档就别用贵档

把"任务"翻译成"需要多少能力"，档位就定了。这张表是可以直接照抄的：

| 任务类型 | 需要的档位能力 | 落到哪档 | 例子 |
| --- | --- | --- | --- |
| 分类 / 路由 | 2 | `cheap-small` | 意图识别、请求分流 |
| 抽取 / 改写 | 3 | `cheap` | 从工单取订单号、口语改写成工单 |
| 常规问答 / 工具调用 | 4 | `standard` | 知识问答、查订单、调外部 API |
| 多步推理 | 5 | `frontier` | 多条件约束下的计算、排错 |
| 长程规划 | 5 + 思考预算 | `reasoning` | 任务分解、方案取舍 |

规则只有两条，代码也只有两行：

```python
def select_tier(task: TaskType) -> str:
    if task.needs_thinking_budget:
        return "reasoning"
    for tier in CAPABILITY_ORDER:      # cheap-small → cheap → standard → frontier
        if TIERS[tier].capability >= task.required_capability:
            return tier
    return "frontier"
```

注意第二条规则的措辞：**能力够用的最便宜档位**，不是"最好的那个"。
实验里对每一类任务都断言了这一点——如果还有更便宜的档位能力也够，
选型就判错。这条约束是防止"顺手升档"的主要抓手。

## 4. 分级路由：分流是省钱，不是赌质量

任务分档之后，路由就是一次成本优化：让每一类请求走它该走的档位。

但**分流的前提是便宜档在它负责的任务上质量不掉**。所以路由的判据不是
"平均便宜了多少"，而是两个条件同时成立：

| 条件 | 判据 | 不成立怎么办 |
| --- | --- | --- |
| 成本下降 | 分流后总成本 < 全走标准档 | 路由没意义 |
| 质量不掉 | 便宜档在它负责的任务上，成功率 ≥ 标准档 | 把那类任务放回标准档 |

实验里的一组流量（1038 条请求，分 5 类任务）：

| 方案 | 总成本 | 加权成功率 |
| --- | --- | --- |
| 全走标准档 | 3.4005 美元 | 0.973 |
| 分级路由 | **2.2409 美元**（降 34.1%） | **0.975**（不降反升） |

成功率不降反升，是因为最难的那部分（多步推理）被换到了更强的档位。
**路由不是把任务整体降级，是把预算花在刀刃上。**

还有一个容易忽略的结论：**贵档那一小撮请求才是账单的大头**。
实验里多步推理只占 0.8% 的请求，却占了 26.8% 的成本。
所以优化账单时，先看清"钱花在哪儿"，再决定要不要动流量结构。

> 分级路由在 Agent 运行时的完整形态（路由决策本身的成本、临界点怎么算）
> 见 `AI/Agent/15-成本与延迟工程.md`。本章讲的是**协议层怎么实现**：
> 怎么把一条请求判到一个档位上去。

## 5. 坑：换模型后 JSON 严格性变了，结构化输出直接坏掉

这是本章最容易在生产上炸掉的一处，因为**提示词一个字没改**。

同一份 schema、同一条提示词：

````
模型 A：{"city":"杭州","days":3}
模型 B：好的，结果如下：
        ```json
        {"city":"杭州","days":3}
        ```
        还需要别的城市随时告诉我。
````

```python
json.loads(text_a)             # 通过
json.loads(text_b)             # JSONDecodeError —— 换个模型就坏
extract_json(text_b)           # 容错解析能救回来，但必须显式容错
validate_against_schema(...)   # 校验：能 parse 不代表符合 schema
```

两句话要分清：

- **A 模型是"能用"不是"好"。** 它没有废话，但它的输出同样要过校验——
  第 3 章讲过，`additionalProperties: false` 的 schema 下面，
  多一个 `confidence` 字段就该判失败。**能 parse 不等于符合 schema。**
- **B 模型不是"坏了"，是"不严格"。** 换模型之后，解析端必须容错：
  先抠 JSON，再校验，校验失败按第 3 章的策略重试。

> **纪律：结构化输出的成功率是模型的一项指标。**
> 迁移时必须统计"校验通过率"，而不是只看"看起来对不对"。
> 换模型之后这个数字从 99% 掉到 70% 是完全可能的——而线上看到的现象是
> "偶尔解析失败"，很难联想到是换了模型。

## 6. 换模型会破坏什么：七类必须重测的行为

换模型不是"换个字符串"。同一份代码、同一份提示词，行为可能在七个地方变：

| # | 破坏性变化 | 具体表现 | 怎么测 |
| --- | --- | --- | --- |
| 1 | **工具调用格式** | `arguments` 从 JSON 字符串变成已解析的对象；字段名 `arguments` → `parameters` | 重跑工具调用用例，确认解析端两种形状都能吃 |
| 2 | **JSON 严格性** | 严格遵守 schema 的模型换成会加围栏、加废话的 | 重跑全部结构化输出用例，统计校验通过率 |
| 3 | **上下文长度** | 同样长的历史，新模型接受，旧模型直接 400 | 用历史最长那条用例重跑 |
| 4 | **流式事件形状** | 分片粒度（逐字 / 整块）、`finish_reason` 出现的时机都不同 | 重跑流式用例，确认拼接器对两种形状都成立 |
| 5 | **思考字段** | 有的端点根本不返回 `reasoning` | 重跑思考预算用例，确认解析端能容忍字段缺失 |
| 6 | **错误码与限流** | 限流从 429 变成 503，错误体结构也换了 | 重跑错误分类用例，确认退避策略覆盖新状态码 |
| 7 | **安全策略** | 内容过滤严不严不同，同一个输入可能一边通一边被拦 | 用曾经被拦过的输入重跑，确认拦截口径没变 |

第 1 类和第 4 类最阴险：**它们不报错，只是静悄悄地给出错误结果**。
工具参数从字符串变成对象时，`json.loads` 抛 `TypeError` 还算好事——
真正糟的是那种"只读最后一片"的流式消费代码换个模型就把正文丢了。

所以这张清单不能被压缩成"重新跑一遍测试"。每一类对应**一次独立的重测**，
每一项都要有数字。实验里把清单做成了可执行的函数：给两份"模型行为画像"
做差集，能逐项检出上面七类变化；画像没变时保持安静——不误报才有资格当闸门。

## 7. 迁移纪律：五条规矩

清单是"要测什么"，纪律是"怎么测才不翻车"。五条：

| 规矩 | 具体做法 | 防的是什么 |
| --- | --- | --- |
| **版本 pin 死** | 生产写 `vendor-x-2025-03-01`，不写 `latest` | 半夜行为漂移，事后查不出是谁改的 |
| **评测集不许动** | 迁移前后跑同一份评测集，同一个指纹 | 分数虚高，决策建立在两把不同的尺子上 |
| **影子流量** | 新旧模型并跑同一批真实请求，比对输出 | 上线才发现坏，用户先看到 |
| **灰度放量** | 按比例放，盯成功率与成本 | 全量翻车 |
| **一键回滚** | 配置改一个值就能切回旧版本 | 止损时间以小时计 |

其中两条最容易被违反，也最贵：

**版本 pin 死。** `latest` 意味着今天的请求和昨天的请求可能落在不同的模型上，
而你的评测集是三天前跑的。请求体里的 `model` 必须是**构造时定下的常量**：
升级意味着新建一个客户端对象，旧客户端不受任何影响——版本切换必须是一个
显式动作，而不是某天早上自动发生的事。

**评测集不许动。** 迁移前后分数要可比，前提是尺子没变。实验里演示了这个反例：
把模型答不对的两条难例从评测集里删掉，**模型一点没变**，分数从 0.846 变成 1.000。
所以评测集要带指纹（用例 id + 期望值的哈希），指纹一变就说明分数不可比。

**影子流量怎么判**：并跑同一批真实请求，逐条比对输出，分歧率超过**事先定好的**
阈值就不许放量。阈值必须提前定——事后再定阈值就变成了找理由。

## 8. 选型不是一次性的：定期复评，别信排行榜

模型能力、价格、上下文长度都在变。今天 `standard` 档够用，两个月后
新出的便宜档可能已经把抽取任务做得更好；也可能昨天 `frontier` 才有的能力，
今天 `standard` 档就有了。所以选型是一次**带复评节奏**的决策，不是一次性动作。

两件必须定期做的事：

1. **价格表复评。** 价格一漂移，选型矩阵的结论就可能翻盘——原来值得用
   `frontier` 的任务，现在可能用 `cheap` 就够；反过来也可能。
2. **能力复评。** 新模型、新版本进来时，跑一遍自己的评测集，看它是不是
   在你的任务分布上更好。评测集就是为此存在的。

至于公开榜单：**它的任务分布不是你的任务分布**。
公开榜的第一名在自己的评测集上可能排第二甚至更后。实验里给了这么一组数：
公开榜第一 `model-A`（0.95）在自有评测集上只有 0.72，而公开榜第二的 `model-B`
在自有评测集上是 0.88，反而是自己评测里的第一。**榜单可以用来认识候选模型，
不能用来做决策。**

---

## 一句话结论

> **选型是"任务难度 → 档位"的映射，迁移是"同一份评测集 + 七类重测"的流程。**
> 版本 pin 死、评测集不许动、影子流量并跑、灰度放量、一键回滚——
> 这五条规矩挡住的是绝大多数"升个版本就出事故"。
> 而榜单不能替你选模型：只有你自己的评测集能。
