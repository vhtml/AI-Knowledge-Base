# 05 · 推理模型与思考预算

> **篇要回答**：推理模型什么时候值得用？思考预算怎么配？为什么推理模型常常**不适合**放在工具调用链路上？

---

## 1. 推理模型多出来的那一段

普通模型的响应是一段内容。推理模型的响应是**两段**：

```
[思考] 用户问 17×23，先算 17×20=340，17×3=51，340+51=391。验算：17×23=391 ✓
[回答] 391
```

两段的差别不只是"多了一段字"：

| | 普通模型 | 推理模型 |
| --- | --- | --- |
| 输出结构 | `content` | `reasoning` + `content` |
| 首字延迟 | 短 | **长**——要先把思考写完 |
| 输出 token | 少 | 多，且**思考部分计入输出计费** |
| 适合的任务 | 抽取、分类、改写、简单问答 | 多步推理、复杂规划、调试 |
| 工具调用 | 干脆 | **容易打转**（见第 4 节） |

---

## 2. 思考预算

推理模型允许你限制它能花多少 token 思考。预算的取值形态各家不同，
概念上分三档：

| 档位 | 适合 | 成本 |
| --- | --- | --- |
| **低** | 简单推理、几乎不需要想的 | 低 |
| **中** | 需要两三步推导 | 中 |
| **高** | 长链条推理、搜索式问题 | 高 |

**预算不是"越多越好"。**

思考 token 是**按输出价计费**的。一个思考预算拉满的推理调用，
单次成本可能是同档普通模型的 5–10 倍。

---

## 3. 什么时候**不该**用推理模型

这四类任务用推理模型是纯浪费：

1. **抽取**——从文本里取字段，规则和普通模型都够；
2. **分类**——意图识别、路由判定；
3. **简单改写**——翻译、润色、格式转换；
4. **工具调用密集的链路**（见第 4 节）。

判断依据一句话：**如果正确答案不需要超过两三步推导，就别开推理。**

---

## 4. 推理模型与工具调用的张力

这是本章最重要的一条。

推理模型的工作方式是"想清楚再动"。放进 Agent 循环里：

```
模型思考 2000 token → 调工具 → 拿到结果 → 模型重新思考 2000 token → 再调工具 → …
```

每轮都要重新思考一次，**多轮工具调用 = 多倍推理 token**。

更麻烦的是，工具结果常常**推翻**模型之前的推理，于是它要重新想——
想得更长。

于是出现了这个反直觉现象：

> **在工具调用链路上开推理，成本涨得比成功率涨得快。**

| 场景 | 普通模型 | 推理模型 |
| --- | --- | --- |
| 单轮复杂推理 | 准确率低 | **准确率高很多** ✅ |
| 三轮工具调用 | 准确率 X | 准确率只高一点，成本翻倍 ❌ |
| 高延迟要求 | ✅ | ❌ 首字延迟翻倍 |

> **一条纪律**：**推理预算留给"模型自己想"的任务，不要留给"模型反复试"的链路。**
> 如果你的 Agent 链路工具调用多，要么关掉推理，要么把推理放到链路之前的规划步骤里
> （第 7 章的"计划-执行-重规划"模式：规划那一步用推理模型，执行那几步用普通模型）。

---

## 5. 思考内容要不要回填给模型

推理模型的 `reasoning` 字段是**可以**放进下一轮上下文的。但多数时候**不该放**：

| 放进去 | 不放进去 |
| --- | --- |
| 模型能看到自己上一步为什么那么想 | 上下文更短、更便宜 |
| 有时能自我修正 | 上一轮的错推理不会被后续当成"已经想过的结论" |
| | 避免思考里的假设被当成事实 |

**默认不回填。** 除非你有明确的理由——比如让模型检查自己上一步的推理是否成立
（这属于第 8 章"反思"，但反思的对象是**结果**而不是思考过程）。

> 一个坑：把思考内容回填之后，下一轮模型很可能**沿着上一步的错误假设继续走**，
> 因为它把思考当成了既有结论。这比不回填更糟。

## 6. 预算怎么分配

三种策略：

### 策略 A：按任务类型静态分配

```python
budget = {
    "extraction": "low",
    "simple_qa": "low",
    "multi_step_math": "high",
    "planning": "high",
}
```

简单、可预测，适合任务类型事先已知的场景。

### 策略 B：先用小预算试，不够再加大

```python
answer = call(task, budget="low")
if not passed_check(answer):
    answer = call(task, budget="high")
```

**必须有可验证的判据**（`passed_check`），否则你会变成无脑重试。
能用确定性 checker 判定的（跑测试、算数值），就用 checker，别用模型自评。

### 策略 C：不预判，让模型自己决定

部分厂商支持"自动"预算。好处是省心，坏处是**成本不可预测**——
你没法为它做预算护栏（第 15 章）。

## 7. 性价比判断

推理模型贵 N 倍，成功率只高 M 倍。什么时候划算？

```
单次成本 = C_普通 × N
成功率   = P_普通 × M

期望成本 / 成功率 = C_普通 × N / (P_普通 × M)
```

相对普通模型的性价比倍数 = `N / M`。

- `N / M < 1` → 推理更划算；
- `N / M > 1` → 单次更贵，得看**任务价值**能不能覆盖这个差价。

举例：普通模型 $0.01 / 90% 成功，推理模型 $0.06 / 96% 成功。
`N/M = 6/1.07 ≈ 5.6`——单次贵 5.6 倍。

- 如果一次成功的价值是 $0.01 → 不划算；
- 如果一次成功的价值是 $1（比如少一次人工返工）→ 划算。

> **所以推理模型的决策不是"准不准"，是"这个任务值多少钱"。**

---

## 8. 实操清单

- [ ] 抽取、分类、改写任务**关掉**推理
- [ ] 工具调用链路密集的任务**关掉**推理，或把推理前移到规划步骤
- [ ] 思考内容**默认不回填**进上下文
- [ ] 思考预算有上限，且计入成本护栏
- [ ] 动态预算策略必须有**确定性判据**，不能用模型自评
- [ ] 推理 token 在 usage 里单独可见（否则你不知道钱花在哪）
- [ ] 高延迟要求的服务不要用推理模型
- [ ] 用黄金集对比"开/关推理"的准确率与成本（第 12 章）

---

## 一句话结论

> **推理模型是给"需要想"的任务用的，不是给"需要多试"的链路用的。**
> 在工具调用链路上开推理，成本涨得比成功率快；
> 思考内容默认别回填——它会让模型沿着上一步的错误假设继续走。
