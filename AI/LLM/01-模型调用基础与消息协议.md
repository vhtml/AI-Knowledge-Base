# 01 · 模型调用基础与消息协议

> **这篇要回答**：一次模型调用到底发生了什么？消息协议长什么样、每个字段是干嘛的？换模型需要改多少代码？

---

## 1. 一次调用的解剖

模型 API 看着像一个函数：`model(messages) -> response`。但要真上生产，
得知道这个函数背后有几个独立的开关，每一个都会影响结果：

```
请求
├── model          选哪个模型
├── messages       聊天历史（协议的核心）
├── temperature    采样随机性
├── max_tokens     输出上限（推理模型另有参数）
├── stop           停止序列
├── top_p          核采样
├── tools          工具声明（第 2 章）
├── response_format 结构化输出（第 3 章）
└── stream         是否流式（第 4 章）
```

**这 8 个开关里，只有 `messages` 是必填的。** 其余全是"可调的旋钮"，
每个旋钮都有它自己的一章。搞混旋钮的含义，是新手最常见的错误来源。

---

## 2. 消息协议：四种 role

聊天接口只认四种角色：

| role | 谁说的 | 什么时候用 |
| --- | --- | --- |
| `system` | 你（开发者） | 设定行为边界，全局生效 |
| `user` | 终端用户 | 用户的输入 |
| `assistant` | 模型 | 模型自己的输出，也包括它的工具调用意图 |
| `tool` | 工具执行结果 | 把工具返回值回填给模型 |

### 2.1 system 的位置不是随便定的

`system` 消息必须放在**最前面**，且**整个会话只有一条**（少数厂商允许多条，
但语义上应当合并成一条）。它不是"用户的第一次发言"，而是**运行时配置**。

这个区别很重要：用户消息会被模型当成"对话内容"来回应，
系统消息会被当成"行为规则"来遵守。把两者搞混，模型就会开始跟你聊规则。

### 2.2 assistant 不只是文本

`assistant` 消息有两种形态：

```json
{"role": "assistant", "content": "我来查一下订单。"}
{"role": "assistant", "content": null, "tool_calls": [{"id": "call_1", "type": "function", "function": {"name": "查订单", "arguments": "{}"}}]}
```

第二种是**工具调用意图**——注意 `content` 是 `null` 而不是空字符串。
这是第 2 章的主线。

### 2.3 tool 消息必须带 tool_call_id

工具结果不是凭空回填的，它必须指明"这是哪次调用的结果"：

```json
{"role": "tool", "tool_call_id": "call_1", "content": "订单已发货"}
```

`tool_call_id` 缺失或对不上，模型就无法把结果和请求对应起来——
一轮并行调用多个工具时更是完全没法分辨。**这是第 2 章要重点展开的坑。**

## 3. 多轮对话的形状

多轮对话在协议上就是**一个越来越长的 messages 数组**：

```python
[
    {"role": "system",    "content": "你是订单助手"},
    {"role": "user",      "content": "我的订单到哪了"},
    {"role": "assistant", "content": None, "tool_calls": [...]},
    {"role": "tool",      "tool_call_id": "call_1", "content": "已发货"},
    {"role": "assistant", "content": "您的订单已发货"},
]
```

三个必须知道的点：

1. **每一轮都要重发全部历史**——没有服务端会话状态这回事（除非厂商另开接口）。
   所以对话越长，每次调用的输入 token 越多。
2. **历史里有 `null` 内容和工具调用**，它们同样计入 token。
3. **历史可以裁剪**——这是 Agent 侧"上下文工程"的活，见 `AI/Agent/05-上下文工程：窗口预算与压缩.md`。

## 4. 换模型要改多少代码

答案是：**一行都不用改**——前提是你没有把厂商 SDK 的类型泄漏到自己的业务代码里。

自己定义一个最小客户端协议：

```python
class ModelClient(Protocol):
    def complete(self, messages, tools=None, temperature=None,
                 response_format=None) -> ChatResponse: ...
```

然后写两个实现：一个走真实端点，一个用脚本回放假响应。
上层代码只认协议，切换时零改动。

这也是本套教程坚持"不引入框架"的原因之一：
**框架提供的价值，有一大半是"帮你守住这层边界"。**

## 5. 参数旋钮的取舍

### 5.1 temperature：什么时候该调

| 场景 | temperature | 理由 |
| --- | --- | --- |
| 工具调用、代码、抽取 | `0` | 需要可复现 |
| 创意写作、头脑风暴 | `0.7`–`1.0` | 需要多样性 |
| 客服话术、翻译 | `0`–`0.3` | 需要稳定 |

**temperature 解决不了指令含糊。** 提示词写得含糊时，调温度只是让错误更随机。

### 5.2 max_tokens：被截断是最难查的故障之一

模型达到输出上限时，`finish_reason` 会是 `length` 而不是 `stop`。
表面看是"模型没说完"，实际上往往是**你说得太多**，或者**它在重复**。

> **诊断规则**：`finish_reason == "length"` 时，先怀疑输入，再怀疑模型。

### 5.3 stop：极少数场景有用

用停止序列截断输出（比如让模型只输出到某个分隔符）。
多数场景下，**结构化输出（第 3 章）比 stop 序列可靠得多**。

---

## 6. finish_reason：被低估的字段

| 值 | 含义 | 该做什么 |
| --- | --- | --- |
| `stop` | 正常说完 | 继续 |
| `length` | 撞到输出上限 | 查输入是否过长、是否在重复 |
| `tool_calls` | 要调工具 | 执行工具并回填（第 2 章） |
| `content_filter` | 被内容过滤 | 改写输入，别重试原请求 |

**很多人在封装 SDK 时直接丢掉了这个字段**，然后在"模型好像没说完"这种问题上
查不到任何线索。保留它，排查难度会降一个数量级。

## 7. usage 与计费

响应里的 `usage` 告诉你这次花了多少：

```json
{"usage": {"prompt_tokens": 1240, "completion_tokens": 86, "total_tokens": 1326}}
```

关键认知：**输入 token 通常远多于输出 token**。一次带 10 轮历史的对话，
输入可能上万 token，输出只有几十。

所以优化成本的第一杠杆不是"让模型少说话"，而是**别把没用的东西塞进上下文**。
这一条会贯穿整个 Agent 教程。

> 定价、缓存、批量折扣在 `07-上下文窗口、定价与缓存.md` 展开。

## 8. 错误分类：哪些能重试

模型 API 的失败不是一种，而是四类，处理方式完全不同：

| 类别 | 典型信号 | 能不能重试 |
| --- | --- | --- |
| **认证失败** | 401 / 403 | **不能**，重试一万次也是错的 |
| **限流** | 429 | 能，但要**退避** |
| **服务端故障** | 500 / 502 / 503 | 能，退避重试 |
| **请求本身有问题** | 400 | **不能**，改请求 |

把 400 当成 429 重试，是最常见的浪费：你会看到一堆重复的失败请求，
但真正的原因（参数写错了、schema 不对）一次都没被修。

## 9. 一个最小但完整的调用

```python
from openai import OpenAI

client = OpenAI(base_url=base_url, api_key=api_key)
response = client.chat.completions.create(
    model="some-model",
    messages=[
        {"role": "system", "content": "你是订单助手，回答不超过两句话。"},
        {"role": "user", "content": "订单 A-1001 到哪了？"},
    ],
    temperature=0,
    max_tokens=200,
)

choice = response.choices[0]
if choice.finish_reason == "length":
    ...  # 被截断了，别当成正常结果直接用
```

六个要点：system 在前、temperature=0、max_tokens 必设、
检查 finish_reason、保留 usage、不要把 SDK 类型泄漏到上层。

---

## 一句话结论

> **模型调用看着是一个函数，其实是八个旋钮加一份消息协议。**
> `messages` 是骨架（system 在最前、tool 必带 tool_call_id），
> `finish_reason` 是最容易被丢掉却最该保留的字段，
> 错误分类决定你是在修问题还是在制造噪声。
