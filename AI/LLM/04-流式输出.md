# 04 · 流式输出

> **这篇要回答**：流式返回的增量怎么正确拼接？流式和工具调用怎么配合？流式到底改善了什么、没改善什么？

---

## 1. 流式改变的是"什么时候看到"，不是"总共花多久"

流式最容易被误解成"更快"。

打开 `stream=True` 之后，模型 API 的行为变化只有一个：**内容到达你的时间是分段的，不是一次性**。模型该做的 prefill 还是要做，该逐 token 解码的还是要解码，总工作量一个 token 都没少。

所以要分开记两笔账：

| 指标 | 含义 | 非流式 | 流式 |
| --- | --- | --- | --- |
| **TTFT** | 从请求发出到看到第一个字 | = 总延迟 | **显著变小** |
| **总延迟** | 从请求发出到拿到完整回答 | 基线 | **和上面一样，没变** |

流式改善的是**首字延迟（TTFT, Time To First Token）**，没改善的是**总延迟**。

> **坑**："我用了流式所以更快"——这句话在批量抽取、离线分类、后台跑批的场景下是**错的**。
> 流式的价值全部落在**终端用户的体感**上；批量任务该用非流式，
> 它少一层协议解析，而且失败时重来一遍更干净。

流式还有一个容易被忽略的收益：**错误更早暴露**。非流式请求失败，你等到超时才知道；
流式请求在第一个分片之前就断了，错误立刻抛出来。链路健康度监控也靠这一点。

---

## 2. delta 是增量：用 `=` 拼只会剩下最后一个分片

这是流式**第一大坑**，而且它不报错——代码照跑，只是答案少了一大截。

协议里每个分片的 `delta.content` 是**这次新生成的那几个字符**，不是到目前为止的全文。
把它当成全量去覆盖，答案就只剩最后一个分片：

```python
# 错：每次覆盖，前面全没了
text = ""
for chunk in stream:
    text = chunk.delta          # 结果只剩最后一个分片

# 对：累加
text = ""
for chunk in stream:
    text += chunk.delta         # 结果才是完整回答
```

判断办法很简单：**把某个分片的 delta 单独打印出来，如果它是一句完整的话，那多半是厂商做了"累积式"包装**——那是另一套协议，别混着用。OpenAI 兼容协议给的是增量。

排查这类 bug 的症状是"回答只剩最后一句"或者"回答是乱码"。

> **记住**：流式的一切拼接都只有一个动作——`+=`。没有例外。

---

## 3. 一个流里有五类分片，各自带不同的信息

一个流不是"一串文本"。它最多同时携带五类东西，解析器必须认全：

| 分片类型 | 携带什么 | 出现位置 | 解析器该做什么 |
| --- | --- | --- | --- |
| **文本增量** | 新增的几个字符 | 流的绝大部分 | `+=` 累加进正文 |
| **工具名分片** | 工具名的一部分 | 调工具时 | 按 `index` 累加名字 |
| **工具参数分片** | 参数 JSON 的一段文本 | 调工具时 | 按 `index` 累加，**拼完整才能解析** |
| **`finish_reason`** | `stop` / `length` / `tool_calls` | **末尾一到两个分片** | 记下来，别丢 |
| **`usage`** | token 统计 | 末尾，**可能单独占一个分片** | 扫全流找 |

这张表对应本章实验的 `check_chunk_kinds` 和 `check_usage_tail` 两组断言。

注意 `finish_reason` 那一行：**它不是每个分片都带的**。它是末尾的一次性信号。
把 `chunk.finish_reason` 写成"每片都读一下最后覆盖谁"没问题，
但写成"取第一个分片的 finish_reason"就永远拿到 `None`。

---

## 4. 工具调用的流式是另一套形状：参数是分片的 JSON

非流式下工具调用的参数是一个**完整的 JSON 字符串**：

```json
{"id": "call_1", "type": "function", "function": {"name": "查订单", "arguments": "{\"order_id\": \"A-1001\"}"}}
```

流式下这**完全不是一回事**。同一个分片里，参数是一个 JSON 字符串的**碎片**：

```
分片 1: name="查订"                    arguments=""
分片 2: name="单"                      arguments='{"order_id"'
分片 3: name=""                        arguments=': "A-1001"}'
```

三个必须记住的点：

1. **工具名也会被切碎**。名字分片同样要 `+=`，不能假设"名字一次到齐"。
2. **参数是分片的 JSON 文本**，中间任意位置切开都不合法——单个分片拿去
   `json.loads` 必然抛 `JSONDecodeError`。必须**拼完整再解析**。
3. **并行调用靠 `index` 归位**。两个工具调用的分片是**交错到达**的，
   按到达顺序拼会把两次调用的参数混成一坨——这类 bug 极难查，
   因为参数看起来还是合法 JSON，只是内容错了。

拼完之后，工具调用的处理逻辑和非流式**完全一致**：拿到完整参数 → `json.loads` →
校验 schema → 执行工具 → 用 `tool_call_id` 回填。这条链路见
`AI/LLM/02-工具调用协议.md`。

> **坑**：把流式工具调用的参数片段直接丢给 `json.loads`，然后用
> `except: pass` 吞掉异常。结果是**工具调用静默消失**，
> 模型收到的 assistant 消息里没有 tool_calls，于是它改用自然语言回答你。

---

## 5. finish_reason 和 usage 都藏在末尾，解析器必须认

### 5.1 finish_reason：末尾那一两片才有

`finish_reason` 的取值和第 1 章一样：`stop` / `length` / `tool_calls` /
`content_filter`。但它出现的位置不一样——**只有末尾的分片带**。
流式解析器如果漏了它，就丢掉了"模型是不是还想说但被截断了"这条关键线索。

### 5.2 usage：可能单独发一个分片

真实协议在 `include_usage` 打开时，末尾会**再发一个分片**，它只带 `usage`，
没有文本、没有 `finish_reason`：

```
分片 N-1: delta=""  finish_reason="stop"
分片 N  : delta=""  usage={"prompt_tokens": 120, "completion_tokens": 14, ...}
```

于是有两个常见写法会导致**成本统计永远是 0**：

- 只在"带 `finish_reason` 的那个分片"上读 `usage` → 读到空；
- 只在"带文本的分片"上读 `usage` → 读到空。

正确做法是**扫全流**：任何一个分片带 `usage` 就把它合并进来。
本章实验里这条断言的反例就是这么构造的。

### 5.3 一个完整的拼接器长这样

把前面几节的规则合起来，拼接器大概就是这么多行：

```python
class StreamAssembler:
    """把分片累积成一个完整结果——delta 是增量，一律 +=。"""

    def feed(self, chunk):
        self.text += chunk.delta                     # 文本增量
        for piece in chunk.tool_calls:               # 工具调用：按 index 归位
            draft = self.drafts[piece.index]
            draft.name += piece.name_delta
            draft.arguments += piece.arguments_delta
        if chunk.finish_reason:                     # 末尾才有
            self.finish_reason = chunk.finish_reason
        if chunk.usage:                              # 可能单独占一个分片
            self.usage.update(chunk.usage)
```

四个动作，一个都不能少：累加文本、按 index 归位工具调用、记 `finish_reason`、
合并 `usage`。少一个，症状分别是"回答少一截"、"工具参数串了"、
"不知道模型是不是被截断"、"成本永远显示 0"。

## 6. TTFT 和总延迟是两笔账，别混成"流式更快"

用一个可算的模型把这件事讲透。假设：

- prefill（把上下文算成 KV cache）= 800 ms；
- 每输出一个 token = 120 ms；
- 一共 6 个 token。

那么第 i 个 token（从 0 开始）就绪的时刻是 `800 + i × 120`：

| 时刻 | 非流式 | 流式 |
| --- | --- | --- |
| 800 ms | 还在生成 | **第一个 token 交付**（TTFT） |
| 920–1280 ms | 还在生成 | 逐个交付 |
| 1400 ms | 一次性交付全部 | 最后一个 token 交付（总延迟） |

对照两列的最后一行：**总延迟完全相同，都是 1400 ms**。
流式只是把"交付点"从最后那一刻挪到了第一刻。

所以：

- **流式让用户早看到内容**——对话、打字机效果、进度条，全靠它；
- **流式不让模型早算完**——总延迟一分不省；
- **流式不省 token**——生成的还是那些 token。

判断一个场景该不该上流式，问的问题不是"要不要更快"，而是**"用户在等的时候能不能看点东西"**。
能，就该上；不能（比如后台批处理要等完整 JSON），就不该上。

## 7. 取消与半截流：流会在你没准备好的时候结束

### 7.1 取消：客户端断开，服务端也得停

用户关掉页面、客户端超时、Agent 决定换策略——这时候必须**主动关闭流**：

```python
from contextlib import closing

with closing(client.stream(messages)) as stream:
    for chunk in stream:
        render(chunk)
        if should_stop():
            break          # 退出 with 时生成器被关闭
```

不关闭流，后果是**你还在为没人看的 token 付费**——服务端会继续解码到结束，
把整段答案都生成出来，只是没人接收。

需要注意各厂商的计费口径不同：有的在收到断连后立刻停算，有的已经生成的部分照样计费。
**别把"取消"当成省钱手段当成唯一指望**，但该关一定要关。

### 7.2 半截流：收到的部分能用，但必须能标记"没正常结束"

连接中途断掉时，你手里的东西是**半成品**：

- 已经收到的文本仍然合法、仍然可以展示给用户；
- 但它**不是完整回答**——没有 `finish_reason` 就是没说完。

判断"流有没有正常结束"只有一个可靠信号：**收到了 `finish_reason`**。
没有它，就是半截流。

这里有个容易混淆的地方：**半截流**（连接断了，没有 `finish_reason`）和
**被截断**（`finish_reason == "length"`，撞到 `max_tokens`）长得像，含义完全不同：
前者是故障要重试，后者是结果要改请求。解析器必须能把两者区分开。

## 8. 什么时候必须用流式，什么时候不需要

| 场景 | 该不该流式 | 理由 |
| --- | --- | --- |
| **对话 / 聊天** | **该** | 用户在等，字越早出现体感越好 |
| **打字机效果** | **该** | 没有流式根本做不出来 |
| **长工具调用期间的进度反馈** | **该** | 工具跑几十秒，没有输出就像卡死了 |
| **代码生成 / 逐行渲染** | **该** | 大段内容能边出边看 |
| **后台批处理** | **不该** | 没人等着看，总延迟一样，还多一层解析 |
| **结构化抽取** | **不该** | 要的是完整 JSON，流式反而要等拼完；见 `AI/LLM/03-结构化输出.md` |
| **离线评测 / 回归** | **不该** | 非流式结果更好比对，也更容易重试 |

最后两行的理由值得展开：**流式不会让结构化抽取更可靠**。
分片到达的 JSON 本来就是碎的，你最终还是要等它拼完整才能解析——
流式在这里只增加了"半截 JSON"这个新的失败模式。

---

## 一句话结论

> **流式是"送达方式"的改变，不是"速度"的改变：delta 是增量所以一律 `+=`，
> 工具调用是另一套形状所以参数要拼完整再解析，
> 末尾的 `finish_reason` 和 `usage` 不能丢，
> 而流式只改善首字延迟，从不改善总延迟。**
