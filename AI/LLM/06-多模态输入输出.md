# 06 · 多模态输入输出

> **这篇要回答**：一张图片、一段音频怎么发给模型？不同模态各有什么限制、分别怎么计费？

---

## 1. content 不只是字符串

普通对话里 `content` 是一段字符串。多模态下，`content` 变成一个**块列表**：

```json
{
  "role": "user",
  "content": [
    {"type": "text", "text": "这张图里是什么？"},
    {"type": "image_url", "image_url": {"url": "https://example.com/a.png"}}
  ]
}
```

四种常见的块类型：

| type | 用途 | 关键字段 |
| --- | --- | --- |
| `text` | 文本 | `text` |
| `image_url` | 图片 | `image_url.url` |
| `input_audio` | 音频 | `input_audio.data` + `input_audio.format` |
| `file` | 文档 | `file.file_data` / `file.file_id` / `file.filename` |

**块可以混排，而且顺序有意义。** "先看这张图，再看这段文字"和反过来，效果可能不同。

---

## 2. 图片：URL 还是 base64

两种传法：

| 方式 | 请求体 | 何时用 |
| --- | --- | --- |
| **URL** | 小（就是个链接） | 图片能被公开访问 |
| **base64 内联** | 大（膨胀约 33%） | 图片是私有的、临时生成的 |

base64 的代价是**每次调用都要重传**——如果这张图在多轮对话里反复出现，
每一次都在为它付 token 和带宽。

> **一条纪律**：能用 URL 就用 URL。
> 但要注意 **URL 必须能被模型服务端访问到**——内网 URL、需登录的链接、
> 带临时签名的链接都可能拉不到。私有图片用 base64 或先上传成 file_id。

---

## 3. 图片的 token 不是按字节算的

**按尺寸算。**

常见的估算方式是把图片缩放到某个基准分辨率，再按面积折算 token。
大致规律（各家具体算法不同，以各家文档为准）：

| 尺寸 | 数量级 |
| --- | --- |
| 512×512 | ~数百 token |
| 1024×1024 | ~上千 token |
| 2000×2000 | ~数千 token |

三条实践含义：

1. **缩小图片能省钱**，但要权衡清晰度；
2. **"高清模式"会翻倍**，只在真的需要读小字时才开；
3. **一张大图可能比一整页文字还贵**。

> **坑**：很多人以为"图片免费"或"按 KB 计费"，结果账单出来发现图像 token 是大头。

---

## 4. OCR 还是视觉模型

这是多模态里最实用的一个判断：

| | OCR | 视觉模型 |
| --- | --- | --- |
| 输出 | 文字 | 理解后的回答 |
| 成本 | 极低 | 高 |
| 能理解版面/图表/关系 | 否 | 是 |
| 适合 | 文档、截图、表格取字 | 需要"看懂"的任务 |

**能用 OCR 解决的，不要用视觉模型。**

典型场景：把一份 50 页 PDF 的文字抽出来做检索。
用 OCR + 文本模型，比把 50 页图喂给视觉模型便宜几个数量级，效果还更准。

**但要注意**：OCR 抽出的文字里可能藏着注入指令（第 13 章）——
文档里的"忽略前面的指示"会被 OCR 抽出来，然后被当成数据读进上下文。
处理方式和工具结果一样：标注来源，危险动作走审批。

---

## 5. 视频：抽帧

视频不能直接发。做法是抽帧：

```
视频 → 抽 N 帧 → 每帧当图片发 → 模型理解
```

成本 = `N × 单帧 token`。

抽帧策略：

| 策略 | 帧数 | 适合 |
| --- | --- | --- |
| 固定间隔 | 均匀 N 帧 | 镜头变化少的 |
| 关键帧 | 场景切换点 | 讲解类视频 |
| 稀疏采样 + 字幕 | 少帧 + 文字 | 访谈、字幕齐全的 |

**先抽字幕**。有字幕的视频，字幕就是最省的多模态输入——纯文本、极便宜、
信息密度还高。

---

## 6. 音频：先转写

音频同样不能直接进大多数模型（除非模型原生支持音频输入）。

推荐路径：

```
音频 → 转写（ASR）→ 文本 → 文本模型
```

理由：
- 转写便宜；
- 文本可以被检索、被缓存、被复用；
- 文本模型的推理能力比音频模型强。

原生音频输入适合**情感、语气、声音识别**这类"必须听出来"的任务。

---

## 7. 多模态输出：另一个模型

"让模型生成一张图"和"让模型看一张图"是**不同的接口**：

| | 输入 | 输出 | 谁做 |
| --- | --- | --- | --- |
| 视觉理解 | 文本 + 图片 | 文本 | 主模型 |
| 图像生成 | 文本（提示词） | 图片 | 图像生成模型 |

**不要指望主模型"顺手"生成图片。** 它们是两个模型、两套计费、两套错误处理。

如果你的产品要"生成配图"，那是一次独立的模型调用 + 独立的失败处理
（生成失败、审核不通过、耗时超预算）。

---

## 8. 限制清单

发请求前要确认的：

- [ ] 图片格式在支持列表里（jpg / png / webp / gif）
- [ ] 图片大小在单图上限内
- [ ] 请求体大小在上限内（多图 base64 时尤其容易超）
- [ ] 块数量在上限内
- [ ] 音频格式（wav / mp3）与采样率受支持
- [ ] 文档格式受支持（pdf / docx / txt…）
- [ ] URL 是模型服务端**能访问**的

超限时的表现通常是 **400 报错**，不是静默降级——所以要在客户端先校验。

---

## 9. 成本速查

| 模态 | 计费方式 | 相对成本 |
| --- | --- | --- |
| 文本 | 按 token | 1× |
| 图片 | 按尺寸折算 token | 10×–100×（一张大图） |
| 音频 | 按分钟（转写 API） | 视时长 |
| 视频 | 抽帧后按图片算 | 帧数 × 图片 |

**所以多模态的第一优化点永远是：能不传图就不传图，能转文本就转文本。**

---

## 一句话结论

> **多模态的 content 是块列表，不是字符串；图片按尺寸计费，一张大图可能比一整页文字还贵。**
> 第一原则是"能不传就不传"——OCR 优先于视觉模型，字幕优先于抽帧，转写优先于音频模型。
