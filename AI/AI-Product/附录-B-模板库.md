## 1. 场景筛选打分卡

> 用途：在写 PRD **之前**判断这个需求值不值得做。目标是尽早否掉"看起来很酷"的 AI 需求。

```markdown
# 场景筛选：<场景一句话>

## 基本信息
- 场景名称：
- 谁在用（角色）：
- 现在没有 AI 的时候，这件事怎么做：
- 想解决的痛点：

## 四条判据（每条只填「是 / 否」）

| 判据 | 判据的问题 | 权重 | 成立 | 证据（具体到某次访谈/某段流程） |
| --- | --- | --- | --- | --- |
| 有确定性 | 这件事的对错**有没有客观判据**——错了能自动发现，而不是靠人读一遍才知道？ | 30 | 是/否 |  |
| 可容错 | 错一次的代价用户**愿不愿意承受**（用户愿不愿意用第二次）？ | 25 | 是/否 |  |
| 有语料 | 有没有可复用的历史数据/语料？ | 20 | 是/否 |  |
| 有交互杠杆 | 能否借用户的一次确认，补上模型的短板？ | 25 | 是/否 |  |

总分 = 成立判据的权重之和（0–100，四条权重之和为 100）

## 判定
- [ ] reject：总分 < 40
- [ ] pilot：总分 40–69
- [ ] build：总分 ≥ 70

判定结论：<reject / pilot / build>
未通过的判据（不成立的判据逐条写明原因）：
如果砍成规则/搜索能解决吗：<是/否/部分，说明>

## 不确定性预算（上线前允许浪费掉的最大比例）
- build：30%
- pilot：15%
- reject：0%

## ROI 粗算（仅 pilot/build 需要）
- 频次：<每周/每天几次>
- 单次节省：<分钟>
- 月度总价值：<节省小时数 × 小时成本>
- 月度总成本：<调用成本 + 基础设施 + 人力投入摊销>
- 粗略 ROI：
```

> 这张表的权重与阈值与配套实验 `ai_pm_lab week2` **完全一致**
> （权重 30/25/20/25，阈值 40 / 70，判据名相同）。改这里就要同步改实验，否则笔记和实验会各说各话。

**填写要点**

- "证据"一栏必须落到具体事实。写"用户觉得挺好"不算证据，写"3 位销售说每周写 2 次周报，平均 90 分钟"才算。
- 判据**不满足**比**得分低**更重要。任一条为 0，即使总分高也要停下来看。
- 这张表**要存档**。半年后你会想知道当初为什么做或不做。

## 2. 任务账本

> 用途：把"痛点"翻译成可排优先级的任务。这是 AI 产品需求文档的地基。

```markdown
| 任务 ID | 任务描述（动词开头） | 触发场景 | 频次/月 | 单次节省(分) | 月成本 | 变异性 | 容错度 | 语料可得 | 交互杠杆 | AI Fit 档位 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| T-01 |  |  |  |  |  | 低/中/高 | 低/中/高 | 有/部分/无 | 强/弱 | reject/pilot/build |  |

## 变异性说明
（同一任务每次输入差多少？差得越多，越需要模型而不是模板）

## 优先级排序
排序公式（与实验 `ai_pm_lab week2` 一致）：

    rank_score = (频次 × 单次节省分钟 / 60) / 月成本 × 档位系数

档位系数：build = 1.2，pilot = 1.0，reject = 0.8
—— 系数只做倾斜，压不过成本项：避免一个低价值的 build 场景挤掉高价值的 pilot。

| 排名 | 任务 ID | rank_score | AI Fit 档位 | 不确定性预算 |
| --- | --- | --- | --- | --- |
```

**填写要点**

- "变异性"是 AI 场景的关键列。高度模板化的任务用规则更便宜更稳。
- "语料可得"要问到**权限**，不只是"有没有这份文档"。拿不到就是没有。
- 排序结果和 [第 4 章](04-用户研究：还原真实工作流与需求优先级.md)的优先级公式保持一致，别自己另发明一套。
- 算出来的 `rank_score` 要能**和实验 `ai_pm_lab week2` 的输出对上**——对不上说明你的口径和实验口径分叉了。

## 3. 用户访谈提纲

> 用途：AI 场景的访谈和传统访谈最大的不同——用户不知道模型能做什么，所以你要问**过去发生的事**，不是问未来想要的功能。

```markdown
## 破冰（2 分钟）
- 这周你主要在忙什么？

## 锚定过去（15 分钟，问题必须落到最近一次）
1. 上一次做 <任务> 是什么时候？当时的具体步骤是什么？
2. 当时卡在哪一步？卡了多久？
3. 你为这件事准备了哪些东西（模板/清单/脚本/找谁问）？
4. 如果那次结果有问题，会出在哪儿？你怎么发现的？
5. 同样一件事，上周和上个月的做法一样吗？哪里不一样？

## 边界与信任（8 分钟）
6. 这件事做错了，谁来承担后果？最坏的后果是什么？
7. 如果有个工具帮你做了前 <n> 步，你希望它做到什么程度？
8. 你怎么判断一个答案靠不靠谱？现在靠什么判断？
9. 有没有你**绝对不会**让 AI 碰的部分？为什么？

## 收尾（5 分钟）
10. 如果这件事能解决，你每周能省多少时间？
11. 你身边谁做这件事最多？
```

**填写要点**

- 第 1、2 题是核心。问"你希望 AI 做什么"会得到假需求，问"上一次你怎么做"才能拿到真实流程。
- 第 9 题挖出的是**红线**，比需求清单更有价值。
- 一次访谈控制在 30 分钟内，超了会拿到敷衍答案。

## 5. 定位与价值主张一页纸

```markdown
# 定位：<产品名>

## 为谁
<具体到角色 + 场景 + 团队规模，不要写"所有人">

## 替代什么
<用户现在用什么替代：Excel？人力？外包？一个口头流程？>

## 凭什么是你
<独有能力 × 独占位置 × 独有数据 × 独有分发 × 合规资质，选一到两条，说透>

## 价值主张
替 <谁> 在 <什么情境> 下 <省了什么 / 提了什么 / 开了什么>，
因为 <为什么可信>，
你可以 <怎么验证>。

## 不做什么（Anti-goals）
- 不做：
- 不服务：
- 不追求：
```

**填写要点**

- "不做什么"比"做什么"更能约束一个 AI 产品的边界。AI 项目最容易死于范围失控。
- 价值主张里的"怎么验证"必须可操作：不是"大家都会用"，而是"首次使用 10 分钟内能拿到一个可直接用的结果"。

## 6. 单位经济模型

> 用途：定价前必须算这张表。**先有成本上限，再定价格**。单价用变量表示，按当期实际费率填。

```markdown
## 输入（当期填值，注明来源与日期）
| 变量 | 含义 | 值 | 来源/日期 |
| --- | --- | --- | --- |
| P_in | 每千输入 token 成本 |  |  |
| P_out | 每千输出 token 成本 |  |  |
| P_cache | 缓存命中部分每千 token 成本 |  |  |
| C_retr | 单次检索开销 |  |  |
| C_tool | 单次工具调用开销 |  |  |
| C_infra | 其它基础设施分摊 |  |  |
| Q_in / Q_out | 单次会话平均输入/输出 token |  |  |
| H | 缓存命中率 |  |  |
| N_retry | 平均重试次数 |  |  |

## 推导
单会话 token 成本 = (Q_in × (1-H) + Q_in × H × cache折扣 + Q_out) × 单价
单会话总成本 C_session = token 成本 + C_retr × 检索次数 + C_tool × 工具次数 + C_infra
每用户月成本 = C_session × 月会话数 × (1 + N_retry)
单用户月收入 ARPU =
毛利率 = (ARPU - 每用户月成本) / ARPU
定价上限（目标毛利率 <M> 时）= 每用户月成本 / (1 - M)

## 结论
- 目标定价：
- 目标毛利率：
- 保本会话数：
- 最坏情况（全部不命中缓存 + 重试 N 次）：
```

**填写要点**

- "最坏情况"那一行别跳过。真实账单里最贵的那批会话才是压垮毛利的。
- 三个降本手段按性价比排序写进 PRD：模型分级路由 → 提示缓存 → 上下文裁剪。降本会掉质量的部分单独列（[第 12 章](12-成本、延迟与单位经济.md)）。

## 8. 评测集与回归门禁

> 用途：把"质量"变成一个能被 CI 挡住的数字。

````markdown
## 评测集结构（JSON）
```json
{
  "version": "2026-11-18",
  "cases": [
    {
      "id": "E-001",
      "task": "任务描述",
      "input": "输入样例",
      "expected": {
        "must_include": ["关键事实1"],
        "must_not_include": ["禁止出现的内容"],
        "reference": "参考答案（可选）"
      },
      "critical_errors": ["会误导用户的关键错误"],
      "soft_errors": ["不致命的质量问题"],
      "tags": ["单轮", "检索", "中文"],
      "source": "日志/专家标注/合成"
    }
  ]
}
```

## 打分规则
- 关键错误一票否决：该条判失败，不参与加权平均（为什么：关键错误是"会误导用户做决策"，被平均分会掩盖）
- 软错误按条扣分
- 总分 = 通过用例数 / 总用例数

## 门禁
| 变更类型 | 必须通过 | 阈值 |
| --- | --- | --- |
| Prompt 修改 | 全量评测集 | 不低于基线 |
| 检索/知识库变更 | 检索相关子集 + 全量 | 不低于基线 |
| 模型升级 | 全量 + 人工抽检 | 不低于基线，且关键错误数不增加 |
| 流程/工具变更 | 受影响子集 | 不低于基线 |

## 基线记录
| 日期 | 版本 | 通过率 | 关键错误数 | 备注 |
| --- | --- | --- | --- | --- |
````

**填写要点**

- 评测集要**有来源标签**。全是合成的评测集会让你对自己的产品产生虚假的安全感。
- 关键错误和软错误要分开列。没有这个区分，模型评分只会给你一个没有行动价值的平均分。
- 门禁阈值写"不低于基线"而不是绝对数字。基线随产品演进，绝对数字很快失效。

## 9. 指标字典与指标树

```markdown
## 指标树
北极星指标：<一句话描述用户获得了什么价值>
├── 护栏指标（不能被牺牲）
│   ├── 幻觉率 / 越权次数 / 单会话成本 / P95 延迟 / 投诉率
└── 诊断指标（解释北极星为什么涨跌）
    ├── 首次成功率、采纳率、修改率、复用率、…

## 指标字典
| 指标名 | 类型(北极星/护栏/诊断) | 定义 | 计算口径 | 数据来源 | 采集延迟 | 是否可判伪 | 目标值 | 负责人 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  | 是/否 |  |  |

## 北极星指标的三条自检
1. 它反映**用户拿到的价值**吗（不是我们做了多少功能）？
2. 它是**领先**指标吗（还是等收入来了才知道）？
3. 它**可判伪**吗——能写出"什么情况下这个数字下降就说明产品变差了"？
```

**填写要点**

- 第 3 条自检最容易被跳过。写不出"什么情况下它会变差"，说明它不是北极星，只是又一个好看的数字。
- 护栏指标必须在北极星之前定好，否则团队会用护栏换北极星。

## 10. 风险登记册

```markdown
| 风险 ID | 风险描述 | 触发条件 | 影响 | 概率 | 等级 | 缓解措施 | 兜底方案 | 责任人 | 复检周期 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

## 必查风险类别（每类至少一条，没风险就写"已评估，不适用"）
- 幻觉与错误建议
- 越权与数据访问
- 偏见与不当输出
- 隐私与数据留存
- 内容滥用
- 依赖与过度信任
- 合规义务
- 供应商依赖

## 事件响应
- 发现渠道：
- 响应时限：
- 决策人：
- 对外口径：
```

**填写要点**

- "已评估，不适用"也是一种有效填写。**留空才是风险**。
- 等级判定用"影响 × 概率"，影响要写清对谁：用户被误导？成本失控？监管处罚？
- 合规类风险要挂到具体法规条款（[第 13 章](13-安全、合规与风险治理.md)）。

## 11. 灰度与上线检查单

```markdown
## 上线前
- [ ] 评测门禁通过（不低于基线，关键错误数不增加）
- [ ] 失败态逐条走查（每个失败场景都真的试过）
- [ ] 成本压测（模拟最坏情况会话量）
- [ ] 降级预案演练（模型不可用 / 超时 / 超预算时会发生什么）
- [ ] 权限与数据边界复核（谁能看什么、留多久）
- [ ] 合规义务落地（标识、告知、备案/评估要求）
- [ ] 监控与告警就位（成本、延迟、错误率、幻觉抽样）
- [ ] 回滚方案与操作手册
- [ ] 客服/销售的话术与升级路径

## 灰度
| 阶段 | 范围 | 观察窗口 | 放量门槛 | 回滚条件 |
| --- | --- | --- | --- | --- |
| 内部 |  |  |  |  |
| 1% |  |  |  |  |
| 10% |  |  |  |  |
| 50% |  |  |  |  |
| 100% |  |  |  |  |

## 上线后
- [ ] 首周每日复盘（真实失败案例 → 补评测集）
- [ ] 首月成本与指标周报
- [ ] 风险登记册复检
```

**填写要点**

- 灰度门槛要用**指标**写，不要用"感觉还行"。见第 9 份模板的指标字典。
- "首周每日复盘 → 补评测集"这条回路是 AI 产品迭代的核心，见 [第 14 章](14-指标体系、数据闭环与%20PMF.md)。

## 怎么用这套模板库

**顺序别搞反。** 推荐顺序：

```
场景筛选（1）→ 任务账本（2）→ 定位（5）→ 竞品（4）
    → 单位经济（6）→ AI PRD（7）→ 评测集（8）→ 指标（9）→ 风险（10）→ 灰度（11）
```

前四份是**决策**，后五份是**承诺**。用决策去填承诺，而不是反过来——
先写 PRD 再想场景，是 AI 项目最常见的死法。

## 一句话结论

> **模板的价值不是格式统一，而是逼你在动笔之前把该想清楚的东西想清楚。**
> 这十一份模板串起来就是一条完整的 AI 产品流水线——
> 任何一格填不出来，说明那个环节的问题还没解决，方案就不该进评审。
