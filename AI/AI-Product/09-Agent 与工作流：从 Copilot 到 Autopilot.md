# 09 · Agent 与工作流：从 Copilot 到 Autopilot

> **这篇要回答**：同一个 AI 功能，该让模型只给建议，还是让它自己干完？该停在自动化阶梯的哪一级？

---

## 1. 自动化等级六级阶梯

AI 功能的形态不是二元开关（"有 AI / 没 AI"），而是一条**连续的自动化阶梯**。产品经理真正的工作，是决定用户和系统各自承担多少。

| 级别 | 形态 | 用户做什么 | 系统做什么 | 出错谁负责 |
| --- | --- | --- | --- | --- |
| L0 | 手动（Copilot） | 自己写完，系统只补全 | 补全当前光标处的一小段 | 用户 |
| L1 | 建议（Suggest） | 从候选里挑一个 | 生成候选方案，不落地 | 用户 |
| L2 | 草稿（Draft） | 修改草稿后提交 | 生成完整可编辑产物 | 用户 |
| L3 | 带审批自动执行 | 只在关键点点一次"同意" | 执行到不可逆动作前停下等审批 | 系统执行，用户签字 |
| L4 | 自动执行 | 只看结果，出问题再介入 | 全流程执行，事后可追溯 | 系统（需兜底与回滚） |
| L5 | 全自动（Autopilot） | 只给目标和预算 | 自己发现、规划、执行、汇报 | 系统（需抽检与熔断） |

```
        用户的动作量 ↓，系统的动作量 ↑，错误半径 ↑

 L5  Autopilot   ▓▓▓▓▓▓▓▓▓▓▓▓▓  自己发现问题、自己排期、自己汇报
 L4  自动执行     ▓▓▓▓▓▓▓▓▓▓▓     全流程跑完，用户看结果
 L3  带审批       ▓▓▓▓▓▓▓▓        执行 + 一个审批卡
 L2  草稿         ▓▓▓▓▓          给一份可改的成品
 L1  建议         ▓▓▓            给几个候选
 L0  手动         ▓              补全几个字
```

**升一级省下的用户动作，换来的是更大的错误半径。** 这笔账只有产品经理能算，因为只有你知道"错一次"的代价是重写一段文案，还是赔一笔钱。

**产品经理怎么用它**：先把功能定级写进 PRD 的第一段——"本功能为 L2 草稿级，系统不直接写库"，这句话会直接决定后面所有的交互、评审和兜底设计。定级不清是后面所有返工的源头。

## 2. 该停在哪一级：风险 × 频次 × 确定性

三个维度决定上限。**任何一个维度亮红灯，就往下退一级**。

| 维度 | 问什么 | 怎么量 | 亮红灯时 |
| --- | --- | --- | --- |
| **风险** | 做错了能撤回吗？影响钱、影响外部客户、影响不可逆数据吗 | 三档：只读 / 可写 / 危险写 | 降到 L3 或更低，并强制审批 |
| **频次** | 一天发生多少次？人工兜底扛得住吗 | 日调用量 × 单次人工复核耗时 | 频次高必须上自动化，否则成本压不住 |
| **确定性** | 同一输入，输出稳定吗？判断依据能写成规则吗 | 评测集上的重复一致率（见 [11-评测体系：AI 产品的质量标准.md](11-评测体系：AI%20产品的质量标准.md)） | 不确定就锁死在 L2 以下 |

核心决策表：

| 你的处境 | 判断依据 | 该怎么做 | 常见错误 |
| --- | --- | --- | --- |
| 每天都发生上千次、错了只是小瑕疵 | 高频 + 低风险 + 错误可容忍 | 直接上 L4 自动执行，后台抽检 | 还在让人一条条点确认，成本压不下来 |
| 错了能撤回，但没人盯得住 | 中频 + 低风险 | L3：执行前弹一次轻确认 + 批量撤销入口 | 做成 L2 让人天天改草稿，效率没提升 |
| 涉及资金、对外发送、删数据 | 危险写 | 最高 L3，危险动作单独二次确认 + 完整审计日志 | 直接自动执行，只在提示词里写"请谨慎" |
| 一次性的低频任务 | 低频 + 低风险 | L1/L2 就够，别为偶发需求做自动化 | 为一个月用一次的场景搭一整套 Agent 平台 |
| 输出必须逐字正确、且有明文规则 | 高确定性（规则可枚举） | 用确定性工作流，不要用 Agent | 用 Agent 去干本该写死的分支逻辑 |
| 结果要写进客户可见的系统 | 风险外溢 | L3 + 影子模式（先跑不生效，对比人工结果） | 直接放量，靠线上投诉发现不对 |
| 用户不知道该不该信 AI | 信任尚未建立 | 从 L2 起，先把准确率打到用户满意 | 一上来就 L4，用户第一次踩坑就流失 |

**产品经理怎么用它**：做功能立项时，用这张表填出"建议级别"和"兜底级别"两栏。建议级别是理想态，兜底级别是出事时的落点——两栏必须都写。

## 3. 工作流优先原则

**能用确定流程解决的，不要交给 Agent 决策。** 这不是保守，是产品经济学：工作流可预测、可测试、可排期；Agent 会带来不确定性、成本和调试难度。

Anthropic 的工程文章把这条界线说得很清楚：workflow 是"通过预定义的代码路径调用模型"，agent 是"由模型自己动态决定步骤和工具"（[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)，核实于 2026-11）。

| 信号 | 怎么判断 | 该怎么做 |
| --- | --- | --- |
| 步骤固定，分支可枚举 | 能画出流程图且没有"看情况" | 写工作流，模型只负责每个节点的填槽 |
| 输入输出都是结构化字段 | 入参出参能用 schema 说清 | 工作流 + schema 校验 |
| 失败情况可以枚举 | 你能列出 3–5 种典型错误 | 工作流 + 每种错误一条分支 |
| 判据是业务规则，不是理解力 | 规则能写成 `if/else` | 别用 Agent，直接写代码 |

反过来，**下面这些信号说明确实该上 Agent**：目标不确定（用户自己也没想清楚要什么）、路径需要探索（要试几种方案才知道行不行）、中间产物需要判断质量（写完要自己检查再改）。

**产品经理怎么用它**：让工程师在 PRD 里回答一句"这个功能如果写成 if/else，能不能写出来"。能写出来就别做 Agent；写不出来，做一个能自检的 Agent（生成后自己验一遍）也比让模型自由发挥安全。

## 4. Agent 的产品契约

Agent 的行为不可完全预测，但它的**边界可以完全写死**。产品经理要交付的不是"一个 Agent"，而是一份契约。

| 条款 | 要写清什么 | 例子 | 缺了会怎样 |
| --- | --- | --- | --- |
| **能力边界** | 允许做什么、明确禁止做什么 | 只允许读工单系统，禁止写财务库 | 模型尝试越权工具时无人拦截 |
| **工具集** | 有哪些工具、各自读写档位 | `search_tickets`(只读)、`update_ticket`(可写) | 工具越加越多，没有取舍 |
| **停止条件** | 什么时候算完成、什么时候必须停 | 最多 10 轮工具调用；达到预算上限即停 | 死循环，烧钱还不产出结果 |
| **失败怎么办** | 工具失败、超时、返回空时的动作 | 重试 2 次 → 降级为"给出建议 + 转人工" | 一失败就抛 500，用户只看到报错 |
| **超时怎么办** | 整体时长上限与超时后的状态 | 单任务 90 秒，超时保存进度并提示 | 长任务卡死，用户只能刷新 |
| **预算** | 单次任务可用的 token / 工具调用 / 金额上限 | 单任务上限 X，触顶即停并汇报 | 一次异常调用吃掉整天配额 |

契约用配置写出来，就是产品规范；用提示词"嘱咐"出来，就是碰运气。

一份契约片段长这样（示意）：

| 契约字段 | 示例值 |
| --- | --- |
| 目标 | 根据工单描述定位问题并给出处理建议 |
| 允许的工具 | `search_tickets`、`search_runbook`、`draft_reply` |
| 明确禁止 | 写财务库、直接向客户发送回复 |
| 停止条件 | ① 给出带引用来源的建议　② 工具调用轮数 ≥ 10　③ 累计成本 ≥ 单任务上限 |
| 工具失败时 | 重试 2 次后转人工，并带上已收集的上下文 |
| 超时时 | 保存进度，告知用户可稍后从通知继续 |

**产品经理怎么用它**：这份契约是验收标准的一部分。"系统能自己发现并改正"不算验收标准，"工具失败 2 次后转人工且带全上下文"才算。落笔位置见 AI PRD 的「4.3 能力边界」与「4.4 工具与权限」（[附录-B 模板库](附录-B-模板库.md)）。

## 5. 多智能体：什么时候值得

多智能体的收益是**分工带来的上下文隔离**（一个 agent 专注读代码，一个专注读文档，互不污染）；代价是**协调开销、token 放大和更难的失败定位**。

| 你的处境 | 判断依据 | 该怎么做 | 常见错误 |
| --- | --- | --- | --- |
| 任务需要 3 个以上**互不依赖**的子任务 | 子任务可并行、输入输出边界清楚 | 值得做多智能体，并行跑 | 串行编排并行子任务，延迟叠加 |
| 子任务之间要频繁交换信息 | A 的中间产物是 B 的输入 | 单智能体 + 分工提示，或一个图 | 多 agent 互传消息，状态难追 |
| 子任务同质、只是数据量大 | 同一件事干很多遍 | 并行 + 批处理，不用多智能体 | 误以为"量大"就需要多 agent |
| 团队没有评测集 | 见 [11 章](11-评测体系：AI%20产品的质量标准.md) | 先别做，多 agent 的失败很难归因 | 多 agent 上线后靠用户投诉发现退化 |
| 目标是"看起来像多智能体" | 只是架构偏好 | 不做 | 过度设计，维护成本翻倍 |

**产品经理怎么用它**：多智能体的决策依据不是"任务复杂"，而是"**子任务之间能否真正解耦**"。解耦不了，多智能体只是把一个难调试的 agent 拆成几个更难调试的 agent。

## 6. 人在环路的产品化

审批不是"加一个弹窗"，是一个独立的产品流程。要解决三件事：**审批点放哪、审批信息给什么、被打断后怎么恢复**。

**审批点放哪**：原则是"放在不可逆动作之前最后一步"。规则越简单越好——一个任务里超过 2 个审批点，用户会麻木。

| 审批点位置 | 后果 |
| --- | --- |
| 放在每一步之前 | 用户变成点击机器，审批疲劳，绕过率上升 |
| 放在不可逆动作之前 | 用户只在真正出事的那一步集中注意力 |
| 放在全部完成之后 | 等于事后通知，失去审批意义 |

**审批信息给什么**：审批人只有几秒钟，必须给够决策所需的最少信息。

| 要素 | 内容 | 缺了会怎样 |
| --- | --- | --- |
| 做什么 | 动作 + 目标对象（工单 #1234 打回） | 审批人看不懂，盲点"同意" |
| 为什么 | 触发原因 + 依据来源（命中的规则、检索到的文档） | 无法判断合理性 |
| 影响范围 | 会改动哪些数据、会不会外发 | 低估风险，误批 |
| 可撤销性 | 能否回滚、回滚窗口多长 | 把可撤销操作当不可逆操作严格审批 |
| 成本 | 预计消耗的时间/金额 | 高成本任务被随手批准 |
| 兜底 | 不批准的话下一步走哪 | 审批人不敢批，怕卡住流程 |

**被打断后怎么恢复**：审批是异步的，可能几分钟也可能几天。用户回来时，系统必须能接着上次干——这要求任务状态、检查点和上下文在服务端持久化，而不是留在页面内存里。实现层的参考见 [LangGraph 第 8 章：人在环路](../LangGraph/08-人在环路：中断、审批与恢复.md)。

| 恢复场景 | 必须做到 | 常见错误 |
| --- | --- | --- |
| 用户审批后回到系统 | 从暂停点继续，不重新跑一遍 | 重复计费、重复副作用 |
| 用户拒绝 | 走明确的拒绝分支，把理由回灌 | 系统卡在中间态 |
| 审批超时 | 自动降级或转人工，任务可被认领 | 任务永远悬挂，队列越积越长 |
| 用户换设备 | 任务状态跟账号走 | 状态绑在会话上，找不回来 |

**产品经理怎么用它**：把审批当成一条独立的用户旅程来设计——有进入页、有等待态、有结果页、有超时态。它是整个流程里唯一"用户必须做决定"的地方，体验好坏直接决定自动化等级能不能往上抬。

## 7. 长任务的上下文管理、中断与恢复

超过几分钟的任务，用户会：中途关页面、手机锁屏、隔天回来看。所以长任务的产品设计重点不是"更聪明"，而是"**别丢**"。

```
任务开始
  │
  ├─ 步骤1 ──── 检查点 A ──── 步骤2 ──── 检查点 B ──── 步骤3 ──► 结果
  │              │                            │
  │         用户关页面                      服务重启
  │              │                            │
  └────── 回来后从 A 继续，从 B 继续，不从头重跑 ────────┘
```

| 长任务现象 | 根因 | 产品侧处置 |
| --- | --- | --- |
| 越到后面越笨 | 上下文被中间产物塞满，关键约束被挤掉 | 定期把中间产物压缩成摘要，保留决策依据 |
| 刷新后进度没了 | 状态在页面内存里 | 服务端持久化检查点 |
| 长任务做完但用户没看到 | 缺少主动通知 | 完成/失败都要推送到用户会去的地方 |
| 用户等太久不知道在干嘛 | 没有进度可视化 | 展示"当前在第几步、已花多久" |
| 中途要改需求 | 没有可介入点 | 定义清楚哪些步骤可改、哪些不可改 |

**产品经理怎么用它**：长任务的验收标准要加一条——"**关掉页面再回来，任务不丢、不错、不错算**"。这一条过不了，功能就只是 demo。

## 8. 失败态设计与可观测性最小集

失败态是 AI 产品体验里最被低估的一半。传统软件报错有明确归因，AI 产品的失败常常是"它说它做了"。

**给用户看的失败，三件套**：

1. **发生了什么**：用业务语言说，不要暴露异常栈（"检索服务超时" → "没能查到工单历史"）
2. **影响是什么**：哪些部分已经完成、哪些没做（部分失败要明确说"草稿已生成，但未发送"）
3. **下一步选什么**：给 2–3 个可选动作（重试 / 换个关键词 / 转人工 / 手动完成），别只给一个"失败"页

| 失败类型 | 用户看到的 | 系统必须做的 |
| --- | --- | --- |
| 工具返回空 | "没找到相关工单，换个关键词试试" | 区分"真的没有"和"查询写错了" |
| 工具报错 | "工单系统暂时不可用，你的草稿已保留" | 保留中间产物，不要整单丢弃 |
| 超时 | "任务超时，已保存进度，可稍后继续" | 落检查点 |
| 越权/触发风控 | "这个操作需要管理员权限，已转交" | 记录审计，不重试 |

**可观测性最小集**：没有这六个字段，线上出事只能靠猜。

| 字段 | 记什么 | 用来回答什么产品问题 |
| --- | --- | --- |
| 任务/会话 ID | 贯穿全链路的标识 | 用户报障时能捞出完整过程 |
| 每步动作 | 调了哪个工具、传了什么（脱敏） | 是选错工具还是参数错 |
| 每步结果摘要 | 返回条数、是否空、错误码 | 区分"模型错了"和"数据源空了" |
| 成本 | token 数与工具调用次数 | 哪些任务类型烧钱 |
| 最终状态 | 成功 / 需人工 / 失败 / 被拦 | 自动化等级实际达到几级 |
| 人工介入点 | 在哪一步、谁介入、改了什么 | 人工成本曲线 |

**产品经理怎么用它**：先定"要回答哪些产品问题"，再倒推要记哪些字段。反过来做（先上全量追踪再想用途）通常半年后没人看。

## 9. 案例：从 Copilot 到 Autopilot 的三级跳（示意案例）

> 以下为虚构案例，用于演示决策过程，**不代表任何真实公司的内部数据**。

**场景**：某公司 IT 服务台助手。最早的形态是在工单输入框里补全话术（L0），后来改成给整段回复草稿（L2），最终做到自动分类并派单（L4）。

**第一跳：L0 → L2（用确定性工作流，不上 Agent）**

- 判据：回复模板由 6 个固定字段拼装，全部可枚举 → 属于第 3 节的"能用工作流"信号
- 做法：表单收集字段 → 工作流拼装 → 人工微调后发送
- 效果方向：用户从"复制模板改字段"变成"确认字段"，**任务出错率下降，但用户操作量几乎没变**——这正是 L2 的特征
- 踩坑：初期想直接上 Agent 自动收集信息，结果它会漏问必填项，客服回头补录，反而多了一步

**第二跳：L2 → L3（只在危险写前面加审批）**

- 判据：自动派单属于"可写"，改错了会影响工单流转，但没有不可逆风险 → 风险维度是黄灯
- 做法：分类与派单建议自动给出；**"关闭工单"和"外发邮件"两个动作挂审批卡**，审批卡展示影响范围与可撤销性
- 关键设计：审批卡上写清"这张工单今天不会被关"，否则用户会担心积压而一律同意，审批就白设了
- 踩坑：审批卡信息不足，审批人闭眼点同意；后来补上"依据来源"（命中的知识库条目）后，批准率从"几乎全批"变成有区分度

**第三跳：L3 → L4（高频低风险才敢自动）**

- 判据：日均工单量大、人工兜底扛不住 → 频次维度是红灯（必须自动化）；但关闭工单不可逆 → 保留 L3 尾巴
- 做法：自动分类 + 自动派单全自动跑（L4），"关闭工单"仍留审批（L3）；并且**影子模式**跑两周，只记录人工的真实分类结果做对比
- 上线判据（示意）：自动分类与人工分类的一致率达到团队约定阈值才放量；不达标就退回 L3 而不是继续调参
- 踩坑：一开始把"关闭工单"也自动化了，误关了两张真实工单。虽然做了回滚，但信任修复花了两周

**这个案例真正想说明的三件事**：

1. 三级跳的顺序是**先提可靠性、再提自动化等级**，不是反过来
2. 每一级都要配一条**兜底路径**（L4 退回 L3、L3 转人工），而不是指望模型不出错
3. L5（Autopilot）在这类场景里根本没被采纳——收益不抵风险，这本身就是一个合格的结论

## 10. 常见误区

| 误区 | 现象 | 根因 | 纠偏 |
| --- | --- | --- | --- |
| "Agent 越强，产品越好" | 直接上 L4/L5，线上事故靠人工救火 | 把模型能力当产品能力 | 能力上限之外，还有契约、兜底、监控 |
| "先用 Agent 顶一下，以后再改工作流" | 半年后重写，推倒重来 | 把 Agent 当临时方案 | 从工作流起步是更省的总成本 |
| "加个提示词就行" | 出错就补一段"请务必……"，行为越来越不可预测 | 用自然语言代替规格 | 边界写进契约和校验，不写进提示词 |
| "多 agent 显得先进" | 延迟翻倍、成本翻倍、失败难定位 | 架构偏好驱动 | 按"子任务能否解耦"决策 |
| "自动化等级越高越省事" | 用户完全不信任，全部推翻重来 | 跳过了信任积累 | 等级是爬坡出来的，不是一次性切换 |
| "用户不点确认就是不需要确认" | 审批疲劳导致全是"同意" | 审批卡信息不足 | 审批卡给足决策信息，坏信息导致空审批 |
| "长任务失败就是重跑一次" | 重复副作用、重复计费 | 没有检查点 | 长任务必须可恢复，见第 7 节 |

## 11. 本章练习

**这次练习要用你自己的真实数据。** 示例数据只能验证你算对了，验证不了你的判断——
真数据才会暴露判断里的漏洞。

**输入**：你手上一个真的可以做成 Agent 的功能——比如"每周从工单系统汇总未闭环问题并给出处理建议"。不要用"全能助手"这种笼统的东西。

**步骤**：
1. 按第 2 节给风险、频次、确定性各打一个 0–1 分（0 = 安全 / 低频 / 确定，1 = 高风险 / 高频 / 不确定），定出自动化等级，并写出**为什么不能再升一级**。
2. 按第 4 节写一份 Agent 契约，六行齐全：目标 / 允许的工具 / 明确禁止 / 停止条件 / 失败怎么办 / 超时怎么办。
3. 按第 3 节检查一遍"这件事能不能用确定性工作流做"——如果能，说明你为什么还要用 Agent。

契约照第 4 节那张表的格式写：

| 契约字段 | 你的值 |
| --- | --- |
| 目标 | |
| 允许的工具 | |
| 明确禁止 | |
| 停止条件 | |
| 工具失败时 | |
| 超时时 | |

**产出**：一份 Agent 契约 + 定级理由（含"不能再升一级的原因"）+ 一句"为什么不用工作流"。

**怎么算做对**：① "明确禁止"那行至少写了两条你真的不敢让它做的事；② 停止条件是可判定的（"工具调用轮数 ≥ 10"），不是"差不多了"；③ 你能说出这个 Agent 失败时用户会看到什么。

## 12. 本章要点

- 自动化是六级阶梯（手动 / 建议 / 草稿 / 带审批 / 自动 / 全自动），每一级都要重新分配"出错谁负责"
- 停在哪一级由**风险 × 频次 × 确定性**共同决定，任何一维亮红灯就往下退一级
- 能用确定性工作流解决的，不要交给 Agent；判据是"能不能写成 if/else"
- Agent 必须交付**产品契约**：能力边界、工具集、停止条件、失败与超时的动作、预算上限
- 多智能体的判据是"子任务能否解耦"，不是"任务看起来复杂"
- 审批是独立产品旅程：放在不可逆动作前，卡片给足决策信息，任务可恢复
- 长任务的验收标准要加一条：关掉页面再回来，任务不丢、不错、不错算
- 失败态三件套：发生了什么、影响什么、下一步可选；可观测性最小集六字段

---

## 一句话结论

> **自动化等级不是技术选择，是风险与信任的共同产物**：先证明可靠，再往上抬一级，
> 每升一级都配好兜底路径——Copilot 到 Autopilot 的三级跳，赢在每一步都留了退路。
