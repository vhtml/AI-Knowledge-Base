# 01 · AI 产品经理的角色、能力模型与边界

> **这篇要回答**：AI 项目里的产品经理到底做什么？能力该怎么自评、怎么补、边界在哪？

---

## 1. 哪些活变贵了，哪些活变便宜了

AI 没有消灭产品经理的工作，而是把它从「把需求翻译成页面」挪到「把意图翻译成可验收的能力边界」。
下面这张表是本章的起点：左边是传统 PM 的日常，右边是 AI 项目里同一件事的新形态。

| 传统 PM 的活 | AI 项目里的变化 | 方向 | 原因 |
| --- | --- | --- | --- |
| 写 PRD、画流程图 | 少描述「界面长什么样」，多定义「输入什么、输出什么、错了怎么办」 | 变便宜 | 界面形态由实现决定，约束条件才是真正的设计对象 |
| 需求评审 | 多一维议题：这次失败算谁的 | 变贵 | 输出有概率性，错误归属必须提前谈死 |
| 排期与任务拆解 | 要给评测、灰度、回归留出时间 | 变贵 | 质量靠数据判定，不能靠「感觉没问题」 |
| 跟用户沟通 | 从「问你要什么」变成「给样本、给选项、问边界在哪」 | 变贵 | 用户不知道模型边界，问不出真需求 |
| 画交互原型 | 主流程能被提示词与工具编排替代，异常态仍要画 | 部分变便宜 | 例外路径才是产品的剩余价值 |
| 推动上线 | 增加可观测、埋点、审计留痕 | 变贵 | 没有 trace 就没法定位问题出在哪一层 |
| 定义验收标准 | 从「功能可用」变成「抽样质量可测」 | 变贵 | 概率性输出必须先有判定口径 |

两条价值链的差别，本质是**确定性从哪来**：

```
传统：需求 → 方案 → 开发 → 验收 → 上线
                    ↑
             确定性来自"写清楚"

AI ：场景 → 任务 → 数据 → 评测 → 兜底 → 上线 → 回归
                         ↑            ↑
                确定性来自"测出来"   兜底决定能不能上线
```

**PM 怎么用它**：接到任何需求先问一句——这件事的确定性来自写清楚，还是来自测出来？
前者走传统流程，后者必须额外补三样东西：评测集、兜底方案、回归机制。

## 2. 三类核心能力

能力模型只用来诊断，不用来考核。三类能力，对应三种「如果缺了会怎样」。

| 能力 | 解决什么问题 | 可观察行为 | 缺了会怎样 |
| --- | --- | --- | --- |
| **业务判断力** | 决定做不做、为谁做 | 能把「老板的想法」翻译成「某角色在某频率下损失多少时间」；能说清砍掉这个需求的后果 | 做出没人用的 AI 功能 |
| **AI 素养** | 决定能不能做、做成什么样 | 能用三句话讲清一次失败为什么失败（见 [02-技术地基：模型能力边界、上下文与推理参数.md](02-技术地基：模型能力边界、上下文与推理参数.md)）；知道结构化输出为什么比自由对话可靠 | 需求在技术上能跑，在产品上跑不通 |
| **落地推动力** | 决定能不能真的上线 | 能在没有确定答案时给出可验收的小切口；能让法务与工程在方案定稿前而不是上线前介入 | 停在 demo，或者带着未决风险上线 |

**判断标准**：这三类能力对应三个不同的问题——

- 业务判断力回答「值不值得做」
- AI 素养回答「能不能做、做到什么程度」
- 落地推动力回答「能不能真的推上线」

一个常见的失败模式是只补第二类：技术团队很强、业务价值说不清、上线后没人用。
另一个是只补第一类：判断出场景有价值，但压不住「这效果达不到预期」的落差。

## 3. 八维能力模型与自评判据

八个维度，每个维度按 1–5 分给自己打分。判据必须可观察，否则自评就是自我安慰。

| 维度 | 1 分 | 3 分 | 5 分 |
| --- | --- | --- | --- |
| **场景判断** | 需求来了先答应 | 能拆成任务并判断哪步可自动化 | 能主动否掉高风险低价值需求，并给出替代方案 |
| **技术理解** | 分不清模型档位、说不清上下文是什么 | 知道哪类任务该用哪档模型、知道幻觉从哪来 | 能读调用链与 trace，判断问题在模型还是在编排 |
| **评测设计** | 试几条感觉还行就算通过 | 能写抽样清单和明确的对错判据 | 维护回归集，用数据判断改动是变好还是变坏 |
| **数据与知识** | 不知道语料在哪、能不能用 | 能列出可用语料、来源与所需权限 | 能设计语料的更新与失效机制 |
| **成本与商业** | 不关心 token 与延迟 | 能粗算单次成本与月度量级 | 用 ROI 口径取舍场景，能预判成本随用量的走势 |
| **交互与信任** | 把 AI 输出直接甩给用户 | 能给出置信度提示与人工接管路径 | 设计出让用户逐步建立信任的交互节奏 |
| **跨职能推动** | 等算法排期 | 能对齐目标与验收口径 | 目标冲突时能给出可裁决的方案 |
| **合规意识** | 上线前才想起来问法务 | 知道数据出域、留存与留痕的红线在哪 | 把合规约束提前翻译成产品设计约束 |

雷达图长这样（示意，八个维度各自独立打分，不做加权平均）：

```
                 数据与知识
                    ▲
       合规意识 ◄───┼───► 成本与商业
            ╲       │       ╱
             ╲      │      ╱
      跨职能推动 ────┼──── 场景判断
             ╱      │      ╲
            ╱       │       ╲
       交互与信任 ◄───┼───► 技术理解
                    ▼
                 评测设计
```

**PM 怎么用它**：先按上表硬打分，再看短板**排序**——排序比分数重要。
实验把 **3 分及以下**设为短板线（3 分意味着这条能力在真实项目里会反复卡住）；
先覆盖最短的两条，各配一个三个月动作，这就成了你的提升计划（本章练习会把这套流程跑通）。

自评表模板（示意）：

```yaml
# 自评雷达 · 填写示例结构
person: "<你的名字>"
date: "2026-11"
scores:
  场景判断: 4
  技术理解: 2      # ← 短板 1
  评测设计: 3
  数据与知识: 2    # ← 短板 2
  成本与商业: 3
  交互与信任: 4
  跨职能推动: 3
  合规意识: 1      # ← 最高风险
plan:
  - dimension: 技术理解
    action: "每周跑一次 ai_pm_lab week1，把速查卡背成肌肉记忆"
  - dimension: 数据与知识
    action: "整理本业务的语料来源清单与权限清单"
```

## 4. 角色分工：谁定什么，谁拍板

AI 项目失败最常见的原因不是能力不够，是**没人拍板**。
下表把「定」和「拍板」分开——拍板权必须唯一，定义权可以多方参与。

| 角色 | 定什么（可协商） | 拍板什么（唯一责任人） | 不负责什么 |
| --- | --- | --- | --- |
| **AI 产品经理** | 场景选择、任务拆解、体验流程、兜底方案 | 这个场景做不做、验收口径是什么 | 模型内部结构、训练方案 |
| **算法 / 模型工程** | 档位选择、提示与评测方法、延迟与成本优化 | 技术方案是否可行、性能指标能否达成 | 产品优先级、用户要不要这个功能 |
| **应用工程** | 编排、工具接入、埋点与可观测 | 系统稳定性、灰度与回滚 | 场景该不该做 |
| **设计** | 交互形态、异常态、可信度表达 | 交互是否可用 | 模型能力边界 |
| **法务 / 合规** | 数据使用边界、留痕与审计要求 | 什么数据不能进、什么场景不能上 | 产品节奏 |
| **提示工程 / 评测** | 提示模板、样例集、回归用例 | 提示版本与评测集的准入 | 是否上线 |

遇到一件事没人认领时，按下表走（决策表）：

| 你的处境 | 判断依据 | 该怎么做 | 常见错误 |
| --- | --- | --- | --- |
| 业务方提「做个 AI 助手」，没人说得清谁用 | 说不清具体角色、频率、损失 | 先回现场做任务级调研，再谈功能（见 [04-用户研究：还原真实工作流与需求优先级.md](04-用户研究：还原真实工作流与需求优先级.md)） | 直接开需求会、排期、画原型 |
| 模型可能出错，业务方不接受任何错误 | 错误可被发现、后果可回滚吗 | 把「人工复核 + 兜底」写进首发范围，不承诺零错误 | 口头承诺「不会出错」 |
| 想换更强的模型 | 现有版本是瓶颈，还是任务本身不适合模型 | 先跑回归集，用数据看瓶颈在哪一层（见 02 章） | 拿 demo 体验当评测结论 |
| 提示词改了三轮还在调 | 问题在提示词，还是任务本身不该交给模型 | 回到任务级筛选（见 [03-场景筛选：什么该用 AI、什么不该.md](03-场景筛选：什么该用%20AI、什么不该.md)） | 陷进提示词调优黑洞 |

## 5. 三条入行路径与 90 天补齐清单

没有「标准路径」，只有不同的起点和不同的最短补法。

| 路径 | 手上已有的 | 最大缺口 | 90 天主线 |
| --- | --- | --- | --- |
| **技术转产品** | 工程直觉、看得懂链路 | 用户研究与优先级判断 | 补「从任务到价值」的翻译能力 |
| **业务转 AI** | 领域知识、客户关系、优先级直觉 | 模型边界直觉、评测设计 | 补「不靠猜的技术判断」 |
| **创业 / 内部转岗** | 决策快、能推动 | 方法论沉淀、可重复流程 | 补「把直觉写成可复用清单」 |

90 天补齐清单（模板，按起点勾选）：

```markdown
## 技术转产品 · 90 天
- [ ] 第 1–30 天：跟 3 个真实用户过一遍完整作业（不提问，只看）
- [ ] 第 31–60 天：把手上一个功能拆成任务清单，标出可自动化与不可自动化的步骤
- [ ] 第 61–90 天：独立产出一份带验收口径与兜底方案的 PRD
```

```markdown
## 业务转 AI · 90 天
- [ ] 第 1–30 天：跑完 02 章的速查卡，能默写「三类任务 → 档位」对应关系
- [ ] 第 31–60 天：为 1 个场景写抽样清单 + 对错判据 + 回归用例
- [ ] 第 61–90 天：主导一次模型升级的灰度与回归评审
```

```markdown
## 创业 / 内部转岗 · 90 天
- [ ] 第 1–30 天：写下本业务的 10 条「不做 AI」的判据
- [ ] 第 31–60 天：把每条判据落成可勾选的清单（可直接变成需求评审模板）
- [ ] 第 61–90 天：主持一次被否掉的需求复盘，写成决策记录
```

## 6. 五个常见误区

| 误区 | 一句话表现 | 反制动作 |
| --- | --- | --- |
| **把 AI PM 当提示词工程师** | 觉得自己该会写 prompt 才算入行 | 提示词是手段；判断「该不该用模型」才是岗位 |
| **需求传声筒** | 业务方说什么就做什么，只做翻译 | 每个需求都要问出「谁的什么任务、多高频率、损失多少」 |
| **demo 驱动** | 拿演示效果当产品结论 | demo 是最好情况；demo 不算验收标准 |
| **迷信模型能力** | 相信「现在的模型什么都能做」 | 所有能力边界以自己的评测集为准，不以厂商宣传为准 |
| **忽视合规** | 数据出域、留存、留痕等上线前才问 | 合规是设计约束，不是上线前的手续 |

补一条更隐蔽的：**用别人的能力曲线规划自己的路线图**。
同一个模型在有良好语料和没有语料的两个团队里表现完全不同，厂商公布的基准分数不构成你项目的证据。

## 7. 案例拆解：把一个「智能客服」需求拉回产品（示意案例）

以下是**示意案例**，用于演示拆解动作，不对应任何真实公司的内部数据。

**背景**：业务方提需求——「用 AI 做智能客服，替代人工坐席」。演示很惊艳。

**PM 的四步动作**：

1. **拆到任务层**。「接待用户」不是一个任务，是一串：识别意图 → 查订单 → 判断能否承诺 → 组织回复 → 引导转人工。
2. **逐步判断可自动化性**。前三步高度可自动化且有历史语料；第四步要查实时订单，语料里没有；第五步是兜底不是能力。
3. **算口径**。真正能承诺的是「意图识别 + 知识回答」，涉及金额、承诺时效、政策解释的部分必须人工兜底。
4. **写验收口径**。不写「客服体验提升」，写「意图识别准确率 ≥ 某阈值（由抽样集测定），承诺类问题 100% 转人工」。

**结果**：范围从「替代坐席」缩到「辅助坐席 + 转人工路由」。项目从「要替代人」变成「要减少重复劳动」，
首版范围反而更清晰，也才谈得上评测与上线。

**PM 怎么用它**：任何「看起来很酷」的 AI 需求，都先做第 1 步；
第 1 步做不出来，说明这个需求还没想清楚，不该进入排期。

## 8. 能力升级节奏：每周投什么、怎么复盘

能力是练出来的，但练什么必须先知道。按周固定节奏，比按心情突击有效。

| 周期 | 投入 | 产出物 | 验收标准 |
| --- | --- | --- | --- |
| 每周一次 | 30 分钟读一篇官方文档更新（提示、工具调用、计费口径） | 一条「本周能力变化」笔记 | 说得清它改变了哪个产品决策 |
| 每周一次 | 跑一次本周实验（见本章练习） | 一份可复现的输出 | 输出进了决策记录，而不是读完就扔 |
| 每两周一次 | 拿一个真实决策复盘 | 一条决策记录（背景 / 判据 / 结论 / 事后回看） | 能指出当时哪个判据用错了 |
| 每月一次 | 更新八维自评 | 新一版雷达 | 最低两项有对应动作，且有产出物 |

复盘看三个数，不看感觉：

- **决策记录条数**：这个月你做了几次「基于明确判据」的选择，而不是靠直觉拍板
- **评测通过率**：产品上线前的抽样集，有多少比例达到预设阈值
- **返工次数**：同一类问题第二次犯的次数

三个数都不难看，但**返工次数不降**，说明学的东西还没接进工作流。

## 9. 本章练习

```bash
cd Demos/examples && uv run --project .. python -m ai_pm_lab week1
```

实验做两件事：

1. **八维能力自评雷达**：实验用一份样例自评数据跑通完整流程（打分 → 短板排序 → 三个月提升计划）。
   你先按第 3 节给自己打一次分，再用同样的规则跑一遍对照——**自己的短板通常和样例不一样**。
2. **技术边界速查卡**：生成「任务类型 → 模型档位 → 常见翻车点 → 产品兜底」的速查表，
   这是 [02-技术地基：模型能力边界、上下文与推理参数.md](02-技术地基：模型能力边界、上下文与推理参数.md) 的预演。

**怎么算做对**：

- 每个维度的分数能对应到第 3 节某一档的描述，而不是随手给个整数
- 短板排序有理由：实验的短板线定在 **3 分及以下**，但低分不等于最该补，还要看它是否卡住你当前的项目
- 三个月计划里每条动作都能落到一个具体产出物，没有「多学习 AI」这类无法验收的句子
- 速查卡每一行都带产品兜底——只写「怎么做」不写「错了怎么办」的算没做

## 10. 本章要点

- AI 没减少 PM 工作，只是把确定性来源从「写清楚」换成了「测出来」
- 三类核心能力：业务判断力定值不值得、AI 素养定能不能做、落地推动力定能不能上线
- 八维雷达按 1–5 分打分，**排序比分数重要**，最低两项配三个月动作
- 打分必须可观察：对应到具体行为，而不是「感觉我懂」
- 拍板权必须唯一；定义权可以多方参与，拍板权多人等于没人拍板
- 五条常见误区里最贵的两个是 demo 驱动和迷信模型能力
- 每周固定节奏 + 每两周一条决策记录，比突击学习更能形成能力
- 复盘只看三个数：决策记录条数、评测通过率、返工次数

---

## 一句话结论

> **AI 产品经理的核心能力，是在答案不确定时仍能给出可验收的小切口**：用业务判断力决定值不值得做，
> 用 AI 素养判断能做到什么程度，用落地推动力让它真的上线。
