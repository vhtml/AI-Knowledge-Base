> 这个附录把四个典型场景从头走一遍：原始需求是什么、走了哪些岔路口、每个岔路口怎么定的、最后付出了什么代价。

**关于案例的说明**：以下四个案例是**基于公开可见的产品形态与行业常见做法整理的合成案例**，
用来演示决策方法。其中涉及的具体数字（成本、耗时、比例）均为**示意值**，
不代表任何一家真实公司的内部数据，也不构成对该公司的评价。真实项目请用你自己的数据替换。

## 案例 1 · 设备维修知识助手

### 一句话背景

某制造集团的设备维修班组要在故障时快速查到历史工单、备件参数和维修方案，
现有系统是一堆无人维护的 Word 文档和共享盘里的扫描件。

### 用户与原始需求

- **用户**：设备维修技师（约 60 人）、班组长、设备管理工程师
- **原始需求**："做一个维修问答机器人，维修工单里遇到故障描述能直接问出历史解决方案。"
- **表面需求 vs 真实需求**：表面是"问答"；真实是**在故障现场、几分钟内拿到能照做的步骤**。

### 决策链

| # | 岔路口 | 选项 | 怎么定的 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 这事该用 AI 吗？ | 规则引擎 / 知识库检索 / 大模型问答 | 四条判据打分：结果唯一性 **1**（同一故障可能有多种修法）、容错度 **0**（照错步骤可能损坏设备）、语料可得 **1**（有历史工单但格式极乱）、交互杠杆 **2**（技师能追问"这个型号呢"）→ 总分偏低 | **没有直接做问答机器人**，先做"检索 + 人工确认" |
| 2 | 语料怎么办？ | 直接喂文档 / 先做工单结构化 | 访谈发现：真正有用的是结构化故障码 + 现象 + 处置，Word 文档只有 20% 可用 | **先做数据治理**，把 3 年历史工单清洗成结构化记录（这是产品的活，不是技术的活） |
| 3 | 权限怎么设计？ | 全员可见 / 按角色可见 | 维修技师需要全部历史工单；但部分工单含设备序列号与故障细节，涉及客户保密信息 | **按角色 + 按设备线双层隔离**，检索在权限过滤之后做，不是在结果之后过滤 |
| 4 | 回答不确定怎么办？ | 强行给答案 / 给候选 + 标注置信 | 技师一旦被误导会照做，容错度为 0 | **必须给"最相关的 3 条历史工单 + 相似度提示"，不生成新步骤** |
| 5 | 自动化到哪一级？ | 自动生成维修方案 | 生成的步骤可能是对的，但班组不信任 | 停在**建议级**，由技师点开原始工单自己判断 |

### 方案要点

```
技师输入故障现象 + 报警码
      ↓
权限过滤（角色 + 设备线）     ← 先过滤再检索，避免"检索到但看不到"的错乱感
      ↓
结构化故障特征匹配（故障码 / 现象 / 设备型号）
      ↓
返回 3 条最相关历史工单：故障现象 / 当时怎么修 / 换了什么备件 / 工单号
      ↓
每条附"可点开原文"与"发生时间 / 设备型号是否一致"提示
      ↓
无匹配时明确说"没有找到同类记录"，并给出转人工的路径
```

**关键设计**：产品不生成答案，只做**高召回检索 + 可核对的呈现**。
在容错度低的场景，"把对的找出来"比"说的漂亮"重要得多。

### 评测标准（示意）

| 指标 | 定义 | 目标（示意） |
| --- | --- | --- |
| 召回命中率 | 返回的 3 条里至少 1 条与真实故障同类 | ≥ 85% |
| 引用正确率 | 每条引用确实来自历史工单且未串行 | 100%（硬门禁） |
| 忠实度 | 摘要不引入工单里没有的信息 | ≥ 95% |
| 越权召回率 | 检索结果中含用户无权查看的工单 | 0（硬门禁） |

**评测量大**：历史工单里由资深技师标注 200 组"现象 → 相关工单"，作为金标准。

### 成本与单位经济（示意）

| 项 | 值 | 说明 |
| --- | --- | --- |
| 单次查询输入 token | 约 3k（系统提示 + 结构化查询 + 权限上下文） | 结构化检索比全文塞入便宜一个量级 |
| 单次查询输出 token | 约 400（三条摘要） | 输出短是省成本的主要手段 |
| 单次查询成本 | 设为变量 `C_session` | 结构化匹配部分不花 token |
| 每技师月查询 | 约 80 次 | 现场高频、事后低频 |
| 相对替代方案 | 原本查文档约 25 分钟/次 | 这是价值锚，也是定价锚 |

**注意**：这个案例里**模型不是成本大头**，数据治理和结构化清洗才是。
这是"不选大模型做生成"带来的额外收益。

### 合规与风险

| 风险 | 等级 | 处理 |
| --- | --- | --- |
| 越权检索到其他客户/产线的工单 | 高 | 权限过滤前置 + 越权召回率为 0 的硬门禁 + 租户级隔离测试 |
| 技师过度信任 AI 给出的历史修法 | 中 | 只给历史记录不生成新步骤；界面明确标注"历史记录，非本设备建议" |
| 工单中的个人信息进入模型上下文 | 中 | 入库前脱敏；日志留存策略明确 |
| 知识库过期（旧方案照搬到新机型） | 中 | 工单带机型与生效日期；过期条目降权并标注 |

### 踩过的坑

1. **第一版做了生成式回答**。评测里"生成内容流畅度"很高，但技师测试时发现一条错误处置建议差点被照做。
   → **教训**：容错度低的场景，流畅度是负资产。评测指标从"回答好不好"改成"引用对不对"。
2. **权限做在检索之后**。用户看到"检索到 3 条但点开提示无权限"，体验极差，还暴露了"这里有什么"的元信息。
   → **教训**：权限是前置条件，不是后置过滤器。详见 [第 8 章](08-知识类产品设计：检索与引用.md)。
3. **数据治理被当成"等工程排期"**。工单清洗卡了两个月，功能没人用。
   → **教训**：数据治理是产品工作，需求优先级应高于功能开发。见 [第 4 章](04-用户研究：还原真实工作流与需求优先级.md)。

### 可迁移的结论

- **当容错度低时，产品的正确形态往往是"更聪明的检索"，而不是"更会说话的生成"。**
- **数据治理的优先级常常高于功能开发**——这是 AI 产品与传统软件产品最大的节奏差异之一。
- 权限、时效性、引用可核对性，这三件事是知识类产品的**信任基础设施**，不是加分项。

## 案例 2 · 客服工单 Copilot

### 一句话背景

某电商平台的售后客服团队，80 人，每天处理 6000 单，人工写回复模板 + 查政策 + 填工单。

### 用户与原始需求

- **用户**：一线客服、客服主管
- **原始需求**："给客服一个 AI 助手，实时告诉客户怎么答复。"
- **关键发现**：真正最耗时的不是"回复"，而是**"判断这个工单该走哪个流程、退货还是换货、要不要人工升级"**。

### 决策链

| # | 岔路口 | 选项 | 怎么定的 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 做全自动客服 Agent？ | 全自动 / Copilot | 退货政策涉及金额，答错直接产生资损 | **先做 Copilot**，客服自己决定用不用 |
| 2 | 提示词还是工作流？ | 自由对话 / 固定流程 + 节点 | 影子观察发现客服的判断依据高度结构化（订单状态 → 政策 → 动作） | **做成工作流**：状态判断是规则，回复措辞是模型 |
| 3 | 怎么让客服信？ | 展示"AI 说的" / 展示依据 | 客服主管反馈："不给出处他们不会用" | **每条建议都带政策条款号 + 历史相似工单**，可点开核对 |
| 4 | 自动化到哪一级？ | 自动回复 | 主管明确："可以自动发那些 100% 确定的话术" | 分两档：**确定性子类自动发**（如物流延迟标准话术），其余给草稿 |
| 5 | 怎么衡量？ | 回复字数 / 人工时长 | 主管更关心"客服愿不愿意用" | **采纳率**（生成的建议被原样或轻改使用的比例）作为核心诊断指标 |

### 方案要点

```
工单进来 → 规则引擎判定类别（是否标准工单）
      ↓
┌─ 标准子类 → 自动套用已审核话术（无需模型）
└─ 非标准 → 模型生成回复草稿
              ├─ 引用：政策条款号 / 订单信息 / 相似历史工单
              ├─ 置信提示：高 / 中 / 低
              ├─ 拒答出口：无法判断时给"转二线"按钮，而不是硬答
              └─ 可撤销：客服改一个字即记录反馈
      ↓
客服确认发送 / 修改后发送 / 忽略
```

**关键设计**：把"规则能判的"从模型手里拿走，模型只处理**真正需要语言理解的部分**。
这样既省钱，又让结果更可预测。见 [第 9 章](09-Agent%20与工作流：从%20Copilot%20到%20Autopilot.md)。

### 评测标准（示意）

| 指标 | 定义 | 目标（示意） |
| --- | --- | --- |
| 意图分类准确率 | 工单类别判对 | ≥ 98% |
| 政策引用正确率 | 引用的条款适用于该工单 | ≥ 95% |
| 草稿采纳率 | 客服未大幅修改就发送 | ≥ 40%（首版） |
| 错误建议率 | 会造成错误承诺的建议 | ≤ 1%（硬门禁） |

### 成本与单位经济（示意）

| 项 | 值 | 说明 |
| --- | --- | --- |
| 单工单模型调用 | 1 次（分类靠规则） | 不做多轮自我反思 |
| 输出长度 | 约 200 token | 长回复既贵又降低采纳率 |
| 缓存收益 | 政策文本可缓存 | 系统提示 + 政策片段命中率可到相当比例 |
| 每工单成本 | 设为变量 `C_session` | |
| 价值锚 | 客服单工单处理时长约 6 分钟 → 目标降到 3 分钟 | 80 人 × 6000 单/天 → 这是定价与 ROI 的基础 |

### 合规与风险

| 风险 | 等级 | 处理 |
| --- | --- | --- |
| 错误承诺造成资损 | 高 | 金额相关一律不自动发送；"错误建议率 ≤1%"为硬门禁；自动发送仅限 100% 确定话术 |
| 客服为省事不核对 | 中 | 界面默认展示依据；忽略操作也被记录并进入抽检 |
| 用户投诉"不是真人" | 中 | 回复签名区保留"AI 辅助生成"说明，符合生成内容标识要求（见 [第 13 章](13-安全、合规与风险治理.md)） |
| 未成年人误用 | 低 | 保留年龄相关策略继承 |

### 踩过的坑

1. **第一版让模型同时做分类和回复**。分类准确率只有 80%，因为模型"倾向于先猜类别再编理由"。
   → **教训**：能写成规则的判断不要交给模型。**结构化任务用规则，语言任务用模型。**
2. **自动发送范围定得太宽**。第一版自动发了 12% 的工单，三天内就出现两起不该自动承诺的纠纷。
   → **教训**：自动化的边界要用**错误代价**倒推，不是用"模型准确率够高"倒推。
3. **反馈只在不满意的客服那里收**。改了一句话的客服不会点"差评"，他们的沉默才是最常见的信号。
   → **教训**：把"被修改的幅度"当成一等反馈信号。见 [第 14 章](14-指标体系、数据闭环与%20PMF.md)。

### 可迁移的结论

- **"Copilot 先行"不是保守，是给团队学习的时间**：先让一线建立信任，再谈自动化等级。
- **反馈的采集方式决定迭代速度**。让用户额外点一下评价，比不上从"他改了多少"里自动读出信号。
- 自动化的边界要按**错误代价**分档，而不是按模型能力分档。

## 案例 3 · 代码助手

### 一句话背景

某开发工具团队做了一个代码补全 + 对话式编程助手，从"补全单行"演进到"完成一个任务"。

### 用户与原始需求

- **用户**：企业内 200 名开发者
- **原始需求**："让 AI 能帮我们写代码。"
- **关键发现**：开发者真正的时间不在"写"，而在**"读别人的代码、查 API 怎么用、在仓库里定位"**。

### 决策链

| # | 岔路口 | 选项 | 怎么定的 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 做什么形态？ | 单行补全 / 对话问答 / 任务级 Agent | 影子观察发现"查 API 用法"占开发者查询类工作的最大比例 | **先做仓库内的检索 + 问答**，补全作为基础能力保留 |
| 2 | 代码检索怎么做？ | 向量检索 / 精确符号检索 + 向量兜底 | 代码检索对精确性要求极高，"搜错了函数名"就完全没用 | **符号索引为主、向量召回为辅**，且要求引用文件与行号 |
| 3 | 能不能自动改代码？ | 直接改 / 给补丁 / 分支 + PR | 企业最怕 AI 改坏主干 | **只开分支 + 提 PR，人工评审是强制的** |
| 4 | 自动等级怎么定？ | 全自动 | 存在"看起来跑通但引入边界 bug"的风险 | 停在**带审批的自动执行**：可以跑测试、可以改文件，但合并必须人点 |
| 5 | 成本怎么控？ | 统一用最强模型 | 仓库上下文很大，长上下文成本高 | **模型分级路由**：简单检索用小模型，复杂重构用大模型；提示缓存复用仓库上下文 |
| 6 | 怎么证明有用？ | 写代码行数 | 行数增加可能意味着产出更多垃圾代码 | **以"变更通过评审率"和"评审耗时变化"为核心指标** |

### 方案要点

```
开发者提问 / 发起任务
      ↓
意图判断（问代码 / 查 API / 改代码 / 跑命令）
      ↓
┌─ 问代码 → 符号检索 + 向量兜底 → 返回片段 + 文件行号 + 精确引用
├─ 查 API → 官方文档检索（版本锁定）→ 版本 + 出处
├─ 改代码 → 开分支 → 生成补丁 → 跑测试 → 提 PR（强制人工评审）
└─ 跑命令 → 只读命令直接跑；写操作需确认（权限档位：写）
      ↓
引用可点开核对；命令执行记录在会话里
```

**关键设计**：**权限三档**（读 / 写 / 危险写）在工具层面显式标注，
写操作需要确认，危险写（删文件、推分支、发布）必须二次确认并说明后果。见 [第 10 章](10-工具、多模态与企业系统集成.md)。

### 评测标准（示意）

| 指标 | 定义 | 目标（示意） |
| --- | --- | --- |
| 检索命中 | 给出的文件行号确实包含相关实现 | ≥ 90% |
| 补丁通过率 | 生成的补丁通过仓库测试 | ≥ 70%（首版） |
| 评审通过率 | PR 被人工合并的比例 | ≥ 60% |
| 越权写入 | 未确认即修改仓库文件 | 0（硬门禁） |

### 成本与单位经济（示意）

| 项 | 策略 | 说明 |
| --- | --- | --- |
| 仓库上下文 | 提示缓存 | 同一仓库的公共文件可复用，是最大的一笔节省 |
| 模型分级 | 简单/复杂路由 | 检索类走小模型，改代码走大模型 |
| 上下文裁剪 | 只取相关目录 | 不把整个仓库塞进去 |
| 重试 | 限制 + 退避 | 失败重试是最容易被忽略的成本放大器 |
| 每开发者月成本 | 设为变量 | 与企业席位费对比得出毛利空间 |

### 合规与风险

| 风险 | 等级 | 处理 |
| --- | --- | --- |
| 引入漏洞代码 | 高 | 必须过现有 CI 与扫描；扫描结果作为合并门禁 |
| 命令执行造成破坏 | 高 | 权限三档；危险写二次确认；默认只读 |
| 代码外泄 | 中 | 企业部署可用私有端点；训练数据策略明确写入合同 |
| 版权与许可证 | 中 | 引用出处；生成内容的许可证提示；依赖许可证扫描 |

### 踩过的坑

1. **给"任务级 Agent"过早开权限**。能自主改多个文件并执行命令后，模型偶尔会做出"看起来合理但删掉了不该删的东西"的改动。
   → **教训**：自动化等级提升必须**换一档权限**同时提升，而不是只换模型。
2. **上下文全量塞入仓库**，单次会话成本高到无法商用。
   → **教训**：上下文工程是产品成本设计的一部分，不是工程细节。见 [第 12 章](12-成本、延迟与单位经济.md)。
3. **用"生成了多少代码"当成功指标**，团队开始倾向于让 AI 生成更多代码。
   → **教训**：选错指标会直接改变团队行为。

### 可迁移的结论

- **开发者愿意为"检索 + 解释"付费，不一定愿意为"替你写完"付费**——除非你的评测和护栏足够可信。
- 自动化等级与权限档位必须**绑定提升**。
- 上下文工程直接决定商业可行性，属于产品决策。

## 案例 4 · 合同条款审阅

### 一句话背景

某中型企业的法务与商务部需要一个工具，在签合同前标出偏离公司标准模板的条款。

### 用户与原始需求

- **用户**：商务经理（主要用户）、法务（把关人）
- **原始需求**："AI 帮我们看合同有没有问题。"

### 决策链

| # | 岔路口 | 选项 | 怎么定的 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 给不给结论？ | 直接说"这条有问题" / 只标出偏离点 | 法务明确："我们不信任 AI 的判断，我们只信它标得准" | **只做定位与归类，不做对错判断**；风险等级由人定 |
| 2 | 怎么保证不漏？ | 只看合同正文 / 对照标准模板逐条比 | 漏审是法务最不能接受的 | **以公司标准模板为基准做逐条对照**，输出"缺失 / 偏离 / 一致"三态 |
| 3 | 自动化到哪一级？ | 自动出修改建议 | 法务的修改建议高度个性化，AI 给错还不如不给 | 停在**建议级 + 草稿级**，改写文本必须人确认 |
| 4 | 怎么定义"准"？ | 总体准确率 | 漏一条违约金条款比多标十条重要得多 | **按条款类型分别看召回率**，且关键条款类型（违约金、管辖权、知识产权）单独设硬门禁 |
| 5 | 幻觉风险怎么办？ | 允许自由文本回答 | 合同分析必须可溯源 | **强制结构化输出 + 每条结论必须引用原文位置**，无出处则不输出 |

### 方案要点

```
上传合同（PDF / Word）
      ↓
解析成条款序列 → 与标准模板逐条对齐
      ↓
三态标注：缺失 / 偏离 / 一致
      ↓
每条输出：原文位置（页/段/字符区间）+ 条款类型 + 偏离描述
      ↓
关键条款类型单独成组，标记"必须人工过"
      ↓
允许生成改写草稿（标记为草稿，人工确认后才可复制）
```

**关键设计**：**结论的形状由用户的信任方式决定**。
法务要的是"标得准、位置对"，不是"说得像律师"。产品形态必须服从用户的验证路径。

### 评测标准（示意）

| 指标 | 定义 | 目标（示意） |
| --- | --- | --- |
| 条款对齐召回率 | 标准模板中的条款被找出的比例 | ≥ 95% |
| 关键条款召回率 | 违约金/管辖权/IP 类条款 | 100%（硬门禁，宁可误报） |
| 原文定位准确率 | 引用位置确实对应所述内容 | ≥ 99% |
| 幻觉率 | 无原文依据的结论 | 0（硬门禁） |

**评测集来源**：法务标注 300 份真实（脱敏）合同，每份标出缺失/偏离条款与位置。

### 成本与单位经济（示意）

| 项 | 说明 |
| --- | --- |
| 输入 | 合同全文 + 标准模板，单次输入大但**同一客户的模板可缓存** |
| 输出 | 结构化标注结果，长度可控 |
| 成本变量 | `C_session`，主要由输入 token 决定 |
| 价值锚 | 法务审一份合同约 40 分钟；商务自己初筛可省大部分等待时间 |
| 定价锚点 | 按"份"计价比按席位更贴合价值（**用量/结果型定价**，见 [第 6 章](06-定位、价值主张与商业模式.md)） |

### 合规与风险

| 风险 | 等级 | 处理 |
| --- | --- | --- |
| 漏审关键条款 | 高 | 关键条款类型召回率 100% 硬门禁；宁可误报 |
| 结论被当成法律意见 | 高 | 界面明确标注"辅助工具，非法律意见"；结论为"偏离"而非"违法" |
| 合同内容进入训练数据 | 高 | 明确数据不用于训练；企业部署可用私有端点；留存期限与删除机制 |
| 跨境传输 | 中 | 数据驻留方案在合同中明确（欧盟客户需评估跨境传输合规） |
| 生成内容标识 | 低 | 内部工具，若内容外发需按 [第 13 章](13-安全、合规与风险治理.md) 评估标识义务 |

### 踩过的坑

1. **第一版让 AI 直接给"这条条款有风险"的结论**。法务试用后说："你凭什么说它有风险，给我依据。"
   → **教训**：产品形态服从用户的验证路径。用户的验证动作是"翻原文"，不是"读判断"。
2. **用整体准确率做验收**，掩盖了关键条款类型的召回不足。
   → **教训**：指标要**按风险类型分组**，总体平均会掩盖最要命的问题。见 [第 11 章](11-评测体系：AI%20产品的质量标准.md)。
3. **把"提供改写建议"和"给出风险判断"一起上线**。合规同事要求先下线改写功能。
   → **教训**：能力上线顺序应按**风险从低到高**排，而不是按开发难度排。

### 可迁移的结论

- **高风险场景里，AI 的正确角色是"高召回的定位器"，不是"结论给出者"。**
- **评测指标必须按风险类型分组**，总体平均会系统性掩盖最贵的错误。
- **能力上线顺序按风险排**，不按开发难度排。

## 四个案例的横向对照

| 维度 | 案例 1 知识助手 | 案例 2 客服 Copilot | 案例 3 代码助手 | 案例 4 合同审阅 |
| --- | --- | --- | --- | --- |
| 错误代价 | 中高（照做损坏设备） | 中（资损） | 中（漏洞/破坏） | 高（漏审关键条款） |
| 最高自动化等级 | 建议 | 部分自动发送 | 带审批自动 | 建议 + 草稿 |
| 核心指标 | 召回命中率 | 采纳率 | 评审通过率 | 关键条款召回率 |
| AI 的角色 | 检索器 | 措辞生成器 | 任务执行者 | 差异定位器 |
| 成本大头 | 数据治理 | 调用量 | 上下文 | 输入 token |
| 最贵的坑 | 权限后置 | 自动化边界过宽 | 上下文全量 | 指标未分组 |

### 从对照里能读出的四条通则

1. **错误代价决定自动化等级，不决定模型选型。** 四个案例的模型侧差别远小于形态差别。
2. **AI 的角色是跟着"验证路径"走的**：用户能怎么核对，产品就长成什么样。
3. **成本大头常常不在 token 上**，而在数据治理、上下文长度、重试上。
4. **评测指标必须按错误类型分组**，总体平均会掩盖最贵的错误。

## 一句话结论

> **这四个案例里，AI 技术选型几乎没有起到决定作用，起决定作用的是三件事：错误代价、用户的验证路径、数据治理的优先级。**
> 这也是整套教程反复讲的那句话的展开——**先判场景，再谈方案**。
