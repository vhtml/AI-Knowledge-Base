# 08 · 知识类产品设计：检索与引用

> **这篇要回答**：知识类 AI 产品为什么卡在"答不准"？RAG 全链路里哪些是产品决策、哪些是技术实现，以及三个核心指标该怎么定义和测？

---

## 1. 两种范式：检索增强 vs 长上下文塞满

这不是技术路线之争，而是**产品能力的选择**——它直接决定你的产品能不能引用、能不能更新、能不能分权。

| 判断维度 | 选检索增强（RAG） | 选长上下文塞满 |
| --- | --- | --- |
| **知识体量** | 远超单次上下文能装下的规模 | 一次能全部装下 |
| **知识时效** | 频繁更新，需要随时生效 | 稳定不变，长期不变 |
| **溯源要求** | 必须给到句级引用与来源 | 不要求，用户只看结论 |
| **权限要求** | 需要按用户/部门过滤 | 单一权限域内使用 |
| **任务性质** | 先筛选再综合（问题明确） | 需要同时看全部材料（探索、整体判断） |
| **成本结构** | 检索开销 + 少量生成开销 | 上下文 token 随资料量线性上升 |

### 决策表：这一版该选哪个范式

| 你的处境 | 判断依据 | 该怎么做 | 常见错误 |
| --- | --- | --- | --- |
| 知识库大且每周都在变 | 单次装不下，且用户会追问"最新政策" | 检索增强为主 | 每次把全部文档塞进上下文，成本失控且过期 |
| 资料少而稳定，任务需要跨文档综合 | 总量能装下，问题是"整体判断" | 长上下文为主 | 拆成碎片后反而丢失整体关系 |
| 用户明确要求"告诉我依据" | 有引用是硬需求 | 检索增强 + 句级引用 | 只给结论，用户无法采信也无法追责 |
| 多部门数据、权限不一 | 同一问题不同人能问出不同答案 | 检索增强 + 检索层过滤 | 靠提示词要求模型"别回答没权限的" |
| 两者都要 | 多数知识类产品的真实状态 | **混合**：先检索缩小范围，再把选中片段长上下文读完 | 只做一层，把"检索不到"当成唯一失败原因 |

**产品经理怎么用它**：选范式时先问**产品需求**，而不是技术偏好。
"要不要引用""要不要按人过滤""知识会不会更新"——这三个问题的答案，几乎直接决定了范式。

**别忘了**：范式是可以在产品迭代中切换的，先按当前需求选，别为未来的可能性过度设计。

## 2. RAG 全链路：每个环节都是产品决策

RAG 常被当成"技术方案"，但链路上的每一环都对应一个**用户能感知到的差异**。

检索增强的原始设定见 [RAG 论文](https://arxiv.org/abs/2210.03629)，工程实现可对照 [LangChain RAG 教程](https://python.langchain.com/docs/tutorials/rag/)（均核实于 2026-11）。

| 技术环节 | 对应的产品决策 | 用户能感知到的差异 |
| --- | --- | --- |
| **切分** chunking | 按什么粒度切：固定长度 / 章节结构 / 语义边界 | 答案是否漏掉前半句上下文；引用是否指向半截话 |
| **嵌入** embedding | 按什么口径建索引：按部门 / 按主题 / 混合 | 搜"报销"却找不到"费用报销制度"这类同义不同词 |
| **召回** retrieval | 召回几篇、怎么召：关键词 / 向量 / 混合、几路并行 | 明明有资料却找不到；或召回一堆不相关的 |
| **重排** rerank | 召回 N 篇后是否重排、留 Top K | 引用是否切题，还是"引了但没引对" |
| **生成** generation | 约束多严、是否允许外部知识、要不要强制带引用 | 答案是否胡说；是否每句话都有出处 |
| **引用** citation | 引用到哪一级：文档 / 段落 / 句子 | 用户能不能点开就核对到那一句 |

**这张表怎么用**：当用户抱怨"答得不对"时，**按链路顺序排查**，不要一上来改提示词（示意流程）。

```
用户说答得不对
   │
   ├─ 正确片段根本没被召回？ ──→ 切分 / 嵌入 / 召回 / 重排
   │
   ├─ 召回了，但引用指向了别的段落？ ──→ 重排 / 生成时的引用绑定
   │
   └─ 引用对得上，但结论超出引用？ ──→ 生成约束 / 拒答策略
```

**顺序很重要**：召回没命中时，生成侧再怎么调都是徒劳。
在检索层修的收益，通常远大于在提示词里调参数。

## 3. 数据治理是产品工作

知识类产品有一个别的产品没有的依赖：**它依赖别人维护好数据**。
这件事一旦没人负责，模型再好也答不准。

| 必答问题 | 没有答案会怎样 | 典型做法 |
| --- | --- | --- |
| **谁维护** | 文档越积越旧，没人负责 | 每个知识域指定 owner，纳入定期评审 |
| **多久同步** | 用户拿到过期政策 | 定义同步节奏，并把它作为对外承诺的一部分 |
| **过期怎么办** | 已废止的制度仍被检索并引用 | 生效/失效日期 + 废止标记 + 下线流程 |
| **冲突怎么裁决** | 两份文档说法不一致，系统随机挑一份 | 明确的优先级规则 + 定期冲突扫描报告 |

### 冲突裁决的典型优先级（示意规则，需按自身情况定）

```
最新生效版本  >  所属部门的权威版本  >  通用制度  >  历史归档
```

**关键区分**：**"没有"和"过期"是两回事**。
检索不到就明说没有；检索到了但已过期，要明确标注状态。
把过期内容当成现行内容输出，是知识类产品最典型也最伤信任的失败。

**产品经理怎么用它**：数据治理不该只当运营清单，它是**产品承诺的组成部分**。
"我们的答案来自最新生效的制度"——这句话能不能说出口，取决于上面四个问题有没有答案。
同时要记住：**治理成本会随知识量线性增长**，这会反过来约束产品选什么场景做（见第 1 节的范式选择）。

## 4. 权限与租户隔离：这是产品设计，不是技术细节

**越权检索 = 数据泄露**。哪怕最终答案没说出敏感内容，检索层碰到过、缓存里留下过，就算事故。

三条设计规则：

1. **权限过滤必须在检索层**，不能靠提示词约束。
   "不要回答用户无权查看的内容"是一句请求，不是一道闸门——模型不构成安全边界。
2. **引用也是泄露通道**。即使结论无害，引用原文片段同样会暴露无权查看的内容。
3. **过滤不能"先召回后过滤再展示"**，那等于先看过。过滤要在候选进入生成之前完成。

这类问题在 [OWASP 大模型应用 Top 10](https://owasp.org/www-project-top-10-for-large-language-model-applications/) 中被单列为敏感信息泄露与过度代理执行等条目（核实于 2026-11），做安全设计时可直接对照。

### 决策表：索引隔离方案怎么选

| 方案 | 成本 | 风险 | 适用 |
| --- | --- | --- | --- |
| 共享索引 + 后置过滤 | 低 | 过滤漏一条即泄露，且难审计 | 极小规模、同一权限域 |
| 共享索引 + 前置过滤 | 中 | 实现复杂，需仔细验证 | 中等规模、多权限域 |
| 按权限域分区分索引 | 中高 | 运维复杂度上升 | 大多数企业产品（按部门/租户分区） |
| 每租户独立索引 | 高 | 成本与运维压力最大 | 强合规客户、隔离要求高 |

**产品经理怎么用它**：这不只是选型，是**要写进商务承诺的事**——
"我们支持私有化部署""数据不跨租户"这类说法，背后就是这张表的某个选择。

## 5. 引用与溯源的可交互设计

引用如果不能点开核对，就只是装饰。第 07 章讲了兜底四件套，这里讲**具体怎么做**。

| 决策点 | 选项 | 建议 | 理由 |
| --- | --- | --- | --- |
| **引用粒度** | 文档级 / 段落级 / 句子级 | 句子级 | 段落级仍要用户自己找，句子级一步到位 |
| **呈现形式** | 角标 / 脚注 / 侧栏 | 角标 + 侧栏 | 脚注需要跳转，打断阅读 |
| **打开方式** | 新窗口 / 内嵌 / 抽屉 | 内嵌抽屉 | 不离开当前上下文，便于连续核对多处 |
| **版本** | 显示当前版 / 锁定当时版 | 锁定当时版 + 更新提示 | 引用要可复现，"文档后来改了"必须让用户知道 |
| **混合来源** | 内部 / 外部 / 模型常识 | 分别标注 | 让用户知道哪部分有企业依据、哪部分是通识 |

**一个容易忽略的细节**：当引用的原文在你核对之前已经被更新或删除，
界面要显示"该片段已于某日期更新/已下线"，而不是给一个打不开的链接。

**判断引用有没有用**：看**核对率**——用户点开引用的比例（[第 07 章](07-对话式体验设计：信任、不确定性与拒答.md)的行为指标）。
核对率过低说明引用增加噪音、没带来价值；核对率过高说明用户根本不信任答案。
健康的做法是引用少而准，但每一条都能点开。

## 6. 知识缺失时的正确行为

知识类产品最危险的失败不是答不出，而是**答得很像真的**。缺知识时的正确行为（示意流程）：

```
检索不到
   │
   ├─ 明确说没找到，并说清搜了哪些范围
   ├─ 放宽一次再搜（换同义词 / 换检索域 / 放宽过滤）
   ├─ 仍无 → 给出相近内容，并标注「这是相近资料，不是该问题的答案」
   └─ 仍无 → 指向负责的人/群，并附上已查过的范围
```

### 决策表：四种"没答上"的正确处理

| 情况 | 系统行为 | 为什么 |
| --- | --- | --- |
| **知识库里完全没有** | 明确说没有 + 转人工路径 | 此类编造代价最高 |
| **有，但检索没召回** | 换查询放宽再试一次 | 这是召回问题，不是知识缺失 |
| **召回了但不相关** | 说"没找到相关答案" + 给相近内容 | 避免用一堆引用堆砌出可信的假象 |
| **相关但不完整** | 答出有依据的部分，明确标出缺口 | 诚实且仍然有用 |

**还有一种隐蔽的失败：引用存在，但结论并不被引用支撑。**
比如引了一条"报销期限是 30 天"的制度，却得出"逾期可以补报"。
引用在、结论不在——这正是"回答忠实度"要抓的问题，也是第 7 节的评测重点。

**产品经理怎么用它**：缺知识时的兜底路径不是"兜底文案"，而是一条**完整的用户旅程**：
被告知没有 → 知道谁负责 → 提交需求 → 未来可被检索到。
这条旅程本身就是产品的一部分。

## 7. 评测：三个指标的定义与测法

| 指标 | 定义 | 怎么测 | 失败说明 |
| --- | --- | --- | --- |
| **召回命中率** | 正确的知识片段是否出现在召回结果里 | 标注每个问题"应召回片段"，跑检索后比对 | 检索层（切分/嵌入/召回/重排） |
| **引用正确率** | 给出的引用是否来自期望来源、并且真的支持对应的结论 | 逐条检查"引用内容 → 结论"的蕴含关系 | 生成时的引用绑定错位 |
| **回答忠实度** | 回答里的事实性陈述是否都能在召回内容中找到支持 | 把回答拆成陈述句，逐句检查是否被上下文支持 | 生成编造、引入外部知识 |

### 三者的关系：一条排查链（示意）

```
先查 召回命中率 ──► 再查 引用正确率 ──► 最后查 回答忠实度
   检索不到            引到了但配错          配对了但编了
```

**为什么必须按这个顺序**：召回没命中时，引用正确率与忠实度这两个指标失去意义
（没有东西可引）。反过来只看忠实度，你可能一直在修一个"检索层"的 bug，
只是恰好被提示词掩盖了。

### 测法的三个工程要点

1. **黄金集**：固定一批问题 + 标注好的应召回片段，作为回归基线。
   任何改动前后跑同一批，才能比较。
2. **拆到陈述句**：忠实度不是给整段打分，是把答案拆成事实性陈述逐句判。
   整段打分会把"3 句对 1 句错"算成对。
3. **评审方式**：大批量可用模型辅助评审，但**抽样人工复核**必须保留——
   评审模型和被测模型共享盲区时，错误会互相掩盖。

完整的评测门禁与回归流程见[第 11 章](11-评测体系：AI%20产品的质量标准.md)。

### 阈值（示例默认值，需自行校准）

| 指标 | 默认下限 | 低于阈值时先动哪里 |
| --- | --- | --- |
| 召回命中率 | 0.80 | 切分粒度、嵌入口径、召回路数 |
| 引用正确率 | 0.90 | 引用粒度与绑定方式 |
| 回答忠实度 | 0.80 | 生成约束、拒答策略、模型选择 |

> 上表是**本教程给出的示例默认值**，不是行业标准。不同业务风险差异极大——
> 涉及医疗、法务、付款决策的场景应显著更严；请用自己的黄金集校准后再使用，
> 并把"改阈值"和"改算法"当成两件事分开做。

## 8. 案例拆解：企业知识问答的三次失败迭代（示意案例）

> 以下为**示意案例**，用于演示"按链路顺序排查"的思路。
> 数字为示意，用箭头表示方向而非具体分数，不代表任何真实公司的内部数据。

一个虚构的内部制度问答产品，连续三次迭代：

### 第一次：答案"只答了一半"

| 维度 | 内容 |
| --- | --- |
| 症状 | 答案常漏掉条件、例外，引用指向半句话 |
| 根因层 | **切分**：所有文档按固定长度切，把一条制度切成了三片 |
| 修法 | 按文档结构切（章节 / 条款 / 附件），并给每片补上标题与所属章节作为上下文 |
| 指标方向 | 召回命中率 ↑，引用正确率 → |

### 第二次：答案找到了，引用却对不上

| 维度 | 内容 |
| --- | --- |
| 症状 | 检索到的片段是对的，但引用指向了相邻的另一段 |
| 根因层 | **召回 + 生成绑定**：召回 Top K 未经重排，生成时引用序号与片段错位 |
| 修法 | 召回后加重排再取 Top K；生成时强制"结论—依据"成对产出，引用绑定到片段而非序号 |
| 指标方向 | 召回命中率 →，引用正确率 ↑，回答忠实度 → |

### 第三次：答案有依据了，却夹带"通常做法"

| 维度 | 内容 |
| --- | --- |
| 症状 | 制度没写的内容，模型用常识补了一句，读起来很顺但无依据 |
| 根因层 | **生成约束**：提示未限制"仅依据提供材料"，也未定义材料不足时的行为 |
| 修法 | 提示显式约束只用材料；把"补充说明"单独分区并标注**非依据**；材料不足时强制走"没找到"的模板 |
| 指标方向 | 回答忠实度 ↑ |

### 三次迭代的共同教训

1. **每一轮只动一层**：动多处就无法归因，下次出问题不知道是哪次改动引起的
2. **先修检索再修生成**：第一次的切分问题如果用提示词去绕，会一直绕
3. **每一轮都要留黄金集**：没有基线，"变好了"只是感觉

**这一章的方法论落点**：知识类产品的迭代节奏，本质上是**沿着链路一层层收敛**。

## 9. 常见误区清单

- **把 RAG 当纯技术方案**：每个环节都对应用户可感知的差异
- **所有文档都用同一种切分**：合同、制度、FAQ 的最佳粒度完全不同
- **引用做成装饰**：不可点开的引用既不增加信任也增加噪音
- **只看回答好不好，不看三个指标**：不知道该修检索还是修生成
- **用提示词做权限隔离**：模型不是安全边界，过滤必须在检索层
- **知识库无人维护**：模型再强也答不准，治理成本随知识量线性增长
- **用长上下文掩盖检索问题**：成本上涨、可溯源性下降，还可能拿到过期内容
- **没有黄金集**：改动无法比较，迭代变成抽奖
- **把"有引用"当"有依据"**：引用存在但不支持结论，是忠实度问题
- **照抄别家的阈值**：业务风险不同，阈值必须用自己的数据校准
- **把"没找到"当成需要隐藏的失败**：它是知识缺口信号，应该被记录并排期

## 10. 本章练习

**这次练习要用你自己的真实数据。** 示例数据只能验证你算对了，验证不了你的判断——
真数据才会暴露判断里的漏洞。

**输入**：10 条**真实**的用户问题与对应答案样本（你的产品、你的客服工单，或你所在领域的公开问答都行）。

**步骤**：
1. 按第 7 节的三项指标逐条判：召回命中率（正确片段有没有被检索到）、引用正确率（引用是否支持结论）、回答忠实度（有没有引入材料外的信息）。
2. 算出三个率。
3. 按第 2 节的排查链定位**最弱的那一环**（切分 / 嵌入 / 召回 / 重排 / 生成 / 引用）。
4. 对最弱那一环写一个具体改法。

**产出**：10 条评测记录 + 三个率 + 一个"最弱环节 + 改法"的结论。

**怎么算做对**：
- 你能说出这 10 条里哪几条是**知识缺失**而不是检索失败——这两类的改法完全不同
- 三个率里**最低的那个**决定了改哪一环，不要取平均
- 改法是产品动作（改切分策略、改召回方式、加引用位置），不是"调调模型"

---

## 11. 本章要点

- 范式选择看**产品需求**：引用、权限、更新频率三者基本决定选 RAG 还是长上下文
- RAG 每个环节都是产品决策：切分 / 嵌入 / 召回 / 重排 / 生成 / 引用，各有用户可感知的差异
- 排查顺序：**召回 → 引用 → 忠实**，检索没修好就去调提示词是浪费
- 数据治理是产品工作：谁维护、多久同步、过期怎么办、冲突怎么裁决，四个问题都要有答案
- **越权检索等于泄露**：权限过滤在检索层，提示词不是安全边界
- 引用要**可点开、到句级、锁版本**，否则只是装饰
- 缺知识时的正确行为是"没找到"加兜底路径，不是编
- 三个指标：**召回命中率 / 引用正确率 / 回答忠实度**，配黄金集做回归；阈值是示意的，必须用自己的数据校准

---

## 一句话结论

> **知识类产品的准确率不是调出来的，是一层层收出来的**：先在检索层把对的片段找出来，再在生成层让每个结论都挂在依据上，最后用"资料里没有"守住不编的底线。
