# 10 · 工具、多模态与企业系统集成

> **这篇要回答**：工具 schema 怎么设计才不翻车？权限怎么分档？多模态各适合什么活？企业集成清单上必须有哪些项？

---

## 1. 工具就是产品的能力边界

模型自己不会做事，它只能**调工具**。所以工具集就是这个产品的能力边界与风险边界——它比提示词更能决定产品能做什么、不能做什么。

由此得到一个反直觉但关键的结论：

> **工具 schema 设计，本质上是交互设计。**

用户看到的是一段话，模型看到的是一份 schema。schema 里写"这个工具干什么、什么时候用、参数什么含义、失败了返回什么"，就是给模型的需求文档；schema 里没写，模型就只能猜。

Anthropic 关于工具设计的工程文章给出的几条建议，正好是 PM 该写进需求文档的东西：工具名要说清做什么、描述里要写明**什么时候该用哪个工具**、参数要少而明确、错误信息要让模型能自我纠正（[Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)，核实于 2026-11）。

| 现实里常见的写法 | 后果 |
| --- | --- |
| 工具名 `query_data`，描述 "查询数据" | 模型不知道该用它还是 `search_docs`，乱调 |
| 参数 `q: string`，描述 "查询条件" | 模型自由发挥格式，后端 400 |
| 失败时返回 `{"error": "failed"}` | 模型无法判断该重试、换参数还是转人工 |

**产品经理怎么用它**：写工具清单时，不要只写"要接一个查询接口"，要写成**给模型看的能力说明书**。工具清单本身就是产品需求文档的一部分（对应 AI PRD 的「4.4 工具与权限」，见 [附录-B 模板库](附录-B-模板库.md)）。

## 2. 工具设计四问

每个工具都要回答四个问题。答不全的工具，不要上线。

| 问题 | 要写清什么 | 判据 | 常见错误 |
| --- | --- | --- | --- |
| **给什么信息** | 这个工具能访问什么数据范围、返回什么类型的内容、什么时候**不该**用它 | 描述里同时写了"适合"和"不适合" | 只写能力不写边界，模型会在错的时候用它 |
| **要什么输入** | 最少必需参数、每个参数的取值域、单位、默认值、格式 | 参数能枚举就枚举，日期格式写死 | 参数过多且互相重叠，模型填错组合 |
| **返回什么** | 返回结构、条数上限、是否分页、**空结果与错误怎么表示** | 空结果和错误必须可区分 | 空数组和错误都返回 `[]`，模型以为查到了 |
| **失败怎么办** | 错误码、哪些可重试、哪些要换参数、什么时候该转人工 | 错误信息自带"下一步建议" | 只有一句 500，模型原地重试到超时 |

一个合格的工具描述长这样（示意，仅表达写法，不是可运行代码）：

```json
{
  "name": "search_tickets",
  "description": "按关键词检索本团队的工单。只用于查历史工单；要查知识库请用 search_runbook。返回最多 20 条，按更新时间倒序。",
  "parameters": {
    "keyword":  {"type": "string", "description": "工单标题或正文中的关键词，1-3 个词"},
    "status":  {"type": "string", "enum": ["open", "pending", "closed"], "default": "open"},
    "days":    {"type": "integer", "description": "只看最近 N 天，默认 30"},
    "exact":  {"type": "boolean", "default": false, "description": "true=精确匹配，false=模糊"}
  }
}
```

注意描述里的三句话：**做什么**、**跟谁的区别**、**返回什么**。这三句缺一，模型就会在边界上犯错。

对照上面四个问题看这份 schema：`description` 同时回答了"给什么信息"和"返回什么"，
`parameters` 的 `enum` / `default` / 类型回答了"要什么输入"，
错误约定（这里靠 description 里"返回最多 20 条"这类边界说明）回答了"失败怎么办"。

> **这是全套教程里唯一保留的代码形态，原因是它有用**：JSON 是工具与模型之间的**契约格式**，
> 不是你要写的程序——但工程每加一个工具，schema 长什么样、描述怎么写，**是你评审的第一道关**。
> 看不懂它，就只能相信工程的判断；看懂了，你才能指出"这个描述会让模型在边界上犯错"。

## 3. 工具调用的三类翻车

工具出问题分三大类，产品侧的兜底方式完全不同。

| 翻车类型 | 表现 | 根因 | 产品侧兜底 |
| --- | --- | --- | --- |
| **幻觉参数** | 传了不存在的工单号、编造日期、参数格式乱 | 参数取值域没说清，或缺存在性校验 | schema 枚举 + 后端存在性校验；查不到就返回"没找到 X，可选 Y/Z"，而不是让模型自己编 |
| **越权** | 调了用户本来无权访问的工具或数据 | 权限校验放在模型侧，或按工具而非按用户授权 | 授权永远在服务端按用户身份判定；模型只提出请求，不做决定（见 [OWASP LLM Top 10](https://genai.owasp.org/llm-top-10/)，核实于 2026-11） |
| **重复调用与死循环** | 同一个工具同样的参数反复调，直到超时 | 没有调用预算，失败后模型不知道怎么换路 | 单任务调用次数上限 + 同参重复检测 + 幂等键 + 连续失败即转人工 |

三条兜底里，**越权那条是硬要求**。参数幻觉影响体验，重复调用影响成本，越权影响的是"这产品能不能卖"。

**产品经理怎么用它**：把"三类翻车"写进工具清单的验收标准，每类至少给出一条自动拦截规则。规则要落在服务端，不是落在提示词里。

## 4. 权限模型三档

工具按"做错了的后果"分三档，而不是按"技术上属于读还是写"分。

| 档位 | 定义 | 典型工具 | 确认设计 | 兜底要求 |
| --- | --- | --- | --- | --- |
| **只读** | 只读取，不改变任何状态 | 检索、查详情、列目录、读知识库 | 不需要确认 | 结果要带来源；空结果与错误分开 |
| **可写** | 改变系统内状态，但**可撤销** | 建工单、改字段、加评论、排期 | 轻确认（可在结果页批量撤销） | 提供撤销入口与撤销窗口；记录操作者 |
| **危险写** | 不可逆、外发、涉及资金或权限 | 发邮件给客户、退款、删生产数据、改角色 | **显式确认**：展示具体对象 + 参数 + 影响范围 + 是否可撤销 | 二次校验 + 审计日志 + 熔断（可一键停用该工具） |

**确认设计里的四个细节**，比有没有弹窗重要得多：

| 细节 | 做法 | 为什么 |
| --- | --- | --- |
| 确认什么 | 显示具体对象与参数（"给 customer_318 发邮件：内容见下"） | 笼统的"确认执行"等于让用户闭眼点 |
| 默认按钮 | 危险写默认焦点在"取消" | 防手滑，也防"一路回车" |
| 能否批量 | 危险写**不允许**批量一键确认 | 批量放行是事故的放大器 |
| 确认有效期 | 超过有效期需重新确认 | 防止旧确认被复用 |

**产品经理怎么用它**：把"权限档位"这一列填进工具清单时，要问的不是"这个接口是 GET 还是 POST"，而是"**最坏情况下这条工具会造成什么损失，谁来承担**"。承担得起就往下降一档，承担不起就升级为危险写。

## 5. MCP 与标准接入的取舍

Model Context Protocol（MCP）是一套开放协议，把工具、资源、提示的暴露方式标准化，客户端接一次就能接多个 server（[MCP 官方介绍](https://modelcontextprotocol.io/introduction)、[规范](https://modelcontextprotocol.io/specification)，核实于 2026-11；工程侧实现见 [LangGraph 第 13 章](../LangGraph/13-MCP%20接入与工具生态.md)）。

对 PM 而言，重点不是协议细节，而是**这个选择带来什么商业后果**。

| 你的处境 | 判断依据 | 该怎么做 | 常见错误 |
| --- | --- | --- | --- |
| 工具能力是公司核心资产 | 工具集构成产品差异化 | 自研工具 + 自建 MCP server，把接口标准化 | 只在提示词里堆能力，没有可复用的接口层 |
| 需要接很多长尾第三方工具 | 供应商多、维护成本高 | 用 MCP 生态接入，但给每个 server 单独授权与沙箱 | 图省事全量接入，工具冲突、权限失控 |
| 单一供应商深度集成 | 对方有成熟治理能力 | 走对方原生接入，换供应商成本可接受 | 为了"避免锁定"自建全套，浪费工程 |
| 企业客户要求数据不出域 | 合规是硬约束 | MCP server 私有化部署，工具描述与调用日志留在域内 | 用了公共 server 才发现数据出域 |
| 团队要长期维护 | 工具描述会腐化 | 建"工具描述的所有制 + 变更评审"机制 | 工具越接越多，无人维护，最后模型乱调 |

**产品经理怎么用它**：把 MCP 当成一个**采购与锁定**问题来决策，而不是技术选型问题。要问清楚三件事：工具描述谁维护、权限在 server 侧还是客户端侧、换掉 server 的成本是多少。

## 6. 多模态：什么该用、什么不该用

多模态的价值是**拿到文本之外的证据**，不是"让模型更聪明"。选错模态，误差会以另一种形式回来。

| 模态 | 适合的任务 | 不适合的任务 | 产品侧要注意 |
| --- | --- | --- | --- |
| **图片** | 界面截图理解、商品图归类、票据与证件识别、图表读数 | 精确计数与测量、小字号密集文字的逐字 OCR、涉及人身安全或法律效力的判断 | 提示用户拍清楚；原图留存与脱敏策略；识别结果必须可人工修正 |
| **语音** | 会议转写、语音下单、客服录音质检、免手操作 | 需要精确数字与专有名词的场景、多人抢话、方言口音重 | 关键指令要**回显确认**（"我听到的是……对吗"）；原始录音与转写分开存 |
| **视频** | 监控事件筛查、操作录像摘要、长视频内容检索 | 逐帧精确分析、实时判断、长视频的全量深度理解 | 抽帧策略决定成本；输出要带时间戳；成本随时长增长 |
| **文档** | PDF 报告抽取、合同条款结构化、表格转结构化数据 | 版式复杂或扫描质量差的表格、需要跨多文档推理的问题 | 引用精确到页码/段落；表格解析失败要有兜底；长文档先分块再索引 |

判断口诀：**能用结构化数据解决的，不要用图像猜**。截图转表格再分析，永远比"让模型看图"更可控，也更便宜。

**产品经理怎么用它**：多模态选型时先问"这份输入有没有对应的结构化来源"。有，就先接结构化来源；没有，才考虑多模态，并且必须配套人工修正通道与准确率评测（评测方法见 [11-评测体系：AI 产品的质量标准.md](11-评测体系：AI%20产品的质量标准.md)）。

## 7. 企业集成：为什么这些是采购决策

下面四项在技术文档里看是"配置项"，在企业采购评审里看是"过不了就出局"：

| 集成项 | 技术上看是什么 | 采购方真正问的 | 不满足的后果 |
| --- | --- | --- | --- |
| **SSO** | 一个登录入口 | 能不能用我们现有的 IdP？员工离职后权限能否立刻回收？ | 采购被安全评审打回，或要求自建账号体系 |
| **审计日志** | 一张日志表 | 每一次 AI 的读与写，能否按"谁、何时、依据什么"复盘？ | 出了事无法定位责任，产品进不了受监管行业 |
| **数据边界** | 网络策略 | 我们的数据会不会被用于训练、会不会出境、存在哪？ | 法务不签字，功能再好也上不了线 |
| **权限继承** | 一次鉴权 | AI 看到的权限是否与员工在源系统里的一致？ | 用户看到不该看的内容——**这是安全事故，不是体验问题** |

关键区别在于：**前两项是"能不能卖"，后两项是"会不会出事"。** 而"权限继承"最容易被忽略——很多团队给 AI 配了一个超级账号方便了事，等于把全公司的数据开放给了一个不可控的执行体。

**产品经理怎么用它**：把这四项直接抄进销售与采购问卷，作为**准入条件**而不是"可选增强"。技术方案晚两个月能补，采购不过审是产品白做。

## 8. 集成清单：五项与不做的影响

| 集成项 | 接了能得到什么 | 不接会卡在哪 | 决策要点 |
| --- | --- | --- | --- |
| **身份（SSO）** | 免登录、按角色自动降权、组织架构同步 | 用户每次手动登录；无法按角色区分能力；离职即失权难保证 | 用客户 IdP 还是自建；支持哪些协议 |
| **数据源** | AI 看到业务事实，而不是靠用户描述 | 反复追问用户；事实错误；无法自动执行 | 数据驻留边界；读权限如何继承；同步时效 |
| **通知** | 结果、审批请求、失败提醒能推到用户 | 任务做完没人知道；异步流程断裂；用户以为产品坏了 | 渠道（邮件 / IM / 短信）；频率与免打扰规则 |
| **工单** | 转人工的出口，且上下文完整交接 | 没有兜底路径；事故直接砸到用户；人工成本无法量化 | 交接是否结构化；上下文带哪些字段 |
| **审批** | 危险写的人工闸门 | 危险动作无法落地；企业采购直接不通过 | 审批人从哪来；时限；逾期自动降级策略 |

清单的价值不在于"接了五家"，而在于**每项都能回答"不接会卡在哪"**。如果某一项答不上来，说明它还没被真正考虑过。

**产品经理怎么用它**：把这张表放进 PRD 的「上线与灰度」之前，作为需求的前置依赖清单。集成项按"阻塞关系"排序——身份和数据源通常在最上游，通知和审批依赖它们。

## 9. 案例：一个企业助手的工具清单（示意案例）

> 以下为虚构案例，用于演示清单写法，**不代表任何真实公司的内部数据或采购结果**。

**场景**：某公司给全体员工做一个"制度问答 + 报销咨询"助手，需要接 HR 系统、财务系统和工单系统。

工具清单（列名与 AI PRD「4.4 工具与权限」保持一致）：

| 工具 | 权限档位 | 失败如何处理 | 是否需要确认 | 关键设计点 |
| --- | --- | --- | --- | --- |
| `search_policy` | 只读 | 空结果返回"没找到相关条款"；服务异常转人工 | 否 | 只覆盖已发布的制度；返回带条款号与生效日期 |
| `search_my_receipts` | 只读 | 同上 | 否 | 按当前登录人过滤，用户只能看自己的 |
| `calc_reimbursement` | 只读 | 参数非法返回具体字段名与格式 | 否 | 纯计算，结果可复算，公式对用户可见 |
| `draft_expense_form` | 可写 | 保存失败保留草稿并告知 | 否 | 只生成草稿并展示给用户，不提交 |
| `submit_expense_form` | 可写 | 提交失败返回单据号与可重试标记 | 轻确认 | 提交后 10 分钟内可撤销；重复提交用幂等键去重 |
| `create_it_ticket` | 可写 | 创建失败自动转人工并附上下文 | 轻确认 | 不允许模型自行指定处理人 |
| `notify_hr` | 危险写 | 发送失败进重试队列，超限转人工 | **显式确认** | 只能发给 HR 公共邮箱，不允许模型自填收件人 |
| `query_salary` | 危险写 | 越权请求直接拒绝并记录 | **显式确认** | 仅限本人；任何跨人查询一律拒绝 |

清单写完后的三条产品决策：

1. **越权示例要主动构造**。评审时故意问："如果用户说'帮我看看老王这个月工资多少'，会发生什么？" 合格答案是：工具不发起调用，直接拒绝并告知范围（本助手只能查本人）。
2. **只读工具也不是零风险**。`search_my_receipts` 如果忘了按登录人过滤，就是数据事故；所以"只读"也要写清楚数据边界。
3. **确认不是加在所有工具上**。全部加确认，用户会闭眼点同意，等于没有确认——只有危险写才弹。

**这个案例真正想说明的三件事**：

- 权限档位是按**后果**分的，不是按接口分的
- 每条失败路径都要有动作，"失败怎么办"必须写进清单
- 集成清单和工具清单是同一张表的两个侧面：前者管"能不能接"，后者管"接了会不会出事"

## 10. 常见误区

| 误区 | 现象 | 根因 | 纠偏 |
| --- | --- | --- | --- |
| "工具越多，能力越强" | 工具上百个，模型频繁调错 | 没有取舍，把所有接口都暴露给模型 | 工具集按场景裁剪；描述里写清工具之间的区别 |
| "权限校验让模型自己做" | 提示词写"不要越权"，实际还是越权了 | 把安全责任放在最不可靠的一环 | 授权在服务端按用户身份判定，模型只提请求 |
| "确认弹窗越多越安全" | 用户一路回车，审批形同虚设 | 把确认当成万能挡箭牌 | 只在危险写确认，且必须展示具体对象与影响 |
| "多模态是加分项，先上都行" | 图片/视频场景准确率低，用户流失 | 没按输入类型选模态 | 先找结构化来源，再考虑多模态 |
| "接 MCP 就等于生态开放" | 接了一堆 server，工具描述互相冲突 | 只看数量不看治理 | 控制 server 数量，版本与描述变更要有评审 |
| "集成项是技术排期问题" | 上线前才发现客户 SSO 不兼容 | 把采购约束当成实现细节 | 集成清单前置到 PRD，采购问题先问 |
| "给 AI 一个超级账号方便开发" | 用户能看到别人数据 | 偷懒，绕过权限继承 | 权限随源系统继承，测试也要用真实角色跑 |

## 11. 本章练习

```bash
cd Demos/examples && uv run --project .. python -m ai_pm_lab week5
```

本章练习的第二项就是**工具权限清单校验**：

- 每个工具必须声明三项：**权限档位**（只读 / 可写 / 危险写）、**失败处理**（重试次数、降级动作、转人工条件）、**是否需要确认**；缺一项或档位取值非法直接报错
- 危险写工具**必须**要求确认——声明为危险写却不设确认，审批闸门形同虚设
- 校验器会检出**越权**：工具声明"只读"、实际效果却是写或删，这类不一致会直接绕过审批（样例里就埋了一个这样的工具）
- 输出一张"工具 → 档位 → 失败处理 → 是否确认"的表，填进 AI PRD 的「4.4 工具与权限」

**怎么算做对**：校验器零报错通过；你能对每个"危险写"工具说清"用户看到什么才敢点同意"；你能主动补上至少 1 个原本漏掉的危险写工具，并解释它为什么不能归到"可写"。

## 12. 本章要点

- 工具 schema 就是给模型的需求文档；描述里要写"做什么、跟谁的区别、返回什么"
- 工具设计四问：给什么信息 / 要什么输入 / 返回什么 / 失败怎么办，答不全不上线
- 三类翻车各有兜底：幻觉参数靠 schema 与存在性校验，越权靠服务端鉴权，死循环靠调用预算
- 权限按**后果**分三档：只读、可写、危险写；确认只给危险写，且要展示具体对象与影响
- MCP 是采购与锁定问题：先想清楚工具描述谁维护、权限在谁侧、换 server 的成本
- 多模态按输入类型选：能用结构化数据就别用图像猜；关键语音指令要回显确认
- SSO、审计日志、数据边界、权限继承是采购准入条件，不是技术增强项
- 集成五项（身份、数据源、通知、工单、审批）每项都要能回答"不接会卡在哪"

## 一句话结论

> **工具就是产品的能力边界**：schema 写给模型看，权限按后果分档，越权拦在服务端，
> 多模态按输入类型选，企业集成按采购准入条件排——边界划清楚，产品才敢放量。
