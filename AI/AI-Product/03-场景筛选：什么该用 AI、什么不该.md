# 03 · 场景筛选：什么该用 AI、什么不该

> **这篇要回答**：面对一个「用 AI 做什么」的需求，我怎么快速判断该做、不该做、还是换个做法？

---

## 1. 三层筛选：场景 → 任务 → 数据

大多数失败的需求，是因为**从场景直接跳到了方案**。
场景是业务词（「提升客服效率」），任务是一个个动作（「查订单状态」），
数据是能不能支撑这件事的资产。三层各有各的淘汰理由。

```
场景层：这个业务问题真实吗？
   │   淘汰：不是问题 / 是别人的问题 / 频次太低
   ▼
任务层：这个任务里哪一步适合交给模型？
   │   淘汰：全是确定性计算 / 全是搬运 / 全是固定流程
   ▼
数据层：模型靠什么把这件事做对？
   │   淘汰：没有语料 / 没有权限 / 语料不更新
   ▼
可做：定档位 → 定兜底 → 定评测 → 定验收
```

三层各自的淘汰理由必须分开，否则会混成一句「感觉不太行」：

| 层 | 这一层在回答什么 | 淘汰信号 | 淘汰后怎么办 |
| --- | --- | --- | --- |
| 场景层 | 值不值得解决 | 说不清谁的什么任务、什么频率 | 回现场（见 [04-用户研究：还原真实工作流与需求优先级.md](04-用户研究：还原真实工作流与需求优先级.md)） |
| 任务层 | 该不该用模型 | 拆开后全是确定性步骤 | 换成规则 / 搜索 / 流程自动化 |
| 数据层 | 做得对不对得起来 | 没有对应语料或没有权限 | 先补数据，或把任务缩到有数据的那一步 |

**PM 怎么用它**：任何需求先停在场景层过一遍，别急着拆任务。
场景层就该被否掉的，拆得再细也是浪费。

---

## 2. 四条判据

四条判据缺一不可：**有确定性**（对错能被客观判定）、**可容错**（错了不致命）、
**有语料**（有历史样本可学）、**有交互杠杆**（能借到外部信息或用户的一次确认）。

| 判据 | 满足的可观察表现 | 不满足的可观察表现 |
| --- | --- | --- |
| **有确定性** | 结果有客观判据：标签集固定、字段有标准、输出能被自动核对 | 没有客观判据，错了没人会发现，只能靠人读 |
| **可容错** | 出错的代价被人工复核、抽样或低频次摊薄 | 一错就是资金损失、对外承诺、法律责任 |
| **有语料** | 找得到历史产出与输入，能攒出几十条样例 | 只能找到空模板和口头描述 |
| **有交互杠杆** | 能调工具、查库、读文件，或借用户一次确认补上模型短板 | 只能一次性吐一段文字，没有信息入口 |

**为什么这四条必须同时满足**：任意一条不满足，都可以用更便宜更可靠的技术替代 AI。

- 没有确定性 → 做不出评测集与回归门禁，正确性只能靠人读，成本压不下去
- 不可容错 → 确定性代码 + 人工复核更合适
- 没有语料 → 模型没有依据，再强的档位也是猜
- 没有交互杠杆 → 模型只能凭训练语料编，幻觉风险最高

**PM 怎么用它**：四条逐条打勾，**有任意一条打不上勾，就先别谈方案**，
而是先解决那一条（补数据、降容错、找出工具入口，或把判断挪回给人）。

## 3. 反模式清单：这些需求该用别的东西

| 需求长这样 | 问题出在哪 | 该用什么 | 一眼识别信号 |
| --- | --- | --- | --- |
| 「让它算准确」 | 确定性计算 | 代码 / 公式 / 计算器工具 | 有唯一正确答案，且能被写成公式 |
| 「让它查资料」 | 信息检索 | 搜索 + 展示引用 | 答案在已有文档里，不需要综合判断 |
| 「让它按步骤做」 | 固定流程 | 工作流引擎 / 脚本 | 流程每次都一样，只是没人跑 |
| 「让它填表」 | 格式固定 | 表单 + 校验规则 | 字段和规则都写死在规范里 |
| 「让它搬数据」 | 数据搬运 | ETL / 接口 | 输入输出都是确定的字段映射 |
| 「让它穷举情况」 | 需要完整性 | 规则 + 覆盖率检查 | 「不能漏」比「更快」更重要 |
| 「让它写得像人」 | 风格问题 | 模板 + 风格指南 | 判据是风格一致，不是内容正确 |

**一条产品上的直觉**：**能用规则解决的需求，用模型做是纯浪费**——
规则更准、零幻觉、可解释、零边际成本，还不用评测。
模型的价值在于规则写不下来的那部分判断。

## 4. 「看起来很酷」的 AI 需求怎么拆

拆法：把需求变成一张任务清单，每一步标注**可自动化性**。
不是判断"整个需求能不能自动化"，而是判断"哪一步能"。

可自动化性的四档标注：

| 标注 | 含义 | 判据 |
| --- | --- | --- |
| **可** | 模型做这一步，错了也能被下游规则拦住 | 有语料、有容错、输出结构固定 |
| **半可** | 模型做草稿，人做判断 | 内容要靠人验收，但起草很费时 |
| **不可** | 模型做不了，或做了不如人 | 需要现场信息、承担对外责任 |
| **不该** | 这一步根本不该碰模型 | 纯计算、纯搬运、纯枚举 |

拆解模板（示意）：

```markdown
| 步骤 | 动作 | 可自动化性 | 依据 | 兜底 |
| --- | --- | --- | --- | --- |
| 1 | 收集候选清单 | 可 | 有历史库，字段固定 | 数量与来源交叉校验 |
| 2 | 逐条打分 | 半可 | 维度可枚举，但判断主观 | 分数仅作参考，人可改 |
| 3 | 剔除不合规条目 | 不该 | 有明确规则清单 | 规则优先，模型不参与 |
| 4 | 写摘要 | 可 | 有原文可依 | 摘要必须带原文引用 |
```

拆完再看三件事：

1. **可 + 半可 的占比**。如果只有一两步可自动化，整体就不值得用模型做。
2. **不该 的那几步**。它们往往才是真正的瓶颈（却常被 AI 方案忽略）。
3. **半可 的那几步**。人机分工的边界在这里，是产品设计的重点。

## 5. ROI 粗算公式与算例

先给公式，数值全部是可替换变量：

```
月净收益 = 节省人时 × 人力单价
         + 新增收益
         − 模型月成本
         − 维护人时 × 人力单价
         − 一次性建设成本 ÷ 摊销月数
```

变量口径：

| 变量 | 含义 | 怎么估 |
| --- | --- | --- |
| 节省人时 | 任务原耗时 × 频次 × AI 节省比例 | 影子观察实测，别用访谈里的估计 |
| 人力单价 | 折算到小时的全成本 | 用部门口径，别用月薪除 21.75 |
| 模型月成本 | token 成本 + 调用基础设施 | 按 02 章的成本构成算 |
| 维护人时 | 评测维护、提示维护、失败处理 | **最常被漏掉的一项** |
| 摊销月数 | 建设成本摊到多少个月 | 与项目预期周期一致 |

**示意算例**（数值均为示意，非真实业务数据）：

```
任务：每次活动后汇总 3 份表格
频次：每周 2 次 = 每月 8 次
原耗时：90 分钟/次 → 12 小时/月
AI 节省比例：0.6 → 节省 7.2 小时/月
人力单价：120 元/小时 → 节省 864 元/月
模型月成本：60 元/月（输入短、输出短、8 次调用）
维护人时：1 小时/月 × 120 元 = 120 元/月
一次性建设：20 人时 = 2400 元，摊销 12 个月 = 200 元/月

月净收益 = 864 + 0 − 60 − 120 − 200 = 484 元/月
```

**这个算例最值得注意的不是结果，是维护成本**：
维护成本占比高得惊人，因为只有 8 次调用——**低频任务几乎注定 ROI 难看**，
除非单次人工成本极高。低频 + 高单次价值的任务，是 AI 最容易做成的地方。

**PM 怎么用它**：算 ROI 的真实作用不是证明该做，而是**逼你把维护成本算进去**。
不算维护成本的 AI ROI，全都是假的。

## 6. AI Fit Score 打分卡

把第 2 节的四条判据量化成一个 0–100 的分，配套档位判定。**分数用来横向比较和排序，不用来证明该做。**

| 判据 | 权重 | 为什么是这个权重 |
| --- | --- | --- |
| **确定性** | 30 | 没有客观判据，错了没人会发现；正确性只能靠人读，成本压不下去 |
| **容错** | 25 | 错一次的代价决定用户会不会用第二次；用一次的产品没有留存 |
| **语料** | 20 | 有没有语料决定要不要先花钱建检索，但它可以后补，所以权重最低 |
| **交互杠杆** | 25 | 能借用户的一次确认补上模型短板，等于把一部分判断力外包给用户 |

每条判据只取**成立 / 不成立**两态：成立即拿到全部权重，不成立即 0 分。

```
AI Fit Score = 30×确定性 + 25×容错 + 20×语料 + 25×交互杠杆
              （每项取 1 或 0，满分 100）
```

判据是布尔量，所以**两个人算出来的分一定一样**——
不一样就说明对判据的理解不同，而不是手感不同。这正是打分卡比"拍脑袋打分"值钱的地方。

档位判定（决策表）：

| 你的处境 | 判断依据 | 该怎么做 | 常见错误 |
| --- | --- | --- | --- |
| 总分 ≥ 70 | 四条判据基本都成立 | 立项做；同时定评测、兜底与不确定性预算 | 直接开干，不写验收口径 |
| 总分 40–69 | 至少两条不成立 | 进试点区：做一个小范围验证，拿真实数据再回来打分 | 整体上线，把弱项留给用户承担 |
| 总分 < 40 | 多条不成立 | 别做，人工更便宜——先换规则、搜索或流程自动化 | 换个更强模型再来一遍 |
| 分数高但 ROI 算不过来 | 频次太低或单次价值太小 | 先问能不能提高频次或提高单次价值 | 用"战略价值"绕过算术 |
| 差的那条恰好是语料 | 是不是"可以后补"的那一项 | 语料可后补：先补语料，再回来重打一次分 | 因为一次不达标就整个否掉 |

> 权重与阈值是本章口径；实验实现以 `ai_pm_lab week2` 的判定规则为准，
> 两者不一致时以实验为准，并把差异记进你的决策记录。

## 7. 案例拆解：五个被改判的需求（示意案例）

以下是**示意案例**，用于演示判断动作，不对应任何真实公司的内部数据。

**案例 1：会议录音自动转成待办清单**
判断：语料成立（历史录音与历史待办都在）、容错成立（先出草稿），
但待办没有客观判据（写没写全、该不该派发靠人判断），也没有交互杠杆（纯文本输出）。
得分 = 25 + 20 = 45，落在 40–69 试点区 → **缩到「生成待办草稿、人来确认」这一步**，不承诺自动派发。

**案例 2：AI 自动决定退款金额**
判断：规则明确 → 确定性成立（30 分）；但直接涉及钱，不可容错，也没有语料与交互杠杆 → **30 分，落在 40 以下**。
→ **否掉**，人工更便宜。规则算金额，AI 最多用来解释规则为什么这么算。

**案例 3：帮销售写客户跟进邮件**
判断：语料成立（历史邮件多）、容错成立（发出前人看）、交互杠杆成立（能读 CRM 记录、让人确认），
但"这封邮件好不好"没有客观判据，确定性不成立 → 25 + 20 + 25 = **70 分，刚好在立项线上**。
→ **做**，但重点放在"基于 CRM 真实记录起草"，而不是"自由发挥"。

**案例 4：从 20 个渠道汇总商品信息并统一字段**
判断：字段映射清楚 → 确定性成立（30），但不容错、无语料、无杠杆 → **30 分** → **砍成规则**，用 ETL 加映射表。
原来的 AI 提案只因为"字段有 12 个，映射看起来很复杂"。

**案例 5：AI 客服系统**
判断：意图识别部分语料好、容错高、标签集固定（确定性成立），也能转人工确认（杠杆成立）；
但"承诺类问题"不可容错。→ **拆成两段**：意图识别与知识问答交给模型；涉及金额、时效、政策解释的部分走规则 + 转人工。
详见 [01-AI 产品经理的角色、能力模型与边界.md](01-AI 产品经理的角色、能力模型与边界.md) 的案例拆解。

**规律**：五个案例里，三个的结论都不是「做」或「不做」的二选一，而是**缩小到某一步**或**换成别的方法**。
判断的价值不在于标签，在于把需求改到能被执行。

## 8. 常见误区

| 误区 | 一句话表现 | 反制动作 |
| --- | --- | --- |
| **场景即方案** | 「做个 AI 客服」直接进需求评审 | 先过三层筛选，落到任务层再说 |
| **技术可行等于该做** | 「模型能做，所以能做」 | 补 ROI 与 AI Fit 分，两关都过再说 |
| **只评整体不评步骤** | 「这个流程大概能用 AI 吧」 | 拆到步骤，逐条标可自动化性 |
| **忽略维护成本** | ROI 只算省下的人力 | 把评测、提示维护、失败处理算进去 |
| **分数越高越该做** | 拿高分当立项理由 | 分数只是排序工具，还要过 ROI 关 |

补一条：**"我们公司数据多"不是加分项**。数据多但**没有该任务的历史产出**，
模型依然学不到——语料必须是**这件事**的样本，不是公司所有数据的总和。

## 9. 本章练习

```bash
cd Demos/examples && uv run --project .. python -m ai_pm_lab week2
```

实验做两件事：

1. **AI Fit 打分卡**：对一组候选场景逐条判据打分，输出总分与档位判定（build / pilot / reject）。
2. **任务账本与优先级排序**：把任务拆成账本条目，按频次、单次节省时间与月成本排出优先级。

**怎么算做对**：

- 每条判据的取值都能指到一条可观察的事实（有多少历史样例、错了会怎样、谁来确认），不是直觉
- 至少一个场景被你判为「不做」，并写清了理由——**能否掉场景才是这章的验收标准**
- 判定为「做」的场景，都附了方案走向（缩到哪一步、换什么方法）
- 任务账本里每个条目的频次与耗时都来自观察或记录，不是访谈里的估计
- 你能说清一个场景为什么落在「试点区」而不是「立项」——差的那一条是什么、补上它要多少钱

## 10. 本章要点

- 三层筛选：场景层淘汰「不是问题」，任务层淘汰「不该用模型」，数据层淘汰「做了没底」
- 四条判据缺一不可：有确定性、可容错、有语料、有交互杠杆；任一不成立就换更便宜的技术
- 能用规则、搜索、流程自动化解决的，模型是纯浪费
- 拆到步骤再判断可自动化性；「半可」的那几步才是产品设计重点
- ROI 公式里最常被漏掉的是**维护成本**；低频任务几乎注定算不过来
- AI Fit Score 是布尔加权不是手感打分：≥70 立项、40–69 试点、<40 别做
- 判断的产出常常不是「做 / 不做」，而是**缩小范围**或**换方法**

---

## 一句话结论

> **场景筛选的目的不是淘汰需求，而是把需求改到能被执行**：能用规则做的别用模型，
> 能缩到一步的别做全流程，算不过 ROI 的别用战略价值硬凑。
