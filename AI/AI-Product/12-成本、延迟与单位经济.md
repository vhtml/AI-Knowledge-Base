# 12 · 成本、延迟与单位经济

> **这篇要回答**：一次会话到底花多少钱？成本该从哪几项降？降本会不会掉质量？毛利与定价怎么才算得清？

---

## 1. 成本结构六项

AI 产品的成本不是"模型费用"这一项，而是六项相加。**只盯着 token 费用，通常会漏掉占比更大、也更容易砍的那几项。**

| 成本项 | 怎么计量 | 怎么降 | 备注 |
| --- | --- | --- | --- |
| **输入 token** | 每千输入 token 的价格 × 输入量（`P_in` × `Q_in`） | 裁剪上下文、压缩历史、只传必要片段 | 多轮场景下输入量随轮次线性增长，是隐形大头 |
| **输出 token** | 每千输出 token 的价格 × 输出量（`P_out` × `Q_out`） | 限制输出长度、结构化输出、少写废话 | 输出单价通常高于输入，且长度直接决定用户等待时间 |
| **缓存** | 命中部分按缓存价计（`P_cache`），命中率 `H` | 固定系统提示前缀、把不变内容放在最前 | 缓存价通常低于标准输入价，具体以当期厂商页面为准 |
| **检索** | 单次检索开销 × 检索次数（`C_retr` × `N_retr`） | 减少检索轮次、加本地索引、结果缓存 | 向量库/关键词服务本身也有成本，容易被忘记 |
| **工具调用** | 单次调用开销 × 调用次数（`C_tool` × `N_tool`） | 合并调用、限制轮次、幂等去重 | 外部 API 可能按次收费，也可能按对方的计费口径走 |
| **基础设施** | 网关、向量库、日志、存储的分摊（`C_infra`） | 采样日志、压缩 trace、按量扩容 | 常被当作"固定成本"忽略，但它随调用量线性增长 |

**一条纪律**：单价会变，结构不会变。**把单价写成变量**（`P_in` / `P_out` / `P_cache`），每次报价季更新一次；把结构写进产品设计，则长期有效。厂商当期定价请以其官方页面为准，本章不写死数字（计价口径与提示缓存机制可参考 [Anthropic 官方文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)，核实于 2026-11）。

**产品经理怎么用它**：做成本表时，六项都要有值和来源；算不出来的那一项，写"待测"，别填 0——填 0 是成本失控最常见的起点。

## 2. 单次会话成本怎么估

单次会话的成本不是一个数，是一条链：

```
用户提问
   │
   ├─ 检索 2 次 ──────► C_retr × 2
   ├─ 工具调用 3 次 ───► C_tool × 3
   ├─ 第 1 轮 LLM：输入 1.2k + 输出 0.4k ──► P_in×1.2k + P_out×0.4k
   ├─ 第 2 轮 LLM：输入 3.1k + 输出 0.5k ──►（历史全带上）P_in×3.1k + P_out×0.5k
   ├─ 第 3 轮 LLM：输入 5.4k + 输出 0.6k ──►（又涨了）P_in×5.4k + P_out×0.6k
   ├─ 重试 1 次 ──────► 整条链再来一遍
   └─ 基础设施分摊 ───► C_infra
```

四个必须算进去的放大因子：

| 因子 | 怎么被低估 | 怎么估算 |
| --- | --- | --- |
| **多轮上下文增长** | 只按首轮算输入量 | 逐轮累加，或用"平均每轮输入增量 × 轮数" |
| **重试与降级重跑** | 以为只有一次成功 | 用平均重试次数 `N_retry` 乘上去 |
| **并行调用** | 只算了一次调用的费用 | 并行的 N 个调用，费用是 N 倍（延迟是 1 倍） |
| **缓存未命中** | 假设总是命中 | 命中率 `H` 取保守值，并单独算最坏情况 |

**示意公式**（变量定义见第 5 节）：

```
C_token  = (Q_in×(1-H) + Q_in×H×cache折扣 + Q_out) × 单价
C_session = C_token + C_retr×N_retr + C_tool×N_tool + C_infra
C_user_month = C_session × 月会话数 M × (1 + N_retry)
```

**产品经理怎么用它**：把最坏情况那一行也留着——**真实账单里最贵的那批会话才压垮毛利**，平均数会骗人。同一张表里放"典型会话"和"最坏会话"两行。

## 3. 延迟预算拆解

延迟和成本一样要拆，但**必须拆成两个不同的指标**，因为它们的优化手段完全不同。

| 指标 | 定义 | 用户感知 | 主要优化手段 |
| --- | --- | --- | --- |
| **首 token 延迟（TTFT）** | 从发出请求到看到第一个字 | "它到底有没有在动" | 命中提示缓存、缩短输入、模型分级路由、预热连接 |
| **完整响应延迟（TTL）** | 到拿到完整结果 | "等多久能用" | 限制输出长度、流式、结构化提前终止、并行工具、减少串行轮次 |

```
TTFT = 网关 + 排队 + 预填充(输入) + 网络
TTL  = TTFT + 解码(输出 token 数 × 每 token 时间) + 工具/检索耗时
```

| 你的处境 | 判断依据 | 该怎么做 | 常见错误 |
| --- | --- | --- | --- |
| 用户说"界面卡住" | TTFT 高，总耗时正常 | 优化首 token：缓存、缩短输入、换快模型 | 去优化输出长度，方向完全错了 |
| 用户说"等太久" | TTFT 正常，TTL 高 | 限制输出长度、流式、并行工具调用 | 只换更贵的模型，延迟没改善 |
| 流式已上但仍嫌慢 | 流式首字快，但整体久 | 减少串行轮次、并行化工具、砍掉无用步骤 | 以为是"打字机效果不够好" |
| 交互式场景要求高并发 | 峰值排队 | 分级路由 + 缓存 + 限流降级 | 只在高峰扩容，低谷浪费 |

**产品经理怎么用它**：PRD 里要**分别写 TTFT 与 TTL 两个目标**（附录-B 模板库的「7. 成本与 SLO」已经预留了这两个字段）。只写一个"响应时间"的目标，等于没写。

## 4. 降本五招

| 手段 | 机制 | 相对效果（示意） | 代价与风险 |
| --- | --- | --- | --- |
| **模型分级路由** | 简单请求走更小更便宜的模型，难题才上大模型 | 通常是单项最大的一招 | 需要路由准确率评测；误判会让难题走小模型，质量直接掉 |
| **提示缓存** | 稳定前缀（系统提示、固定资料）命中缓存计价 | 长系统提示或多轮场景明显 | 前缀必须稳定；命中率低的场景几乎无收益 |
| **上下文裁剪** | 只保留相关历史 + 摘要，旧内容丢弃 | 轮次越多收益越大 | 裁掉关键约束会造成"看起来答得挺好但违反规则"，**质量风险高** |
| **批处理** | 非实时任务走批处理接口，换更低的单位成本 | 换取时效的降本 | 不能用于交互式；用户要多等（批处理接口说明见 [Anthropic 官方文档](https://docs.anthropic.com/en/docs/build-with-claude/batch-processing)，核实于 2026-11） |
| **结果复用** | 相同/相似问题直接复用已生成结果 | 重复问题多的场景显著 | 新鲜度问题；必须有失效策略与适用范围 |

**顺序建议**：先做**模型分级路由**和**提示缓存**（收益大、副作用可控），再考虑**上下文裁剪**（收益大但掉质量），**批处理**和**结果复用**属于特定场景的专门手段。

**产品经理怎么用它**：任何一招上线都要配一条评测——把"成本降了多少"和"主指标掉没掉"写在同一张表里，不允许只看成本。

## 5. 单位经济模型

变量定义（沿用 [附录-B 模板库](附录-B-模板库.md) 的「6. 单位经济模型」，填值时注明来源与日期）：

| 变量 | 含义 | 谁提供 |
| --- | --- | --- |
| `P_in` / `P_out` | 每千输入 / 输出 token 成本 | 厂商当期价格页 |
| `P_cache` | 缓存命中部分每千 token 成本 | 同上 |
| `C_retr` / `C_tool` | 单次检索 / 工具调用开销 | 内部服务台账 |
| `C_infra` | 其它基础设施分摊（含网关、向量库、日志、存储） | 平台账单分摊 |
| `C_support` | 人工支持成本（转人工、复核、答疑） | 客服/运营工时台账 |
| `Q_in` / `Q_out` | 单次会话平均输入 / 输出 token | 线上埋点（示意样本量足够即可） |
| `H` | 缓存命中率 | 埋点 |
| `N_retry` | 平均重试次数 | 埋点 |
| `M` | 每用户月会话数 | 埋点 |
| `ARPU` | 每用户月收入 | 定价 × 付费用户数 |

**示意公式**：

```
C_session   = C_token + C_retr×N_retr + C_tool×N_tool + C_infra
C_user_month = C_session × M × (1 + N_retry)
毛利额       = ARPU - C_user_month
毛利率       = (ARPU - C_user_month) / ARPU
定价上限     = C_user_month / (1 - 目标毛利率)      ← 反推用
回本周期(月) = 一次性投入 / 每月毛利额
```

三个常被算错的地方：

| 容易错的地方 | 错在哪 | 正确做法 |
| --- | --- | --- |
| 只用平均会话成本 | 平均掩盖长尾，最贵的会话把利润吃掉 | 用 p75 / p90 成本算压力情形 |
| 忘了免费用户 | 免费用户是成本项，不是收入项 | 单独统计免费用户的月成本，计入整体 |
| 用"理论最大调用量"定价 | 用户不会按理论上限用，但爆发场景会 | 用实测 `M` 定价，另设单用户月度上限 |

**产品经理怎么用它**：这张表要在**定价之前**完成。顺序是"先有成本上限 → 再定价格"，反过来就会用价格倒推成本，最后发现毛利是负的。

## 6. 定价与成本的关系：为什么"免费"常常养不起

免费产品的成本不会趋近于零，反而有三个放大器：

1. **流量放大**：免费会拉来大量低意图用户，他们提问更散、对话更长
2. **免费用户不心疼**：反复重试、无限续写、把工具当玩具用
3. **无上限设计**：很多"免费"产品根本没设成本闸门，等于把预算敞口开给了所有人

三种可行的护栏做法：

| 护栏做法 | 怎么落地 | 优点 | 代价 |
| --- | --- | --- | --- |
| **额度制** | 免费额度 + 付费解锁更多 | 体验完整，收入路径清晰 | 需要精确计量；额度设计错了会卡住真实重度用户 |
| **降级制** | 高峰或超预算时降级到更便宜的模型/缓存答案 | 不阻断使用，保住毛利 | 质量下降要**透明告知**，否则用户以为产品坏了 |
| **熔断制** | 单任务/单用户超预算即停止或转人工 | 成本最硬的保护 | 体验最差，必须配"转人工"出口 |

再加一条通用手段：**反滥用**（限速、异常行为识别、批量注册防控）。免费场景的成本失控，一半来自重度使用，一半来自滥用。

**产品经理怎么用它**：免费不是不能做，是必须**把免费用户明确算进成本表**，并给出一句话能说清的护栏策略。付费设计见 [06-定位、价值主张与商业模式.md](06-定位、价值主张与商业模式.md)。

## 7. 降本与质量的取舍矩阵

不是所有降本都掉质量。**把动作按"是否直接影响主指标"分成三类**，才能放心排优先级。

| 降本动作 | 直接掉质量吗 | 掉在哪 | 兜底措施 |
| --- | --- | --- | --- |
| 模型分级路由 | **会** | 难题被误判走小模型 | 路由准确率单独评测；不确定时升级到大模型 |
| 上下文裁剪 | **会** | 丢掉历史约束、违反规则 | 关键约束固定不裁；裁剪后跑评测 |
| 减少检索轮次 | **会** | 召回不足 → 幻觉上升 | 检索相关率单独评测；召回不足时改查询而非直接砍轮次 |
| 限制输出长度 | **会** | 完整性下降，用户要追问 | 按任务类型分别设上限；关键字段不截断 |
| 关闭引用来源 | **会** | 用户无法自查，信任崩塌 | 只在非关键场景关闭 |
| 提示缓存 | 不会 | 前提是缓存键正确、前缀稳定 | 上线前验证命中行为与输出一致 |
| 批处理 | 不会 | 只影响时效 | 交互式任务不适用 |
| 结果复用 | 视场景 | 新鲜度 / 个性化 | 明确适用范围与失效时间 |
| 减少日志采样 | 不直接影响 | 但**丢掉排障能力** | 关键错误全量采样，其余采样 |

**产品经理怎么用它**：在这张表上签字之前，先回答一个问题——**"这个动作掉的质量，用户能感知到吗？"** 能感知到的降本，要么配评测门禁，要么配灰度与回滚。

## 8. 成本看板与告警

上线后盯四个数就够了：

| 盯什么 | 怎么看 | 阈值怎么定 | 超了怎么办 |
| --- | --- | --- | --- |
| **单会话平均成本** | 按任务类型分组的均值 + p90 | 基线 ± 一定比例 | 查最近的提示/模型/流程改动 |
| **每用户月成本** | p50 / p90 分位 | 与定价上限对照 | 触发降级或额度限制 |
| **毛利率** | (ARPU − 月成本)/ARPU | 目标毛利率 | 暂停放量，先做降本 |
| **异常成本占比** | top 1% 会话占总成本比 | 阈值随业务定 | 查长尾失控会话：重试风暴、循环调用、异常输入 |

阈值定法，三条一起用：

1. **绝对上限**：单任务 / 单用户的成本闸门，超过即熔断（硬保护）
2. **变化率**：周环比超过一定幅度就告警（早发现）
3. **分位数**：单会话成本超过 p99 的若干倍即告警（抓长尾）

**产品经理怎么用它**：告警必须**有明确的接收人和处置动作**——"收到告警之后做什么"没写，告警就只是噪音。成本遥测可以用通用语义约定采集（[OpenTelemetry GenAI 语义约定](https://opentelemetry.io/docs/specs/semconv/gen-ai/)，核实于 2026-11）。

## 9. 案例：把单次会话成本显著降低的四个动作（示意案例）

> 以下为虚构案例，用**相对值**演示降本路径，**不代表任何真实公司的内部数据**。

**场景**：某企业内部知识助手，单会话成本较高，但业务方对质量的要求没有想象中敏感——它主要回答"制度是什么"这类问题。

以改动前的单会话成本记为 **100**（相对基准）：

| 轮次 | 动作 | 做了什么 | 成本变化（相对，示意） | 质量变化（相对，示意） |
| --- | --- | --- | --- | --- |
| 起点 | — | 全部请求走统一模型，全量历史进上下文 | 100 | 基线 100 |
| 第 1 步 | **模型分级路由** | 把"只问制度原文"这类简单问题识别出来走小模型 | 100 → 55 | 任务完成率基本不变，少数难题需人工抽检 |
| 第 2 步 | **提示缓存** | 系统提示 + 制度索引固定前缀化 | 55 → 45 | 不变 |
| 第 3 步 | **上下文裁剪** | 历史只保留最近 2 轮 + 更早内容的摘要 | 45 → 36 | 长对话略有下降，需要评测兜住 |
| 第 4 步 | **结果复用** | 同一制度问题在有效期内直接返回已有答案 | 36 → 31 | 新鲜度类问题需明确有效期 |

**这个案例真正想说明的三件事**：

1. **降本动作有先后**：先做"不改输出质量"的三步（路由、缓存、复用），最后做"会掉质量"的裁剪——顺序反过来，风险收益比很差。
2. **每一步都要跑评测**：第 3 步之后必须用主指标（任务完成率）确认没有跌破基线，否则成本降了、质量塌了，是负收益。
3. **别只看均值**：这个案例里 p90 会话成本的降幅明显小于均值——因为长尾会话大多走的是复杂路径。汇报降本效果时要同时给均值和 p90。

## 10. 常见误区

| 误区 | 现象 | 根因 | 纠偏 |
| --- | --- | --- | --- |
| "成本就是 token 费" | 检索、工具、基础设施成本没进表 | 只看模型账单 | 六项成本逐项列，填不出来写"待测" |
| "用平均成本算毛利" | 账面盈利，账单爆掉 | 平均掩盖长尾 | 用 p75/p90 算压力情形 |
| "先定价，成本以后再看" | 定价后发现毛利为负 | 顺序反了 | 先成本上限，后定价 |
| "降价一定更便宜" | 换便宜模型后用户投诉变多 | 只算 token 单价，不算重试与人工成本 | 换模型重跑全量评测并重算总成本 |
| "免费用户不算成本" | 免费用户占用了大半成本 | 没做用户分层核算 | 免费用户月成本单独统计 |
| "批量砍输出长度" | 内容变短但漏关键点 | 把输出长度当唯一杠杆 | 按任务类型分别设上限，评测把关 |
| "降本动作先做了再说" | 成本降了，质量掉了才发现 | 顺序颠倒 | 先做不掉质量的动作，质量敏感项走灰度 |
| "告警配了没人看" | 成本异常三天后才被发现 | 告警没有接收人和处置动作 | 每条告警绑定责任人与处置手册 |

## 11. 本章练习

**这次练习要用你自己的真实数据。** 示例数据只能验证你算对了，验证不了你的判断——
真数据才会暴露判断里的漏洞。

**输入**：你的产品里一次典型会话的真实构成——输入多少 token、输出多少、检索几次、调几次工具、会话多长。数字自己估，并标注哪些是估的。

**步骤**：
1. 按第 5 节的变量表填入单价与用量（单价用当期实际值，自己核实，不要抄过期的；来源和日期一起记下）。
2. 一步步算：计费输入 token → 单会话成本 → 每用户月成本 → 毛利率 → 回本周期（**按付费用户总数算，不是单用户**）。
3. 再算一次**最坏情况**（缓存完全不命中 + 重试 N 次）。
4. 按第 4 节挑三条降本动作，标注每条的代价。
5. 按第 8 节定出上线后盯哪四个数、阈值在哪。

---

## 12. 本章要点

- 成本是六项之和：输入、输出、缓存、检索、工具、基础设施；填不出来写"待测"，别填 0
- 单价写成变量（`P_in`/`P_out`/`P_cache`），结构写进设计——前者每季更新，后者长期有效
- 单会话成本要算上多轮增长、重试、并行调用与缓存未命中四个放大因子
- 延迟要拆成 TTFT 与 TTL，两者优化手段完全不同，PRD 里分别写目标
- 降本五招排序：模型分级路由 → 提示缓存 → 上下文裁剪 → 批处理 → 结果复用
- 单位经济公式固定：`C_user_month = C_session × M × (1+N_retry)`，毛利率 = (ARPU − 月成本)/ARPU
- 先算成本上限再定价；免费用户是成本项，必须单独核算并配护栏
- 降本动作分三类：掉质量的（路由、裁剪、少检索）、不掉质量的（缓存、批处理）、掉可观测性的（采样日志）
- 看板盯四个数：单会话成本、每用户月成本、毛利率、异常成本占比；每条告警都要有处置动作

---

## 一句话结论

> **成本是产品约束，不是财务问题**：先把六项成本算清、把单价写成变量，
> 再按"先降不掉质量的"顺序动手——毛利率是设计出来的，不是谈出来的。
