# 10 · 工程管线：先渲片段，再渲全片

> **这篇要回答**：代码写完了，怎么变成 MP4？一条 5 分钟的片子要花多少时间？

---

## 1. 管线长什么样

```
film.js + index.html
        │
        ├─→ 逐帧截图（ego lite，一个页面一帧）
        │      frames/000000.png … 000899.png
        │
        ├─→ ffmpeg 编码
        │      -c:v libx264 -preset slow -crf 18
        │      -pix_fmt yuv420p -movflags +faststart
        │
        └─→ 混音（事件音 / BGM）
               → out/film.mp4
```

没有录屏，没有导入剪辑软件，没有手工对齐。
**成片是流水线的输出，不是手工操作的产物。**

---

## 2. 帧数是算出来的

```
帧数 = 时长 × 帧率
```

30 秒 × 30fps = 900 帧。这不是一个"渲到满意为止"的数字，
它是一个**预算数字**：900 帧 × 每帧耗时 = 这条片子的渲染成本。

有了这个数字才能做取舍：1080p30 是 900 帧，4K60 是 5400 帧——
后者是前者的 6 倍，所以 4K 只能留给"平台明确要求"的情况。

---

## 3. 编码参数

| 参数 | 值 | 为什么 |
| --- | --- | --- |
| 编码器 | `libx264` | 兼容性最好，各平台通吃 |
| preset | `slow` | 体积和速度的折中；文件小一点，编码慢一点 |
| crf | 18 | 视觉无损的常用档位（18 以下基本看不出差别） |
| pix_fmt | `yuv420p` | **必须**：H.264 的主流兼容格式，别用 yuv444p |
| movflags | `+faststart` | moov 原子搬到文件头，别人点开就能直接播 |

`yuv420p` 这一条值得强调：很多平台的转码器只吃 420，
用 444 渲出来的片子在别人手机上可能**根本没有画面**。

---

## 4. 并行：实测，不要假设

`--jobs 4` 能提速吗？**要实测**。

实测脚本会渲同样的 6 帧，分别用 1 路和 4 路，报告加速比。
在笔记本上常见的结论是：

| 场景 | 加速比 | 原因 |
| --- | --- | --- |
| 核多、任务轻 | 2–3x | 导航和截图的等待被摊薄 |
| 核少、浏览器吃满 CPU | 0.8–1.0x | 互相抢 CPU，并行反而更慢 |

这里的实现**复用浏览器**：`--jobs 4` 是开 4 个页面，
每个页面串行渲自己那一份帧，页与页之间并行。
所以并行摊薄的是导航和截图的等待，不是浏览器启动成本。

早先的写法是"一帧起一个浏览器进程"，启动才是大头。
换成复用之后，浏览器只付一次启动钱，剩下的并行收益更接近线性。

代价是引入一个浏览器驱动依赖（本教程用的是 ego lite）。
实践建议是：**先把"复用浏览器 + 多页并行"跑通**，
再按实测决定路数——并行路数是量出来的，不是抄来的。

并行还有一条铁律：**并行不能改变结果**。
第 10 章的实验会渲两遍（1 路和 4 路）逐字节比对，验证这一点。

## 5. 检查动作的顺序不能反

| 顺序 | 动作 | 看什么 | 成本 |
| --- | --- | --- | --- |
| 1 | `--sheet 若干时刻` | 风格是否一致、字幕区是否被占 | 秒级 |
| 2 | `--stills 关键帧` | 字号、描边、小字位置 | 秒级 |
| 3 | `--motion 一段时间` | 转场怎么接的 | 秒级 |
| 4 | `--clip 起 止` | 这一段对不对 | 分钟级 |
| 5 | `--det` | 确定性（必须先过） | 秒级 |
| 6 | 全片 `--jobs 4` | 成片 | 十分钟级 |

**全片渲完才发现第 40 秒有一根线穿过了字幕区**，是这条流程里最贵的错误。
联络表（`--sheet`）的价值就在于：几秒钟看完整片的骨架。

`--motion` 专门用来看转场：在一段时间里连取 12 帧拼成一张图。
转场翻车基本都发生在两个场景交接的那两三帧，静态图看不出来，连帧图能看出来。

## 6. 一个容易踩的坑：截图是白纸

用无头浏览器截图时，最常见的问题是**截出来是白的**。
原因几乎总是同一个：页面里的 JS 还没跑完，截图就先发生了。

解法是**等页面加载完再截**。本教程的渲染管线用 ego lite 驱动，
每帧的顺序是：导航到 `?t=…` → 等 `load` 状态 → 截图。

```js
await page.goto(url);
await page.waitForLoadState("load");
await page.screenshot({ path });
```

少了 `waitForLoadState`，你会得到一张纯白图，
然后开始怀疑是不是 Canvas 画错了。

## 8. 和实验的对应

```bash
cd Demos/examples
uv run --project .. python -m vibe_film_lab ch10
```

实验会算出片子的帧数预算，实测 1 路 vs 4 路的渲染速度，
并验证两条路线渲染出的是**逐字节相同**的帧。

渲染用的浏览器是 **ego lite**，不依赖系统里装没装 Chrome：
视口用 CDP 的 `Emulation.setDeviceMetricsOverride` 钉死成 1920×1080，
所以截出来的帧和浏览器窗口多大无关。

---

**一句话**：把"检查"放到"渲染"之前，是这条流水线里最划算的习惯。
全片渲完才发现问题，返工成本是片段的几十倍。
