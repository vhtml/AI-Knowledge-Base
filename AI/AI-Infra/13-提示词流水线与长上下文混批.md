# 13 · 提示词流水线与长上下文混批

> **这章要解决的问题**：一条请求从网关进来到吐出第一个 token，中间要过 tokenize、
> 套 chat 模板、截断、注入、prefill 五道工序。这五道里有两把"静默的刀"：
> 一把砍掉前缀缓存的收益（tokenize 与 prompt 的拼装顺序），
> 一把砍掉 TTFT 的余量（长 prompt 的 prefill）。**判断题**：给你一条真实流量
> （prompt 长度分布、系统提示模板、是否带时间戳），你能不能说清前缀缓存会命中多少、
> p99 TTFT 会落在哪、该打开哪几项开关？本章把这三件事变成可验证的断言——
> 换 tokenizer 后共享块数归零、变量放最后能省多少 prefill、
> 32K prompt 独占引擎多久、分块 prefill 能把 p99 压下来多少。
>
> 实验口径：Qwen2.5-7B-Instruct / H100 SXM 80GB / block=16 / MFU=0.5 /
> 长 prompt 32768 tokens。跑法：`cd Demos/examples && uv run --project .. python -m infra_lab ch13`

---

## 1. 进引擎之前的五道工序

| 工序 | 做什么 | 出问题时的症状 |
| --- | --- | --- |
| tokenize | 文本 → token id | 同一段文本在不同模型上 token 数不一样 |
| 套 chat 模板 | 加角色标记、分隔符 | 模板改一个字，前缀全部作废 |
| 截断 | 超上下文上限时砍历史 | 砍掉多少，决定了前缀还剩多少可共享 |
| 注入 | 塞检索结果、时间戳、用户画像 | 每请求都变的字段放错位置 → 缓存归零 |
| prefill | 一次算完整段 prompt，产出 KV | 长 prompt 独占引擎 → TTFT 尖刺 |

前三道里，**tokenize 和模板都会改变 token 序列**，也就是都会改变前缀缓存的键；
第 4 道"注入"本身不是错的，错的是**把每请求都变的内容放在 prompt 前面**。
另外"先截断还是先注入"也要定：先截断再注入，注入内容不受历史预算约束会超上限；
先注入再截断，注入内容本身可能被砍掉、检索结果丢失。

---

## 2. tokenize 的坑：换 tokenizer 就等于换前缀

第 12 章那套块级链式哈希，节点键的形式是 `(父链哈希, 本块哈希)`：
块哈希由块内 token 折叠而来，链哈希逐块递推。**关键性质**：前 N 个块相同 ⟹
前 N 个节点键必然相同 ⟹ 这 N 块可以共享同一份 KV。
所以只要 token 序列变了，块哈希就变了，缓存就命中不了。

同一段 256 词的系统提示，两个 tokenizer 编出来的结果：

| tokenizer | 系统提示 token 数 | prefill 时间 | KV 显存 |
| --- | --- | --- | --- |
| Tokenizer-A（词表大，整词入表） | 256 | 9.10ms | 0.01GiB |
| Tokenizer-B（词表小，切成子词） | 512 | 13.63ms | 0.03GiB |
| **两者共享的块数** | — | **0** | — |

**共享块数是 0，不是"下降"，是归零**。token 序列从第 0 个 token 就不同，
第 0 块的哈希就不同，链从根上就断了。代价是三重的：

1. **前缀缓存完全失效**——对同一个模型的所有请求都是 0 命中，不是"偶尔不命中"。
2. **prefill 更贵**——13.63ms vs 9.10ms。
3. **KV 显存翻倍**——256 token = 14 MiB，512 token = 28 MiB（每 token 56 KiB），
   两套 token 序列的 KV 要各存一份。

还有一个前提：**同一个 tokenizer 下，同样的文本必须永远得到同样的 token 序列**。
所以真实系统要用固定词表的 BPE/WordPiece/SentencePiece，
实验里也刻意用 CRC32 而不是内置 `hash()`——后者按进程随机化种子取值，
同一输入跨进程结果不同，缓存就不可复现了。

## 3. 缓存友好的 prompt 构造：变化的字段放最后

被测 prompt = 256 token 系统提示 A + 256 token 系统提示 B + 4 token 变量字段
（会话 ID、时间戳、trace ID）+ 20 token 正文，block = 16：

| prompt 布局 | 总 token 数 | 共享块数 | 可省 token | 省下的 prefill | 省下的 KV |
| --- | --- | --- | --- | --- | --- |
| 变量在最前 | 536 | 0 | 0 | 0.00ms | 0.00GiB |
| 变量在中间 | 536 | 16 | 256 | 9.10ms | 0.01GiB |
| 变量在最后 | 536 | 32 | 512 | 13.63ms | 0.03GiB |

换算关系就一条：

```
共享 token 数   = 共享块数 × block_size
省下的 prefill  = prefill_time(共享 token 数)
省下的 KV       = 共享 token 数 × 56 KiB
```

**为什么"变量在最前"是灾难**：变量字段只有 **4 个 token**，却让 **512 token** 的
系统提示全部重算。因为变量在第 0 块里 → 第 0 块的节点键就不同 →
后面每一块的父链哈希都被改写 → 后面所有块全都对不上。
变量在中间能保住 16 块（256 token），变量在最后能保住 32 块（512 token）——
差的不是变量本身的位置，而是"变量后面还剩多少不变的内容"。

推广出的规则：**每请求都变的字段要尽量往后放；必须靠前的字段（租户标识、路由标记）
要尽量短。** 4 token 的变量已经能让 512 token 的系统提示失效，12 token 的变量同理。

顺带一条：**prompt 总长度不变（三种布局都是 536 token），
省下的 prefill 却是 0.00ms 和 13.63ms 的区别**——"总 token 数一样"不等于"成本一样"，
顺序本身就是成本。

## 4. 长上下文的 prefill 成本：TTFT 尖刺从哪来

```
GEMM 项      = 2 × 非 embedding 参数量 × s
注意力项     ≈ 2 × 层数 × hidden_size × s²
prefill 耗时 = max( 总 FLOPs / (峰值算力 × MFU), 权重字节 / (带宽 × MFU) )
```

代入本章口径：非 embedding 参数 6.53B、28 层、hidden 3584、H100 fp16 峰值 989 TFLOPS、
MFU 0.5（可达 494.5 TFLOPS）、带宽 3350 GB/s。注意注意力项是 **s²**——
这是后面所有超线性现象的来源。

| prompt token | GEMM FLOPs | 注意力 FLOPs | 注意力占比 | prefill 时间 | 相对 512 | KV 显存 |
| --- | --- | --- | --- | --- | --- | --- |
| 512 | 6.7T | 0.1T | 0.8% | 13.63ms | 1.0x | 0.03GiB |
| 2048 | 26.7T | 0.8T | 3.1% | 55.79ms | 4.1x | 0.11GiB |
| 8192 | 107.0T | 13.5T | 11.2% | 243.59ms | 17.9x | 0.44GiB |
| 32768 | 428.0T | 215.5T | 33.5% | 1301.22ms | 95.5x | 1.75GiB |

三个要记住的读数：

1. **注意力占比从 0.8% 涨到 33.5%**。512 token 时注意力几乎可忽略，
   32768 token 时它已是三分之一——短 prompt 和长 prompt 是两种不同的负载。
2. **token 数 ×64，时间 ×95.5**。超线性来自 s² 项：8192/512 是 16 倍 token，
   时间却是 17.9 倍。
3. **1301.22ms 单条就越过 1 秒的 TTFT 约定**，而且这段时间引擎**什么别的都做不了**。

还有一个硬下限：prefill 至少要把权重读一遍，15.24 GB ÷ (3350 GB/s × 0.5) = **9.10ms**。
只要算力项低于这个下限，prefill 就卡在 9.10ms 不再下降——实测里 256 token 的 prefill
正好是 9.10ms。算力项要追上这个下限，prompt 至少要 **343 token**。
所以**短 prompt 的 prefill 慢，不是"算不完"，而是"光读权重就 9.10ms"**。

## 5. 混批：长请求阻塞短请求，chunked prefill 怎么救

实验负载：12 条短请求（prompt 128 token / 输出 32 token，到达时刻 0.00–0.11s）
+ 1 条长请求（prompt 32768 token，到达时刻 0.025s）。
前 3 条短请求在长请求到达前就出了首 token，TTFT 分别是 9.1ms / 16.4ms / 17.3ms；
剩下 9 条全部撞在长请求的 prefill 上：

**整块 prefill 时，长请求独占引擎 1301.22ms，期间到达的短请求全部排队，
短请求的 TTFT 从 9.1ms 变成 1400.4ms。**

这 140 倍的差距**不是短请求自己变慢了**，是它的 prefill 排在一个 1.3 秒的大 prefill 后面。
这就是"TTFT 尖刺"的真身：尖刺不会只扎在长请求身上，
它会把**同期所有请求**的 TTFT 一起抬起来。

把 32768 token 切成 16 块 × 2048，每块 prefill 55.79ms，块与块之间让 decode 插进来：

| prefill 方式 | 长请求 TTFT | 短请求 p99 TTFT | 整体 p50 TTFT | 整体 p99 TTFT |
| --- | --- | --- | --- | --- |
| 整块 prefill | 1312.6ms | 1400.4ms | 1335.1ms | 1400.4ms |
| 分块 prefill（2048） | 904.1ms | 991.9ms | 926.6ms | 991.9ms |

整体 p99 TTFT **从 1400.4ms 降到 991.9ms，降幅 29%**。端到端 p99 从 2376.4ms 降到 1967.8ms，
输出吞吐 186.6 → 224.8 token/s，请求吞吐 5.41 → 6.52 req/s，
而 **TPOT 中位数不变（22.32ms）**——分块动的是 prefill 的排布，没动 decode 本身。

块大小怎么选：块太小，每块都要重读一遍权重、全部撞在 9.10ms 的下限上；
块太大，又退回"独占引擎"。实验取 2048，每块 55.79ms，算力项主导，是合理档位。

**一个必须说清的口径**：实验里"32K prompt 的引擎占用从 1301ms 降到 893ms"
在真实引擎里**不成立**——labkit 的解析模型把注意力项**按块结算**
（每块用块大小的 s² 算），所以分块后的总时间也变短了（16 × 55.79ms = 892.7ms）。
真实引擎里 32K prompt 的总 FLOPs 一分都不会少。
**分块 prefill 的真实收益是"每块之间让 decode 插进来"，
让短请求不必等整整 1.3 秒——不是"算得更少"。**
量级（把 p99 压回 1 秒以内）是对的，真实降幅会小于 29%。
而且分块后 p99 是 991.9ms，**仍卡在 1 秒约定边缘**——分块是止血，不是达标，
真正的解法是把 prompt 本身裁短。

## 6. 判断依据：可操作的决策规则

| 观察到的现象 | 根因判断 | 该做的动作 |
| --- | --- | --- |
| 前缀缓存命中率为 0，但系统提示逐字相同 | 每请求都变的字段放在了 prompt 前部 | 把变量字段挪到最后；必须靠前的字段尽量短 |
| 前缀缓存命中率为 0，且各副本缓存量不同 | 路由没做前缀亲和 | 网关加一致性哈希（第 11 章） |
| 同一段文本在不同模型上 token 数不同 | 换过 tokenizer / 换过模型 | 前缀缓存按模型分池，KV 预算分开算 |
| p99 TTFT 尖刺与长请求到达时间吻合 | 长 prompt 的 prefill 独占引擎 | 开 chunked prefill，块大小 1024–4096 |
| 单条 prompt 的 prefill 已超过 1 秒 | prompt 本身太长 | 先做检索裁剪，不要指望调度救 |
| 首 token 慢但 TPOT 正常 | 瓶颈在 prefill，不在模型大小 | 看 prompt 长度分布，别去扩卡 |
| 短 prompt 的 prefill 怎么优化都不变 | 撞在 9.10ms 的权重读取下限 | 优化方向在批处理和缓存，不在单条 prompt |
| 分块后 p99 仍 ≥ 1 秒 | prompt 太长 | 裁剪 prompt；分块只能切碎等待，变不了总量 |

判断"要不要为这条流量做缓存优化"的顺序：
**先量 prompt 长度分布 → 再量 prompt 开头 16 token 是否稳定 → 最后才谈缓存参数**。
第二步是分水岭：开头 16 token 都一样，说明前缀有机会；开头就不一样，缓存怎么配都没用。

## 7. 常见误区

1. **"命中率高就说明 prompt 写得没问题"**——命中率归零的头号原因不是缓存没开，
   而是 prompt 里放了每请求都变的字段。实验里 4 token 的变量放在最前，
   共享块数直接从 32 掉到 0；**总 token 数一样也不等于成本一样**
   （三种布局都是 536 token，省下的 prefill 却是 0.00ms 和 13.63ms 的区别）。

2. **"换 tokenizer 只是 token 数差一点"**——差的是前缀缓存**全废**（共享块数 0），
   KV 还要为两套 token 序列各存一份（14 MiB vs 28 MiB），prefill 从 9.10ms 涨到 13.63ms。

3. **"长 prompt 慢是因为模型大"**——慢在 prefill 这一段：32768 token 要 1301.22ms，
   其中注意力占 33.5%；这段时间引擎不干别的，同期短请求的 TTFT 一起被拖到 1400.4ms。
   加大模型只会更糟。

4. **"chunked prefill 是免费的"**——分块让长请求自己出首 token 更快，
   也意味着 decode 有机会插队，理论上会推高在跑请求的 TPOT。
   本实验 TPOT 中位数没变（22.32ms），但那是因为批不大；真实高并发下必须盯 TPOT。

5. **"prefill 越短越好，能优化就优化"**——prefill 有 9.10ms 的硬下限（读一遍权重），
   343 token 以内怎么优化都是 9.10ms。把精力花在"每请求都变的字段挪到最后"上，
   收益比压缩短 prompt 大得多。

## 8. 自测题

1. **某团队把系统提示从 prompt 开头挪到了"用户问题前面"（即中间），
   前缀缓存命中率从 95% 掉到 0。挪到"最后面"能不能救回来？**
   **答案要点**：链式哈希要求前面每一块都相同，中间变量会让它后面的块全部对不上。
   实验里变量在中间只能共享 16 块（256 token），变量在最后能共享 32 块（512 token）。
   但把系统提示放到最后会让模型先看到用户问题再看到系统提示——
   **顺序改对了，模型行为可能反而变差**，缓存和效果要一起权衡。

2. **同一段 512 token 的系统提示，模型 A 的 tokenizer 编出 256 token，
   模型 B 编出 512 token。前缀缓存命中率和 KV 显存分别受什么影响？**
   **答案要点**：token 序列不同 → 从第 0 块哈希就不同 → 共享块数 0，前缀缓存完全失效。
   KV 从 14 MiB 涨到 28 MiB（每 token 56 KiB），prefill 从 9.10ms 涨到 13.63ms。

3. **一台 H100 上跑 32K prompt 的请求，p99 TTFT 到了 2.4 秒，
   同期短请求也一起变慢。给出两个动作，分别压在哪一段？**
   **答案要点**：(a) 开 chunked prefill（2048 块）——实验里整体 p99 从 1400.4ms 降到 991.9ms，
   降幅 29%，压的是**排队等待**；(b) 缩短 prompt（检索裁剪）——
   1301.22ms 的独占 prefill 是根因，裁短 prompt 才压得住**总量**。

4. **为什么"分块 prefill 把 32K prompt 的引擎占用从 1301ms 降到 893ms"
   在真实引擎里不完全成立？**
   **答案要点**：labkit 的解析模型把注意力项按块结算（每块用块大小的 s²），
   所以分块后总时间也变短。真实引擎里 32K 的总 FLOPs 不变，
   分块的收益来自**块与块之间让 decode 插进来**，让短请求不必等满 1.3 秒。
   所以量级对，但真实降幅会小于 29%。

5. **一条 128 token 的短请求，prefill 要 9.10ms，压到 64 token 还是 9.10ms，为什么？
   分块 prefill 之后 p99 是 991.9ms，仍压在 1 秒约定边缘——怎么解释"这还没达标"？**
   **答案要点**：prefill 至少要读一遍权重，15.24 GB ÷ (3350 GB/s × 0.5) = 9.10ms 是硬下限，
   算力项要超过它需要 343 token 以上。而分块只把等待切碎、不改变总量——
   32K 的 prefill 是 1301.22ms，拆成 16 块每块 55.79ms，块间插 decode 只是让短请求有机会插队。
   真要达标必须缩短 prompt：压到 8192 时 prefill 是 243.59ms，才真正进预算。

## 一句话结论

> **tokenize 是模型相关的，换 tokenizer 前缀缓存直接归零；
> 每请求都变的字段必须放在 prompt 最后面（4 token 的变量能让 512 token 的系统提示失效）；
> 32K prompt 的 prefill 要 1301.22ms，单条就吃掉整个 TTFT 预算，
> 并把同期所有请求一起拖到 1400.4ms——分块 prefill 能把 p99 压到 991.9ms（降 29%），
> 但这只是止血：真正的解法是把 prompt 裁短。**
