# 附录 B：工程检查单

上线前、扩容前、换模型前逐项打勾。
每一条都给出**怎么查**，不只是"要查"——查不出证据的项等于没做。

---

## 一、新服务上线前

### 模型与硬件

- [ ] **显存账算过了**：权重 + KV 预算 + 激活 + 运行时开销 ≤ 显存容量，
      且留了至少 10% 余量（长请求会让 KV 峰值超预期）
- [ ] **知道瓶颈是权重还是 KV**：权重占比 > 50% → 先考虑量化或多卡切分；
      KV 占比 > 50% → 先考虑 GQA、KV 量化或更小的 max context
- [ ] **选型验证过**：在目标 GPU 上实测过 TTFT/TPOT/吞吐，
      没有用厂商标称算力推算（MFU 差异通常有 2 倍以上）
- [ ] **卡的选型不是随便挑的**：大 batch 场景选高带宽卡（decode 受带宽限制），
      长 prompt 场景选高算力卡（prefill 受算力限制）

### 容量与 SLO

- [ ] **SLO 有具体数字**：TTFT p99 = ? ms，TPOT p99 = ? ms，可用性 = ?
- [ ] **负载画像有真实数据**：输入长度分布、输出长度分布、峰谷比、租户构成。
      不是"平均 500 token"这种拍脑袋数字
- [ ] **副本数是算出来的，不是拍的**：按第 16 章的公式算，并留了突发余量
- [ ] **做过压测**：用真实负载压到目标 QPS，确认 p99 不退化
- [ ] **知道系统过载时的表现**：排队变长还是直接拒绝？两种都要能接受

### 稳定性

- [ ] **有超时**：请求级、prefill 级、整体 SLA 级，三层超时都配了
- [ ] **有重试但有限**：重试有次数上限、有退避、只对可重试错误重试
- [ ] **限流配了**：入口限流 + 每租户配额，超限返回明确错误而不是干等
- [ ] **熔断配了**：下游异常时快速失败并降级，不要让一个依赖拖垮整个服务
- [ ] **健康检查是真实检查**：不能只看进程活着，要看能完成一次最小推理

### 观测

- [ ] **三个核心指标有看板**：TTFT p50/p99、TPOT p50/p99、吞吐
- [ ] **延迟有三段分解**：排队 / prefill / decode，能看出慢在哪一段
- [ ] **队列深度有监控**：队列深度是扩容的第一信号
- [ ] **KV 利用率有监控**：超过 90% 就该扩容或限流
- [ ] **缓存命中率有监控**：命中率掉了说明路由策略或 prompt 变了
- [ ] **告警能叫醒人**：阈值基于 SLO，不是基于"设备好像有点忙"

### 安全与隔离

- [ ] **租户隔离确认过**：缓存不会跨租户共享 KV，路由不会把 A 的请求送到 B 的副本
- [ ] **鉴权在网关上做**：副本本身不做鉴权（网关上做，副本只信任内网）
- [ ] **prompt 内容不进日志**：用户数据不要原文落盘
- [ ] **超时与连接数有上限**：防止单客户端打满

### 成本

- [ ] **算过每百万 token 成本**：按实际负载画像算，不是按峰值算
- [ ] **算过最坏情况的成本**：如果所有请求都是最长 context + 最长输出，成本是多少
- [ ] **有成本告警**：按小时/天设阈值

---

## 二、日常巡检（每周）

- [ ] p99 TTFT 和 TPOT 是否还在 SLO 内
- [ ] 队列深度是否有异常尖峰
- [ ] KV 利用率是否长期偏高（> 85% 说明该扩容了）
- [ ] 前缀缓存命中率是否稳定（掉了可能是 prompt 模板改了）
- [ ] GPU 利用率是否异常（低说明在等，高但吞吐低说明有别的问题）
- [ ] 是否有 OOM、重试风暴、限流触发异常的时段
- [ ] 实际每百万 token 成本 vs 预算

---

## 三、扩容前

- [ ] **触发指标选对了**：看排队深度或 p99，不是看 CPU/GPU 利用率
- [ ] **算过冷启动时间**：镜像拉取 + 权重下载 + 显存加载 + warmup，
      这个时间就是"扩容生效的延迟"，突发流量下要算进去
- [ ] **扩容速度够快**：从触发到能接单的时间 ≤ 能容忍的业务中断时间
- [ ] **预热脚本存在**：warmup 请求要覆盖真实的 prompt 长度分布
- [ ] **缩容策略安全**：有最小副本数、有排空时间、不会在流量低谷把预热丢掉
- [ ] **新副本能拿到前缀缓存**：亲和路由要能把流量导到新副本，
      否则新副本是冷的（第 11、12 章）

---

## 四、换模型前

- [ ] **重新算显存账**：新模型的参数量、层数、KV 头数都变了
- [ ] **重新算容量**：新模型的每 token 成本不同，所需副本数也不同
- [ ] **tokenizer 变了**：前缀缓存会失效（token 序列不同 → 块哈希不同），
      命中率会掉，需要重新预热
- [ ] **prompt 模板兼容性确认**：新模型的 chat template 不同，
      老 prompt 要重新验证
- [ ] **量化方案重新评估**：新模型可能已经自带更好的量化版本
- [ ] **SLO 重新验证**：新模型的 TTFT/TPOT 基线不同，
      别拿旧阈值报警

---

## 五、故障处理中的检查单

**先止血，再定位**。以下顺序不要乱：

1. [ ] **确认影响面**：哪些租户、哪些模型、什么时间段
2. [ ] **止血**：限流 / 降级 / 扩容 / 回滚，选一个最快的
3. [ ] **看三段分解**：慢在排队、prefill 还是 decode
4. [ ] **看资源**：GPU 利用率、KV 利用率、显存水位
5. [ ] **看变更**：最近有无模型/配置/流量变化
6. [ ] **复盘并补检查单**：这次漏了哪条，下次补上

---

## 六、性能优化的优先级

**按这个顺序做，不要跳**：

1. **先消除浪费**——KV 没复用、prompt 模板重复、batch 上限设错、
   限流配置导致的重试风暴
2. **再改配置**——batch 上限、调度策略、缓存开关、chunk 大小
3. **再换模型形态**——GQA 模型、量化版本、更小参数量
4. **最后动架构**——PD 分离、多副本、多机

**理由**：前两级几乎零成本、零风险，而且很多"架构问题"其实是配置问题。
在消除浪费之前上 PD 分离，就像在漏水的桶里加桶。
