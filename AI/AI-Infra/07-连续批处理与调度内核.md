# 07 · 连续批处理与调度内核

> **这章要解决的问题**：为什么把 batch 开大不能提高吞吐，而把"调度粒度"从"一个请求"改成"一个 token"却可以？静态批和连续批处理到底差在哪一步？为什么一条 4K 的长 prompt 会把整个 batch 的首 token 时延一起拖高，而"分块 prefill"能把它降到十几毫秒——它保护的是谁？以及，显存不够的时候，抢占一条正在生成的序列要付多少重算代价？

---

## 1. 静态批的问题：槽位是租来的，不是自己的

静态批（static batching）是推理服务最早的做法：一批请求进来，凑成一个 batch，
跑完整批，再接下一批。它的三条规矩恰好定义了"静态"这个词：

1. **凑批**：引擎空闲时等一批请求到齐（等待窗口 `batch_window_s`），
2. **整批并行 prefill**：批内所有请求一起算，耗时取最慢的那条，
3. **不补位**：批内某条请求先跑完，它的槽位就一直空着，直到整批结束。

第 3 条是吞吐低的根源，第 2 条是首 token 时延（TTFT）尖刺的根源。
本章实验把这两件事都量化出来（`Demos/examples/infra_lab/lessons/ch07_continuous_batching.py`）。

先看这一份"长短混合"的负载（16 条请求）：

| 租户 | 条数 | prompt | output | 说明 |
| --- | --- | --- | --- | --- |
| interactive | 12 | 128 | 32 | 人机对话，对 TTFT 敏感 |
| longform | 1 | 4096 | 160 | 长文档，TTFT 尖刺源 |
| batched | 3 | 512 | 256 | 离线批处理，可以等 |

在 H100 SXM + Qwen2.5-7B 上（本章全部数字来自 `python -m infra_lab ch07`）：

| 方案 | TTFT p50 | TTFT p99 | p99/p50 | e2e p99 | 输出 token/s | 总耗时 | 槽位空转 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 静态批 | 165.0 ms | 1633.9 ms | **9.90** | 3925.6 ms | 324.3 | 4.046 s | 56.7% |
| 连续批（公共层引擎） | 141.4 ms | 144.9 ms | **1.02** | 2587.7 ms | 481.3 | 2.726 s | — |
| 连续批（本章内核） | 140.3 ms | 142.1 ms | **1.01** | 2602.0 ms | 478.8 | 2.740 s | — |

静态批最刺眼的两行：

- **槽位空转 56.7%**：一批 16 条里，12 条短请求在 0.5 秒就结束了，
  它们剩下的槽位一直空到那条 4096 token 的长请求跑完（1.68 秒）——
  超过一半的槽位时间在空转，这就是吞吐只有连续批 67% 的原因。
- **p99 是 p50 的 9.9 倍**：静态批的 p99 TTFT（1633.9 ms）几乎等于那条长请求的
  **整个生命周期**（1670 ms）。也就是说，后面到的请求不是在等"一个 batch 的 prefill"，
  而是在等**那条最长请求把整批拖完**。

这就是"静态批的 p99 由最长请求决定"的准确含义：不是长请求自己慢，
是它把**排在它后面的人**一起拖死。

## 2. 连续批处理：把调度粒度降到 iteration

连续批处理（continuous batching）的核心只有一句话：

> **每生成一个 token，就重新决定一次谁在跑。**

具体到执行循环，一轮迭代做两件事：

1. **补位**：运行批还有空位、KV 还装得下，就从等待队列里取一条请求做 prefill；
2. **decode**：运行批里所有序列各产出一个 token。

一轮的时长 = `max(prefill 耗时, decode 耗时)`——prefill 和 decode 共享同一套算力。
关键在于第 1 步发生在**每一轮**之后，而不是"整批结束之后"。

这就是上表里 p99/p50 从 9.90 掉到 1.02 的全部原因：
短请求跑完就腾出槽位，下一条立刻补进来，队列不会因为一条长请求而整体停摆。
换句话说，连续批把"等整批"变成了"等一个槽位"。

本章实验同时跑了两个连续批实现（公共层的 `EngineSimulator` 和本章自己写的内核），
两者的 p99 TTFT 相差 1.9%、吞吐相差 0.5%——**同一份负载，两个实现必须给出同一个数**，
这是全课口径一致性的底线（本章有断言守着它）。

## 3. chunked prefill：长 prompt 别再独占整卡

一条 4096 token 的 prompt，一次性 prefill 要多久？

```
prefill(4096) = 114.99 ms      # H100 SXM, mfu 0.5
prefill(2048) =  55.79 ms
prefill( 512) =  13.63 ms
```

而 decode 一轮（batch=8，上下文 512）只要 9.24 ms。也就是说：
**长 prompt 的一次 prefill，等于十几轮 decode 的时间**。在这段时间里，
整张卡上正在生成的序列一个 token 都产不出来——它们只是被"卡住"了。

`chunked prefill`（分块 prefill）的做法是：把长 prompt 切成若干块，
每块单独占一轮引擎时间，块与块之间让 decode 插进来。
于是"独占"变成了"轮流"。

本章实验量的是**卡顿**——每个序列相邻两个 token 之间的最长间隔：

| 方案 | TTFT p99 | TPOT p50 | TPOT p99 | 卡顿 p99 | 输出 token/s |
| --- | --- | --- | --- | --- | --- |
| 整块 prefill | 142.1 ms | 11.73 ms | 14.99 ms | **115.0 ms** | 478.8 |
| 分块 prefill（chunk=512） | 136.1 ms | 11.60 ms | 12.23 ms | **15.3 ms** | 480.5 |

读这张表要注意两个结论：

- **卡顿从 115 ms 降到 15.3 ms**（7.5 倍）——正在生成的序列不再被长 prompt 卡死；
- **TTFT 几乎没变**（142.1 → 136.1 ms），**吞吐几乎没变**（478.8 → 480.5 token/s）。

所以分块 prefill **不是** TTFT 优化，也不是吞吐优化。它是**公平性优化**：
把"一条长请求独占整卡"变成"长请求和短请求轮流用卡"。
卡顿降到 15.3 ms 也正好是 chunk 大小的量级——chunk 调大到 1024，
卡顿回升到 27.5 ms（本章有断言）：**chunk 越小，摊得越平，但调度开销越大**。

还有一个容易被忽略的点：**分块 prefill 的收益取决于调度策略**。
在短作业优先（SJF）下，短请求可以插到长请求的剩余分块前面，
交互请求的 TTFT p99 从 142.1 ms 掉到 **30.4 ms**（4.7 倍），
代价是长请求自己的 TTFT 从 141.4 ms 涨到 **208.5 ms**。
同一套分块机制，换个策略就是完全不同的收益分布——这正是第 8 章的主题。

## 4. 抢占与重算：显存不够时的最后手段

当 KV cache 装不下新请求时，引擎只有三条路：

| 手段 | 做法 | 代价 |
| --- | --- | --- |
| 拒绝 | 排队等槽位 | TTFT 变长，但不浪费算力 |
| 换出（swap） | 把序列的 KV 写到 CPU 内存 | 换进时还要写回，延迟不定 |
| 抢占重算（recompute） | 直接踢掉序列，之后从头重算 | 重算成本 = 一次完整 prefill |

重算成本可以直接用 prefill 时间算出来：

```
重算 512  token ≈  13.63 ms
重算 4096 token ≈ 114.99 ms      # 8.4 倍
```

所以**长请求不该随便被抢**：踢掉一条 4K 的请求，等于白扔 115 ms 的算力。
真实的引擎（vLLM 等）通常只在"重算代价 < 继续跑代价"时才抢占，
并且优先踢已经生成很多 token 的序列——因为它重算时只需要补算剩下的部分，
而不是从头再来。

本章只给抢占定了价（成本表），具体的抢占策略放在第 8 章和多副本章节讨论。

## 5. 吞吐 vs 时延：batch 越大越好吗

连续批让"把 batch 开大"变得可行，但**开大 batch 本身不是目的**：

- batch 越大，一轮 decode 里权重读取被摊得越薄，单位 token 的成本越低 → 吞吐上升；
- 但 batch 越大，单个请求要等越多同伴一起完成 → 它自己的时延上升；
- 更糟的是：batch 里只要有一条长请求，**整轮的时长就由它决定**（本章模型取 max）。

本章实验里，静态批和连续批的差别正是"槽位空转"这一项（56.7%）。
连续批把这个浪费拿掉了，剩下的空转只剩"队列真的空了"那部分。
而连续批内部，batch 大小由 `max_batch` 和 KV 预算决定：
KV 装不下就自动停在更小的 batch 上——这也是第 5、16 章要算的那本账。

## 判断依据

1. **看 p99/p50 比值，不要看 p99 的绝对值。**
   本章静态批 p99 = 1633.9 ms、连续批 p99 = 144.9 ms，绝对值差 11 倍；
   但比值 9.90 → 1.02 更能说明问题：连续批把尾部压回了中位数附近。
   比值 > 3 就说明存在"一条请求拖住一整批"的队头阻塞。
2. **同时看"槽位空转率"和"总耗时"。**
   空转率 > 20%（本章静态批 56.7%）说明吞吐被空槽位吃掉了，
   加大 batch 只会让空转更严重；此时该做的是换调度粒度，不是换硬件。
3. **一条 prompt 的 prefill 时间 > 10 轮 decode 时，必须开 chunked prefill。**
   判据是 `prefill(prompt_tokens) > 10 × decode_step_time`：
   本章 4096 token 的 prefill 是 115 ms，而一轮 decode 是 9.24 ms，比值 12.4 → 该开。
4. **判断分块粒度时，看卡顿 p99 而不是 TTFT p99。**
   chunk=512 → 卡顿 15.3 ms；chunk=1024 → 27.5 ms。
   目标是让卡顿回到"几轮 decode"的量级，而不是追求 TTFT 下降。
5. **估算抢占代价时，用 `prefill_time(prompt_tokens)`，并和"被踢序列剩余的生成成本"比较。**
   4096 token 的重算是 114.99 ms；如果那条序列本来还要跑 2 秒，抢占就不划算；
   如果它只剩 50 ms 的生成量，那重算反而更便宜。

## 常见误区

1. **"batch 开得越大，吞吐越高，所以把 batch 调到最大。"**
   吞吐确实上升，但同 batch 里的请求时延同步上升；而且长请求会让整轮变慢，
   实际吞吐远低于线性外推。本章静态批的槽位空转 56.7% 就是反例。
2. **"连续批处理就是不用固定 batch 槽位了。"**
   槽位还是固定的（受 `max_batch` 和 KV 预算约束），
   变的是**槽位什么时候被回收和复用**——每轮迭代就重排一次。
3. **"分块 prefill 是为了降低 TTFT。"**
   本章数据：TTFT p99 只从 142.1 ms 降到 136.1 ms，改善的是卡顿（115 → 15.3 ms）。
   分块 prefill 保护的是**正在生成的请求**。
4. **"长 prompt 一次性 prefill 更快，分块只是绕路。"**
   总算力一样（甚至分块略省，因为跨块的注意力可以复用），
   差别在**时间分布**：一次性算完 = 独占 115 ms；分块 = 每块只占 13.6 ms。
5. **"抢占重算是免费的，把不要的序列踢掉就行。"**
   4K prompt 重算一次 115 ms。抢占是最后手段，不是常规调度手段。

## 自测题

1. 某服务的 TTFT p50 = 80 ms、p99 = 1200 ms，e2e p99 = 3 s。
   这个服务最可能卡在哪？应该先查什么？
   - 答案要点：p99/p50 = 15，属于典型的队头阻塞；先查是否存在静态批/整批放行，
     再查是否有超长 prompt 独占整卡（chunked prefill 是否开启）。
2. 一条 8192 token 的 prompt，prefill 要 230 ms；一轮 decode（batch=16）约 12 ms。
   该不该开分块 prefill？chunk 取 1024 的话卡顿大概落在什么量级？
   - 答案要点：230 / 12 ≈ 19 > 10，该开；卡顿量级 ≈ chunk 的 prefill 时间
     （1024 token ≈ 29 ms），比独占时的 230 ms 降一个数量级。
3. 静态批的吞吐只有连续批的 67%，且槽位空转率 56.7%。
   换一个更大的 `max_batch` 能改善吗？
   - 答案要点：不能，甚至更糟。空转的根因是"跑完的槽位要等整批结束"，
     batch 越大尾巴越长、空转越多。要改的是调度粒度（连续批），
     而不是 batch 上限。
4. 量化权重到 INT4 之后，为什么 TTFT 几乎不变而 token/s 明显上升？
   - 答案要点：见第 9 章。prefill 是算力瓶颈，decode 是访存瓶颈；
     量化省的是访存带宽，所以只加速 decode。
