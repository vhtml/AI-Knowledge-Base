# 附录 C：常见故障排查

**按症状索引**。每个症状给出：怎么确认根因、怎么修、怎么避免复发。

---

## 症状 1：启动就 OOM

**表现**：加载完权重就报 CUDA out of memory，连第一个请求都接不了。

**按顺序查**：

1. **权重装得下吗**——用第 2 章的公式算，别靠猜。
   70B FP16 ≈ 132 GiB，单张 80GB 卡**必然**装不下
2. **是不是同时加载了多个模型**——服务里常驻了 embedding/rerank 模型，
   它们的显存要算进同一张卡
3. **框架开销超预期**——CUDA context + 通信缓冲 + 显存池预分配，
   通常要留 3–5 GiB，不是 1 GiB
4. **有没有把 KV 预算算成 0**——很多服务的 KV 是**按需增长**的，
   没有设上限时第一个长请求就能把剩下的显存吃光

**修**：换更小的模型 / 量化 / 多卡切分 / 给 KV 设硬上限。

---

## 症状 2：跑了一段时间才 OOM

**表现**：服务跑了几小时后开始 OOM，重启就好。

**这是最常见也最容易被误判的一类**——因为重启能"解决"，
所以很多人当成偶发，直到它第三次发生。

**根因只有一个：显存随时间单调增长。** 查这几个地方：

1. **KV cache 没释放**——请求异常结束后，KV 块没归还。
   典型症状：KV 利用率曲线只升不降
2. **前缀缓存没有淘汰策略**——缓存一直涨到撑满显存。
   需要 LRU + 容量上限（第 12 章）
3. **碎片**——分页虽然省了预留，但块分配得太碎也会浪费。
   看碎片率指标
4. **有内存泄漏**——Python 侧的对象没释放（连接池、闭包持有的引用）
5. **请求长度不受控**——某个客户端发了超长 prompt，
   第一个长请求就把 KV 吃满。**必须设 max context 上限**

**排查手法**：每隔 5 分钟记录一次 KV 使用量和活跃请求数。
如果活跃请求数稳定而 KV 使用量在涨 → 一定是没释放。

---

## 症状 3：TTFT 突然飙高

**表现**：P50 正常，P99 暴涨到几秒甚至几十秒。

**先做三段分解**（第 14 章）——排队 / prefill / decode，定位是哪一段：

| 慢在哪 | 常见原因 | 处理 |
| --- | --- | --- |
| 排队 | 容量不足、突发流量、扩缩容不及时 | 扩容、限流、优化 batch |
| prefill | 长 prompt 打满算力、chunked prefill 没开 | 开 chunked prefill、限制 max context |
| decode | batch 太大导致每步变慢、GPU 被别的任务占用 | 调 batch 上限、检查共享 |

**特别检查**：
- 有没有**长请求阻塞**——静态批或没有 chunked prefill 时，
  一个长 prompt 会让同期所有请求的 TTFT 一起飙（第 7 章）
- 刚做完**扩缩容**——新副本在 warmup，请求都在老副本上排队
- **缓存命中率掉了**——prompt 模板改了或路由策略变了，
  前缀缓存失效导致每个请求都要重算 prefill（第 12 章）

## 症状 4：吞吐上不去

**表现**：GPU 利用率不高，QPS 也上不去。

**诊断顺序**：

1. **GPU 利用率低 + 队列长**→ 卡在**带宽**（decode 访存瓶颈）。
   检查：是不是权重太大（每步都要读一遍）？是不是 batch 太小？
   → 调大 batch、量化权重（第 4、9 章）
2. **GPU 利用率高但吞吐低**→ 卡在**算力**（prefill 吃掉了算力）。
   检查：是不是 prompt 太长？prefill 占比多少？
   → 开 chunked prefill、限制 max context
3. **GPU 利用率低 + 队列短**→ **请求不够**。这是好事，
   说明容量有富余，可以接更多流量
4. **多副本负载不均**→ 亲和路由把流量钉在少数副本上。
   检查每个副本的请求分布（第 11 章）

**别忘了先确认瓶颈在哪**：跑一遍第 3 章的 Roofline 分析，
别凭感觉调参数。

---

## 症状 5：显存水位高但利用率低

**表现**：显存占了 70%，但 GPU 算力只用了一点。

**这是 KV cache 撑着的**。KV 是显存，不是算力。

**算账**：KV 占比高说明你的并发上限受显存限制，
而不是受算力限制。这时候**加卡能提吞吐，但单卡并发已经到顶**。

**可选动作**：
- 量化 KV（FP8）→ 直接换更多并发
- 用 GQA 模型
- 降低 max context
- **让 KV 溢出到主机内存**（vLLM 的 CPU offload）——
  能跑但延迟会跳变，只适合应急

---

## 症状 6：前缀缓存不命中

**表现**：命中率一直是 0 或很低。

**逐条查**：

1. **请求真的有共享前缀吗**——如果每个请求的 prompt 都不同，
   前缀缓存本来就帮不上忙
2. **system prompt 放在最前面了吗**——共享部分必须在前面。
   把变化的部分放后面（第 13 章）
3. **路由把请求打散了吗**——随机路由 + 多副本 = 命中率约 1/副本数。
   必须开前缀亲和路由（第 11 章）
4. **tokenizer 一样吗**——不同模型的 token 序列不同，
   块哈希必然不同。前缀缓存**跨模型不通用**
5. **前缀够长吗**——前缀短于一个块（16 token）就没有复用价值
6. **缓存被淘汰了**——缓存容量太小，LRU 把有用的前缀挤掉了
7. **中间有变化**——prompt 模板里插了时间戳、用户 ID、随机数？
   **每次请求都变的话前缀缓存 100% 不命中**

**快速诊断**：把两个请求的 prompt token 序列前 200 个打印出来对比，
一样却没命中 → 查路由和缓存容量。

---

## 症状 7：成本比预期高

**表现**：账单超预算。

**按这个顺序查**：

1. **每百万 token 成本算对了吗**——按实际负载画像算，
   不是按"平均输出 200 token"这种假设（第 16 章）
2. **有没有浪费的输出**——max_tokens 设太大、模型没学会停止、
   重试产生的重复消耗。**这是最常见的浪费源**
3. **缓存命中率多少**——命中率低意味着大量重复 prefill
4. **有没有无效请求**——爬虫、健康检查探针带真实 prompt、
   前端重复提交
5. **batch 上限是多少**——太小则 GPU 空转，固定成本摊薄不够
6. **副本数是不是太多了**——按峰值配的，平时用不满就在烧钱
7. **模型是不是太大了**——小模型能做的活别用大模型

## 症状 8：副本之间负载不均

**表现**：一个副本忙死，其他闲着。

**原因**：

1. **亲和路由把流量钉住了**——前缀相同的请求都去一个副本。
   **这是设计如此，不是 bug**，但需要限流保护那个副本（第 11 章）
2. **路由只看负载但负载指标不对**——用请求数衡量负载，
   而一个长请求和一个短请求占用差 100 倍。应该用"占用时间"或队列深度
3. **健康检查导致副本被摘除**——副本假死但没被摘除
4. **DNS 层面的负载均衡不均匀**——长连接导致连接粘在少数副本上

---

## 症状 9：扩了容但没生效

**表现**：副本数加了，队列还是长。

**逐条查**：

1. **新副本就绪了吗**——拉镜像、下载权重、加载显存、warmup，
   每一步都可能很慢。看新副本的 ready 状态而不是 pod 数量
2. **新副本注册进负载均衡了吗**——注册了但没被选中
3. **亲和路由把流量钉在老副本**——新副本是冷的，
   拿不到共享前缀，请求不敢过去
4. **触发指标滞后**——用的是利用率而不是队列深度，
   等利用率涨上去已经晚了（第 15 章）

---

## 症状 10：延迟正常但输出质量下降

**表现**：用户报"回答变差了"。

**最可能是量化引入的**：

1. **量化方案是什么**——INT4 需要校准集，AWQ/GPTQ 各有擅长场景
2. **校准数据像不像你的业务**——用通用语料校准，
   在你的领域上掉点很常见
3. **KV 量化有没有开**——长上下文下 KV 掉点比权重量化明显
4. **分组大小是不是太大**——group size 越大精度越差（第 9 章）

**排查方法**：拿量化前后的模型跑同一组评测集对比，
确认掉点幅度可接受。**没有评测就没有质量保证**。

## 通用排查手法

### 三段分解
任何延迟问题，先做：排队 + prefill + decode 三段分解（第 14 章）。
**跳过这一步的排查都是猜。**

### 变更回溯
最近的：模型版本、量化配置、prompt 模板、路由策略、batch 上限、限流阈值、依赖版本。
**80% 的"突然变慢"都能追溯到一次变更。**

### 对照实验
把有问题的配置和正常的配置并排放，只改一个变量。
比"改几个参数试试"快十倍。

### 先止血
线上故障时，**先恢复服务再定位根因**。
限流 → 扩容 → 降级 → 回滚，按这个顺序试。
