# 04 · 访存墙与批量摊薄

> **这章要解决的问题**：生成阶段（decode）慢，到底是模型太大、算力不够吗？本章的判断题是——**"decode 的瓶颈是算力还是带宽？批量到底能把速度提到多快？"**
>
> 三个判断：(1) decode 每一步都要把整套权重从 HBM 读一遍，batch=1 时 GPU 的算力单元大部分时间在空转；(2) 批量能摊薄权重读取，权重读一次服务多条序列；(3) 但 KV 读取量随 batch × 上下文长度线性增长，所以**存在最优 batch，不是越大越好**。

---

## 1. decode 阶段为什么是访存瓶颈

推理分两个阶段，它们的瓶颈完全相反：

| 阶段 | 输入 | 权重被复用次数 | 算术强度 | 瓶颈 |
| --- | --- | --- | --- | --- |
| prefill（处理 prompt） | 一次几千个 token | 每个 token 都过一次权重 | 高（数千 FLOP/byte） | **算力** |
| decode（逐 token 生成） | 一次一个 token | 每步把**整套**权重读一遍 | 极低 | **带宽** |

decode 每走一步，模型必须为**每一个** token 重新读完所有层的所有权重矩阵。这是自回归解码的本质——上一个 token 的输出是下一个 token 的输入，没法像 prefill 那样一次并行处理几千个 token。

用本章的算账口径（qwen2.5-7b，fp16，H100 SXM 80GB，MFU 0.5，上下文 4096）：

- 权重体积 = 7.62B 参数 × 2 字节 = **15.24 GB**
- 每步搬的字节：权重 15.24 GB + KV（batch × 0.2349 GB）
- 每步的 FLOPs：batch × 14.70 GFLOP

于是**算术强度**（FLOPs ÷ 搬运字节）：

| batch | 单步时延 | 整机吞吐 | 算术强度 | 权重占搬运量 |
| --- | --- | --- | --- | --- |
| 1 | 9.24 ms | 108 tok/s | 0.95 | 98.5% |
| 8 | 10.22 ms | 783 tok/s | 6.87 | 89.0% |
| 32 | 13.59 ms | 2355 tok/s | 20.68 | 67.0% |
| 128 | 27.05 ms | 4732 tok/s | 41.54 | 33.6% |

H100 的 Roofline 拐点算术强度 = 989 TFLOPS ÷ 3350 GB/s = **295.2 FLOP/byte**。

**batch=1 时算术强度只有 0.95，是拐点的 0.32%。** 也就是说 GPU 98.5% 的时间在搬数据，只有 0.32% 的算力被真正用上。这就是"访存墙"的全部含义：不是显卡不够快，是它在等数据。

> **本章第一个判断规则**：任何时候有人问"要不要换更快的卡"，
> 先算 decode 阶段的算术强度。**离拐点差两个数量级，换卡没有意义，换算法（量化 / 减 KV 头数 / 复用前缀）才有意义。**

---

## 2. 批量摊薄：权重读一次，服务多条序列

批量之所以有效，是因为**权重读取这一步是整个 batch 共享的**。batch=1 时，15.24 GB 的权重搬运只服务一条序列；batch=16 时，同样是 15.24 GB，服务 16 条序列。

摊薄的程度可以直接量：

| batch | 每序列分摊到的权重读取 |
| --- | --- |
| 1 | 9.099 ms |
| 8 | 1.137 ms |
| 16 | 0.569 ms |
| 32 | 0.284 ms |
| 128 | 0.071 ms |

**每序列的权重成本随 batch 近似 1/B 下降。** 效果是：

- batch 从 1 提到 16：吞吐 **×13.0**，而单步时延只从 9.24 ms 涨到 11.34 ms（+23%）
- 这就是连续批处理（第 7 章）能把单位算力成本压下去的物理基础

关键在于**权重项是常数，KV 项才是变量**。这一步的单步时延可以写成：

```
单步时延(B) = ( W + B × K ) / (BW × MFU)
              └─常数─┘   └─线性─┘
              W = 权重字节数
              K = 每序列每步的 KV 字节数 = 每token字节数 × 上下文长度
```

---

## 3. 代价：KV 读取量随 batch × 上下文线性增长

每生成一个 token，每条序列都要读它**全部历史**的 K/V。batch 越大、上下文越长，这笔账越贵：

- qwen2.5-7b 每 token 的 KV = 2 × 28 层 × 4 KV 头 × 128 head_dim × 2 字节 = **57,344 字节**
- 上下文 4096 时，每条序列每步要读 0.2349 GB 的 KV

于是出现了**拐点**：当 KV 读取量追平权重读取量时，权重摊薄的收益就耗尽了。

```
拐点 batch = W / K = 权重字节数 ÷ (每token KV字节数 × 上下文长度)
```

| 上下文长度 | 拐点 batch |
| --- | --- |
| 512 | 519 |
| 1024 | 260 |
| 2048 | 130 |
| 4096 | **65** |
| 8192 | 32 |
| 16384 | 16 |
| 32768 | 8 |

**拐点 batch 与上下文长度成反比。** 上下文越长，能摊薄权重的空间越小——这直接解释了为什么长上下文服务的 batch 往往开不大。

---

## 4. 最优 batch：拐点之后，延迟的代价超过吞吐的收益

扫描 batch 1→128（上下文 4096）：

| batch | 单步时延 | 整机吞吐 | 算术强度 |
| --- | --- | --- | --- |
| 1 | 9.24 ms | 108 tok/s | 1.0 |
| 16 | 11.34 ms | 1411 tok/s | 12.4 |
| 32 | 13.59 ms | 2355 tok/s | 20.7 |
| **65（拐点）** | **18.21 ms** | **3569 tok/s** | 31.3 |
| 80 | 20.32 ms | 3938 tok/s | 34.6 |
| 128 | 27.05 ms | 4732 tok/s | 41.5 |

拐点在 **batch = 65**（权重读取量 = KV 读取量）。跨过拐点再翻一倍到 128：

- 吞吐 ×1.326（+33%）
- 时延 ×1.485（+49%）
- **性价比（吞吐增益 ÷ 时延代价）= 0.893 < 1**

也就是说：**过了拐点，再往上堆 batch，每多付 1 份延迟只换回 0.89 份吞吐。** 延迟不是"不再下降"，而是**不降反升的代价开始超过收益**。这时继续加 batch 换来的吞吐增长，是以所有在线用户的出字间隔（TPOT）变差为代价的。

另一个容易忽略的结论：**即使 batch 加到 128，算术强度 41.54 仍然远低于拐点 295.2。**

| 上下文 | 算术强度的上限 |
| --- | --- |
| 1024 | 229.4 |
| 4096 | 62.6 |
| 8192 | 34.8 |
| 32768 | 14.0 |

这个上限（每 token 的 FLOPs ÷ 每 token 每步的 KV 字节数）与 batch 无关。**decode 阶段无论 batch 多大，都不可能变成算力瓶颈——batch 的上限来自带宽，不来自算力。** 这是本章最容易被误解的一条。

---

## 5. 时延预算给 batch 划了硬上限

真正决定 batch 的往往不是吞吐最优，而是 SLO。给定 TPOT 预算 15 ms：

- 单步时延 ≤ 15 ms 对应的最大 batch = **42**（拐点 65 之前，SLO 先到）
- 此时整机吞吐 2802 tok/s，而拐点处能跑到 3569 tok/s

**先问 SLO 要多少 batch，再问显存装不装得下，最后才谈吞吐最优。** 三者的顺序不能颠倒——先追求吞吐最优，往往得到一个时延不可用、根本不能上线的配置。

---

## 判断依据

1. **decode 慢先算算术强度**：`FLOPs ÷ 搬运字节`，和 Roofline 拐点比。低于拐点一个数量级以上，就是访存瓶颈，换卡无用，要改算法。
2. **估 batch 上限先算拐点**：`B* = 权重字节数 ÷ (每token KV字节数 × 上下文长度)`。有效 batch 目标设在 B* 附近；超过 B* 后，吞吐增益 ÷ 时延代价会跌破 1。
3. **定 batch 上限按这个顺序**：SLO 允许的最大 batch → 显存允许的并发数 → 取小者。前者算 `step_time(B) ≤ TPOT预算` 的最大 B，后者算 `KV预算 ÷ 每序列KV`。
4. **batch=1 的算力利用率低于拐点的 1% 是正常现象**，不是 bug。任何"单条请求跑不满 GPU"的抱怨，都该用批处理解决，而不是换硬件。
5. **长上下文一定要压低 batch**：B* 与上下文长度成反比，32K 上下文时 B* 只有 8，此时靠加大 batch 摊薄权重已经没什么空间了。

---

## 常见误区

1. **"模型太大所以要换大卡"**——decode 阶段 batch=1 时算力利用率只有 0.32%，大卡的算力根本用不上。真正卡住的是 HBM 带宽，换同带宽的卡没用，得改算法（量化、减 KV 头、复用前缀）。
2. **"batch 越大越快，开到显存上限为止"**——吞吐确实还在涨，但时延涨得更快。batch=65→128 吞吐只涨 33%，时延却涨 49%。而且 batch 上限来自带宽，不来自算力：加到 128 时算术强度 41.5，离拐点 295 还差一个数量级。
3. **"KV cache 只是省一次计算，不重要"**——KV 每步都要读，它既占显存（第 5 章）又是每步的带宽开销（第 3 节的 K 项）。上下文越长，它越 dominates。
4. **"算术强度低说明 GPU 选小了"**——恰好相反：算术强度低说明**该调算法而不是调硬件**。算术强度是工作点的性质，换卡不改变它。
5. **"拐点就是吞吐最优点"**——拐点是权重摊薄收益耗尽点，吞吐在它之后仍然单调上升（只是性价比变差）。真正的最优 batch 还要叠加 SLO 约束。

## 自测题

1. **为什么 decode 的算术强度远低于 prefill？**
   要点：decode 每步只处理一个 token，权重被复用一次却要完整搬运一遍；prefill 里权重被几千个 token 复用。两者算力强度相差几个数量级。
2. **qwen2.5-7b 在 H100 上、上下文 8192 时，拐点 batch 是多少？为什么比上下文 4096 时小？**
   要点：32。`B* = 权重字节数 ÷ (每token KV字节数 × 上下文长度)`，上下文翻倍，KV 项翻倍，拐点减半。
3. **某服务 TPOT 预算是 20 ms，算力无限。把 batch 调到 128 会发生什么？**
   要点：单步时延 27.05 ms 已经超预算，所有在线请求的出字间隔一起变差。应该先按预算算出最大可行 batch（约 60），而不是按吞吐最优或显存上限来调。
4. **"batch 加到 1024 就能把 GPU 算力跑满"——这句话错在哪？**
   要点：decode 的算术强度上限由 `每token FLOPs ÷ 每token KV字节数` 决定，与 batch 无关。上下文 4096 时上限 62.6，H100 拐点 295.2，再大的 batch 也只是访存受限。
5. **为什么"每一步都把权重读一遍"不能靠缓存解决？**
   要点：15.24 GB 的权重远大于任何片上缓存（H100 的 L2 只有 50 MB），每步都必须完整走一遍 HBM。能优化的只有"读一次服务多少条序列"和"权重本身有多大"。
