# 10 · 推测解码与时延收益

> **这章要解决的问题**：推测解码到底能不能省时间？它不改输出质量，为什么还能变快？
> 什么时候开、什么时候必须关？**判断题**：给你一组指标——接受率、batch 大小、
> draft 与 target 的规模比——你能不能在**上线前**算出加速比是 1.8× 还是 0.7×？
> 本章要给出一个能算的公式和三条硬边界。

---

## 1. 机制：draft 猜 K 个，target 一次验 K+1 个

推测解码（speculative decoding）的流程只有四步：

```
   prompt ──▶ draft 模型贪心生成 K 个 token：d1 d2 d3 d4
                    │
                    ▼
          把 [prompt, d1..d4] 一次性喂给 target 模型
                    │
                    ▼
          target 在 K+1 个位置上**并行**给出自己的预测 t1..t5
                    │
                    ▼
          从左往右逐个比对：d1==t1 接受，d2==t2 接受……
          遇到第一个不匹配就停下，回退到那个位置
                    │
                    ▼
          本轮有效产出 = 1 + 连续匹配的个数
```

关键在第三步：target 一次 forward 就把 K+1 个位置全验完。
这只有在 GPU **访存瓶颈**下才划算——因为 decode 阶段每一步都要把整套权重从 HBM 读一遍，
读一遍权重顺手多算几个位置，边际成本几乎为零。

### 1.1 为什么质量不变

这是最容易被误解的一点：推测解码**不是近似**，它是**无损**的。

- draft 猜的 token 只有在 target **自己也预测出同一个 token** 时才被采纳；
- 一旦不匹配，本轮多算的部分全部丢弃，输出退回到 target 自己算的那一步；
- 所以最终输出的分布，与"target 逐 token 贪心解码"**完全一致**。

变的是**每个 token 的平均耗时**，不是 token 的总数，也不是 token 的内容。

> 这也是它和"投机采样（speculative sampling）"的区别：后者用修改过的采样分布换取速度，
> 质量会变；前者靠"target 点头才采纳"保证无损。

### 1.2 加速比公式

设一轮里 draft 猜 K 个 token，期望接受率 α（0~1）：

| 量 | 表达式 |
| --- | --- |
| 每轮期望有效 token | `1 + K·α`（第一个位置总是接受） |
| 一轮耗时 | `C_draft + C_target` |
| 原始解码 N 个 token | `N × C_target` |
| 推测解码 N 个 token | `N/(1+K·α) × (C_draft + C_target)` |

于是：

```
speedup = (1 + K·α) × C_target / (C_draft + C_target)
```

`C_draft` 与 `C_target` 都以"一个 decode 步"为单位。
draft 模型小一个数量级时，`C_draft/C_target ≈ 0.1~0.3`。

### 1.3 盈亏平衡接受率

把上式令 `speedup = 1`，解出 α 的临界值：

```
α* = C_draft / (K × C_target)
```

**这个式子是本章最重要的产出**：它把"要不要开推测解码"变成了一道算术题。

以 Qwen2.5-7B（fp16，H100）配 0.5B draft、K=4 为例，
`C_draft/C_target ≈ 26%`，于是 `α* ≈ 6.5%`。
换句话说：**只要 draft 猜对十分之一，这个配置就不亏**。

而 draft 换成 1.5B（比值 81%），`α*` 升到 20.3%；
换成与 target 同规模的 7B（比值 400%），`α* = 100%`——**永远不可能回本**。

| draft 规模 | 每轮 draft 代价 | 占 target 比 | 盈亏平衡接受率 | α=1 时加速比上限 |
| --- | --- | --- | --- | --- |
| 0.5B | 2.37ms | 26.0% | 6.5% | 3.97× |
| 1.5B | 7.40ms | 81.2% | 20.3% | 2.76× |
| 7B（=target） | 36.46ms | 400.0% | 100.0% | 1.00× |

（实验数据：H100 SXM / Qwen2.5-7B-Instruct fp16 / context=512 / mfu=0.5 / K=4）

## 2. 什么时候有效：三个条件同时成立

### 2.1 接受率要高

接受率 α 直接决定收益，且**没有替代品**。实验扫描结果：

| 接受率 | 每轮有效 token | 加速比 |
| --- | --- | --- |
| 0.05 | 1.20 | 0.95（亏） |
| 0.10 | 1.40 | 1.11 |
| 0.30 | 2.20 | 1.75 |
| 0.50 | 3.00 | 2.38 |
| 0.60 | 3.40 | 2.70 |
| 0.80 | 4.20 | 3.33 |
| 1.00 | 5.00 | 3.97 |

接受率低通常来自这些场景：长文本创作、开放域问答、需要推理的数学题。
结构化输出（代码补全、固定模板、翻译、JSON 抽取）接受率能到 0.7~0.9。

### 2.2 draft 必须便宜一个数量级

draft 模型不是随便找个小模型就行，它的参数量要小到 `C_draft/C_target` 足够低。
经验值是**小 10 倍左右**：7B 配 0.5B~1.5B。
再小下去，draft 自己的接受率会塌（它连"猜个大概"都做不到），两头不讨好。

### 2.3 输出要短

这一条最容易被忽略，但很关键：推测解码加速的是 **decode 阶段**。
- **prefill（长 prompt）不受任何影响**——推测解码只管生成阶段；
- 输出越长，decode 阶段占比越高，推测解码能摊到的固定成本（draft 加载、首次 prefill）越划算；
- 反过来，一个 10 token 的短问答，TTFT 由 prefill 主导，开推测解码几乎没有意义。

> 换个说法：**推测解码改善的是 TPOT（每输出 token 时延），不是 TTFT（首 token 时延）**。
> 你的 SLO 到底卡在哪一个，决定了这个技术值不值得上。

## 3. 什么时候无效：batch 变大是最隐蔽的坑

上面所有分析都基于一个假设：**target 的一次 forward 验证 K+1 个位置，和验证 1 个位置一样贵**。
这只在**访存瓶颈**下成立。

### 3.1 Roofline 视角

decode 步的访存量是「权重 + KV」，计算量随 batch 线性增长。
用第 3 章的 Roofline 口径看 Qwen2.5-7B 在 H100 上、context=512 的工作点：

| batch | target 一步 | target 验证 5 位 | draft 一轮 | 验证/一步 | 加速比 | 瓶颈 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 9.12ms | 9.12ms | 2.37ms | 1.00 | 2.70 | 访存 |
| 8 | 9.24ms | 9.24ms | 2.48ms | 1.00 | 2.68 | 访存 |
| 32 | 9.66ms | 9.66ms | 2.84ms | 1.00 | 2.63 | 访存 |
| 64 | 10.22ms | 10.22ms | 3.32ms | 1.00 | 2.57 | 访存 |
| 128 | 11.34ms | 17.17ms | 4.28ms | 1.51 | 1.80 | 访存 |
| 256 | 13.59ms | 34.34ms | 6.21ms | 2.53 | 1.14 | 访存 |
| 512 | 18.07ms | 68.67ms | 10.05ms | 3.80 | 0.78 | 访存 |
| 1024 | 27.47ms | 137.35ms | 17.74ms | 5.00 | 0.60 | 算力 |

看「验证/一步」这一列：batch ≤ 64 时它恒等于 1.00，
说明多验 4 个位置真的**免费**——权重读一遍，顺手多算几个位置而已。

但 batch 涨到 128 以后，这个比值开始跳：1.51 → 2.53 → 3.80 → 5.00。
原因是 GPU 的算力被填满后，**多算 K 个位置要真金白银地花 FLOPs**，
"免费搭车"变成了"按 K 倍收费"，而 target 的这份额外计算换来的只是 `K·α` 个有效 token。

### 3.2 临界 batch

实验用二分法求出加速比跌破 1 的临界点：

> **接受率 60%、K=4 时，加速比在 batch ≈ 319 处跌破 1。**

这条线是可以提前算的：
先按 `load_balancing_delta` 或第 4 章的模型估出稳态并发，
再对比 `batch` 与临界值——**超了就必须关掉推测解码，或者把 batch 拆开**。

### 3.3 高 batch 下反而更慢

batch=1024 时加速比只有 0.60：target 多算了 4 倍的位置，只换回 3.4 个 token（α=0.6），
**净亏**。而且 draft 的 K 个串行步还要额外占 17.74ms。

这就是为什么生产环境里推测解码通常要**动态开关**：
batch 超过阈值就摘掉 draft 模型，纯 target 解码。

## 4. Medusa / EAGLE：换一种方式拿到并行

上面讲的经典推测解码有个明显短板：**要额外跑一个 draft 模型**。
Medusa 和 EAGLE 换了个思路——不在模型外面加，而是在**模型里面加**。

| 方案 | 结构 | 额外成本 | 特点 |
| --- | --- | --- | --- |
| 经典推测解码 | 独立的 draft 模型 + target 模型 | 多一份权重 + 每轮 K 步 draft 解码 | 通用，任何模型都能套 |
| Medusa | 在 target 上加多个预测头，直接从隐状态预测未来第 1/2/3… 个 token | 几乎为零（几个小线性头） | 需要训练预测头 |
| EAGLE | 在 target 上加一个轻量自回归头，吃 target 的 top-1 token embedding，预测下一层特征 | 一个小模型 | 接受率通常高于 Medusa |

Medusa 的原理值得多说一句：既然"多验几个位置"在访存瓶颈下几乎免费，
那能不能**不要 draft 模型**，直接让 target 自己的隐状态预测出后面的 token？
答案是可以——把最后一层隐状态过一个小的分类头，就能得到"未来第 2 个 token"的分布。
多个头并行，就能一次给出多个候选，target 再用一次 forward 验证。

EAGLE 更激进：它预测的不是 token 而是**特征**——用 target 上一层的输出特征，
经过一个轻量模块预测下一层的特征。因为特征的熵比 token 低（同一个意思可以有多种说法），
接受率比 Medusa 更高。

**判断上的差别**：经典推测解码不需要训练，插上就用，适合先验证概念；
Medusa/EAGLE 需要用你**自己的**数据训练预测头，接受率能更高，但有训练成本和模型绑定。

> 无论哪种方案，第 3 节的 batch 边界都成立——因为它们共享"一次 forward 验证多个候选"这个前提。

## 5. 判断依据

按顺序问自己四个问题，任意一个答"否"就别开：

1. **SLO 卡在 TPFT 还是 TTFT？**
   卡 TTFT 就别开——推测解码完全不动 prefill，开了也白开。

2. **接受率 α 的实测值是多少？**
   拿真实流量跑一遍，不要估。算 `α* = C_draft/(K·C_target)`，
   α 必须**明显高于** α*（至少留 2 倍余量，因为线上接受率会波动）。

3. **稳态 batch 距离临界 batch 还有多远？**
   用第 16 章的容量模型算出稳态并发，和临界 batch 比。
   **安全线建议取临界值的 1/3**——线上 batch 会抖动，峰值才是真正要防的。

4. **draft 模型能不能小 10 倍？**
   不能的话，先去训一个更小的 draft，或者改用 Medusa/EAGLE 路线。

满足以上四条，再确认一条**底线**：**输出必须走 target 验证**。
任何绕过 target 直接采信 draft 输出的实现，都会改变输出质量，不能叫推测解码。

## 6. 常见误区

1. **"推测解码能降低 TTFT"**——不能。prefill 完全没被加速，
   第一个 token 出来的时间只会因为 draft 的额外开销**略微变差**。
   TTFT 敏感的场景（长 prompt、交互式补全）开这个技术是净亏。

2. **"接受率高就一直赚"**——只在小 batch 成立。
   batch 涨过临界点，加速比会跌破 1，变成净亏，而且亏得越来越快（表 3.1 的最后一行）。

3. **"用小模型当 draft 就行"**——小到一定程度接受率会塌。
   0.5B 给 7B 当 draft 和 3B 给 7B 当 draft，接受率不是同一个数。
   参数量差 10 倍是经验起点，不是保证。

4. **"加速比能到 5×"**——理论上限是 `1 + K`（draft 完全免费、接受率 100%）。
   实际能到 2~3× 就很好了。看到宣称 5× 的，先问 K 是多少、batch 是多少。

5. **"draft 输出直接用，省一次验证"**——那是投机采样，不是推测解码，
   质量会变。本章所有结论都建立在"target 点头才采纳"这个前提上。

## 7. 自测题

1. **某服务用 7B target 配 1.5B draft，K=4，实测接受率 0.45，稳态并发 200。
   该不该开？**
   **答案要点**：先算 `α* = C_draft/(K·C_target) ≈ 81%/(4×100%) ≈ 20.3%`，
   0.45 高于它但余量不足 2 倍；再算临界 batch——200 远小于该配置的临界值，
   batch 这一关能过，但接受率余量这一关存疑。
   结论：**可以灰度开，但要盯住接受率，并预留动态关闭的开关**。

2. **为什么推测解码在 batch=64 时验证 5 个位置和验证 1 个位置一样快？**
   **答案要点**：decode 步的访存是「权重 + KV」，权重是整批共享的。
   访存瓶颈下 GPU 主要在等 HBM 送权重，多算几个位置的 FLOPs 是空出来的算力，
   所以边际成本接近零。这正是推测解码的收益来源。

3. **某团队反馈"推测解码上线后 TTFT 反而变差了"，怎么解释？**
   **答案要点**：推测解码不影响 prefill，但 draft 模型要占显存、
   要加载权重、首个 token 之前还要先跑 K 步 draft。
   这些成本直接压在 TTFT 上。解法是接受这个事实——
   **推测解码是给 TPOT 用的技术，不是给 TTFT 用的**。

4. **Medusa 相比独立 draft 模型省掉了什么？多付出了什么？**
   **答案要点**：省掉了独立 draft 模型的权重显存和每轮 K 步串行 draft 解码；
   多出来的是**训练成本**——预测头必须用你自己的数据训，
   而且和 target 模型绑定，换模型要重训。

5. **为什么说"任何能抓住同义改写的阈值，必然也抓住只差一个参数的近似请求"？**
   **答案要点**：这是第 12 章语义缓存的同一个陷阱。
   只差 SKU 的请求与原请求的相似度（≈0.82）**高于**同义改写（≈0.54），
   相似度空间里"更危险的那个"离得更近，阈值无论怎么设都躲不开。

## 一句话结论

> **推测解码不改变输出，只改变每个 token 的平均耗时；
> 而这个收益只有在「target 没被算力填满、接受率过盈亏平衡线、draft 小一个数量级」三条同时成立时才是正的。
> batch 一旦越过临界值，它就从加速器变成负担。**
