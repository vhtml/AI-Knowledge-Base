# 附录 A：术语表

全课术语的准确定义。每条都给出**为什么需要这个概念**，而不只是同义反复——
因为大多数误解都来自"知道这个词，但不知道它在解决什么问题"。

---

## 一、性能与容量

### TTFT（Time To First Token）
首 token 时延：从请求到达服务端到第一个 token 返回给客户端的时间。

**它由三段组成**：排队等待 + prefill 计算 + 调度开销。
交互式产品只对这一段敏感——用户盯着屏幕等字出现。

**常见误解**：以为 TTFT 就是"模型多快"。实际上长 prompt 的 TTFT 主要花在
prefill 上，而 prefill 是**算力瓶颈**（第 3 章），跟 decode 的访存瓶颈是两回事。

### TPOT（Time Per Output Token）
每个输出 token 的平均时延：`(总时长 - TTFT) / 输出 token 数`。
也叫 ITL（Inter-Token Latency）。

**它决定了"字打出来有多快"**。用户体感上的"打字机速度"就是 TPOT，
而不是总时长。一个 10 秒出 500 字的回答（TPOT 20ms）体验上比
一个 3 秒出 50 字的回答（TPOT 60ms）更连贯。

### 吞吐（Throughput）
单位时间完成的 token 数或请求数。

**关键区分**：
- **请求吞吐**——每秒多少个请求，适合短问答场景
- **token 吞吐**——每秒多少个 token，适合长文本生成场景

同一个服务这两个数可以差好几倍，因为请求的"重量"不一样（第 1 章）。

### QPS
每秒请求数。是最常被拿来当容量指标的数字，但**它本身没有意义**——
100 QPS 的短问答和 100 QPS 的长文档生成，资源消耗差一个数量级。

### MFU（Model FLOPs Utilization）
模型浮点运算利用率：实际达到的 FLOPs ÷ 硬件峰值 FLOPs。

**推理侧的 MFU 通常远低于训练侧**（训练能到 40%–50%，推理常常只有 5%–20%），
因为推理的 decode 阶段受带宽限制，Roofline 图上根本到不了算力峰值（第 3 章）。

### 算术强度（Arithmetic Intensity）
每从显存读取 1 字节，能做的浮点运算次数。单位：FLOPs/Byte。

**这是判断"卡在算力还是在卡带宽"的唯一指标**：
- 算术强度 < 拐点 → 受带宽限制（memory bound）
- 算术强度 > 拐点 → 受算力限制（compute bound）

### Roofline 模型
把硬件的峰值算力和峰值带宽画成一张图，算术强度作为横轴，
可达性能作为纵轴。能到达的上限是一条折线：先水平（带宽限制），后 45° 上升（算力限制）。

### 拐点算术强度（Ridge Point）
峰值算力 ÷ 峰值带宽。硬件的一个固有属性。

## 二、显存与 KV cache

### KV cache
推理时缓存的 Key 和 Value 张量。

**为什么必须缓存**：生成第 n 个 token 时，注意力要读第 1 到 n-1 个 token 的 K 和 V。
不缓存的话每一步都要把整个 prompt 重算一遍，复杂度从 O(n) 变成 O(n²)。

**代价**：它和权重一样占显存，而且**随上下文长度线性增长**。
长上下文服务的瓶颈是 KV，不是权重（第 5 章）。

### 每 token KV 字节数
```
2 × 层数 × KV 头数 × head_dim × 元素字节数
```
`2` 是 K 和 V 各一份。这条公式是全课最重要的公式之一——
它解释了为什么 GQA 能省数倍显存，为什么 70B 模型的 KV 吃掉一张卡的大半。

### MHA / MQA / GQA
三种注意力变体，区别在 **KV 头数**：

| 变体 | KV 头数 | KV 显存 | 说明 |
| --- | --- | --- | --- |
| MHA | = 注意力头数 | 基准 | 每个头有自己的 K/V |
| MQA | 1 | 1/头数 | 所有头共享一组 K/V，最省，质量损失最大 |
| GQA | 介于 1 和头数之间 | 可调 | 组数可调，是当前主流折中 |

现代开放模型几乎都用 GQA——8 个注意力头配 4 或 8 个 KV 头（第 6 章）。

### 权重（Weights）
模型参数本身占用的显存。量化就是压这块。

### 激活（Activations）
推理时中间结果的临时显存：隐藏状态、注意力矩阵、中间层输出。

**小 batch 时它的占比不可忽略**——batch=1 时算力用不满，
激活却还是按理论最大值占显存，所以推理的激活开销比训练时更容易被低估（第 2 章）。

### PagedAttention / 分页 KV
借鉴操作系统分页的显存管理：把 KV 切成固定大小的块按需分配，
而不是给每条序列按最大长度预留连续显存。

**收益**：传统做法的显存浪费可达数倍（一条 100 token 的请求也要预留 128K 的位置），
分页后浪费只剩"最后一块没填满"（第 6 章）。

### 前缀缓存（Prefix Caching）
复用**相同 prompt 前缀**已经计算好的 KV。机制是块级链式哈希：
把 token 序列切块，逐块哈希连成前缀树，相同前缀自然命中相同的块。

**这是 agent 场景最大的免费午餐**——同一个 system prompt 后面接不同的用户问题，
前缀部分一次都不用重算（第 12 章）。

### KV 量化
把 KV cache 从 FP16 压到 FP8/INT8。直接换来更多可并发序列数，
代价是长上下文下精度下降比权重量化更明显（第 5、9 章）。

## 三、调度与并发

### 静态批（Static Batching）
固定一组请求一起跑，跑完一起换下一组。

**致命问题**：长短请求混批时，短请求要等最长的那条跑完才返回。
p99 被最长请求拖死，GPU 也在等（第 7 章）。

### 连续批处理（Continuous Batching）
**iteration 级**调度：每生成一个 token 就重新决定谁在跑，
跑完的立刻退出，空出的槽位马上补新请求。

**收益**：吞吐提升 2–4 倍是常态，p99 从"最长请求时长"降到接近 p50。

### Chunked Prefill
把长 prompt 切成块，分多次送进引擎，与 decode 交织。

**解决什么**：一个 100K token 的 prompt 如果一次性 prefill，
会把整个 batch 卡住几秒钟，所有短请求的 TTFT 同时飙高。分块后长请求变慢一点，
但短请求不再被牵连（第 7、13 章）。

### 抢占与重算（Preemption & Recompute）
显存不够时把运行中的序列踢出 batch，腾出 KV 空间。之后要继续时，
可能需要从头重算被驱逐部分的 KV。

**权衡**：重算浪费算力，但不重算就得预留更多显存。

### 调度策略
| 策略 | 规则 | 适合 | 代价 |
| --- | --- | --- | --- |
| FCFS | 先到先服务 | 通用、公平 | 长请求会堵住队列 |
| SJF | 短作业优先 | 短问答为主 | 长请求饿死 |
| 优先级 | 按优先级 | 多租户 | 需要配额防饿死 |
| 老化 | 等待越久优先级越高 | 防止饿死 | 轻微破坏优先级语义 |

### 令牌桶（Token Bucket）
限流算法：桶按固定速率加令牌，桶满则溢出丢弃；每个请求消耗一个令牌。

**允许突发**：桶里的存量可以一次性放出去。
交互式服务需要这个特性——用户连点两下不该被拒（第 11 章）。

## 四、模型优化

### 量化（Quantization）
用更少的比特表示权重（或 KV、激活）。

**关键认知：量化省的是显存和带宽，所以它加速的是 decode（访存瓶颈），
不加速 prefill（算力瓶颈）**（第 9 章）。

| 精度 | 每权重字节 | 典型损失 | 说明 |
| --- | --- | --- | --- |
| FP16/BF16 | 2 | 基准 | 通用 |
| FP8 | 1 | 很小 | 硬件原生支持，训练推理都能用 |
| INT8 | 1 | 小 | 成熟方案（SmoothQuant/W8A8） |
| INT4 | 0.5 | 需校准 | 显存省最多，质量需验证 |

### PTQ / QAT
- **PTQ**（训练后量化）：模型训完再量化。成本低，是主流。
- **QAT**（量化感知训练）：训练时就模拟量化误差。效果好，成本高。

### 分组量化（Group Size）
把权重按组（比如每 128 个一组）各自算缩放系数，而不是整张张量共用一个。

**组越小精度越好，但元数据（缩放系数）开销越大**。INT4 常用 64–128。

### 推测解码（Speculative Decoding）
用一个小模型（draft）先猜若干 token，再用大模型（target）**并行验证**。

**关键性质：输出结果与不用推测时完全一致**（接受/拒绝的判定是精确的），
变的只是**每个 token 的耗时**。

**何时划算**：接受率高、输出短、draft 便宜、batch 小。
batch 大时 target 已经算力饱和，并行验证的优势消失（第 10 章）。

### 接受率（Acceptance Rate）
draft 猜的 token 被 target 接受的平均比例。

**盈亏平衡点**：接受率高到某个阈值，投机采样才比原方案快。
这个阈值可以用 draft/target 的算力比直接算出来（第 10 章）。

### MQA/GQA 的质量权衡
减少 KV 头数会略微降低质量，但**对推理速度的收益是数倍级别**——
因为 KV 直接决定并发数。这是少数"质量损失小、工程收益大"的改动（第 6 章）。

## 五、服务运营

### 网关（Gateway）
推理服务的前置层。职责：鉴权、限流、路由、缓存、观测、计费。

**为什么需要独立一层**：这些横切关注点如果散落在每个副本里，
每加一个副本就要实现一遍，而且很难统一观测。

### 前缀亲和路由（Prefix Affinity Routing）
把 prompt 前缀相同的请求路由到同一个副本，让前缀缓存真正命中。

**反模式**：随机路由 + 多副本。前缀缓存的命中率会随副本数上升而崩塌——
每个副本只缓存到过的那部分前缀（N 个副本，命中率约 1/N）（第 11 章）。

### PD 分离（Prefill-Decode Disaggregation）
把 prefill 和 decode 拆到不同的 GPU 池上。

**为什么有道理**：prefill 是算力密集、decode 是带宽密集，
两者放在同一张卡上会互相干扰。分开后各自用最适合的硬件（第 18 章）。

### 冷启动（Cold Start）
新副本从零到能接请求的时间：拉镜像 + 下载权重 + 加载到显存 + warmup。

**在突发流量下这是扩容的主要延迟来源**，通常几十秒到几分钟。
容量规划必须把它算进去（第 15 章）。

### 弹性扩缩容（Autoscaling）
按指标自动增减副本数。

**关键：扩容指标应该是排队深度或 p99 延迟，不是 CPU/GPU 利用率**——
利用率要等到系统过载了才升高，那时已经晚了（第 15 章）。

### SLO / SLA
- **SLO**：内部目标，通常不写进合同
- **SLA**：对外承诺，写进合同，违约要赔钱

**推理服务的 SLO 通常是三个数字**：TTFT p99、TPOT p99、可用性。

### p99
99 分位延迟。**推理服务必须看 p99 而不是均值**——
用户不会因为一半请求快而满意，他们会因为那 1% 的慢而投诉。

## 六、训练侧（推理也需要懂）

### 数据并行 / 张量并行 / 流水线并行 / 专家并行
四种训练并行策略，切分的东西各不相同：

| 策略 | 切什么 | 通信量 | 适用 |
| --- | --- | --- | --- |
| DP | 切数据 | 每步 all-reduce 梯度 | 模型能装进一张卡 |
| TP | 切矩阵 | 每层 2 次 all-reduce | 模型太大，单卡装不下 |
| PP | 切层 | 只传激活 | 跨节点带宽差 |
| EP | 切专家 | all-to-all | MoE 模型 |

### ZeRO
把优化器状态、梯度、数据分片到各卡。ZeRO-1 切优化器状态，
ZeRO-2 再切梯度，ZeRO-3 连参数也切（用时随用随取）。

### 集合通信原语
- **All-Reduce**：所有卡各得完整结果（求和后广播）——数据并行与张量并行核心
- **All-Gather**：每卡贡献一部分，所有卡得到全部——序列并行、ZeRO-3
- **Reduce-Scatter**：归约后分片——ZeRO-2/3 的梯度归约

### NVLink / InfiniBand
卡间与节点间的高速互联。**训练侧它们的带宽直接决定并行策略能不能用**——
没有 NVLink 时，张量并行只能留在节点内（第 17 章）。

### 混合精度（Mixed Precision）
用 FP16/BF16 做大部分计算，FP32 做累加和归约。省显存、省带宽，
但需要 loss scaling（FP16）或动态 loss scaling（BF16）来避免数值下溢。

### 激活重计算（Activation Checkpointing）
反向传播时不存中间激活，改成重算。**用算力换显存**——
训练时用来支持更大的 batch，推理时基本不适用（推理本来就不用存激活）。

## 易混词速查

| 容易混 | 区别 |
| --- | --- |
| TTFT vs TPOT | 一个是"多久出第一个字"，一个是"之后每秒出几个字" |
| 吞吐 vs QPS | QPS 不看请求重量，吞吐看 token |
| 延迟 vs 吞吐 | 同一个系统此消彼长，不能同时最优 |
| MFU vs 硬件利用率 | 前者看 FLOPs 用没用满，后者看时间用没用满 |
| 显存 vs 内存 | 显存快但小且贵，主机内存大但慢，KV cache 溢出会掉到主机内存 |
| 量化 vs 剪枝 | 量化降精度不降参数，剪枝降参数不降精度 |
| 推测解码 vs 多模型路由 | 前者同一个请求内两个模型协作，后者不同请求路由到不同模型 |
| PD 分离 vs TP | PD 分离拆的是阶段（跨卡池），TP 拆的是层内矩阵（层间通信） |
| 前缀缓存 vs 响应缓存 | 前缀缓存复用 KV（省 prefill），响应缓存复用结果（省全部计算） |
| 限流 vs 背压 | 限流在入口拒绝，背压在内部阻塞；前者丢请求，后者拖慢请求 |
