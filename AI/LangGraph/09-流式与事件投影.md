# 09 · 流式与事件投影

> **这篇要回答**：LangGraph 的五种 `stream_mode` 各自吐的是什么？为什么 `stream` 和 `stream_events` 是两套东西？v1 / v2 / v3 三种投影格式差别在哪？前端到底怎么消费这些通道？

---

## 1. 先把心智模型摆正：流式不是"一种输出"

大多数人第一次用 `graph.stream()` 只关心一件事：**token 什么时候到用户眼前**。
于是写出 `for chunk in graph.stream(x, stream_mode="messages")`——能用，但对生产来说是错的。

LangGraph 的流式是**一个运行过程的多路投影**。同一张图、同一次运行，可以同时被投影成
"状态长什么样"、"这次哪个节点动了"、"模型吐了什么字"、"业务自定义的进度"……

```
                      ┌── values    每步的完整状态快照
   一次 Pregel 运行 ───┼── updates   这一步谁动了、动了哪个键
   （原始事件流）      ├── messages  LLM 的 token 与元数据
                      ├── custom    业务自己塞进去的数据
                      ├── tasks     任务开始/结束（需 checkpointer）
                      └── debug     把上面几路合起来再加上细节
```

**关键直觉**：`stream_mode` 选的不是"输出格式"，而是"**订阅哪一路信号**"。
多路可以同时订阅（`stream_mode=["updates", "custom"]`）。

官方文档把这一层叫 [Streaming](https://docs.langchain.com/oss/python/langgraph/streaming)，
并明确写了：**新应用推荐 event streaming**（下面第 5 节）。

---

## 2. 五种模式到底给什么

以官方文档的"讲个笑话"三节点图（`refine_topic → generate_joke`）为例：

| 模式 | 每块长什么样 | 典型用途 | 别用它做什么 |
| --- | --- | --- | --- |
| `values` | 完整状态快照（每步一个 dict） | 渲染整个面板、存快照、做断言 | 大状态高频刷新会带宽爆炸 |
| `updates` | `{节点名: 该节点的更新}` | 显示"哪一步做了什么" | 想拿最终完整状态时用它会漏字段 |
| `messages` | `(消息块, 元数据)` 二元组 | 打字机效果、流式渲染 | 过滤要靠元数据里的 `langgraph_node` |
| `custom` | 你自己 push 的任意对象 | 进度条、引用来源、成本统计 | 别拿它传状态——它不落盘 |
| `debug` | 任务事件 + 输入输出 + 错误 | 本地调试、排查卡在哪一步 | 生产不要开，噪音大 |

还有两路文档里也列了、但很多教程不提的：

- `checkpoints`：检查点事件，格式同 `get_state()`，**需要 checkpointer**；
- `tasks`：任务开始/结束事件（含结果与错误），**也需要 checkpointer**；
  `debug` 就是这两路的合体再加额外元数据。

`custom` 的官方用法是 `get_stream_writer()`：

```python
from langgraph.config import get_stream_writer

def node(state):
    writer = get_stream_writer()
    writer({"stage": "retrieving", "progress": 40})
    return {"answer": "..."}
```

配合 `stream_mode="custom"` 消费；也可以和别的模式混着订阅：
`stream_mode=["updates", "custom"]`。

> **一个容易忽略的细节**：`messages` 模式的元数据里有 `langgraph_node`、`langgraph_step`、
> `tags`。要**只**要某个节点的 token，靠 `metadata["langgraph_node"]` 过滤，
> 或者给模型打 `tags` 再按 `metadata["tags"]` 过滤。反过来，
> 不想让某次模型调用的输出进流，给那次调用加 `nostream` tag 即可（调用照跑，只是不进流）。

## 3. 三个反直觉的坑

### 坑 1：`updates` 里"没改状态的节点"是 `None`，而 `values` 里**根本没有**它的快照

一个返回 `{}` 的节点：

- 在 `updates` 里表现为 `{"publish": None}`——**节点确实跑了**，只是没写回任何键；
- 在 `values` 里**不产生新快照**——状态没变，就没有新的状态。

于是"values 的块数"和"跑过的节点数"**对不上**。本仓库的实验里，图有 4 个节点，
`values` 只给 4 块快照（初始 + 3 次真实变更），`updates` 给 4 块（最后一个是 `None`）。

写前端时别假设"每来一个 values 块就对应一个节点"。

### 坑 2：v2 格式下，`stream_mode` 多路 / `subgraphs=True` 会改变块的**形状**

v1（默认）格式随参数变形：

| 场景 | v1 形状 |
| --- | --- |
| 单模式 | 裸数据（`{"node": {...}}`） |
| 多模式 | `(mode, data)` 元组 |
| 开 `subgraphs=True` | `(namespace, data)` 元组 |
| 多模式 + 子图 | `(namespace, mode, data)` 三元组 |

写消费端代码时，"我用的是单模式"这个假设会在你加第二个模式的那天崩掉。

### 坑 3：`subgraphs=True` 不开，子图事件**整个消失**

父图里挂了一个 Agent（`create_agent` 返回的就是编译后的图），在父图上开
`stream_mode="messages"`，**默认拿不到内层 Agent 的 token**——因为内层是子图。
官方文档专门提醒这点：`create_agent` 的返回值是编译图，加进父图就变子图；
直接 `agent.stream(...)` 才有 token，包起来反而没有，除非开 `subgraphs=True`。

开了之后，子图事件带命名空间前缀：

```
ns = ()                          → 根图事件
ns = ("agent:8f1c...",)          → 子图事件（节点名:运行 id）
```

**这就是坑 3 的另一半**：子图的事件和根图的事件**混在同一个流里**，
不按 `ns` 过滤，你会把内层的中间态当成根图的最终态渲染出去。

## 4. v1 → v2：统一形状的 `StreamPart`

LangGraph 1.1 起支持 `version="v2"`，把上面那张"形状随参数变形"的表收成一种：

```python
for part in graph.stream(inputs, stream_mode=["values", "updates"], version="v2"):
    if part["type"] == "values":
        print(part["data"])        # 完整快照
    elif part["type"] == "updates":
        print(part["ns"], part["data"])
```

每一块都是同一个信封：

```python
{
    "type": "values" | "updates" | "messages" | "custom" | ...,
    "ns": (),        # 命名空间；根图是空元组，子图是 ("节点名:运行 id",)
    "data": ...,     # 载荷，形状随 type 变
}
```

类型定义在 `langgraph.types`（`ValuesStreamPart` / `UpdatesStreamPart` / …），
联合类型 `StreamPart` 按 `part["type"]` 做可辨识联合，编辑器能自动收窄类型。

**v2 还顺手修了另一件事**：`invoke(..., version="v2")` 返回 `GraphOutput`，
状态在 `.value`、中断在 `.interrupts`，不再把中断塞进状态字典的 `__interrupt__` 键里。

> **迁移建议**：新代码直接上 `version="v2"`；v1 的 `__interrupt__` 键访问方式已标记废弃，
> 未来版本会移除。

## 5. v3：event streaming，投影层

官方在 1.2 引入了 **event streaming**（`stream_events(..., version="v3")`，目前仍是 beta）。
它比 v2 多的不是"更多数据"，而是**一层结构**：

```
Pregel 引擎 ──原始事件──► 事件路由 ──transformer 管道──► 类型化投影
                          (event router)   (StreamTransformer)   stream.messages
                                                                   stream.values
                                                                   stream.subgraphs
                                                                   stream.output
```

拿到的 `stream` 对象暴露这些投影，**可以同时消费，互不抢事件**：

| 投影 | 用途 |
| --- | --- |
| `stream` | 遍历所有协议事件（原始信封） |
| `stream.messages` | 模型消息与 token 增量 |
| `stream.values` | 状态快照，并能 await 最终值 |
| `stream.output` | 最终输出 |
| `stream.subgraphs` | 发现并观察嵌套图运行，不用自己解析命名空间 |
| `stream.interrupts` / `stream.interrupted` | 人在环路的中断载荷 |
| `stream.extensions` | 自定义 transformer 的投影 |

同步代码要严格按到达顺序混着消费，用 `stream.interleave("values", "messages")`；
异步代码用 `astream_events` + `asyncio.gather`。

原始协议事件是这样一个信封：

```python
{
    "seq": 12,                       # 同一次运行内严格递增，排序用它
    "method": "messages",            # 通道名
    "params": {
        "namespace": ["researcher:6f4d"],   # 根图是 []，每层加一段 "名字:运行 id"
        "timestamp": 1730000000000,
        "data": ...,
    },
}
```

### 坑 4：v3 的投影是**拉驱动**的，没订阅就没有数据

v3 没有后台线程——**你消费哪个投影，哪个投影就把图往前推**。
更要命的是，投影只在这个通道**已有订阅者**时才会缓冲数据：

> "先 `list(stream)` 把事件流读完，再回头 `list(stream.values)`" → 拿到 **0** 个快照。
> 因为跑图的时候没人订阅 values 通道，事件到的那一刻就被丢掉了。

本仓库的实验把这条钉成了断言：`values` 投影要么边跑边订阅拿 4 个快照，
要么先跑完再读拿 0 个快照——**不是 bug，是设计**。要"边跑边看"，就用投影；
要"跑完再复盘"，就用原始事件流。

### 坑 5：v3 的投影是**单消费者**的

同一个投影订阅第二次会抛：

```
RuntimeError: StreamChannel 'values' already has a subscriber; use .tee(n) for fan-out.
```

注意这里的 `tee` 是**投影对象上的方法**（`stream.values.tee(2)`），
不是 run 对象上的。它会给你 n 个独立游标，每个分支都拿到同一份数据。

所以："一边渲染 messages、一边记 values"这种需求，要么读原始事件自己分流，
要么对需要的投影 `tee`。

## 6. 自定义通道：把业务数据送出去，而不是塞进状态

`custom` 模式解决的是一类具体问题：**数据对业务有意义，但不该进状态**。
典型是进度、引用来源、实时指标、合规计数。

v1/v2 用 `get_stream_writer()` 就够了。v3 提供了更正规的方式：**stream transformer**。

服务端开一个**具名**通道：

```python
from langgraph.stream import ProtocolEvent, StreamChannel, StreamTransformer

class RedactionStatsTransformer(StreamTransformer):
    required_stream_modes = ("custom",)      # 声明要哪路，运行时才会开

    def __init__(self, scope: tuple[str, ...] = ()) -> None:
        super().__init__(scope)
        self.stats = StreamChannel("redaction-stats")

    def init(self) -> dict:
        return {"redactionStats": self.stats}

    def process(self, event: ProtocolEvent) -> bool:
        ...
        self.stats.push({"total": 3})
        return True
```

三条规则：

1. `required_stream_modes` 决定底层开哪几路——**没人声明的通道根本不会发出**；
2. `StreamChannel("名字")` 具名 = 值会同时进入主事件流（线上是 `custom:<name>`）；
   不具名 = 只在本地可见，适合放 promise、异步迭代器这类**不能序列化**的句柄；
3. transformer 是**观察者**，不回调运行时；它消费事件、往通道里 push。

## 7. 前端怎么消费

服务端把自定义通道推出去之后，前端用两个选择器读
（`@langchain/react` / `vue` / `svelte` / `angular` 都有）：

| | `useExtension` | `useChannel` |
| --- | --- | --- |
| 返回 | 最新一个载荷（`T \| undefined`） | 原始事件的**有界缓冲**（`Event[]`） |
| 订阅写法 | 通道名：`"redaction-stats"` | 完整通道 id：`["custom:redaction-stats"]` |
| 适合 | 只关心当前值的计数器、进度条 | 要历史、要审计日志、要多个通道 |

前端 SDK 侧对应的类型化通道还有 `useMessages`、`useToolCalls`、`useValues`——
能用这些就别退回到自己解协议事件。

**一条实操建议**：
`messages` 走 `useMessages`（打字机）、`values` 走 `useValues`（状态面板）、
业务侧信号走 `useExtension`——三者各司其职，别拿一种通道硬扛所有需求。

> 具名通道的载荷**必须可序列化**（它要变成协议事件上线）。
> 放不下序列化的东西（future、异步生成器、类实例）就用不具名通道。

## 8. 什么时候不该用流式

- **一次性拿结果**：`invoke` 就够，别为了"显得现代"上流式；
- **状态很大、步骤很多**：`values` 每步一份完整快照，内存与带宽都是平方级压力，
  改用 `updates`；
- **纯批处理**（离线跑一万条）：流式只会拖慢速度，用 `invoke` 批量循环；
- **需要审计与复盘**：用原始事件流（v3 的 `for event in stream`），
  它是唯一不丢东西的视图——投影是"有人订阅才缓冲"的。

## 配套实验

`Demos/examples/langgraph_lab/lessons/ch09_streaming.py`

它把上面每条结论都变成了断言：

- 同一张图用 `values` / `updates` / `messages` / `custom` 四种模式跑，
  打印并断言四者的**结构确实不同**；
- 空更新节点在 `updates` 里是 `None`、在 `values` 里不产生新快照；
- custom 数据能传出业务字段，但**不写进状态**；
- 子图事件不开 `subgraphs=True` 就完全看不见，开了带 `ns` 前缀；
- v3 的原始协议事件是 `method/params` 信封，`values` 投影是 4 个快照；
- v3 的两个坑：先跑完再读投影拿到 0 个快照；重复订阅投影抛 `RuntimeError`，
  只能用 `tee` 扇出。

跑法：

```bash
cd Demos/examples
python -m langgraph_lab ch09
```

## 一句话结论

> **流式是给同一次运行开的五路信号，不是五种输出格式**：`values` 看状态全貌、`updates` 看谁动了、
> `messages` 看模型吐字、`custom` 看业务信号、`debug` 看执行细节；
> 真正的坑不在模式本身，而在**订阅关系**——子图事件要显式透出，v3 投影是拉驱动且单消费者的，
> 想多看一眼，就得先想清楚自己订阅的是哪一路。
