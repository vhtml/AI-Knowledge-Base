# 05 · 节点韧性：重试、超时与错误处理

> **这篇要回答**：节点失败之后到底会发生什么？哪些失败该重试、哪些该降级？重试会不会把检查点写花？产出一份能直接抄走的节点可靠性配置。

---

## 1. 失败处理是三段式，而且顺序是固定的

LangGraph 1.2 给节点配了三种彼此独立的机制。它们**不是**三选一，是一条流水线：

```
   ┌────────────────────────────────────────────────────────────┐
   │ 一次尝试（attempt）                                        │
   │   节点函数体执行                                            │
   └───────────────┬────────────────────────────────────────────┘
                   │ 抛异常（含超时抛的 NodeTimeoutError）
                   ▼
        ┌──────────────────────┐   命中 retry_on 且还有次数
        │  retry_policy 生效？ │───是──▶ 等 initial_interval × backoff ──┐
        └──────────┬───────────┘                                      │
                   │ 否 / 次数用完                                     │
                   ▼                                                  │
        ┌──────────────────────┐   配了 error_handler                  │
        │  error_handler 生效？│───是──▶ 处理器把异常翻译成状态/路由 ◀───┘
        └──────────┬───────────┘
                   │ 否
                   ▼
              异常冒泡，整个 run 失败
```

**顺序是写死的**：先重试，重试耗尽才轮到错误处理器。所以"重试几次"和"失败了怎么办"是两个独立旋钮，不要混着调。

三个机制的入口都在 `add_node` 上：

| 机制 | 参数 | 触发时机 | 最低版本 |
| --- | --- | --- | --- |
| 重试 | `retry_policy=RetryPolicy(...)` | 每次尝试抛异常后 | 1.0 |
| 超时 | `timeout=TimeoutPolicy(...)` | 单次尝试跑太久 | **1.2** |
| 错误处理 | `error_handler=fn` | 重试耗尽之后 | **1.2** |

> 节点级 timeout 与 error handler 需要 `langgraph>=1.2`，老版本上 `add_node` 不认这两个参数。

## 2. RetryPolicy：重试什么、重试几次

```python
from langgraph.types import RetryPolicy

builder.add_node("call_api", call_api, retry_policy=RetryPolicy(max_attempts=3))
```

| 参数 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `max_attempts` | `int` | `3` | 总尝试次数（**含**第一次） |
| `initial_interval` | `float` | `0.5` | 第一次重试前等多久（秒） |
| `backoff_factor` | `float` | `2.0` | 每次重试后间隔乘几 |
| `max_interval` | `float` | `128.0` | 两次重试之间的上限 |
| `jitter` | `bool` | `True` | 是否加随机抖动 |
| `retry_on` | 类型 / 序列 / 可调用 | `default_retry_on` | 哪些异常算"可重试" |

### 坑 1：默认的 `retry_on` 比你以为的窄

文档写明：默认**除了**下面这些（及其子类）**都**重试：

```
ValueError  TypeError  ArithmeticError  ImportError  LookupError
NameError  SyntaxError  RuntimeError  ReferenceError
StopIteration  StopAsyncIteration  OSError
```

也就是说 `RuntimeError`（很多人在节点里随手抛的"下游挂了"）**默认不重试**——它被当成确定性错误。加上 `OSError` 家族，默认也不重试。

但这里有一处**文档没写、实现里特判**的地方（实测 langgraph 1.2.20 的 `default_retry_on` 源码）：

| 异常 | 默认会重试？ | 原因 |
| --- | --- | --- |
| `ConnectionError` | ✅ 会 | 源码里在排除清单**之前**特判为可重试 |
| `TimeoutError` | ❌ 不会 | 属于 `OSError` 家族，被排除 |
| `httpx` / `requests` 的 4xx | ❌ 不会 | 只重试 5xx |
| `httpx` / `requests` 的 5xx | ✅ 会 | — |

**所以"网络抖动会自动重试"和"HTTP 超时不会自动重试"可以同时成立**。想稳妥，显式写 `retry_on=`：

```python
from langgraph.types import RetryPolicy, default_retry_on

def custom_retry_on(exc: BaseException) -> bool:
    if isinstance(exc, MyBusinessError):
        return False          # 业务错误重试没有意义
    return default_retry_on(exc)
```

`retry_on` 还能直接给异常类型或类型元组：`retry_on=ConnectionError`。

### 坑 2：重试是 at-least-once，不是 exactly-once

重试会把**整个节点函数从头再跑一遍**。节点里的外部副作用（下单、扣款、发邮件）因此可能执行多次：

```
attempt 1: 节点开始 → 调支付 API → 支付成功 → 进程崩了
attempt 2: 节点开始 → 调支付 API → 又成功一次
```

LangGraph 管不了你的外部系统，能救你的只有**幂等键**：从**已经持久化**的状态推导出来的稳定 key。

```python
def charge_customer(state: State) -> dict:
    # 同一个订单在任何一次重试里都算出同一个 key
    idempotency_key = f"charge:{state['order_id']}"
    provider.charge(..., idempotency_key=idempotency_key)
    return {"charged": True}
```

坑在于：key 必须**在副作用之前就已经落盘**。如果在同一个节点里现生成 key，节点没返回 → key 没进检查点 → 下一次重试生成的是另一个 key，等于没做幂等。正确做法是单独一个节点先生成并落盘 key，再在下一个节点做副作用。

## 3. 节点级 timeout：只管 async 节点

```python
from langgraph.types import TimeoutPolicy

builder.add_node("call_model", call_model, timeout=TimeoutPolicy(run_timeout=120, idle_timeout=30))
```

| 参数 | 含义 |
| --- | --- |
| `run_timeout` | 硬墙钟上限，**永不刷新** |
| `idle_timeout` | "没进展"的上限，**有进展就重置** |
| `refresh_on` | `"auto"`（默认）或 `"heartbeat"`（只认显式心跳） |

`idle_timeout` 在 `refresh_on="auto"` 下，下列任何一件事都会重置计时器：写状态、流式输出、调度子任务、调 `runtime.stream_writer`、以及**任何 LangChain 回调事件**（模型吐 token、工具调用等）。想要严格定义，用 `refresh_on="heartbeat"`，然后在长循环里手动 `runtime.heartbeat()`。

### 坑 3：同步节点配 timeout，编译期就炸

```
ValueError: Node timeouts are only supported for async nodes because
sync Python execution cannot be safely cancelled in-process. Node 'sync_node' is sync.
```

这是**编译期**错误，不是运行期——同步 Python 没法安全取消，所以 LangGraph 直接拒绝。阻塞 I/O 要包超时，就得把节点写成 `async def`，里面用 `asyncio.to_thread` 包住同步调用：

```python
async def fetch(state: State) -> dict:
    data = await asyncio.to_thread(blocking_fetch, state["url"])
    return {"data": data}
```

### 坑 4：`NodeTimeoutError` 不是 `TimeoutError`

超时触发时抛 `langgraph.errors.NodeTimeoutError`，它带结构化上下文：

| 属性 | 含义 |
| --- | --- |
| `node` | 哪个节点超时了 |
| `elapsed` | 超时前跑了多少秒 |
| `kind` | `"run"` 还是 `"idle"` |
| `run_timeout` / `idle_timeout` | 当时配的限值 |

关键点：**它不继承内置 `TimeoutError`**（那是 `OSError` 的子类，在默认不重试清单里）。所以 `NodeTimeoutError` 默认是**可重试**的，配上 `retry_policy` 就能"超时了再试一次"，而且每次尝试的计时器都会重置、超时那次尝试的写入会被清掉。

## 4. error_handler：把异常翻译成状态

处理器在**重试耗尽之后**才触发（没配重试策略时就是失败立刻触发）。签名可以很自由：

```python
from langgraph.errors import NodeError
from langgraph.types import Command

def payment_error_handler(state: State, error: NodeError) -> Command:
    return Command(update={"status": f"compensated: {error.error}"}, goto="finalize")
```

`error: NodeError` 是**按类型注解注入**的（和 `runtime: Runtime` 一个套路），不要也可以，签名写成 `(state)` 或 `(state, runtime)` 都行；需要 `thread_id` 就再加第三个 `config: RunnableConfig`。

`NodeError` 是 frozen dataclass，两个字段：`node`（哪个节点挂了）、`error`（原始异常对象）。

### 坑 5：处理器返回普通 dict，图就**停在那儿**

这是本章最容易踩的一条。处理器有两种返回形态，行为完全不同：

| 处理器返回 | 状态写回 | 失败节点的静态边还走吗 |
| --- | --- | --- |
| 普通 `dict` | ✅ | ❌ **不走**——该 super-step 直接结束 |
| `Command(update=..., goto=...)` | ✅ | 按 `goto` 走 |

实测：失败节点 `boom` 有一条静态边指向 `after`，处理器返回 `{"status": "degraded"}` 后，`after` **没有执行**，整个 run 就结束了。所以：

> **想继续往下走，必须返回 `Command`。** 返回 dict 只能"就地降级并结束"。

另外两条边界：

- 处理器自己抛异常 → 直接冒泡，等同于这个节点没有处理器。
- 节点里 `interrupt()` 抛出的 `GraphBubbleUp` **不会**进处理器——它要暂停给人，不该被当成失败。

## 5. set_node_defaults：图级默认

```python
graph = (
    StateGraph(State)
    .set_node_defaults(
        retry_policy=RetryPolicy(max_attempts=3),
        error_handler=default_handler,
        timeout=TimeoutPolicy(run_timeout=30),
    )
    .add_node("step_a", step_a)
    .add_node("step_b", step_b, retry_policy=RetryPolicy(max_attempts=5))  # 覆盖默认
    .compile()
)
```

- **节点级永远赢**，默认只在节点没配时才生效；
- 默认在 `compile()` 时才解析，`set_node_defaults` 放在 `add_node` 前后都行；
- **子图不继承**父图的默认，每张图各自管各自的。

适用性有个反直觉的矩阵：

| `set_node_defaults` 参数 | 普通节点 | 错误处理器节点 | 为什么 |
| --- | --- | --- | --- |
| `retry_policy` | ✅ | ✅ | 处理器自己也可能遇到瞬时故障 |
| `timeout` | ✅ | ✅ | 卡住的处理器也得能被打断 |
| `error_handler` | ✅ | ❌ | 处理器不能自己抓自己 |
| `cache_policy` | ✅ | ❌ | 缓存处理结果不安全 |

## 6. 重试还是降级：判断依据

官方给的恢复策略分工（[Fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance.md)）：

| 失败类型 | 谁来修 | 用什么机制 |
| --- | --- | --- |
| 瞬时错误（网络抖动、5xx） | 系统 | 节点上的 `retry_policy` |
| 重试后仍失败、可补偿 | 开发者 | `error_handler`（Saga / 补偿） |
| 模型自己能纠正（工具参数写错） | 模型 | 把错误写进 state，`Command` 路由回模型 |
| 需要人来定 | 人 | `interrupt()` |
| 没预料到的错误 | 开发者 | 让它冒泡，别吞 |

落到你自己的业务上，决策就两条轴：**幂等性** + **有没有外部副作用**。

| 失败 | 幂等？ | 有外部副作用？ | 决策 |
| --- | --- | --- | --- |
| 下游 503 / 限流 | ✅ 纯读 | 否 | **重试** |
| 写库失败（幂等 upsert） | ✅ | 是（但幂等） | **重试** |
| 写库失败（非幂等 insert） | ❌ | 是 | **降级**，别重试 |
| 支付扣款 | ❌ | 是 | **降级**到补偿流程 |
| 参数校验失败 | — | 否 | **降级**，重试一万次还是同样的错 |
| 业务规则拒绝（余额不足） | — | 否 | **降级**，重试是浪费 |

一句话：**重试只能用在"再跑一遍不会造成额外后果"的地方。** 有副作用又不能幂等的失败，正确姿势是把它移出可重试节点——放到 `error_handler` 里，或者交给按 task id 去重的独立 worker。

配套实验里这张表是可执行的：`decide_strategy(exc, side_effect_free)`。

## 7. 重试与检查点：重试不落盘

**检查点写在 super-step 边界上，不是函数中间。** 所以：

- 重试发生在**一个 super-step 内部**，失败尝试写进状态的东西会被丢弃；
- 失败尝试**不会**额外产生检查点；
- 外部副作用在检查点边界**之外**，LangGraph 管不着。

实测：同一张图，一次成功和重试两次之后产生的**检查点数量完全一样**（都是 3 个）。这正是你想要的——检查点记录的是"业务进展"，不是"尝试次数"。

副作用在边界之外这件事还有一个推论：**"本地没有记录"不等于"副作用没发生"**。如果供应商提交成功但回执丢了，图里看着像没成，重试又是一次真扣款。正确做法是拿幂等 key 去查供应商的状态，而不是盲目重试或盲目补偿。

## 8. 编译后的图能读回配置（工程自检用）

这些配置在编译后的图上是可读的，第 17 章的自检就靠它们：

```python
graph = builder.compile()
node = graph.nodes["resilient"]          # graph.nodes 是 dict
node.retry_policy                         # → 策略**元组**，不是单个 RetryPolicy
node.retry_policy[0].max_attempts         # → 5
node.timeout                              # → TimeoutPolicy 实例（不是元组）
node.timeout.run_timeout                  # → 30.0
graph.nodes["plain"].retry_policy         # → None（没配就是 None）
```

两个容易踩的点：

1. **`retry_policy` 是元组。** `add_node` 接受"一个或多个"策略，落盘时统一成元组，哪怕你只传了一个。取值得写 `node.retry_policy[0].max_attempts`，直接 `node.retry_policy.max_attempts` 会报 `AttributeError: 'tuple' object has no attribute 'max_attempts'`。
2. **`graph.get_graph().nodes` 也是 dict**（键是 `__start__` / 节点名 / `__end__`），不是"节点对象列表"，别按列表遍历。

## 9. 一份能抄走的可靠性配置

```python
from langgraph.types import RetryPolicy, TimeoutPolicy
from langgraph.errors import NodeError
from langgraph.types import Command

def is_transient(exc: BaseException) -> bool:
    return isinstance(exc, (ConnectionError, TimeoutError))

def handler(state: State, error: NodeError) -> Command:
    return Command(update={"status": "degraded"}, goto="finalize")

builder.add_node(
    "call_api",
    call_api,
    retry_policy=RetryPolicy(
        max_attempts=3, initial_interval=0.5, backoff_factor=2.0, jitter=True,
        retry_on=is_transient,
    ),
    error_handler=handler,
)
builder.add_node(
    "call_model",          # 异步节点才配 timeout
    call_model_async,
    timeout=TimeoutPolicy(run_timeout=120, idle_timeout=30),
)
```

**什么时候不该用这些机制**：流程只有一步、失败就重跑整条链更划算——先加一个干净的 `error_handler` 兜底，别一上来就铺三层。

## 一句话结论

> **重试是给"再跑一遍没坏处"的失败准备的，超时是给"卡死了"的节点准备的，处理器是给"重试也救不回来"的失败准备的**——
> 而决定用哪一个的两个依据只有：这次失败幂不幂等、会不会已经产生了外部副作用。
