# 08 · 人在环路：中断、审批与恢复

> **这篇要回答**：怎么让图停下来等人？人答完话怎么接着跑？审批节点该放在工具执行前还是状态变更后？LangChain 的 `HumanInTheLoopMiddleware` 和我手写的 `interrupt()` 是什么关系？

---

## 1. 中断是什么：一次被捕获的异常

`interrupt()` 不是"暂停语句"，它是**抛异常**。异常沿调用栈往上冒，
被运行时接住，运行时把当前状态写进检查点，然后把控制权交还给你的应用。

```
节点代码                  运行时                    你的应用
   │  decision = interrupt(q)
   ├─────────────────────►│ 抛 GraphInterrupt
   │                       │ 1. 保存检查点 / 记下 pending task
   │                       │ 2. 停止调度下一个节点
   │                       ├───────────────────────►│ 返回 {..., "__interrupt__":[...]}
   │                       │◄───────────────────────┤ 人做决定 → Command(resume=...)
   │                       │ 3. 从头重跑该节点
   │                       │ 4. interrupt() 返回 resume 值
   ▼                       ▼                       ▼
```

**"从头重跑"这四个字是本章所有坑的源头。** 官方文档写得很明确：
恢复时运行时**重启整个节点**，不是从 `interrupt()` 那一行继续。
所以 `interrupt()` **之前**的代码会再执行一遍。

配套实验 `ch08_hitl.py` 用一个 trace 列表把这件事钉死了：

```
暂停后 trace=['before-interrupt']
恢复后 trace=['before-interrupt', 'before-interrupt', 'after-interrupt']
```

`before-interrupt` 出现了两次，`after-interrupt` 在暂停时**根本没出现过**——
这同时证明了"返回值在恢复前不可用"和"节点从头重跑"。

官方文档：[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts.md)

## 2. 暂停那一刻到底发生了什么

按官方文档的顺序，调用 `interrupt()` 后：

| # | 发生什么 | 你能观测到吗 |
| --- | --- | --- |
| 1 | 图在**调用点**挂起（节点级暂停，最终落在 super-step 边界） | `snapshot.next` 仍指向该节点 |
| 2 | 状态用 checkpointer 存下来 | `graph.get_state(config)` 能读到 |
| 3 | 值交给调用方 | `result["__interrupt__"]`（`invoke`）或 `stream.interrupts`（`stream_events` v3） |
| 4 | 图**无限期等待**，直到有人恢复 | 不会超时、不会自动继续 |
| 5 | 恢复时把响应塞回 `interrupt()` 的返回值 | 节点从头重跑后才拿到值 |

三个必须分清的层次：

- **`interrupt()` 是动态的**，可以放在代码任意位置、按业务条件触发；
  `interrupt_before` / `interrupt_after` 是**静态断点**，官方明确说
  **不推荐用于 HITL**，只适合调试。
- **中断不限于工具调用**。它可以放在任意节点里，用来"改一段文本"、
  "补一个缺失字段"、"让人确认一次状态变更"。
- **`__interrupt__` 是 `invoke` API 的出口**。用 `stream_events(..., version="v3")`
  的话，改看 `stream.interrupted`（布尔）和 `stream.interrupts`（载荷元组），
  最终状态在 `stream.output`。

## 3. 恢复：只有 `Command(resume=...)` 这一种姿势

```python
from langgraph.types import Command

config = {"configurable": {"thread_id": "approval-123"}}

# 第一次：跑到中断停下
result = graph.invoke({"request": "转账 500"}, config)
pending = result["__interrupt__"][0]

# 第二次：同一个 thread_id，把决定送回去
final = graph.invoke(Command(resume={"type": "approve"}), config)
```

三条硬规则：

1. **必须用同一个 `thread_id`。** 换个线程就等于开了一条新线，恢复不到任何东西。
2. **`Command(resume=...)` 是唯一被设计成 `invoke`/`stream` 输入的 `Command` 形态。**
   `Command` 的其他参数（`update` / `goto` / `graph`）是给**节点函数返回**用的。
   官方专门警告：**不要拿 `Command(update=...)` 当输入去续多轮对话**，
   续多轮请直接传普通输入字典。
3. **恢复时的值会成为 `interrupt()` 的返回值。** 传 dict、传 bool、传字符串都行，
   载荷要 JSON 可序列化。

### 想让恢复值"带类型"：`response_schema`

```python
from pydantic import BaseModel

class Decision(BaseModel):
    approved: bool
    note: str | None = None

def node(state):
    answer = interrupt({"question": "approve?"}, response_schema=Decision)
    return {"answer": answer}          # answer 是 Decision 实例，不是 dict
```

- 需要 `langgraph>=1.2.12`。
- 可以传 Pydantic 模型、`typing_extensions` 的 `TypedDict` 或 dataclass。
- LangGraph 会把它转成 JSON Schema 放进 `Interrupt.response_schema`，
  **和 `value` 载荷分开**——客户端可以照着 schema 渲染表单。
- 有 schema 时恢复值会被校验：非法就抛 `ValidationError`，**且什么都不保存**，
  修正后可以用同一个 thread_id 再答一次。
- 传 JSON Schema **字典**的话，LangGraph 原样暴露但**不校验**恢复值。

## 4. 三种（其实四种）决策

LangChain 的 HITL 规范定义了四种决策类型。LangGraph 的 `interrupt()` 本身不限制，
但这是事实上的行业通用约定：

| 决策 | 含义 | 工具会执行吗 | 典型场景 |
| --- | --- | --- | --- |
| ✅ `approve` | 按模型提的原始参数执行 | ✅ 原样执行 | 邮件草稿照发 |
| ✏️ `edit` | 改了参数再执行 | ✅ 用改后的参数 | 换个收件人再发 |
| ❌ `reject` | 拒绝执行，把反馈退回给模型 | ❌ 跳过 | 拒绝删库并说明原因 |
| 💬 `respond` | 人直接替工具回答 | ❌ 跳过，当作**成功**结果返回 | "ask_user" 型工具 |

> **坑：`reject` 和 `respond` 不是一回事。**
> `reject` 会把"被拒绝"这件事作为**错误状态**反馈给模型；
> `respond` 的消息被当作**成功的工具结果**。
> 官方明确说：**不要用 `respond` 去拒绝有副作用的工具**——
> 那会让模型以为操作成功了。

在裸 LangGraph 里，这四种就是你自己约定的载荷：

```python
def approval(state):
    answer = interrupt({
        "question": "是否批准？",
        "request": state["request"],
        "options": ["approve", "edit", "reject"],
    })
    if answer["type"] == "edit":
        return {"request": answer["request"]}      # 改后的内容写回状态
    if answer["type"] == "reject":
        return {"decision": "reject"}
    return {"decision": "approve"}
```

分叉可以用条件边，也可以让节点直接返回 `Command(goto="proceed")`。
条件边更直白；`Command(goto=...)` 更适合"审批节点本身决定往哪走"的写法。

## 5. 批量模式 vs per-call 模式

这是 LangChain `HumanInTheLoopMiddleware` 的两档策略，**默认是批量（batched）**。

| | **Per-call** | **Batched（默认）** |
| --- | --- | --- |
| 什么时候暂停 | 每个待审调用**开始执行时** | 模型响应之后、**任何工具执行之前** |
| 每轮几个中断 | 每个待审调用一个 | 整个模型轮次一个 |
| 没被 gate 的调用 | 立刻执行 | **一起等** |
| 怎么回答 | 每个中断一个决策，**按中断 ID 匹配** | 一个决策列表，**按位置匹配** |
| 带 `response_schema` | ✅ | ❌ |
| 校验时机 | **先校验再保存** | 保存后才在应用时校验 |
| 要求 | `langchain>=1.4.6` | 无 |

批量模式的中断载荷长这样：

```python
{
    "action_requests": [
        {"name": "write_file", "args": {...}, "description": "..."},
        {"name": "execute_sql", "args": {...}, "description": "..."},
    ],
    "review_configs": [
        {"action_name": "write_file", "allowed_decisions": ["approve", "edit", "reject", "respond"]},
        {"action_name": "execute_sql", "allowed_decisions": ["approve", "reject"]},
    ],
}
```

回答是一个**按顺序对应**的决策列表：

```python
Command(resume={"decisions": [
    {"type": "approve"},
    {"type": "reject", "message": "先归档再删。"},
]})
```

**批量模式的四个真实问题**（官方文档自己列的）：

| 批量模式的问题 | 后果 | per-call 怎么解决 |
| --- | --- | --- |
| 决策**按位置**匹配调用 | 本想批 `write_file`、拒 `execute_sql`，发成 `[reject, approve]`，**DELETE 跑了** | 每个决策按调用自己的中断 ID 绑定 |
| `allowed_decisions` 藏在 `review_configs` 里 | 客户端得自己把两个列表按位置配对，还得硬编码按钮 | 每个中断的 `response_schema` 直接列出允许的决策 |
| **答案先保存、后校验** | 一个决策对两个调用 → `ValueError: Number of human decisions (1) does not match number of hanging tool calls (2).`；改对了再发还是同样的错，**线程卡死** | 先校验再保存，改好了重发即可 |
| **编辑的参数不校验** | 改 `write_file` 时漏了 `content`，工具照样跑，模型收到一个它没发过的调用的报错 | 编辑被拒：`edit.edited_action.args.content Field required` |

官方结论：**新项目用 per-call**，LangChain 计划在下一个大版本把它变成默认；
如果你的审批 UI 已经按批量格式写了，就先留在批量模式。

> **并行分支同时中断时怎么办？**
> 裸 LangGraph 里，多个并行节点各自 `interrupt()`，恢复时要**按中断 ID 字典**回答：
> `Command(resume={interrupt.id: value})`。
> 没回答的中断会继续挂着，可以一个一个来。

## 6. 与 LangChain `HumanInTheLoopMiddleware` 的关系

一句话：**LangGraph 的 `interrupt()` 是原语，LangChain 的中间件是封装。**

```python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware

agent = create_agent(
    model=model,
    tools=[write_file, execute_sql, read_data],
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                "write_file": True,                                  # 全部四种决策
                "execute_sql": {"allowed_decisions": ["approve", "reject"]},
                "read_data": False,                                  # 安全操作，不拦
            },
            description_prefix="Tool execution pending approval",
        ),
    ],
    checkpointer=InMemorySaver(),     # HITL 必须配检查点器
)
```

| 维度 | 裸 `interrupt()` | `HumanInTheLoopMiddleware` |
| --- | --- | --- |
| 层级 | LangGraph 运行时原语 | LangChain Agent 层的中间件 |
| 拦什么 | 你放在哪就拦哪 | **只拦工具调用** |
| 决策类型 | 自己约定 | 内置 approve/edit/reject/respond |
| 模式 | 无（一次中断对应一次回答） | batched / per_call |
| 谁来执行工具 | 你自己写节点 | 中间件：批了就跑、拒了就合成错误 ToolMessage、respond 就直接把人的话当结果 |
| 要不要 checkpointer | **必须** | **必须**（否则中断无法恢复） |

中间件的生命周期挂在 `after_model` 钩子上（批量模式）：
模型出响应 → 中间件检查工具调用 → 需要审就发 `interrupt()` →
等决策 → 按决策分别执行 / 合成 ToolMessage → 继续。

**中间件顺序有讲究**：per-call 模式下，`HumanInTheLoopMiddleware` 要排在
`ToolRetryMiddleware`、`ToolErrorMiddleware` **之前**，这样它才能包住它们；
否则重试会重新问一次审批。

还可以用 `when` 谓词按参数粒度决定拦不拦（需要 `langchain>=1.3.3`）：

```python
def writes_outside_workspace(request: ToolCallRequest) -> bool:
    path = request.tool_call["args"].get("path", "")
    return not path.startswith("/workspace/")

HumanInTheLoopMiddleware(interrupt_on={
    "write_file": {"allowed_decisions": ["approve", "edit", "reject"], "when": writes_outside_workspace},
})
```

> **坑：`when` 谓词在恢复时会再跑一次**，必须对同一个调用返回同样的结果。
> 恢复时如果它返回 `False`，工具会**无视审批人的决定直接执行**——
> 连 `reject` 都会被忽略。

## 7. 审批节点该放哪

两个常见位置，代价完全不同：

| 方案 | 放哪 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 工具执行前**（`interrupt` 写在工具函数里） | 工具内部 | 审批逻辑跟着工具走，天然可复用；模型调哪个工具就审哪个 | 工具要能被序列化；`interrupt` 的语义散在各个工具里 |
| **B. 状态变更后**（独立的审批节点 + 条件边） | 图上一个独立节点 | 审批是显式的一步，能在图上**看见**；分支一目了然；副作用天然在审批之后 | 每种审批场景都要加节点，图会变长 |
| **C. 混合**：审批节点只改状态，副作用单独成节点 | 图上两个节点 | 副作用**一定**在审批之后，且能被单独重试 | 节点多，图更长 |

**实践建议**：

- **副作用一律放在 `interrupt()` 之后**，并尽量**拆成独立节点**——
  这样"审批没通过"就等于"副作用节点根本没进"。
  第 8 章实验就是这么设计的：暂停时 `execute` 节点压根没跑，日志里没有 `executed:`。
- **不要在 `interrupt()` 之前做非幂等的副作用。** 节点从头重跑意味着中断前的副作用会**重放**：
  审计日志写两遍、记录建两条。官方给的两个解法：用 upsert 这类幂等操作，或把副作用挪到中断之后。
- **别把审批做成"大过滤器"。** 一次审批一次决策，比"审核十个字段再逐个问"体验好得多。

## 8. 五个必须知道的坑

### 坑 1：节点从头重跑，不是从 `interrupt()` 那行继续

本章开头已经用实验证明了。**所有**"中断前代码会重放"的推论都源于此。

### 坑 2：别把 `interrupt()` 包在 try/except 里

中断就是靠抛异常实现的。`try: interrupt(...) except Exception:` 会把它吞掉，
**中断根本不会传回图**。要兜异常就写具体的异常类型。

### 坑 3：别在节点里循环调 `interrupt()`

`while True: answer = interrupt(...)` 看着能反复问，
实际上每次恢复都会**重放之前所有轮次**——第一次恢复重放 1 轮，第二次重放 2 轮。
官方给的正确写法是**一个节点一次 `interrupt()`**，
把重问的问题写进状态，用条件边绕回这个节点。

### 坑 4 / 坑 5：顺序不能变，载荷要能序列化

- **别重排、别条件跳过 `interrupt()`**：一个节点里有多个 `interrupt()` 时，
  恢复值**严格按索引**匹配。顺序每次都必须一致，跳过就会错位，拿到别人的答案。
- **别传不可序列化的东西**：载荷要能存进检查点。函数、类实例、自定义对象可能存不进去，
  或者换个序列化器就崩了。只传 JSON 友好的类型。

## 9. 什么时候不该用中断

| 场景 | 建议 |
| --- | --- |
| 只是想让模型多输出几步 | 别用中断，那是流式和子图的活 |
| 审批只需要"是/否"，且没有人工 | 直接用条件边 |
| 需要人**连续**输入多个字段 | 一次中断收一个结构化对象，比中断 N 次强 |
| 批量工具审批 | 用 LangChain 的 `HumanInTheLoopMiddleware`，别自己手写 per-call 那套 ID 绑定 |
| 只是想在图里留个断点调试 | 用 `interrupt_before` / `interrupt_after`（静态断点），别用 `interrupt()` |

一个判断标准：**如果没有人会真的看到并回答这个中断，那它就不该是中断。**
把 `interrupt()` 当调试断点用的人，最后都会遇到"节点莫名其妙重跑"的灵异事件。

## 一句话结论

> **中断 = 抛 `GraphInterrupt` + 落一个检查点 + 把控制权交给你。**
> 恢复只用 `Command(resume=...)`、只用同一个 `thread_id`；
> 记住节点**从头重跑**，所以副作用必须放在中断之后且要幂等。
> 审批决策是 approve / edit / reject / respond 四选一：
> 裸图自己约定，LangChain 的 `HumanInTheLoopMiddleware` 已经替你封装好了——
> 默认批量模式，新项目建议切到 per-call。
