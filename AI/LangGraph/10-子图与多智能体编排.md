# 10 · 子图与多智能体编排

> **这篇要回答**：一个子图怎么接进父图？共享键和手工映射差在哪、什么时候必须手工映射？`Command` 在这里扮演什么角色？多智能体的四种模式（subagents / handoffs / router / 自定义工作流）分别适合什么？把子图注册成"工具"和注册成"子智能体"到底差在哪？

---

## 1. 子图就是"当节点用的图"

官方定义很朴素：**一个图被当作另一个图的节点用，它就是子图**。

它的价值有三层：

- **复用**：一组节点在多张图里重复用；
- **分工**：不同团队各写各的子图，只要**接口（输入输出 schema）**对齐就能拼起来；
- **多智能体**：子图是搭多智能体系统最省事的骨架。

但"当节点用"这句话里藏着本章的全部难点：**节点之间传的是状态，
而父图和子图的状态 schema 未必一样。**

---

## 2. 两种跨边界方式

官方文档明确列了两种，区别只在**状态怎么对齐**：

| | 方式 A：子图作为节点 | 方式 B：在节点里调用子图 |
| --- | --- | --- |
| 怎么写 | `builder.add_node("expert", compiled_subgraph)` | 节点里 `subgraph.invoke(...)` |
| 前提 | 父子**共享 state 键** | 键名可以完全不同 |
| 谁做映射 | 运行时自动：只传父图声明过的键，只写回父图声明过的键 | **你手写**：进 map 一次，出 map 一次 |
| 私有键 | 子图可以有自己的私有键，不外泄 | 完全隔离 |
| 典型用途 | 多智能体共享 `messages` 通道 | 每个 Agent 有自己的私有消息历史 |

```
方式 A：子图当节点（共享键）

  父图 state {question, answer}
        │  自动：只传父图声明过的键
        ▼
  子图 state {question, answer, scratch}
        │  自动：只把父图声明过的键写回
        ▼
  父图 state {question, answer}      ← scratch 留在子图里，不外泄

方式 B：子图当独立图（键名不同）

  父图 state {question}
        │  你手写：{"expression": state["question"]}
        ▼
  子图 state {expression}
        │  你手写：{"answer": out["result"]}
        ▼
  父图 state {question, answer}
```

**判断标准只有一条：父子 schema 有没有同名的键。**
有 → 方式 A（少写代码，少犯错）；没有 → 方式 B（必须写映射）。

---

## 3. 键名不同时，映射怎么写

映射不是"能跑就行"，它是**两份 schema 之间的契约**。写法：

```python
class ParentState(TypedDict):
    question: str
    answer: str

class MathState(TypedDict):
    expression: str
    result: str

def call_math(state: ParentState) -> dict[str, Any]:
    # 进：父图 → 子图
    outcome = math_graph.invoke({"expression": state["question"]})
    # 出：子图 → 父图
    return {"answer": outcome["result"]}
```

三条实践规则：

1. **进出的键名要写在同一行代码里**。映射散落在几个节点里，改 schema 时必漏。
2. **子图节点用 `state.get(key, default)` 而不是 `state[key]`**。
   这样映射漏了键时，子图不会 KeyError 崩掉——而是给你一个**看起来合理的错答案**。
   （本仓库第 10 章实验把这个坑做成了断言：漏映射时子图返回"空式子"，
   不抛异常，只是结果悄悄变了。）
3. **映射出错不会有人提醒你**。类型检查器看不见字符串键名，
   单元测试不写这个 case 就永远发现不了。

## 4. `Command`：把"改状态"和"选路"合成一件事

子图自己只管产出结果；**要不要改父状态、改完往哪走**，用 `Command` 表达：

```python
from langgraph.types import Command

def call_reviewer(state: RouteState) -> Command:
    outcome = reviewer.invoke({"text": state["text"]})
    return Command(
        update={"verdict": outcome["verdict"], "stage": "reviewed"},
        goto="publish",          # 改完状态，直接跳到 publish
    )
```

配套两件事：

- 节点可以声明它可能跳到哪：`builder.add_node("review", call_reviewer, destinations=("publish",))`。
  运行期 `Command.goto` 自己就能解析目标，不声明也能跑；
  声明的价值是**静态分析**——`get_graph().draw_mermaid()` 里那条
  `review -.-> publish` 的虚线边只有声明了才画得出来；
- 从**子图**里往父图跳，用 `graph=Command.PARENT`：

```python
return Command(goto="sales_agent", update={...}, graph=Command.PARENT)
```

这正是 handoffs 模式里 agent 之间转移控制权的底层机制。

> **`Command` 与条件边的分工**：条件边的路由函数**只选路、不改状态**；
> 需要"改状态 + 选路"时用 `Command`。两者别混写成同一个函数。

## 5. 子图的持久化：三种模式，选错就出事故

`compile(checkpointer=...)` 的取值决定子图**记不记得上一次**：

| 模式 | 写法 | 行为 | 适合 |
| --- | --- | --- | --- |
| 每次调用（默认） | `checkpointer=None` | 每次调用从头开始；单次调用内仍支持中断 | 大多数多智能体场景 |
| 按线程 | `checkpointer=True` | 同一 thread 上跨调用累积状态 | 需要多轮记忆的子 Agent |
| 无状态 | `checkpointer=False` | 完全不落检查点 | 纯函数式子图 |

两条硬约束：

1. **父图必须编译时带 checkpointer**，子图的持久化能力才有意义；
2. **按线程模式不支持并行调用同一个子图**——两次调用写同一个命名空间，会冲突。
   官方建议用 `ToolCallLimitMiddleware` 限制并行，裸 LangGraph 则要自己防。

还有一个容易忽略的点：按调用隔离模式下，子图状态**只在调用期间**可查
（`get_state(config, subgraphs=True).tasks[0].state`），调用结束就没有可查的历史了。

## 6. 多智能体四种模式

官方文档给了一张选型表（⭐越多越擅长）：

| 模式 | 分布式开发 | 并行 | 多跳 | 直接和用户对话 |
| --- | :-: | :-: | :-: | :-: |
| **subagents**（主管 + 子智能体当工具） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐ |
| **handoffs**（状态驱动的交接） | - | - | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **router**（先分类再分发） | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | - | ⭐⭐ |
| **自定义工作流**（LangGraph 自己搭） | 看你怎么切 | 看你怎么切 | 看你怎么切 | 看你怎么切 |

（文档还有第五种 **skills**：单智能体按需加载专家提示词，本文不展开。）

```
subagents：路由全在主管身上          handoffs：状态变了行为就变
  User → 主管 ──┬→ 子A(工具)          User → Agent(当前步骤)
                └→ 子B(工具)                   │ 工具写 current_step
                     ↓ 结果回到主管             ↓ 换配置/换 Agent
                  主管再回答用户              同一段对话继续

router：先分类，再并行，最后汇总
  Query → 分类器 ─┬→ AgentA ┐
                   └→ AgentB ┴→ 汇总 → 答案
```

各自的适用场景，一句话版：

| 模式 | 什么时候用 | 代价 |
| --- | --- | --- |
| **subagents** | 多个**互不相干**的领域，需要中心化管控 | 结果要回流到主管再回答，**多一次模型调用** |
| **handoffs** | 客服那种**分步收集信息**的流程，顺序约束是硬要求 | 状态驱动的交接容易写成屎山；多 Agent 场景下上下文要手工管 |
| **router** | 输入有**清晰的类别**（不同垂直领域），要并行查多个源再汇总 | 无状态：每轮都要重新分类；多轮对话要自己管历史 |
| **自定义工作流** | 流程是**业务规则**决定的、要审批、要可恢复 | 控制流全归你，复杂度也全归你 |

**subagents 与 router 的区别**（最容易混的一对）：
router 是**一次分类**的预处理步骤，不维持对话状态；
subagents 的主管是**维持上下文的完整 Agent**，会跨多轮决定调谁、怎么合并结果。

## 7. 把子图注册成"工具"和"子智能体"的区别

LangChain 生态里，"一个子 Agent"有两种挂法：

| | 注册成**工具** | 注册成**子智能体**（subagent） |
| --- | --- | --- |
| 长什么样 | `@tool` 包装一个函数 | `create_agent(..., name="xxx")`，被别的 Agent 当工具调用 |
| 谁看到它的过程 | 默认看不到；只有 `name=` 的具名 Agent 才会出现在 `stream.subagents` | 具名子 Agent 会出现在 `stream.subagents`（含 `.name` 与 `.cause`） |
| 状态能不能查 | **查不到** | **查不到**（它在工具函数里被调用，LangGraph 无法静态发现） |
| 中断 | 会向上传播 | 会向上传播 |

> **反直觉的点**：官方文档明确写——**"子图状态查看"不适用于"在工具函数里调用的子图"**
> （也就是 subagents 模式），因为 LangGraph 无法静态发现它。
> 但**中断照样能一路传回顶层图**。
>
> 也就是说：**想调试子 Agent 内部状态，就别把它藏在工具里**——
> 改成"在节点函数里调用子图"，状态就能被 `get_state(config, subgraphs=True)` 看到。

同时记住：具名子 Agent 的名字和描述，是主管 Agent **唯一的路由线索**，
它是提示词工程的一部分，不是随便起的。

## 8. 上下文隔离：省 token 的代价

subagents 默认**无状态**：每次调用都从干净上下文开始，记忆全在主管那边。
这带来两个后果：

**好处**：主对话不会被子 Agent 的中间推理撑爆；多领域并行时 token 消耗最低
（官方对比：三个语言各约 2000 token 文档，subagents 约 9K tokens，handoffs 约 14K+）。

**代价**：

1. **子 Agent 看不到主线程上下文**。它只能看到你显式塞给它的东西。
   官方给了两种模式：**isolated**（默认，只给任务描述）和 **forked**
   （Deep Agents 里：把父的完整消息历史 + 系统提示词一起复制过去）。
2. **重复请求不省调用**。官方数据：同一请求重复问一次，
   subagents 要 4+4=8 次调用，handoffs 只要 3+2=5 次——因为子 Agent 每次都从头再来。
3. **要显式传上下文，就会有代码**。LangChain 的做法是从 `runtime.state` 里取父的历史，
   自己决定塞多少给子 Agent。

一句话：**隔离是拿"重复劳动"换"主上下文干净"**。
任务重复度高、要多轮记忆 → 别隔离；上下文大、任务独立 → 隔离很值。

## 9. 四个坑

### 坑 1：手工映射错了不报错

父子键名不一致时，映射漏一个键 → 子图读到空值 → 返回一个**语义上说得通但完全错误**的结果。
没有异常、没有警告，只有错答案。（第 10 章实验里，漏映射让"1+1"算成了"空式子"。）

### 坑 2：`get_state(subgraphs=True)` 看不到工具里的子图

子 Agent 挂在工具函数里 → 不可静态发现 → 查不到它的状态。
想调试就改成在节点函数里直接调用。

### 坑 3：子图按线程模式 + 并行调用 = 检查点冲突

同一个按线程子图被同时调用两次，两次写同一个命名空间。
官方给 LangChain 的解法是 `ToolCallLimitMiddleware`；裸 LangGraph 要自己限制并行。

### 坑 4：handoff 时必须成对带上 AIMessage + ToolMessage

用 `Command.PARENT` 交接时，只更新状态而不带上
"触发交接的那条 AIMessage"和"对应的 ToolMessage"，
接收方会看到一段**不合法的对话历史**（工具调用没有响应），模型可能直接报错或胡说。

```python
return Command(
    goto="sales_agent",
    update={
        "active_agent": "sales_agent",
        "messages": [last_ai_message, transfer_message],  # 必须成对
    },
    graph=Command.PARENT,
)
```

顺带一条实践建议：**别把子 Agent 的全部历史塞给下一个 Agent**——
只交接这一对消息，必要时在 ToolMessage 里放一份摘要。

## 配套实验

`Demos/examples/langgraph_lab/lessons/ch10_subgraphs.py`

六条断言把本章的结论钉住：

- 子图作为节点时，共享键被写回父图，**私有键不外泄**；
- 子图独立调用时，字段按映射关系传递；**漏映射不报错，只是结果变了**；
- `Command(update=..., goto=...)` 同时完成"改状态"和"选路"；
- 编排器按规则把任务路由到不同的专家子图，结果写进父状态；
- 子图内部的事件在父图流里带 `("节点名:运行 id",)` 前缀，
  根图事件是空命名空间——**两者混在同一个流里，要自己按 `ns` 过滤**。

跑法：

```bash
cd Demos/examples
python -m langgraph_lab ch10
```

## 一句话结论

> **子图边界上的唯一问题是"状态怎么对齐"**：有同名键就直接挂成节点（自动传、自动写回、
> 私有键不外泄），键名不同就手写映射（进一次出一次，且必须自己防错）；
> 要"改状态 + 选路"用 `Command`；多智能体选模式看**路由由谁决定**——
> 模型决定用 subagents、状态决定用 handoffs、分类决定用 router、业务规则决定就自己搭工作流。
> 记住两条硬约束：工具里的子图**查不到状态**，隔离的子 Agent **看不到主线程上下文**。
