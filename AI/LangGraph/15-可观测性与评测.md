# 15 · 可观测性与评测：没有 trace 的 Agent 调试等于猜

> **这篇要回答**：Agent 跑出来一个坏结果，我怎么知道是哪一步坏了？改了一版提示词，怎么证明它真的更好了？

---

## 1. 核心问题：Agent 是黑盒

普通函数写错了，看栈就找到了。Agent 写错了——同一段输入，这次过了那次没过，
中间可能调了三次模型、两个工具、走了四个分支。**没有 trace，你只能反复重跑去撞。**

这就是 LangSmith 存在的理由：**把一次运行拆成可见的步骤树**。

```
run（一次 invoke）
├── node: retrieve          输入/输出/耗时
├── node: llm               prompt / 补全 / token 数
├── node: tool: search      入参 / 返回
└── node: llm               最终回答
```

每个节点都是一个 **run**，父子关系构成一棵树。有了这棵树，"为什么答错"从猜变成查。

---

## 2. 三个环境变量（以及一个必须避开的坑）

```bash
export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY=<your-key>
export LANGSMITH_PROJECT=my-agent-project
```

> **坑（几乎所有人都踩过）**：老教程里的 `LANGCHAIN_TRACING_V2` / `LANGCHAIN_API_KEY`
> **已经彻底失效**。写错名字**不会报错**，只是静默不上报数据——
> 你会以为是网络问题、是 key 失效、是 SDK 版本不对，白查半天。

现在还有一种"agent-based workspace"的写法，用 `LANGSMITH_AGENT_ID` +
`LANGSMITH_AGENT_ENVIRONMENT` 指定注册的 Agent 与环境；
传统的 project 工作区则继续用 `LANGSMITH_PROJECT`。**两套别混用。**

---

## 3. 不想全上报时：选择性追踪

不是每次调用都值得上报。用上下文管理器精确控制：

```python
import langsmith as ls

with ls.tracing_context(enabled=True, tags=["prod"], metadata={"user_id": "u_1"}):
    agent.invoke({"messages": [...]})      # 这一段会被追踪
```

`invoke` 的 `config` 也能带 `tags` / `metadata`，用于在一条 trace 里做区分——
**按版本号打标签，是"改完提示词想知道有没有变好"最省事的做法。**

---

## 4. 敏感数据：先想清楚再上报

trace 里会有用户输入、工具返回、可能带手机号身份证。
LangSmith 提供**匿名化器**在上报前做替换：

```python
from langsmith import Client
from langsmith.anonymizer import create_anonymizer

client = Client(anonymizer=create_anonymizer([
    {"pattern": r"\b\d{3}-?\d{2}-?\d{4}\b", "replace": "<ssn>"},
]))
```

**默认不追踪，先显式打开。** 这是本教程唯一的默认建议——
剩下所有能力都可以后加，泄出去的数据收不回来。

## 5. 评测的三种形态

| 形态 | 判定方式 | 适合 | 成本 |
| --- | --- | --- | --- |
| 确定性断言 | 精确匹配 / 包含关系 | 有标准答案的事实性问题 | 零 |
| 黄金集对比 | 一批带参考答案的样本 | 检索质量、分类准确率 | 零（检索要联网） |
| LLM-as-judge | 模型给轨迹打分 | 开放式回答、推理质量 | 有 token 成本 |

**从确定性开始。** 黄金集能覆盖的问题，别急着上 LLM 判官——
判官本身有噪声，会让你的分数不可复现。

### 本仓库已有的做法

`Demos/examples/rag-demo/backend/rag.py` 里有一份 `GOLD` 黄金集：
每条包含 `question` / `page` / `title` / `needle`，跑完把结果写成 `eval_log.json`。
**先有黄金集，再谈优化**——没有黄金集的"感觉变好了"不算数。

## 6. 轨迹评测：AgentEvals

官方 `agentevals` 包专门评"Agent 干了什么"，而不只是"答了什么"。

```bash
uv add agentevals
```

**轨迹匹配**（确定性、免费）有四种模式：

| 模式 | 判定 | 适合 |
| --- | --- | --- |
| `strict` | 消息结构与工具调用**完全同序**（内容可不同） | 强制"先查政策再授权"这类顺序 |
| `unordered` | 工具调用**任意顺序** | 只关心"都查了"，不关心先后 |
| `subset` | 只调用了参考里的工具（不多调） | 不许越界调工具 |
| `superset` | 至少调了参考里的工具（可多调） | 必须做的动作都做了 |

**LLM 判官**（开放式质量）：
`create_trajectory_llm_as_judge(model=..., prompt=...)`，不需要参考轨迹。

> **坑**：`strict` 比对的是**结构**不是**内容**——它要求工具调用和消息角色一致，
> 但消息正文不同也算匹配。想卡内容，得自己再写一个评估器。

## 7. 把评测接进 CI

两种官方接法：

```python
# 1) pytest 集成
import langsmith as t

@pytest.mark.langsmith
def test_trajectory():
    result = agent.invoke(...)
    t.log_inputs({})
    t.log_outputs({"messages": result["messages"]})
    evaluator(outputs=result["messages"], reference_outputs=reference)
```
```bash
pytest test_trajectory.py --langsmith-output
```

```python
# 2) evaluate 函数：跑数据集，产出可比较的实验结果
from langsmith import Client

results = client.evaluate(
    run_agent,
    data="your_dataset_name",
    evaluators=[trajectory_evaluator],
)
```

数据集要求 `input` / `output` 两个字段，轨迹评测时 `output` 可以只保留助手消息。

## 8. 不接 LangSmith 也能做的事

追踪不是只有 LangSmith 一个选择，本地照样能看见：

```python
class TraceCollector(BaseCallbackHandler):
    def on_chain_start(self, serialized, inputs, **kwargs): ...
```

把 handler 塞进 `config={"callbacks": [collector]}`，
就能在本地拿到节点级的输入输出。**这在单元测试里比开云端追踪更好用**——
不依赖网络、不产生数据外泄、断言能写死。

第 16 章会讲 LangSmith Studio：它是"运行中的图"的可视化调试器，和 trace 是互补的——
**Studio 用来交互式断点调试，trace 用来事后复盘。**

---

## 一句话结论

> **没有 trace 的 Agent 调试等于撞运气，没有评测集的优化等于自我感动。**
> 先用确定性评估器把行为钉死，再考虑 LLM 判官；
> 追踪默认关着，开之前先想清楚什么数据不能出门。
