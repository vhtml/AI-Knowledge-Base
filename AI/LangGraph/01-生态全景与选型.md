# 01 · 生态全景：框架、运行时、harness 三层怎么分

> **这篇要回答**：LangChain、LangGraph、Deep Agents 到底是三个竞品还是一套东西？我该从哪一层开始？网上那些"LangChain 取代 LangGraph""LangGraph 2.0 发布了吗"的说法哪些是真的？

---

## 1. 一句话分清三层

官方文档把这套生态拆成三种角色（[Runtimes, frameworks, and harnesses](https://docs.langchain.com/oss/python/concepts/products)）：

| 角色 | 是谁 | 提供什么 | 什么时候用 |
| --- | --- | --- | --- |
| **框架 Framework** | LangChain | 模型、工具、Agent 循环、结构化输出这些抽象 | 想快速起步，团队要统一写法 |
| **运行时 Runtime** | LangGraph | 持久化、流式、人在环路、低层编排控制 | 长任务、有状态、要抗故障 |
| **harness** | Deep Agents | 规划、文件系统、子智能体、上下文管理 | 长程复杂任务，要"开箱即用"的自愈能力 |
| **横切平台** | LangSmith | 追踪、评测、部署、Prompt 管理 | 任何一层都建议开 |

```
┌─────────────────────────────────────────────┐
│  harness      Deep Agents                    │  ← 长程任务预设：规划/文件/子智能体
├─────────────────────────────────────────────┤
│  framework    LangChain  create_agent       │  ← 抽象层：模型/工具/中间件
│               └─ 底层跑的就是 ↓             │
├─────────────────────────────────────────────┤
│  runtime      LangGraph  StateGraph         │  ← 状态机：检查点/中断/流式
└─────────────────────────────────────────────┘
        ↕ 横切
   LangSmith（追踪 / 评测 / 部署 / Prompt）
```

**最反直觉、也最重要的一条**：

> LangChain 的 Agent **不是**"另一种东西"，它**就是**一张编译后的 LangGraph 图。

这不是类比，是事实。本章配套实验里有一行断言：

```python
from langchain.agents import create_agent
agent = create_agent(model, tools=[])
assert isinstance(agent, CompiledStateGraph)   # ← 它真的是张图
```

所以"我该学 LangChain 还是 LangGraph"是个**伪命题**——
LangChain 的 Agent 就是 LangGraph 的图，只是官方把那张图藏起来了，不让你看见。

## 2. 版本地图（2026 年 11 月实测）

| 事件 | 时间 | 含义 |
| --- | --- | --- |
| LangChain & LangGraph 1.0 | 2025-10-22 | 正式版 + API 稳定性承诺：1.x 线内不破坏兼容 |
| LangGraph 1.1 | 2026-03 | 流式与 invoke 的类型化输出（v2 投影） |
| LangGraph 1.2 | 2026-05 | 节点级超时、节点错误处理、优雅停机、`DeltaChannel`、v3 流式（beta） |
| 本机当前 | 2026-11 | `langgraph 1.2.20` / `langchain 1.5.0` / `deepagents 0.7.38` |

**两个必须知道的版本事实**：

1. **没有 LangGraph 2.0。** 网上写"LangGraph 2.0 发布"的文章基本是造谣。1.x 线承诺到 2.0 之前不做破坏性变更。
2. **2026 年发版非常勤**——LangGraph 一年发了 30 多个稳定版。这意味着
   **锁版本**不是保守，是必须：生产环境 pin 死 `langgraph==1.2.20`，升级前读 changelog。

## 3. 选型决策表

按顺序判断，命中即停：

| 你的处境 | 选谁 | 为什么 |
| --- | --- | --- |
| 长程任务：要规划、要管文件、要委派子任务 | **Deep Agents** | 这些脚手架自己写要几周 |
| 需要自定义控制流：确定性的循环、分支、反思重试 | **LangGraph** | 控制权在你手里 |
| 单一职责 + 固定工具集 | **LangChain `create_agent`** | 十行起步，中间件够用 |
| 只是模型调用 / 检索链路，没有 Agent 循环 | **LangChain 直接用模型** | 上框架是浪费 |
| 需要审批、要断点续跑、要能重启 | **LangGraph** | 持久化是一等公民 |

**反模式**：给一个线性流程硬画状态图。流程只有三步且不需审批，就用 `create_agent` 或普通 Python 函数。
LangGraph 的灵活是有成本的——状态、归约器、边都要自己设计，复杂度自己扛。

## 4. 三层混搭才是常态

真实项目几乎都是混着用：

```
Deep Agents 编排器
   └─(把 LangGraph 图注册成子智能体)
        └─ LangGraph 子图：某个确定性子流程（比如结构化取数 + 校验）
```

反过来也行：把 LangChain 写的工具挂进 LangGraph 的节点里，
LangChain 的工具、检索器在 LangGraph 节点和 Deep Agents 工具里都能直接用。

**判断标准**：凡是"流程里哪一步走哪条路"是**业务规则**决定的，写 LangGraph；
凡是"让模型自己决定用哪个工具"，用 `create_agent`；
凡是"任务长到需要管理文件和子任务"，上 Deep Agents。

## 5. 三个必须避开的坑

### 坑 1：环境变量换了名字

老教程里的 `LANGCHAIN_TRACING_V2` / `LANGCHAIN_API_KEY` **已经失效**。
现在只有 `LANGSMITH_TRACING` / `LANGSMITH_API_KEY` / `LANGSMITH_PROJECT`。

写错名字**不报错**，只是静默不上报数据——你会以为是网络问题白查半天。

### 坑 2：`InMemorySaver` 上生产

开发期用 `InMemorySaver` 没问题，进程一重启检查点全没。
生产至少换 `SqliteSaver`（单机）或 Postgres 检查点器（多副本）。

### 坑 3：把三层当三选一

见第 1 节。它们是叠在一起的，不互斥。

## 一句话结论

> **选型看任务的"形状"，不看名字**：需要规划与文件 → harness；需要控制流与持久化 → runtime；
> 需要统一抽象与快速起步 → framework。三层是叠的，LangChain 的 Agent 本身就是一张 LangGraph 的图。
