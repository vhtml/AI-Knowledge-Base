# 17 · 迁移与工程实践：一份能跑的上线检查单

> **这篇要回答**：从 0.x 迁到 1.x 要改哪些地方？把一套 Agent 放上线之前，有哪些事**必须**先做对？

---

## 1. 1.0 到底改了什么

LangGraph v1 的破坏性变更比想象中少——**核心图 API 一个字没动**，
`StateGraph`、检查点器、`interrupt()`、`Command`、`Send` 全部照常工作。
变的是一批"预制件"的归属：

| 废弃的东西 | 换成 |
| --- | --- |
| `langgraph.prebuilt.create_react_agent` | `langchain.agents.create_agent` |
| `AgentState` / `AgentStatePydantic` | `langchain.agents.AgentState` |
| `AgentStateWithStructuredResponse(Pydantic)` | `langchain.agents.AgentState` |
| `HumanInterruptConfig` / `ActionRequest` | `langchain.agents.middleware.human_in_the_loop.InterruptOnConfig` |
| `HumanInterrupt` | `langchain.agents.middleware.human_in_the_loop.HITLRequest` |
| `ValidationNode` | 直接删掉，`create_agent` 自动校验工具入参 |
| `MessageGraph` | 用带 `messages` 键的 `StateGraph` |

唯一真正"破坏"的一条：**Python 3.9 不再支持**（3.9 已于 2025-10 EOL），最低 3.10。

迁移的机械步骤：

```bash
uv add "langgraph>=1.2.20" "langchain-core>=1.8.0"
```

然后全局搜 `from langgraph.prebuilt import`，
把上面那张表里的名字逐个换掉。**换不动的要人工确认**——别让迁移脚本替你猜。

> **坑**：`create_react_agent(model, tools, prompt=...)` 的参数叫 `prompt`，
> `create_agent(model, tools, system_prompt=...)` 的参数叫 `system_prompt`。
> 名字换了，位置没换，代码看着还是"差不多"，但语义变了。

## 2. "1.x 不破坏兼容"是什么意思

官方承诺的是：**LangGraph 自己的 API 在 1.x 线内不破坏兼容**。

它**不承诺**：
- 你的图结构改动不影响老 checkpoint（第 16 章：改节点名会静默丢掉那一步）；
- 你的提示词改动不影响输出质量；
- 升级依赖后你的自定义代码还能跑。

所以"框架说兼容"和"我的系统兼容"是两件事。
**每次升级都要跑一遍你的评测集**（第 15 章）——那才是"兼容"的证据。

## 3. 出错时先查这张表

官方维护了一份常见错误索引（`common-errors.md`），值得收藏：

| 症状 | 多半是 |
| --- | --- |
| `InvalidUpdateError: Expected dict, got xxx` | 节点返回了非字典；或把条件边的**路由函数**当成了节点函数 |
| `InvalidUpdateError: Can receive only one value per step` | 同一个 super-step 里多个节点写了同一个**没有归约器**的键 |
| `GraphRecursionError` | 循环没有出口，或该用 `recursion_limit` 兜底 |
| 恢复后状态停在旧值 | 改了节点名/状态键，老线程找不到节点（第 16 章） |
| 节点超时配置报错 | timeout 只支持 async 节点 |
| 流式拿不到子图事件 | 流式时没开 `subgraphs=True` |

**这类"症状 → 病因"的映射，比记住每个 API 更有用。**

## 4. 上生产前的工程检查单

本章的毕业作品。十条，每条都能落到代码上：

| # | 检查项 | 为什么 |
| --- | --- | --- |
| 1 | **并行写入的键都有归约器** | 否则运行时 `InvalidUpdateError` |
| 2 | **调外部接口的节点有 `retry_policy`** | 网络抖动是常态，不是意外 |
| 3 | **慢节点有 timeout，且是 async 节点** | 同步节点超时无效；没有超时就是无限等 |
| 4 | **有副作用的节点幂等** | 恢复时节点会重跑（第 16 章） |
| 5 | **高风险操作前有人工审批** | 模型不该自己决定扣款、发邮件 |
| 6 | **检查点不是内存版** | `InMemorySaver` 进程一重启全丢 |
| 7 | **状态键新增用 `NotRequired`** | 老 checkpoint 还要能加载（第 16 章） |
| 8 | **没有废弃导入** | `create_react_agent` 等（本章第 1 节） |
| 9 | **没有失效的环境变量名** | `LANGCHAIN_TRACING_V2` 静默失效（第 15 章） |
| 10 | **版本锁死 + 有评测集** | 升级前能跑出可比对的分数（第 15 章） |

### 怎么让它不变成口头清单

**把检查单写成能跑的代码。** 关键是：大部分条目都能从编译后的图上直接读出来：

```python
graph.nodes["fetch"].retry_policy   # → RetryPolicy 或 None
graph.nodes["fetch"].timeout         # → TimeoutPolicy 或 None
```

再配上"这个节点是不是有外部副作用 / 是不是高风险"的节点清单，
检查单就能自动跑、自动拦。

配套实验把这份清单做成了一个可执行的审计器：
**造一张"有问题的图"，看它能不能逐条报出问题。**

## 5. 几条不能靠工具查的规矩

工具能查结构，查不了判断。这些只能靠人：

- **这个节点真的幂等吗？** 标了"幂等"但其实在写库——工具不会知道。
- **这个审批点该放在工具调用前还是状态变更后？** 放错位置，审批就形同虚设。
- **这个重试策略对写操作安全吗？** 重试一次扣款就是扣两次。
- **这个状态键该配什么归约器？** 工具只能提醒你"这是 list"，语义要人来定。

**所以检查单是"下限"不是"上限"。** 它的价值是把"忘了"变成"跑不过"，
不是替你做设计。

---

## 一句话结论

> **迁移是改名字，上线是改判断。**
> 框架的向后兼容只保证你不被框架坑，
> 保证不了你不被自己的改动坑——
> 所以每次发版前跑一遍检查单和评测集，
> 那才是"兼容"真正的证据。
