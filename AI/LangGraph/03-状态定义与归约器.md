# 03 · 状态定义与归约器

> **这篇要回答**：状态到底该怎么定义？哪个键要配归约器、为什么？TypedDict / dataclass / Pydantic 怎么选？input / output / private 三套 schema 各自管住什么？

---

## 1. 状态是"通道集合"，不是"一个字典"

LangGraph 把状态拆成一堆叫 **channel** 的槽位（[Graph API 概览](https://docs.langchain.com/oss/python/langgraph/graph-api.md#state)）。每个槽位有自己的合并规则。

```
                 ┌──────────── 状态 schema（通道集合）─────────────┐
   节点写 ─────► │  channel: text       无归约器 → 覆盖语义        │
                 │  channel: findings   operator.add → 合并语义   │
                 │  channel: errors     operator.add → 合并语义    │
                 └──────────────────────────────────────────────────┘
                          ▲
                          └── 归约器（reducer）决定"新值怎么并进去"
```

一次节点写入要经过三步：

1. **声明通道**：schema 里有哪些键，没声明的键写了会被**静默丢掉**（坑 5）。
2. **声明归约器**：这个键是"覆盖"还是"合并"。
3. **节点写入**：只写自己改的键。

归约器本质是个二元函数（[文档](https://docs.langchain.com/oss/python/langgraph/graph-api.md#reducer-arguments)）：

```
new_value = reducer(left=当前状态里的值, right=节点返回的更新)
```

**没有归约器就是默认归约器**：直接用 right 替换 left。这就是"覆盖语义"的来源——不是 LangGraph 特殊处理的，是默认行为。

> **核心判断规则**：**同一个键会不会被两个节点在同一个 super-step 里同时写？**
> 会 → 必须配归约器；不会 → 别配。
> 配错了不会立刻报错，要等到并行分支真的同时写这个键才炸（见第 3 节）。

## 2. 三种 schema 形态

官方文档的顺序是：默认用 `TypedDict`，需要运行时校验才上 Pydantic（[Define and update state](https://docs.langchain.com/oss/python/langgraph/graph-api-state.md#use-pydantic-models-for-graph-state)）。

| 维度 | `TypedDict` | `dataclass` | `BaseModel`（Pydantic） |
| --- | --- | --- | --- |
| 节点拿到的对象 | 字典，下标 `state["k"]` | 实例，属性 `state.k` | 实例，属性 `state.k` |
| 默认值 | 写不出来 | 写在字段声明里 | 写在字段声明里 |
| 运行时校验 | 无 | 无 | **仅输入侧** |
| 图的输出类型 | `dict` | `dict` | `dict`（**不是**模型实例） |
| 性能 | 最快 | 快 | 递归校验有开销 |
| 什么时候用 | 默认选它 | 需要默认值 / 想要属性访问 | 需要挡掉非法输入 |

### 坑 1：Pydantic 的校验只发生在输入侧，输出**不是**模型实例

```python
class OverallState(BaseModel):
    a: str

graph.invoke({"a": 123})   # ValidationError：挡在进图那一刻
graph.invoke({"a": "hi"})   # 正常，但返回 {'a': '...'}——是 dict，不是 OverallState
```

官方文档在 Known Limitations 里写死了这四条：输出不是模型实例、只校验到第一个节点的输入、
Pydantic 的报错堆栈不告诉你是哪个节点出的错、递归校验慢。

**所以**：别写 `result.a`——`result` 是字典，`result["a"]` 才对。
Pydantic 换来的是"外部脏数据进不来"，不是"类型安全的输出"。

### 坑 2：dataclass 和 TypedDict 的取值方式不一样

同样写 `state["text"]`，在 `TypedDict` 下能跑，在 dataclass 下抛
`TypeError: 'DState' object is not subscriptable`。这是切 schema 时最容易漏的一类回归。

## 3. 归约器：覆盖 vs 合并

| 写法 | 语义 | 适合什么键 |
| --- | --- | --- |
| 不写 `Annotated` | 覆盖（last-write-wins） | 只有一个节点会写的标量、当前结论 |
| `Annotated[list[str], operator.add]` | 拼接追加 | 并行分支的产出、日志 |
| 自定义归约器 | 自己定合并规则 | 去重、计数、取最大值、按 key 合并字典 |
| `Annotated[list[AnyMessage], add_messages]` | 追加 + 按 id 覆盖 + 反序列化 | 消息历史 |
| `Overwrite(...)` | 绕过归约器，直接置值 | 需要**清空**或整体替换的合并键 |

### 坑 3：没归约器的键被并行写，运行时才炸

两个分支同时启动、同时写同一个没有归约器的键：

```
InvalidUpdateError: At key 'plain': Can receive only one value per step.
Use an Annotated key to handle multiple values.
```

这不是"配置错误"，是**运行时**错误——因为编译期你无法知道两个节点会不会真的并行。
如果你在图里画了 `START → a` 和 `START → b` 两条边，它们就在同一个 super-step 里。

**反过来**：给不需要合并的键配了 `operator.add`，看起来没事，
但你其实是在用"列表"掩盖"本该只有一个值"的设计问题。列表越滚越长，
最后没人说得清哪些元素还有意义。

### 什么时候不该用归约器

- **"最后一个说了算"的结论键**（比如 `verdict`、`current_route`）：配归约器会让旧结论赖着不走。
- **标量计数**（比如 `retry_count`）：想覆盖就覆盖，别用 `operator.add`——你多半想的是 `state["retry_count"] + 1` 而不是累加所有历史。
- **字典**：想合并就用自定义归约器写 `{**left, **right}`，别用 `operator.add`（列表拼接）。

## 4. `add_messages` 比 `operator.add` 多做三件事

官方推荐消息键用 [`add_messages`](https://reference.langchain.com/python/langgraph/graph/message/add_messages) 而不是 `operator.add`（[Working with messages](https://docs.langchain.com/oss/python/langgraph/graph-api.md#working-with-messages-in-graph-state)）：

| 能力 | `operator.add` | `add_messages` |
| --- | --- | --- |
| 追加新消息 | ✅ | ✅ |
| 按 `id` 覆盖已有消息 | ❌ | ✅ |
| 把 `{"role": "user", "content": "..."}` 转成消息对象 | ❌ | ✅ |

第 2 条是人在环路的前提：审批人改了模型上一轮的输出，LangGraph 会**替换**那条消息，
而不是在历史里再塞一条矛盾的。而 `operator.add` 只会追加。

```python
from langgraph.graph import MessagesState

class State(MessagesState):   # 预置的 messages: Annotated[list[AnyMessage], add_messages]
    documents: list[str]
```

`MessagesState` 是预置好的单一 `messages` 通道，继承它再加字段就行。

## 5. `Overwrite`：绕过归约器，以及它的两个坑

### 坑 4：返回空列表**清不掉**已累积的值

归约器是"把 right 并进 left"。空列表被并进去，什么也没发生：

```python
class State(TypedDict):
    errors: Annotated[list[str], operator.add]

# node A 返回 {"errors": ["bad sql"]}
# node B 返回 {"errors": []}
# state["errors"] 仍然是 ["bad sql"] —— 空列表被合并进去了，不是清空
```

这对错误缓冲、重试计数这类"每轮必须清零"的字段是实打实的 bug 来源。
官方给的解法是 `Overwrite`：

```python
from langgraph.types import Overwrite

def clear_errors(state: State):
    return {"errors": Overwrite([])}      # 绕过归约器，直接置空
```

JSON 形式也支持：`{"errors": {"__overwrite__": [...]}}`。

### 坑 5：`Overwrite` 在并行时是"独占"的

官方文档的警告原文要点：

- 同一个 super-step 里，**同一个键只能有一个节点用 `Overwrite`**，否则抛
  `InvalidUpdateError: Can receive only one Overwrite value per super-step.`
- `Overwrite` 会**顺手丢掉**同一 super-step 里其它节点对同一键的普通写入——
  最终该键只剩 `Overwrite` 的值。

```
   super-step 内              结果
   ┌──────────┬──────────┐   errors = ["overwritten"]
   │ Overwrite│ 普通写入  │   ← 普通写入被丢弃，不是合并
   └──────────┴──────────┘
```

换句话说：**`Overwrite` 是"这一轮由我说了算"，不是"把我加进去"。**
并行分支里用 `Overwrite` 等于宣告"别的分支别碰这个键"——而框架会在你不知情时
把别人的结果扔掉。清理累积字段时，先确认那个键当前不会被并行写。

## 6. input / output / private 三件套

不是所有通道都该让调用方看见。官方提供三种 schema（[Define input and output schemas](https://docs.langchain.com/oss/python/langgraph/graph-api-state.md#define-input-and-output-schemas)）：

```
                     ┌──────────────── OverallState（图内部真身）──┐
   invoke 输入 ─────► │  question / user_input        （input）   │
                     │  ★ private_key                 （private） │
                     │  answer / graph_output         （output）  │
   invoke 输出 ◄───── └───────────────────────────────────────────┘
```

| schema | 作用 | 怎么配 |
| --- | --- | --- |
| `input_schema` | 调用方**能传**哪些键 | `StateGraph(Overall, input_schema=Input)` |
| `output_schema` | 调用方**能拿到**哪些键 | `StateGraph(Overall, output_schema=Output)` |
| 私有通道 | 只给内部节点用，不进主 schema | 节点用独立的输入/输出注解声明 |

实测行为（配套实验里跑过）：

- `invoke` 的返回值**只有 output schema 的字段**；
- 私有通道可以在 `invoke` 里完全看不见，却**照样出现在 `values` 流里**——

  ```
  {'user_input': 'My'}
  {'foo': 'My name', 'user_input': 'My'}
  {'foo': 'My name', 'user_input': 'My', 'bar': 'My name is'}      ← 私有通道泄漏
  {'foo': ..., 'graph_output': '...', 'bar': 'My name is'}
  ```

  想在流里也藏掉，得显式传 `output_keys=["graph_output"]`。

**为什么三件套重要**：它让"内部实现"和"对外契约"解耦。调用方只看到 `answer`，
中间怎么算出来的随便换；反过来，哪天你把 `answer` 改名，外部一行代码都不用动。

**但也别滥用**：多一套 schema 就多一套心智负担。判断标准很简单——
**这个键调用方真的需要吗？**不需要、且不该出现在对外响应里的，才是私有通道。

## 7. 设计清单

写状态 schema 前，先把这几个问题答完：

1. 每个键**会被几个节点写**？≥2 就得想清楚归约器（还是说本来就该只让一个节点写）。
2. 这个键**要不要能被清空**？要 → 合并型归约器 + `Overwrite`，或者干脆别配归约器。
3. 这个键**要进 `invoke` 的返回**吗？不要 → 别放进 output schema；要藏彻底 → 私有通道。
4. 需要**挡住脏输入**吗？只有外部输入不可信时才值得上 Pydantic。
5. 有没有**没声明的键**被节点偷偷写了？那会被静默丢掉——先补声明。

## 一句话结论

> **状态设计就是并发设计**：一个键会不会被多个节点同时写，决定了它该覆盖还是该合并；
> 归约器定合并，`Overwrite` 破合并，三套 schema 定谁能看见什么——
> 写不对不会立刻报错，会在并行分支第一次撞车时才炸。
