# 06 · 工具调用与工具节点

> **这篇要回答**：模型到底怎么"调用"一个函数？`@tool` 装饰器生成了什么、模型看见了什么？`ToolNode` 是什么、值不值得用？工具报错该在工具里处理还是扔给节点？工具和结构化输出到底差在哪？

---

## 1. 一句话拆解：工具调用是两次模型往返

"模型调用工具"听着像一步，其实是**模型、图、模型**三方接力：

```
 用户            模型节点              工具节点            模型节点
  │                 │                     │                    │
  │  "北京天气?"    │                     │                    │
  ├────────────────▶│                     │                    │
  │                 │  AIMessage(         │                    │
  │                 │   tool_calls=[...]) │                    │
  │                 ├────────────────────▶│                    │
  │                 │                     │  执行函数          │
  │                 │                     │  → ToolMessage     │
  │                 │◀────────────────────┤                    │
  │                 │  把 ToolMessage 拼进消息历史               │
  │                 ├──────────────────────────────────────────▶│
  │                 │                     │                    │ 读结果
  │                 │◀──────────────────────────────────────────┤
  │  最终回答        │  AIMessage(正文)    │                    │
  │◀────────────────┤                     │                    │
```

三句话记住分工：

- **模型只负责"提议"**：它输出 `tool_calls`（工具名 + 参数），不执行任何代码；
- **图负责"决定下一步"**：条件边看到 `tool_calls` 就去工具节点，否则直接结束；
- **工具负责"干活"**：结果以 `ToolMessage` 的形式回到消息历史，模型再读一次。

这个"模型 ↔ 工具"的循环，就是 LangChain `create_agent` 的内部结构——第 12 章会拆它。

## 2. `@tool`：注解给类型，docstring 给说明

```python
from langchain.tools import tool

@tool
def search_database(query: str, limit: int = 10) -> str:
    """Search the customer database for records matching the query.

    Args:
        query: Search terms to look for
        limit: Maximum number of results to return
    """
    return f"Found {limit} results for '{query}'"
```

模型看到的是这份 JSON Schema：

```json
{
  "title": "search_database",
  "description": "Search the customer database ... Args: query: ... limit: ...",
  "properties": {
    "query": {"title": "Query", "type": "string"},
    "limit": {"title": "Limit", "type": "integer", "default": 10}
  },
  "required": ["query"]
}
```

对应关系：

| 工具里写的 | Schema 里落在哪 | 模型看得见吗 |
| --- | --- | --- |
| 函数名 | `title` / 工具名 | ✅ |
| 类型注解 `query: str` | `properties.query.type` | ✅ |
| 默认值 `limit: int = 10` | `properties.limit.default` + 不进 `required` | ✅ |
| docstring 全文 | `description` | ✅ |
| docstring 里的 `Args:` 段落 | **不进 `properties.*.description`** | ⚠️ 见坑 1 |

### 坑 1：docstring 的 `Args:` 不会变成字段说明

这是最容易"以为配了其实没配"的地方。写了

```python
@tool
def add(a: int, b: int) -> int:
    """两数相加。

    Args:
        a: 第一个加数
        b: 第二个加数
    """
```

实测生成的 schema 里，`properties.a` 只有 `{"title": "A", "type": "integer"}`——**没有 `description`**。模型拿到的是"一整坨 docstring 文本" + "两个没有说明的裸字段"，它没法知道 `a` 和 `b` 哪个是被乘数。

想让字段说明真的进 schema，得用 Pydantic：

```python
class WeatherInput(BaseModel):
    """Input for weather queries."""
    location: str = Field(description="City name or coordinates")
    units: Literal["celsius", "fahrenheit"] = Field(default="celsius", description="Temperature unit preference")

@tool(args_schema=WeatherInput)
def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
    """Get current weather and optional forecast."""
    ...
```

实测这份 schema 的 `properties.location.description` 就是 `"City name or coordinates"`。

> 工具名用 `snake_case`。官方明确警告：名字里有空格或特殊字符，部分模型供应商会报错或直接拒绝。

另外两个官方约束：`config` 和 `runtime` 是**保留参数名**，不能当工具参数用（需要运行时信息就用注入的 `ToolRuntime`）。

## 3. 消息往返：tool_calls ↔ ToolMessage

一次完整往返长这样：

| 消息 | 类型 | 关键字段 |
| --- | --- | --- |
| 模型提议 | `AIMessage` | `content` 常为空，`tool_calls=[{"name", "args", "id"}]` |
| 工具回话 | `ToolMessage` | `content` = 结果字符串，`tool_call_id` 回指那次调用 |

两个硬约束：

1. **每个 `tool_call` 都必须有一条对应的 `ToolMessage`**。工具如果返回 `Command`（要写状态），`Command.update["messages"]` 里**必须**带一条 `tool_call_id` 匹配的 `ToolMessage`，否则 `ToolNode` 直接抛 `ValueError`。
2. **`tool_call_id` 必须对得上**。`ToolNode` 靠它把结果和调用配对；写错了模型看到的就是一段没有来由的文本。

## 4. ToolNode：官方预置的"工具那一半"

```python
from langgraph.prebuilt import ToolNode

builder = StateGraph(MessagesState)
builder.add_node("tools", ToolNode([search, calculator]))
```

手写版大概长这样：

```python
def tool_node(state: MessagesState) -> dict:
    result = []
    for call in state["messages"][-1].tool_calls:
        tool = tools_by_name[call["name"]]
        result.append(ToolMessage(content=tool.invoke(call["args"]), tool_call_id=call["id"]))
    return {"messages": result}
```

两者行为一致（配套实验里跑同样的输入、比对同样的 `ToolMessage`）。`ToolNode` 替你做掉的：

- **并行执行**同一条消息里的多个工具调用；
- **错误处理**（见下一节）；
- **状态注入**：工具能通过 `ToolRuntime` 读到图状态、`context`、`store`、`tool_call_id`；
- 校验"每个 tool_call 都要有 ToolMessage"这条不变量。

### 坑 2：ToolNode 直接当节点用时，看到的状态就是节点输入

`ToolNode` 只能读到**传给它的**状态。作为图节点时它拿到整份图状态；但如果你在别的节点里手动 `tool_node.invoke(...)`，传什么它就只能看到什么：

```python
tool_node.invoke(state)                        # 工具能看到全部状态
tool_node.invoke({"messages": state["messages"]})  # 工具只看得到 messages
```

自定义字段（`user_id` 之类）要能被工具读到，就得把整份状态传进去。

### 手写循环 vs `create_agent`：差别只有"谁替你连线"

| 维度 | 手写"模型节点 + 工具节点" | `create_agent` |
| --- | --- | --- |
| 图长什么样 | 你自己建 2 个节点 + 条件边 | 内部就是 `model ↔ tools` 两节点 |
| 控制流 | 随便改：审批、限流、换模型 | 固定循环，靠中间件加料 |
| 状态 schema | 完全自定义 | `AgentState`（可继承扩展） |
| 工具错误 | 你自己 try/except | 中间件（如 `ToolRetryMiddleware`） |
| 适合 | 流程里有业务规则分支 | 工具集固定、让模型自己决定 |

实测 `create_agent(model, tools=[add]).get_graph()` 的节点就是 `['__start__', 'model', 'tools', '__end__']`——和手写那张图**结构完全一样**。第 12 章讲怎么用中间件把"固定循环"改造成"你的循环"。

## 5. 工具出错：三条路径，选哪条

实测 langgraph 1.2.20 的 `ToolNode`：

| 错误来源 | 默认行为 | `handle_tool_errors=False` |
| --- | --- | --- |
| **参数不合法**（类型错、缺必填） | 转成 `ToolMessage(status="error")`，内容是 `"Error invoking tool 'add' with kwargs {...} ... Please fix the error and try again."` | 抛 `ToolInvocationError` |
| **工具内部抛异常** | **冒泡**（异常直接冲出图） | 抛原异常 |
| **工具名不认识** | 转成 `ToolMessage(status="error")`，内容是 `"Error: xxx is not a valid tool, try one of [...]"` | — |

### 坑 3：工具内部的异常，默认**不会**被翻译成 ToolMessage

只有"参数不合法"会被默认处理器接住。工具函数体里 `raise RuntimeError("订单服务不可用")`，默认是**直接冒泡打断整个 run**。

这其实是好设计：工具内部的异常多半是**代码 bug 或下游彻底挂了**，悄悄吞掉、让模型以为是"查不到订单"，比崩掉更危险。

`handle_tool_errors` 有四档：

```python
ToolNode([t])                              # 默认：参数错→ToolMessage；内部异常→冒泡
ToolNode([t], handle_tool_errors=True)     # 任何异常→ToolMessage(status="error")
ToolNode([t], handle_tool_errors="稍后再试")  # 任何异常→固定文案
ToolNode([t], handle_tool_errors=False)     # 任何异常→直接抛
```

### 工具错误该在哪处理？

| 错误性质 | 处理位置 | 为什么 |
| --- | --- | --- |
| 参数不合法（模型填错） | **交给节点**（ToolNode / 处理器） | 让模型看见错误、纠正参数再来一次 |
| 下游瞬时不可用（5xx） | **工具内部重试**，或节点级 `retry_policy` | 第 5 章那套机制 |
| 业务规则拒绝（库存不足） | **工具内部转成正常返回值** | 这是"答案"，不是"错误" |
| 代码 bug（`TypeError`） | **让它冒泡** | 吞掉只会让 bug 更难发现 |

最典型的正例：工具内部把"库存不足"变成一句正常的文本返回，模型据此改口径；而不是抛异常让整条链崩掉。

> LangChain 侧还有一层：`create_agent` + `@wrap_tool_call` 中间件可以把工具异常统一转成 `ToolMessage`。第 12 章细讲。

## 6. 工具 vs 结构化输出

两者都在"约束模型的输出"，但方向相反：

| | 工具调用 | 结构化输出（`response_format`） |
| --- | --- | --- |
| 模型输出什么 | `tool_calls`：**要做什么** | 直接是**结果本身**（按 schema 校验） |
| 模型调用次数 | 至少 2 次（提议 + 读结果） | 1 次 |
| 消息历史 | 多出 `AIMessage(tool_calls)` + `ToolMessage` | 只多一条最终消息 |
| 适合 | 查数据、跑动作、要副作用 | 分类、抽取、路由 |
| 能不能让模型"再来一次" | 能：结果回到历史里，模型能接着调 | 不能：一次成型 |

实测：走工具路线，4 条消息（human / ai(tool_calls) / tool / ai(最终)）、2 次模型调用；结构化输出路线只有 1 条最终消息，外加一个校验过的对象字段。

**判断标准**：要"过程"就用工具（模型得看到中间结果才能决定下一步）；要"产物"就用结构化输出（少一次往返，还白拿 schema 校验）。两者不互斥——`create_agent` 可以既带工具又带 `response_format`。

## 7. 什么时候别自己写工具节点

- 工具集固定、流程没有业务分支 → 直接 `create_agent`（第 12 章）；
- 工具来自 MCP → 用适配器接进来（第 13 章），别自己包 HTTP；
- 只有一个工具、只查一次 → 直接在节点里调函数，连 schema 都不用生成。

自己手写"模型 + 工具"循环的理由只有一个：**流程的分支是业务规则定的，不是模型定的**。

## 一句话结论

> **工具不是"模型调用了函数"，而是"模型提出调用意图、图决定下一步、工具把结果写回消息历史"的三个角色分工**——
> `@tool` 负责把这份意图约束成 schema，`ToolNode` 负责执行与报错翻译，而该重试还是该降级，取决于那次失败到底会不会留下副作用。
