# 07 · 持久化：检查点与时间旅行

> **这篇要回答**：LangGraph 的状态到底存在哪？进程重启后怎么接着跑？怎么"回到过去"改一步再重走？检查点和"长期记忆"是一回事吗？

---

## 1. 一句话模型：状态机 + 事件溯源

第 2 章说 LangGraph 是状态机。这一章补上另一半：**状态机的每次状态跃迁都被记下来了**，
所以它同时具备事件溯源（event sourcing）的性质。

```
一次 invoke 的时间线：

  输入          super-step 0      super-step 1      super-step 2      结束
   │                 │                 │                 │              │
   ▼                 ▼                 ▼                 ▼              ▼
 ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐
 │ckpt │→ │ckpt │→ │ckpt │→ │ckpt │→ │ckpt │→ │ckpt │→ │ckpt │→ │ckpt │
 │ -1  │  │  0  │  │  1  │  │  2  │  │  3  │  │  4  │  │  5  │  │  6  │
 └─────┘  └─────┘  └─────┘  └─────┘  └─────┘  └─────┘  └─────┘  └─────┘
   │         │        │        │        │        │        │        │
   └─────────┴────────┴────────┴────────┴────────┴────────┴────────┘
                              同一 thread_id 下的一条链
```

**每一次跃迁 = 一个 super-step 边界 = 一个检查点。** 这是本章所有 API 的共同地基：

- 想知道"现在在哪" → `get_state`（取链尾）
- 想知道"走过哪" → `get_state_history`（取整条链）
- 想"如果当时那样就好了" → `update_state`（在链上分叉）

官方文档：[Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers.md) ·
[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence.md)

## 2. 三个 id 的层级

初学者最容易把这三个 id 混为一谈。它们是**三层嵌套**，各管一件事：

| id | 粒度 | 取值 | 谁来生成 | 作用 |
| --- | --- | --- | --- | --- |
| **`thread_id`** | 线程 | 你给，如 `"user-42"` | **你** | 一条时间线；状态的主键 |
| **`checkpoint_ns`** | 图层级 | `""` / `"node:uuid"` / `"a:uuid\|b:uuid"` | 运行时 | 这份状态属于哪张图（子图会嵌套） |
| **`checkpoint_id`** | 时刻 | ULID，如 `"1f1e0d94-…"` | 运行时 | 某一个 super-step 边界上的快照 |

```
thread_id = "user-42"          ← 你定的：这条线程是谁的
└── checkpoint_ns = ""         ← 根图：空字符串
    ├── checkpoint_id = 1f1e…-61aa   step=-1  source=input
    ├── checkpoint_id = 1f1e…-62bb   step=0   next=("pick_topic",)
    └── checkpoint_id = 1f1e…-63cc   step=1   next=("count_round",)
```

子图被当成节点调用时，会开自己的命名空间，多层用 `|` 连接：

```
thread_id = "t1"
└── checkpoint_ns = ""                    父图
    └── checkpoint_ns = "sub:uuid"        子图
        └── checkpoint_ns = "sub:uuid|inner:uuid"   孙图
```

**关键推论**：`checkpoint_id` 是**被 `thread_id` 圈住的**。
拿 A 线程的 `checkpoint_id` 去 B 线程查，查不到任何东西——本章实验里对这条做了断言。
一个常见的错误设计是"用 `checkpoint_id` 当会话 ID"，那等于把指针和存储混为一谈。

节点内部可以读到自己的命名空间：

```python
def my_node(state, config: RunnableConfig):
    ns = config["configurable"]["checkpoint_ns"]   # 根图是 ""，子图是 "node:uuid"
```

## 3. 什么时候落盘：每个 super-step 之后

官方文档给了一个精确的计数：图 `START → node_a → node_b → END` 跑完，**正好 4 个检查点**。

| # | 内容 | `next` |
| --- | --- | --- |
| 1 | 空检查点 | `("__start__",)` |
| 2 | 用户输入 `{"foo": "", "bar": []}` | `("node_a",)` |
| 3 | `node_a` 的输出 `{"foo": "a", "bar": ["a"]}` | `("node_b",)` |
| 4 | `node_b` 的输出 `{"foo": "b", "bar": ["a","b"]}` | `()` |

规律是：**检查点数 = 节点数 + 2**。多一个输入检查点和一个 `__start__` 检查点。

还有一个容易忽略的细节：LangGraph 除了 super-step 级的完整检查点，
还会在**节点级**把每个节点的输出写进 `checkpoint_writes` 表。
这些不是完整快照，它们的作用是**待写入恢复（pending writes）**——
同一 super-step 里 A 节点成功、B 节点炸了，恢复时 A 不用重跑。
但**时间旅行只能从完整的 super-step 检查点恢复**，不能从节点级写入恢复。

## 4. 选哪种 checkpointer

| 实现 | 装在哪个包 | 进程重启 | 多副本 | 什么时候用 |
| --- | --- | --- | --- | --- |
| `InMemorySaver` | `langgraph-checkpoint`（自带） | ❌ 全丢 | ❌ | 单机测试、原型 |
| `SqliteSaver` | `langgraph-checkpoint-sqlite` | ✅ | ❌ 单写者 | 本地开发、单机部署 |
| `PostgresSaver` | `langgraph-checkpoint-postgres` | ✅ | ✅ | 生产、多副本 |
| `MongoDBSaver` | `langgraph-checkpoint-mongodb` | ✅ | ✅ | 已有 MongoDB 基础设施 |

开发期换生产只改一行 `compile(checkpointer=...)`：

```python
from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.checkpoint.postgres import PostgresSaver

# 本地
with SqliteSaver.from_conn_string("checkpoints.db") as saver:
    graph = builder.compile(checkpointer=saver)

# 生产（Postgres 首次使用需要跑一次 setup() 建表）
with PostgresSaver.from_conn_string(DB_URI) as saver:
    saver.setup()
    graph = builder.compile(checkpointer=saver)
```

> **坑：SqliteSaver 不等于"能上生产"。**
> 它是**单进程单写者**的。多个副本同时写同一个 SQLite 文件会互相踩，
> 而且没有 Postgres 那套成熟的复制与运维工具。要多副本就上 Postgres。

## 5. 三个 API

| API | 干什么 | 返回 |
| --- | --- | --- |
| `graph.get_state(config)` | 取链尾（或指定 `checkpoint_id` 那一格） | `StateSnapshot` |
| `graph.get_state_history(config)` | 取整条链，**最新在前** | `list[StateSnapshot]` |
| `graph.update_state(config, values)` | 在指定检查点处分叉 | 新的 `config` |

`StateSnapshot` 值得记住的字段：

| 字段 | 含义 |
| --- | --- |
| `values` | 这一格的状态快照 |
| `next` | 接下来要跑的节点；`()` 表示图已跑完 |
| `metadata["source"]` | `"input"` / `"loop"` / `"update"`——这格从哪来 |
| `metadata["step"]` | super-step 计数器 |
| `tasks` | 这一格待执行的任务，含 `interrupts`（第 8 章） |
| `parent_config` | 上一格的 config；`None` 表示这是第一格 |

按条件找历史中的某一格，是调试的主手法：

```python
history = list(graph.get_state_history(config))

# 找到"某节点还没跑"的那一刻
before_node_b = next(s for s in history if s.next == ("node_b",))

# 找到由 update_state 造出来的分叉
forks = [s for s in history if s.metadata["source"] == "update"]

# 找到中断发生的那一格（第 8 章）
interrupted = next(s for s in history if s.tasks and any(t.interrupts for t in s.tasks))
```

> **坑：`get_state_history` 是倒序的。**
> 列表第一个是**最新**的一格，不是最早的一格。
> "我要最早那次运行的状态"得写 `history[-1]`，而不是 `history[0]`。

跨线程列全部线程，用的是 checkpointer 自己的 `.list`，不是图 API：

```python
for tup in saver.list(None):        # 注意是 None，不是 {}
    print(tup.config["configurable"]["thread_id"])
```

`SqliteSaver` 会把任何非 `None` 的 config 当成线程过滤器，缺 `thread_id` 直接抛错。

## 6. 时间旅行：replay 与 fork

时间旅行不是一个 API，是**两个玩法**，底层都是"从历史检查点恢复"：

```
时间线：  c0 ──► c1 ──► c2 ──► c3            （原始执行，永不改变）
                        │
                        └──► c2' ──► c3'     （fork：从 c2 改状态另起一条）
```

| 玩法 | 做什么 | 怎么写 | 代价 |
| --- | --- | --- | --- |
| **Replay 重放** | 从某格重跑后面的节点 | `graph.invoke(None, snapshot.config)` | LLM 调用会**真的再发一次** |
| **Fork 分叉** | 改状态后从那格继续 | `graph.update_state(cfg, values)` 再 `invoke(None, new_cfg)` | 同上 |

```python
history = list(graph.get_state_history(config))
before_joke = next(s for s in history if s.next == ("write_joke",))

# Fork：把 topic 改掉再重跑
fork_config = graph.update_state(before_joke.config, values={"topic": "chickens"})
fork_result = graph.invoke(None, fork_config)      # joke 节点读到的是 chickens
```

**三条必须知道的语义**：

1. **Replay 不是读缓存，是重执行。** 文档明确警告：LLM 调用、API 请求、
   甚至 `interrupt()` 都会**重新触发**，结果可能和上次不同。
   从最终检查点（`next` 为空）重放是 no-op。
2. **`update_state` 不回滚。** 它**新造一个检查点**分叉出去，原历史原封不动。
   想"撤销"某次操作，你得自己 `update_state` 把值改回去，而不是指望它有撤销语义。
3. **`update_state` 走归约器。** 文档原话：值会经过 reducer 处理，
   所以**有归约器的通道是追加而不是覆盖**。`notes` 配了 `operator.add`，
   你传 `{"notes": ["manual"]}`，结果是 `["之前那些…", "manual"]`——不是 `["manual"]`。

`as_node` 参数用来告诉运行时"这次更新算哪个节点产出的"，它决定了恢复后**从哪个节点继续**。
默认会从版本历史推断；只有在**并行分支同时改了状态**（否则 `InvalidUpdateError`）、
**新线程没有历史**、或者**想跳过某个节点**时才需要显式指定。

时间旅行的完整规则见官方文档：[Use time-travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel.md)。
其中一条容易被忽略：**带 `interrupt()` 的图，时间旅行时中断会被重新触发**——
被中断的节点会重跑，然后为新的 `Command(resume=...)` 再次停下。

## 7. checkpointer 与 store 的分工

这是本章最容易搞混的一对，官方文档专门开了一页（[Stores](https://docs.langchain.com/oss/python/langgraph/stores.md)）：

| | **Checkpointer** | **Store** |
| --- | --- | --- |
| 存什么 | 图状态的**快照** | 应用自己定义的**键值数据** |
| 范围 | **一个 thread 内** | **跨 thread** |
| 记忆类型 | 短期、线程级 | 长期、跨线程 |
| 典型用途 | 对话连续性、HITL、时间旅行、容错 | 用户偏好、事实、共享知识 |
| 怎么访问 | 调用时传 `thread_id` | 节点里用 `runtime.store` 读写 |

一句话：**checkpointer 管"这次对话进行到哪"，store 管"这个人是谁"。**

```python
from langgraph.store.memory import InMemoryStore
from langgraph.runtime import Runtime

store = InMemoryStore()
store.put(("user-1", "memories"), "pref-1", {"food": "pizza"})   # 命名空间 = 元组

# 节点里读（runtime 由运行时注入）
async def node(state, runtime: Runtime):
    items = await runtime.store.asearch(("user-1", "memories"), query="喜欢吃什么")
```

短期记忆（对话历史）和长期记忆（跨会话的用户画像）的完整配方，
见官方文档 [Add memory](https://docs.langchain.com/oss/python/langgraph/add-memory.md)。

`store` 的三条实操细节：

- **命名空间是按前缀匹配的**。`search(("alice",))` 会把 `("alice","memories")`、
  `("alice","preferences")` 全捞出来。想只取一层，传完整命名空间再在客户端过滤。
- **`limit` 默认 10，超出部分静默截断**，没有任何溢出信号。要翻页就自己传 `offset`。
- **排序依后端而定**。`InMemoryStore` 按插入顺序，`PostgresStore` 按 `updated_at` 倒序。
  别依赖顺序，自己按 `item.updated_at` 排。

## 8. Durability：落盘和执行的权衡

LangGraph 提供三档持久化时机，可以在每次执行时指定：

```python
graph.invoke(input, config, durability="sync")
```

| 档位 | 什么时候落盘 | 崩溃后能恢复吗 | 什么时候选 |
| --- | --- | --- | --- |
| `"exit"` | 只在图退出时（成功、报错、被中断） | ❌ 中途崩了啥都没有 | 长跑批处理，不怕丢进度 |
| `"async"` | 边跑边异步写 | ⚠️ 有小概率丢最后一次写 | **默认档**，多数场景够用 |
| `"sync"` | 下一步开始前同步写完 | ✅ 每个检查点都落盘 | 金融、审批，不能丢 |

不传 `durability` 时默认是 `"async"`（`langgraph/pregel/main.py` 里 `CONFIG_KEY_DURABILITY` 的默认值）。

新线程的第一个检查点也受这一档影响：`"sync"` 会在第一个用户节点执行前就把
输入检查点（step `-1`）和 step `0` 提交掉；`"exit"` 则一个都不写。

> **坑：崩溃在第一个检查点落盘之前，线程等于"从没被调用过"。**
> 官方文档说得很直接：这种情况下 `get_tuple()` 返回 `None`，
> `invoke(None, config)` 抛 `EmptyInputError`——
> **和"用户压根没提交过请求"完全无法区分。**
> 要区分"没受理"和"受理了但丢了"，得在自己的系统里留受理记录（outbox），
> 别指望检查点。

## 9. 五个坑

### 坑 1：`InMemorySaver` 上生产

`InMemorySaver` 和 `MemorySaver` 把检查点存在 RAM 里，进程一重启全没。
更阴的是**它不报错**——你的图会安静地从空状态重新跑，看起来像"模型失忆"。

### 坑 2：`update_state` 不是撤销

它是**分叉**。原历史永远保留。想"撤销上一步"，要么从更早的检查点 fork，
要么用 `update_state` 把值手动改回去。

### 坑 3：`update_state` 走归约器，列表通道会追加

上面讲过。带 `operator.add` / `add_messages` 的通道，追加语义。
用 `update_state` "修正"一个列表，结果往往是越修越长。

### 坑 4：PostgresSaver 的 `thread_id` 有长度上限

`thread_id` 存在有长度限制的列里，超了直接数据库报错。
官方建议**控制在 255 字符以内**，需要确定性 ID 就用 UUID 或哈希。

### 坑 5：检查点会无限膨胀

默认每个 super-step 都把**每个状态通道的完整值**写一遍。
长对话里 `messages` 通道越滚越大，检查点体积是 O(N²) 级别。
两个官方给的解法：

- `DeltaChannel`（**beta**，需要 `langgraph>=1.2`）：只存增量，体积 O(1)。
  代价是每次调用要沿祖先链回放，重建状态更慢。
- 定期 prune：删掉 N 天前的检查点。注意用了 delta 通道时，
  **不能删掉存活检查点依赖的祖先写入**，否则状态会静默重建为空。

## 10. 什么时候不该用检查点

持久化不是免费的。每次 super-step 都要写一次存储，存储越慢，图越慢。

| 场景 | 建议 |
| --- | --- |
| 纯计算，无状态，一次性跑完 | **别加 checkpointer**。加了就多一份磁盘 IO，收益为零 |
| 只想要"对话记忆" | 检查点已经够了，别急着上 store |
| 需要跨会话记住用户偏好 | 上 store，命名空间按 `user_id` 分 |
| 状态里塞了大对象（整个 DataFrame） | 别直接进状态通道。检查点会把它复制 N 遍 |
| 高频短对话 | 配 `durability="exit"`，别为了一句话写两次盘 |

一句话原则：**检查点解决的是"进程死了怎么接着跑"，不是"怎么记住用户是谁"。**
这两个问题分别对应 checkpointer 和 store，混用会同时得到两个系统的缺点。

---

## 一句话结论

> **LangGraph 把"跑到哪一步"当成一等数据存下来**：每个 super-step 边界落一个检查点，
> `thread_id` / `checkpoint_ns` / `checkpoint_id` 三层定位一个时刻，
> 于是"续跑"只是复用同一个 `thread_id`，"回到过去"就是在历史检查点上分叉。
> 但记住两件事：`update_state` 是分叉不是撤销、而且走归约器；
> 跨线程的长期记忆属于 store，不属于 checkpointer。
